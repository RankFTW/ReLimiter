# AGENTS: ReLimiter production source

This file adds production-code rules under `src/`. Follow the root `AGENTS.md` as the shared baseline.

## Runtime and timing invariants

- Treat Present callbacks, marker hooks, scheduler enforcement, presentation-gate execution, fine sleep/spin paths, ETW callbacks, and CSV producer calls as latency-sensitive hot paths.
- Do not add routine blocking, heap allocation, file I/O, synchronous flushing, or contended mutex acquisition to a hot path. Move non-critical work to an existing worker or a clearly owned new worker.
- QPC is the timing authority. TSC-based timing is an acceleration hint and must retain calibration, fallback, and drift protection.
- Do not simplify or retune scheduler formulas, constants, state transitions, feedback, or call ordering without reading the surrounding rationale and producing capture-backed before/after evidence.
- Check all affected modes: VRR and fixed refresh, foreground and background, marker and Present fallback, and applicable FG/DMFG states.

## Pacing design constraints (user decisions, binding until the user changes them)

Rationale and evidence: the local work-item records (root `AGENTS.md`, Repository boundaries).

- Mechanisms must be general across games and systems. Do not tune a hold, release or fallback around a threshold or operating point found in one capture (a GPU load level, a budget value); a result that improves only at one point means a part of the problem is missing.
- Previously settled pacing must survive architectural changes: compare against the regression capture set in `.agents/skills/pacing-capture-analysis/references/capture-protocol.md` before and after any change to release timing, holds or the Reflex Sleep path. A change that trades long frames or cadence restarts for a few ms of latency is rejected by default; the user prefers smooth pacing and accepts about 4 ms of latency for it.
- No native Present hold as a pacing mechanism (it measured much worse frame-time jitter). Everything must work with hardware-accelerated GPU scheduling (HAGS) on.
- GPU wait releases are timed against the next frame's heavy GPU work (or its Present call) with a fixed distance, never gated on GPU load or hold length; the collision guard stands aside only by the queue-order check, not by scaling a number.
- Prefer deterministic mechanisms over retries and backoff. Late-frame catch-up keeps the render queue (keep), it does not restart after a late frame.
- Cadence grid source lateness (`CadenceGrid::PlanNext` step 3): judge a source against S = T − min(L(n), L(n − 1)), the S its wait aimed at. ReLimiter switching the lead (another output rung's or FG divisor's lead, a restarted lead) is not the game being late: judged against the new lead, the first frame after the FG input wait engaged restarted the cadence and moved T 4.4–10.5 ms later (CONTROL Resonant FG 2× at 130, lead 17.15 → 21.65 ms), a long displayed interval at every such switch. Within a rung the lead moves at most one slew step per frame, so the rule only acts at those switches.
- One pacer: the Reflex Sleep bypass is not a setting. The game's NvAPI Sleep returns without the driver whenever ReLimiter paces a positive cap, held or not (`Scheduler_PacesSource`, `NvAPI_ShouldBypassSleep`, `PacingPipeline_SleepBypass()`, true exactly while the effective `pacing_test_mode` is off); only Dynamic MFG passthrough and the test modes use the driver's Sleep.
- Driver pacing inside `NvAPI_D3D12_SetAsyncFrameMarker`: under the Reflex Sleep bypass with DLSS-G the NVIDIA driver still paces, by sleeping the thread that calls the game's Present inside this call (Streamline's `sl.dlss_g`, through `sl.common`; the long calls are PRESENT_END, type 5). `Hook_SetAsyncFrameMarker` is pass-through timing only (telemetry `async_marker_wait_us`); never suppress, delay or alter that marker or its result. In Gears it sleeps when the game's PRESENT_START of frame n comes before about frame n − 1's Reflex GPU end (a heavy GPU frame n − 1, a fast render thread), and the slept real frame is misplaced far more often (9–21% against 1–2%). Do not chase it with a later release: the render thread absorbs most of the shift (PRESENT_START moves 0.22–0.34 ms per ms of release), so it would starve the GPU long before it removed the sleeps.
- Flip metering block (developer `flip_metering_off`, `InstallFlipMeteringBlock`, `Hook_QueryInterface` in `nvapi_hooks.cpp`): returns nullptr from `nvapi_QueryInterface` for `NvAPI_D3D12_SetFlipConfig` (ID 0xF3148C42), as Special K, OptiScaler and RenoDX Commander do, so DLSS Frame Generation runs as on a GPU without hardware flip metering. It reproduces that state on a Blackwell test machine; never default it on. It is installed during init, not with the deferred hooks, because frame generation resolves the function itself and a pointer resolved before the hook stays usable; interception ends with the addon's teardown (`DisableAllHooks`). The first hidden request logs its caller module; without that line the block did not reach frame generation. With metering, a capture shows `flip_delay_qpc` on every row and the real frame's display − `etw_ready_qpc` near its flip delay; without it, both are 0 and every frame is shown as soon as it is ready.
- SetFlipConfig observer (`Hook_SetFlipConfig` in `nvapi_hooks.cpp`, with the deferred NvAPI hooks): an inline pass-through hook on the function itself, so it also sees callers that resolved it earlier. It never alters the call, the configuration or the result; it logs the first configuration and each change of the batch size, presented frames, status and feedback (never per batch; at most 16 lines). It resolves the function through the block's trampoline whenever the block's hook exists, enabled or not (a reload can re-enable a retained hook): its own request must never reach the block, which would log it as the first hidden request. Under the block, frame generation that asks for the function afterwards never gets it; a line then comes from a caller that resolved it before the block. A user capture without flip delay where frame generation still issues each group's Presents within a few ms (the metered path) means metering was asked for and not applied; this line says whether the call was rejected, metering was off at the caller, or the driver reported `no_iflip` or `mirroring_detected`.
- Separate presenter (`fg_route_unsupported`; `SeparatePresenter`, `RecordSeparatePresent`, `RejectRoute`, `PublishSeparatePresenter` in `streamline_gpu_handoff.cpp`; `PacingCapability::FgSeparatePresenter`): without hardware flip metering DLSS-G presents each group from its own thread and queue after the worker's return Signal, overlapping the next cycle (Valor Mortis with `flip_metering_off`: every Present on one other thread and never on the worker's queue, 38% begun inside the worker interval). The worker-local Present contract never holds there, so the route reports unsupported, not pending. Only positive evidence turns `worker_signal_before_present` into `worker_present_on_other_queue`: a native Present of the bound swapchain outside any source scope, on another thread and a known other queue, recorded with the failing cycle's token (a stale Present can only miss a cycle; `present_queue_not_worker` also counts, an unknown queue does not). Keep qualification running under that reason (`FgRouteQualificationPending`); clear it on a completed cycle, a worker-local Present, a new route identity, an FG multiplier change or FG stopping, never on time. Do not relax the worker-present contract to hold such a presenter: another queue loses the queue-order proof that its Presents depend on the held work, and if that queue is the game's source queue the hold would stall the previous frame's Present. That needs a fence-chain proof first (a worker Signal the presenter's queue or thread waits on).
- Control file (developer `control_file`, `control_file.h/.cpp`, `Config_SetLiveKey` in `config.cpp`): the test harness's channel into ReLimiter. A poller thread reads `relimiter_control.txt` and queues new commands (`ControlFile_Parse`: complete lines, growing seq); `ControlFile_OnPresent`, after the presenter guard in `on_present_impl`, runs them under the config owner lock (`Config_TryLockOwner`), which both OSD callbacks (`DrawSettings`, `DrawOSD`) hold for their frame because every ReShade runtime runs them on its own present thread; when the lock is held the commands wait for a later present, so the paced thread never blocks on it. The poller writes `relimiter_control_status.txt`. The present callback touches only static queues, flags and counters, never a handle, so a callback still running at shutdown cannot use a closed one; `ControlFile_Start` empties the queues, so a retained module's reload runs nothing queued before it. `capture start` uses `FrameTimeline_StartCapture` (a new epoch even while capturing) and reports a rejected transition as a failure. `Config_SetLiveKey` covers exactly the keys the OSD changes at runtime and publishes them the way the OSD does (`ValidateConfig`, the cap atomics, `Config_ApplyPacingPipeline`); add a key there only when the OSD can change it live. It queues no save, but `AddonUninit` saves all settings, so the harness restores the INI after a session.
- Chain diagnostic (`ChainRecord`, `AggregateChain`, `ReportChain`, `StreamlineHandoff_RecordQueueFence` in `streamline_gpu_handoff.cpp`, called from `ObserveFence` before its Interested filter): counts only, no authority. It records the Signals and Waits of the FG worker's queue and the separate presenter's queue, for designing a hold for frame generation without hardware flip metering. Keep its lifetime model as it is: hooks only push records for queues the installer worker published, each tagged with one global epoch that every queue destroy advances, and the installer worker aggregates in push order, dropping older epochs and resetting both sides on a newer one. Per-queue lifetime schemes (lock-free tables, per-side lifetimes, last-seen tracking) each failed review on destroy races.
- DLSS-G display order (measured in Gears and CONTROL): the generated frame between real frames n − 1 and n is shown about 0.15 ms after frame n's Reflex GPU end (frame generation included), and real frame n about half an interval later, at a delay the driver sets. Under the Reflex Sleep bypass that delay follows half of frame n's SIMULATION_START interval (r 0.71–0.86), not the GPU gap it lands in, so the source release rhythm is an input to real-frame placement. The real/generated labels come from `PresentFrameGrouper` (present_association.h): the PCL marker lands on the first present of an app frame (the generated one), so the last present of a multi-present group is real. Captures before that fix have the labels swapped under DLSS-G.
- Reflex report ingestion (`TryIngestReflexLatency`): take every unseen report per poll, oldest first. Polls run once per frame, so one report per poll keeps any backlog for good (Gears' reports arrived 250 ms late), and every report-driven loop then acts on stale frames.
- Lockstep credit (`GatedHoldTicks`, later frames' waits inside [s, p]): keep the whole credit on the GPU waits too, even when the frame's readiness is its output point. In a pipelined engine the next frame's wait overlaps frame n's render submission, so the credit hides GPU-throughput lateness (Gears FG 2× at 120 11.2–12.5 ms on 53–100% of frames, 0.2–1.4% of the 12–28% late frames counted), but bounding it by the frame's GPU idle inside its span (a developer A/B, removed) changed no display measure beyond the run-to-run spread.
- Frame span demand (`SerialFrameDetector`, feedback `SerialFrameArrivalUs`, `ReflexOwnedWaits::arrival_qpc` from `SourceStageFrame::game_arrival_qpc`): a pair is serial when the game reached ReLimiter for frame n + 1 at or after frame n's PRESENT_END, before any wait of ReLimiter's own; a frame ReLimiter did not plan arrives at its simulation start. Never judge from the released simulation start: ReLimiter's own hold puts that after the previous Present for a pipelined game, and the detector then read the whole frame span (Gears FG 2× at 120, measured with the since-removed Adaptive cap: serial by the release 96% of pairs with it, 58% without, CONTROL 96%; by the arrival 0% in all three; Rogue Core 100% either way). The frame span ran p90 19.5–21.4 ms in Gears against a GPU execution p90 of 18.3 ms. An arrival off the driver clock (clock map not stable) breaks the pair without judging it.
- Lateness ReLimiter accepts on purpose is not late-frame evidence (`LeadGuardOutcome::reduction_us`; `EmitSample` adds it to the slack). The reduction includes the slew back up after the guard's limit relaxed.
- The slack is T − s + the guard's reduction − X, T the plan's output target (`LeadFrameStart::output_target_qpc`): whether the frame was ready by its target. Never L − X: that credits a frame released after S with time it never had (a source late within the grid's tolerance and source slack). Judged against L its lateness depended on the lead estimator instead: Gears FG 2× at 120 1.7% at its 34.5 ms lead and 93% at the 28 ms own-work lead the replay predicts. Cadence-off captures: 0.1–0.3% of grid frames were late against T but not against L.
- A reset restarts windows, never the physics: frames released before it still explain the frames after them (`Previous`, decontamination, the anchors), but their later events add nothing to the windows it cleared. `ResetBuckets` finalizes pending frames and gives up their C and D (the old release point). Without that every frame in flight at the reset (release → output point spans the lead, 1.3–2.7 intervals in CONTROL FG 2× at 130) became a sample of the new regime.
- One collision model for the GPU queue wait (`CollisionGuardedLeadUs`, `CollisionOffsetUs`, `BehindWait`): L ≤ I + Q10(D) − H (Reflex GPU times) or I + Q10(C) − M (without), H = 1.0 ms (`kPacingGpuWaitHeadroomDefaultUs`) and M = 2.5 ms, both fixed. Do not learn H or M from late resumes and do not condition them on GPU load: the learned headroom widened to 1.75 ms on 10 of 123 resumes at a session's start and could never narrow (the guard keeps releases out of the region below the edge), so a slow section's margin stayed for the session; per-load-band learners were rejected because the heavy bands never collect the background a learner needs (235 and 1 resumes at ≥ 2 ms in the two heaviest bands across 47 Rogue Core captures, which hold half the late resumes) and the load gradient is composition (heavy sections hold briefly; with holds ≥ 500 µs late at 0.5–1 ms is 0.05–0.75% across loads). The GPU wait cap (lead ≤ median X + a cap lowered by late resumes) is removed for good: at a fixed distance short holds are the late ones (3.9% under 250 µs against at most 0.45%), so capping the hold pushed the wrong way. A relaxing limit returns the lead at the lead slew, never in one step (`Bucket::held_back`). The guard stands aside only while the heavy-work window is current (`WorkCurrent`); without reports no pair can show the queue order changing. Late resumes are measured and shown, never acted on.
- Collision model evidence (`LeadController::RecordWorkStart`, `RecordCallTime`, `GpuGateVerdict`, `GpuGateEvidence`, `PendingFrame::gpu_wait_lead`, `OnSourceRelease`, `OnGpuReport`, `WorkCurrent`): D is sampled only after a predecessor (grid index − 1, same lifecycle = identity domain + producer epoch + controller generation, same FG divisor, a sampled GPU queue wait frame) whose GPU waited at its gate (probe at or before the Signal, else readiness before the Signal); a not-waited, missing, other-lifecycle or other-divisor predecessor adds none, since D after it does not measure a release the wait could collide with. For a GPU queue wait frame with a resume probe expected, the verdict stays pending until the probe event arrives (`GpuGateVerdict`); readiness decides only when no probe time is available (no pre-wait time) or the slot closed. A pending verdict defers the sample and the successor is revisited on any event of the predecessor (GpuReady, GpuResume, OutputRelease) and on its source release. Only paths that seal a decision once (the D samples) wait for the probe; consumers that read a frame's gate at one event (the FG input wait's queue-order pair) take `GpuGateEvidence`, the evidence present then. C (`RecordCallTime`) is unchanged: every GPU-wait sample, the D-less fallback. The work age counts every frame planned with the GPU wait's lead (`gpu_wait_lead`: held) in `OnSourceRelease` and resets on any Reflex report of such a frame in `OnGpuReport`, with or without a D sample (mirror of `fg_report_age_frames_`); never reset it inside `RecordWorkStart`: an age reset only by D samples ages in every stretch without waited releases (a pause, GPU-bound frames) although reports keep arriving. There is no cold guard while no window is warm.
- GPU waits' lead sample (`LeadController::SampleUs`, `BehindWait(rung, divisor)`, `RecordConcurrency`, `LeadSampleWaitsForReport`, `HandoffFirstWorkStreams`): where an output's queue order says the next frame's GPU work runs behind the wait (32 waited pairs, none concurrent, Reflex reports current; each GPU output keeps its own pairs, the FG input wait's "waited" is its readiness before the Signal), X = max(p, r − d) − s with d = max(0, f − w_c), f the GPU's pass of frame n − 1's gate (max(r_{n−1}, u_{n−1}), whether or not that frame waited), w_c = min(p, w + F); otherwise the measured max(p, r) − s. Behind the wait r_n = o_{n−1} + P_n, so a sample that keeps the wait for frame n − 1 is L + P_n − I and the lead is neutrally stable: it only ratchets up (CONTROL FG 2× at 130: 20 ms in light stretches, 39–43 ms after one heavier second and kept after the load fell; real-frame PC latency 58–61 ms at 40 ms against 38–39 ms at 20 ms, display jumps above 4 ms 1.3–1.6 against 0 per 1,000 in those lighter stretches). The former carried-delay chain removed that wait only after a frame whose GPU waited at its gate and only cumulatively; the 30% of frames after one that did not wait set Q99. Never apply d with concurrent or unknown order: the GPU then starts frame n's work beside the wait (Rogue Core), and an early start point turned ordinary overlap into a fictitious carried delay that kept the lead below X with most frames late. The invariant: a sample must not contain o_{n−1}. Q99 of 256 is the fourth-largest sample, so any branch that keeps such a sample (≈ L + r − T) on 1.2% of frames pins the lead at or above itself. A frame the cap released whose own submissions set its readiness keeps X, which then follows its release, not o_{n−1}: its report shows the GPU waited ≥ `LEAD_HANDOFF_GPU_IDLE_US` inside its work for its submissions (span − A − the FG input wait's hold inside the span; an unknown hold keeps d out) while its first work streamed (driverStartTime before the middle of its own render submission). Without that, Gears FG 2× at 120 with the Adaptive cap (cadence on or off) had cap-held frames that started their GPU work 1.6–1.8 ms after the gate and idled 2.6–3.1 ms in it, the render thread 5 ms after the release for 11.5 ms and readiness 12.6 ms after its last submission (X 28–31 ms p50); the sample S − d put the lead's fixed point at about (Q99(S) + I)/2, 29 ms with half the frames ready after their targets, and the Adaptive cap stretched to +19–43% to buy lead (real fps 48.8–50.9 against 56.3 with it off; jitter above 2 ms 91–101 per 1,000 against 17.8 at a 33.5 ms lead). Never keep X on starvation alone: with a long lead Gears' first work reached the driver only at frame n − 1's Signal (driverStart − o_{n−1} p10/p50/p90 −0.19/+0.10/+1.20 ms, 17–21 ms after RENDERSUBMIT_START against 0.7–0.9 ms when streaming), the GPU then caught up with the held submissions, and 3.7% of frames kept X − L of +0.25…+0.8 ms: the lead stayed at 45 ms for 30–40 s (PC latency +10 ms). The streaming test leaves 0.31% of frames of that section with X − L p50 −0.72 ms; CONTROL fires 0.00–0.02%. A kept sample waits for the frame's report (about 2 intervals); a frame closed without one leaves d out (`report_missing_samples`). The outcome (slack, rings, room, handoff) stays at readiness. Residual: a frame whose first work streams but a later submission is held could still keep a sample that follows o_{n−1}; check the firing frames' RENDERSUBMIT_END − o_{n−1} for a constant. The slack takes the measured readiness, never the sample: behind the wait the sample hides GPU throughput lateness by design. Residual: at leads above about 32 ms in CONTROL the FG input call p is pinned about 4 ms after frame n − 1's release while the render thread's Present waits for it, so the sample keeps a slope of 0.2–0.25 on L there; it still falls.
- Held-first lead samples (`SampleUs`, `HandoffFirstWorkStreams`): keep a frame whose first work reached the driver in the second half of its render submission in the lead window with today's sample; do not leave it out or drop its `p` or its in-span GPU idle. In Gears FG 2× at 120 (five captures, cadence and Adaptive cap) its Present call, render-submission end and first submission follow its own render-thread start (slopes 0.0–0.2 against how early that start was before frame n − 1's gate, 0.5–0.7 for streamed frames), its in-span idle shrinks with an earlier start (−0.2 to −1.0), and its sample does not move with the release depth (−0.15 to +0.08): its 26 ms against 23 for streamed frames is its own longer path, which the lead can cover. Frame to frame the held-first rate follows frame n − 1's gate arriving late (+2.1 to +7.0 points per ms), not the release; only blocks across a session tied it to the lead, confounded with load. Left out, an all-held-first stretch never replaces the window's samples (the lead stayed at 51 ms in a model of `TestFgHeldFirstWorkLeadFalls`).
- Lead spike floor (`LeadController::RecordSpikeArrival`, `RecordSpikeGpu`, `SpikeFloorUs`, `NextLeadUs`; always on, `kPacingLeadSpikeFloor`): behind the wait the warm target is max(Q_q(X) + allowance, Q_tail(a) + Γ), a = (w − s − q) + F_n from streaming, not Signal-pinned frames (e < o_{n−1} ≤ w excluded), Q_tail the second-largest of 32 block maxima of 64 arrivals (`LEAD_SPIKE_TAIL_RANK`, about 31 s), Γ the median r − g of 32. Size it from the arrival only: the game's simulation, render-thread turnaround and first submission did not move with the lead (simulation p50 / p99 5.1 / 11.7 ms at L 41, 5.05 / 12.1 at L 29.8 in CONTROL Resonant FG 2× at 130; render submission p50 7.8–8.0 ms with the floor on and off). Never from GPU stalls or RENDERSUBMIT_END − (f + G): back-pressure keeps that +4–5 ms at Q99 at any lead (L 40–41 → 44–46 ms) and Gears' bulk submission puts it at p50 +0.5–1.4 ms (lead 38–40, more render-ahead bubbles). Never from the lead samples' queue q or the predecessor wait: that is the ratchet 4e18d0c removed. Why: the own-work lead's Q99 leaves rare long simulations out (CONTROL at L 29.5: queue in front of the render thread p50 0.0–0.1 ms, GPU stalls > 3 ms 7.9–18 per minute, display jumps > 4 ms 5.2–9.5 per 1,000 against 1.3–1.6 at the earlier 40 ms lead whose 6–9 ms queue absorbed them). The rank is the coverage: a game whose long simulations recur keeps the largest k − 1 of each window uncovered, 3–5 display jumps each when the GPU runs back to back. Rank 4 (live, CONTROL v38) cut stalls > 3 ms 11.9 → 2.4 per minute (cadence 19.5 → 6.8) and jitter > 2 ms 25.1 → 10.4 (20.9 → 13.0) per 1,000 for 2.2–2.6 ms of PC latency, leaving 22–25 ms simulations 5–9 ms beyond it. Rank 2 (live, CONTROL v39, same-session floor off as control): jumps > 4 ms 5.4 → 1.4 per 1,000 (cadence 7.8 → 3.1), long frames 1.7 → 0.4 (2.7 → 1.1), stalls 11.3 → 2.8 (13.3 → 4.5) per minute for 2.0–2.1 ms of PC latency; replayed, 0% binding in five Gears archives and +0.25 ms in CONTROL's light scene. Never rank 1: one isolated hitch would set the lead for 31 s,. No load threshold: the floor lies below the lead where the arrival tail is thin (CONTROL light scene, Gears), and it is not part of the 3 I budget (`budget_limited` from the own target only).
- Users do not tune: ship the recommended defaults (`config_version` migration), keep developer keys behind `developer_settings`, and keep user-facing text plain. The FPS cap exists to prevent the latency ReLimiter would otherwise add; never treat it as a latency source or lower it to hide a pacing defect.
- Removed pacing settings (`kConfigVersion` 6): the settings listed in `kRemovedKeys` (`config.cpp`) no longer exist. They are neither read nor written, the startup rewrite drops them from an older INI, and `LogRemovedKeysWithValues` logs one info line naming those that held a non-default value on a non-first launch; only the version 5 migration (queue law and probe defaults) is kept. `DropRemovedPresetKeys` deletes `show_adaptive_smoothing` from the local and shared `OSD_Preset_*` sections at every start (idempotent, outside the version gate) and warns once per file when a deletion fails. What is left of the settings in `pacing_resolver.h` are the `constexpr` values the default path runs with: `kPacingLeadCoverage`, `kPacingFgLateSpacing`, `kPacingLeadSpikeFloor`, `kPacingGpuWaitHeadroomDefaultUs`, `kPacingUnifiedEveryFrameServiceDefault` and `kPacingUnifiedQueueTargetDefaultUs`; `PacingPipeline_VrrTargetFps` and `PacingPipeline_VrrIntervalUs` are the cap-off target and the unified-versus-LFC interval choice that `OnMarker` calls. `PacingPipelineConfig` keeps only `gpu_probes`, `unified` (derived), `test_mode` and the unified developer keys; the published globals `g_reflex_sleep_bypass`, `g_bypass_low_latency_off`, `g_driver_low_latency_off`, `g_sleep_status_every_frame`, `g_marker_forward_after_wait`, `g_gpu_start_probe` and `g_fg_presenter_probe_us` do not exist (`PacingPipeline_SleepBypass()` replaces the first). `Config_SetLiveKey` has 15 live keys and refuses every removed key as `not a live key (launch-only keys: edit the INI and relaunch)`. The code the settings used to switch is gone: nothing stretches the interval (`DrainReflexReports` keeps the Reflex report drain; the interval is the base interval), pauses holds, waits before the Sleep by a learned margin, limits a release by the render thread or the GPU, injects a stall, alternates held and not-held blocks, measures the GPU start, runs priority or presenter probes or polls the Sleep status every frame, and the marker is always forwarded before the wait. `PreSleepWaitUntil(target)` is always the precise wait. What stays and is not reachable by configuration: `period_governor.*` (`LfcHysteresis`, `PeriodGovernor_LfcIntervalUs`, `GovernorCause` and its text), `source_placement.h` (`PRE_SLEEP_ACTIVITY_S`), `render_handoff.*` (`RenderHandoff_PublishPresentEnd` and `RenderHandoff_LeftPresent`, read by the FG executor's render-thread check), `rung_feasibility.h` (`FeasibilityCause` and its text), `s_low_latency_forced_off` (the Sleep-mode transition log reads it), `PacingRung::NativeHold` and `PresentGate_Execute`'s NativeHold support in `presentation_gate.*` (no production caller), the telemetry schema's governor, feasibility, pre-Sleep margin, stall and `gpu_first_submit_qpc`/`gpu_start_qpc` columns (not written; the schema goes in a later cleanup), and the enumerators `PacingFallbackReason::SmoothingOff`, `Infeasible` and `PacingSourcePlacement::PreSleep` (nothing produces them). Do not extend any of it, and do not let an entry here about it justify new work.
- Latency conclusions need Reflex active (FG forces it on). An offline replay that keeps the game's render-thread timing as captured can reject a release rule but never approve one; approval needs a live capture.
- Unified pacer (no setting: `unified` is derived by `PacingPipeline_ClampConfig`, true for a 64-bit process with the effective `pacing_test_mode` off, so a default `PacingPipelineConfig{}` clamps to true on 64-bit and false on Win32): one start law replaces the other pacing mechanisms while it paces.   - Unified hard limit: evaluated at T(n), after the Sleep hook's start wait reached it (E = the clock then, or the arrival of a frame already late), not at the arrival. Fewer than four unfinished frames (`kUnifiedMaxOutstanding` = 4): no wait. Otherwise it is inactive (flag `0x0008`, `up_outstanding` empty) when no completion exists yet or the newest (`g_up_ready_qpc`) is older than 2 × I(n); there is no 32-frame rule and absent completions never stall a frame. With fresh evidence it waits on `g_up_ready_index` until fewer than four are unfinished or ONE absolute deadline, max(T, E) + I(n), then releases anyway (`0x0004`). `up_outstanding` is the count re-read at the recorded release R (the count only falls between E and R, so 4 or more at R means the time-out).
  - Unified hold credit and queue target: invariant, a hold spends the GPU's spare time; spare time is banked over one report window; a debt is repaid by releasing the next frames earlier by the debt. The law keeps a credit c in [−J, +W×J] µs (J = the display-side interval `UnifiedPacer_DisplayInterval`, W = `kUnifiedExpireAge`, the report window of freshness and expiry), starting at 0, set to 0 by `Reset()` and while the report stream is not live (`QueueWaitLive`); each used report refills `min(W×J, c + J − gpuActiveRenderTime(k))` once, and every frame that `GrantHold` granted spends its actual hold once when `RefreshHold` knows it (`c = max(−J, c − h)`; a frame without a hold debits nothing). `GrantHold` returns `{live, credit, advance = max(0, −c)}` (idempotent per frame, `{false, 0, 0}` when not live) and the executors release the frame's resolved target earlier by the advance; the bounds follow the J of the latest grant, and the debit lags by the 3 to 5 frames in flight (the floor −J bounds the debt). `UnifiedStatus::service_usable` stays the usable-Ĝ definition of the hardware term only. Fixed values of the two options: every-frame service on (`kPacingUnifiedEveryFrameServiceDefault`) and a queue target of 2000 µs (`kPacingUnifiedQueueTargetDefaultUs`, `kUnifiedQueueTargetUs`); the earlier estimator with its 4000 µs target no longer exists as a setting. The queue target is 2 ms because in Gears a queue costs GPU time only once it is sustained above about 3 ms (nothing below, +0.3 ms per frame at 4 to 5 ms, +0.6 ms above 6.5 ms); lower than 2 ms bought no frame rate and leaves the GPU waiting for work more often. The earlier estimator (only frames that waited) needs a standing queue, and 4 ms is the target that kept its saturated pairs; the every-frame estimator does not. The queue term is `P = (z̃ − target) × kUnifiedGain` with the gain 0.1: the gain sets how far a disturbance moves the standing queue (queue = target + disturbance / gain), and at a saturated GPU every millisecond of queue costs frame rate and latency, so it must be large enough to hold the queue near the target; 0.1 is stable under the 3 to 5 frame report delay; 1/32 was measured and left the queue at 8 ms with the GPU as the limit, more than the 0.3 to 0.5 fps a smaller gain gained at a frame rate edge was worth (clamp ±Ĝ/8, median of three and freshness unchanged). Known limit: where the cap is out of reach in Gears the unified pacer is 0.3 fps and about 1 ms behind NVIDIA's limiter. Options of the law (`UnifiedOptions`, `UnifiedPacer::SetOptions`, set again from every keyed configuration snapshot from the constants, not cleared by `Reset()`): the every-frame service (fixed on) makes the service loop take a sample from every reported frame whose predecessor resolves, `G_k − max(0, −z_raw)` (a frame the GPU had to wait for still says how long the GPU needs once the wait is taken out, so the estimate follows a GPU that got faster once the queue emptied and never depends on a standing queue), but a corrected sample is never accepted below the frame's own GPU active time (then the sample stays `G_k` and `kUpCorrectionRefused` 0x80000 is set on the plan when the newest used report was refused): an estimate too small starts frames faster than the GPU can finish them; and the queue target option replaces `kUnifiedQueueTargetUs` in the queue term only (the lead and the credit never use it); `UnifiedStatus::service_sample_*` and `gpu_wait_*` report the newest used report's sample and wait whatever the options. Hold share (developer key `unified_hold_share`, `UnifiedOptions::hold_share` in [0, 0.25], default 0 = off, window medians computed only when it is above 0): the credit's refill of a used report is the signed `J − gpuActiveRenderTime(k)` (share 0, a cap that gives room, or no frame generation), except where no cap gives room (`J − Am < a`, `a = min(share × C, A)`, C the median completion spacing, A the median frame-generation time and Am the median GPU active time over the newest used reports, lower middle for an even count, `a = 0` without frame generation): there every used report refills the same allowance `a` (heavy, light or unknown active time) and the credit's upper bound is `W × a` instead of `W × J`, clamped when the case is entered and at every refill, the lower bound stays −J, and the case is decided per report from the current window. The reason: with no cap or one the hardware cannot reach, the display-side interval is shorter than the GPU's own frame time and the credit never filled; the allowance is a deliberate, bounded spend, not measured spare time, so it must not pile up in a bank sized for 32 intervals, and it is bounded by the frame-generation time because a hold costs little frame time only where it overlaps GPU work after the frame is complete (a fifth of the hold where frame generation runs), while on a route without frame generation the hold blocks the queue and costs its full length; holds lengthening C change the budget by only share × that lengthening (no ratchet).

ONE small lock (`Tables`, a test-and-set flag) guards the two bounded tables (512 entries) of outermost Signals and of Waits (the probe's and ReLimiter's own, which run nested, are not recorded), the per-queue command list counters (8 rows) and the decision's publication. EVERY acquisition, on any thread, is a bounded spin (`Tables::kSpinBound` 512 test-and-set iterations with a pause, no kernel wait; there is no unbounded `Lock()`): a Signal, Wait or Execute detour (game threads) that does not get it DROPS the event and COUNTS it; the evaluator's `Reader::Pull` is SKIPPED and COUNTED (`pulls_skipped`); `Tables::PublishDecision` that does not get it is DISCARDED and counted like a stale decision. Uncontended cost per Signal or Wait detour call about one interlocked exchange, one epoch load and a release store (~20-30 ns; `Tables::NoteExecute` is lock-free for a known row, below); worst case the spin bound, a few microseconds up to ~20, then drop. `Tables::Clear` (swapchain, presenting queue or queue lifetime change, any destroyed queue on whichever thread releases it, teardown with the key off) advances ONE lifetime epoch (`Tables::Epoch`, not the frame counter entries age by) with a plain atomic add at once, which invalidates every published decision (a decision is stored with the epoch it was computed for and `PublishedQueue` returns 0 unless that is current), and resets the tables when the bounded lock comes free; otherwise the clear is pending (`ClearsDeferred`): the next successful lock holder, a writer or the pull, finds the epoch it holds the tables for behind (`SyncLocked`) and resets them first, once (no per-slot ownership words, generation tags or reserved states). The destruction of a queue that is neither the adopted nor the presenting one only restarts the evaluation window: it does NOT retire an active adoption (the boundary and tag mechanism does not use the tables, its samples stay valid, and stopping the law's feed for a window would disturb pacing for nothing); an adoption lasts until a completed window decides otherwise or the adopted queue, the presenting queue or the swapchain goes away. An evaluation never runs under the lock: `Reader::Pull` copies only the entries newer than its previous successful pull (bounded by the table size; more are counted as loss) and the rows under it, then the resolver and `Evaluator` run on the copy, and the lock is taken again only for `PublishDecision`; a submitting thread never waits behind an evaluation. A skipped pull moves no cursor: the frames stay in the consumer's backlog (8 frames, each with its own scope, window and key) and the next successful pull, which holds the entries of every frame since the previous one (none lost, none twice), resolves them in order, so no frame is evaluated with a part of its Signals missing or counted as having zero; eight skipped pulls in a row restart the window. A window whose epoch changed restarts and adopts nothing (`Evaluator::AddFrame`'s `epoch`, `FillPrevious` ignores edges of another epoch); a window in which any record was dropped or lost (lock time-out, rows overflow, entries overwritten before the copy; `loss_total` snapshotted BEFORE the window's first frame) does not qualify for any queue, and a pull that finds new loss poisons every window any affected frame belongs to: `Evaluator::BeginPull(loss, pending_frames)` sets a watermark of `pending_frames + 1` frames (the backlog it resolves plus the frame current at the pull, whose events were not all recorded and which the NEXT pull resolves: production's one-frame lag), each frame resolved inside it poisons its window, and the poison outlives the pull that saw the loss. A resolver follows the presenting queue's per-frame Waits to the queue that signalled the same fence AND value (up to 3 hops, a CPU-signalled fence ends the branch, entries age out after two 64-frame windows and join only within 4 frames of the Wait, the tables are cleared on a lifetime change; fences are neither hooked at release nor retained: an AddRef would delay a game that waits for the fence's reference count or reports live objects at device teardown; accepted residual risk: a reused fence address that carries the same value within 4 frames adds one edge in one frame, and adoption needs one Signal and one first-hop edge on the same fence in every frame of a 64-frame window, so a false join can only make a window not qualify, never adopt a different queue, which also rests on the core invalidating the frame after an irregular boundary; tested). Role 3 (`render queue by dependency`, `queue_role` 3): the frame boundary is the adopted queue's Signal of the dependency fence (a core boundary with a boundary id and no identity), the tag comes from the presenting queue's Wait of the same value (`Kind::BoundaryTag`); both read the session generation before their role, fence and queue checks and are revalidated after admission (session, role, fence, queue); the output hold stays on the presenting queue and its announce, release and enqueue calls are no-ops for any other queue. ## Hooks and external APIs

- Derive the active graphics API from the current presenting device during launcher, game, and swapchain transitions. Never reinterpret DX9, Vulkan, or OpenGL native handles as DXGI swapchains.
- Use typed MinHook trampolines, idempotent installation, and complete failure cleanup. Preserve each hook's established original-call ordering; some marker hooks intentionally call forward first.
- Install hooks in batches, one per site (`HookBatch` in `hooks.h`; every MinHook enable freezes the process, and two engines' freezes can deadlock each other, so a site makes one freeze, not one per hook). A batch is lazy: constructing or destroying one takes no lock and calls nothing, the first install inside it takes `HookInstallGuard`, and the lock is held from that first create to the apply (`Apply` and `Hooks_FlushBatch` release it), so an idle batch never blocks another installer and no site lengthens a lock the present thread waits on; a site whose own code creates hooks (`FocusLock_Install`, `NGXHooks_TryInstall`) holds its own `HookInstallGuard` around that code. Inside a batch `InstallHook`, `InstallHookPublished` and `Hooks_EnableOrQueue` create, publish the trampoline and `MH_QueueEnableHook`, and their `MH_OK` means queued, never enabled. The sites: `Init` (`DoInit`: the flip-metering block and `NGXHooks_Init`, one batch around both), `FirstPresent` (the first present event: the four LoadLibrary hooks and the NvAPI hooks), `LoaderScan` (one scan of the loader-install worker, closed before its 250 ms wait, so discovery, factory probing and drains never run under the install lock for the batch; `NGXHooks_TryInstall` outside the worker opens its own), `FocusLock` (`FocusLock_Install`: `MH_CreateHook` x4, then `Hooks_EnableOrQueue`) and `DxgiFallback` (the DXGI `Present` / `Present1` pair, only when the vtable route is absent). Anything that logs a hook as installed, begins a producer epoch or sets a state flag reads `Hooks_TargetEnabled` AFTER the apply (`NvAPIHooks_ReportInstalled`, `ReportFlipMeteringBlock` and `LoadLibraryHooks_ReportInstalled` run after the batch; the installers call them themselves outside a batch). A group that cannot continue without the enable result (the Streamline hooks, the proxy and queue hooks, the FG input and queue hooks, the NGX transaction, which retains or rolls back on it) calls `Hooks_FlushBatch()` once after its installs: the same apply with the batch still open. `MH_ApplyQueued` is not a transaction: it stops at its first failure with the earlier hooks enabled, so a failed apply enables every hook still queued one by one with `MH_EnableHook`, logs each failure once at warning and leaves the failing hook created and not queued (nothing stays queued, so a later apply never enables it behind its owner's back). Nested batches on one thread are no-ops that queue into the outer one; an empty batch calls MinHook not at all; a refused admission (shutdown) makes installs fail with `MH_ERROR_DISABLED` as before. A retained load's records stay: installing the same target again queues it, and `EnableAllHooks` (`MH_EnableHook(MH_ALL_HOOKS)`) enables the queue too, settles every record to enabled and, when it stops at a failing hook, enables the rest one by one. Never call `MH_EnableHook` per hook inside a batch scope, and never hold a batch across a wait. Every call that freezes (the apply and the one-by-one enables, a single enable or disable, enable-all, the teardown disable) goes through hooks.cpp, never a raw `MH_EnableHook` / `MH_DisableHook` / `MH_ApplyQueued` elsewhere (`Hooks_DisableHook` for a hook's own disable): those run on the hook installer thread (`Hooks_StartInstallerThread` from `DoInit`, key `hook_installer_thread`, default true, a compatibility switch read once; `Hooks_StopInstallerThread` inside `DisableHooksForShutdown`, after the last freezing call). It is created with a security descriptor that denies `THREAD_SUSPEND_RESUME | THREAD_GET_CONTEXT | THREAD_SET_CONTEXT` to Everyone in front of the token's default DACL, so another engine's `OpenThread` for it is refused and the two freezes cannot wait for each other; at its start it opens itself for a suspend, which must fail (a debug privilege bypasses the descriptor), else it is `Unprotected` and every call runs on the requester. Only raw MinHook calls run on it: no ReLimiter lock, no log, no allocation; the requester keeps the install lock, takes the single job slot's lock, posts and waits with no timeout for the job event or the thread handle. `HookInlineOnlyScope` is the explicit way for code in DllMain or a loader callback (none today) to keep a call inline; so are the kill switch, a thread that is not `Ready` yet, and a stopped thread. If the thread ends before it took the job, the requester runs the job; if it ends with a job in flight MinHook is unusable for the rest of the process (`Hooks_MinHookUnusable`: admission closed, every later freezing call `MH_ERROR_DISABLED`, nothing replayed or terminated), and so is every other MinHook call of the product: none is made outside hooks.cpp (`Hooks_Initialize`, `Hooks_CreateHook`, `Hooks_RemoveHook` and the internal queue calls all return `MH_ERROR_DISABLED` without touching MinHook, whose lock the dead thread may hold), and a caller treats that status as "leave the record retained, do not retry". The batch stages record whether the installer ran the apply and whether it is protected in the high bits of the crumb's site byte (`kBreadcrumbInstaller*`). `Hooks_ForgetTarget` after `MH_RemoveHook` of a `Hooks_EnableOrQueue` target.

- Native Present entry (`vtable_copy.h/.cpp` pure rules, `vsync_control.cpp` install and detours): the route's entry is a private copy of the native swapchain object's vtable, not the inline patch. The copy is VERBATIM: the entries from index -1 (the RTTI locator) as far as they are readable, at most 512, never judged and never zero-filled (entries past the vtable's real end are whatever follows it in memory and are never called); every read first queries the region (`VirtualQuery`) and stops at anything that is not committed, readable memory without PAGE_GUARD, so a guard page is never touched (the SEH stays for races); it must cover the whole IDXGISwapChain4 interface (slots 0 to 40) or nothing is installed (logged). Before the copy is published every module that supplies a callable entry of slots 0 to 40 is pinned (`GetModuleHandleEx` FROM_ADDRESS with PIN); ANY of those slots pointing outside every loaded module is code whose lifetime cannot be held (a hook's private thunk its owner frees), so no vtable entry is installed (inline patch only, logged with the slot index). A copy goes only over a vptr inside a loaded module's image (a class vtable), never over a vptr in private memory. The copy names the detours in slots 8 and 22 and the object's vptr points at it. Each copy has an immutable forwarding record (the original vptr and the slot values read at copy time, shared by identical vtable images) and one detour pair, so a detour's record is its template index and the Present path searches nothing; a record is never retargeted. Another module replacing the vptr AFTER our copy is left alone (`VSync_ObserveNativeVptr`: one load and one compare on an ordinary frame; counted, logged once, shown in the `NativeGate vtable route:` line): never a second copy over a foreign vtable (its hook can save our entry and a later copy would chain into a cycle), no vptr write against it, no timers, no retries. While the copy carries the route, `VSync_NoteFinishedPresent` (ReShade's finish_present of the selected native swapchain) counts consecutive completed scopes in which no vtable entry ran (`vtable_copy::FallbackCounter`, 32, reset by any scope with an entry, any thread). The evidence is the selected object's alone: `s_selected_vtable_entries` counts only entries whose body ran for the swap manager's selected object (another object's entries never count or reset the run; the all-entries counter is diagnostics), and the run's baseline is snapshotted whenever it is reset. The fallback's selected identity (object + generation, `PublishFallbackIdentity`) is published on every actual selection, also when an existing binding keeps its copy (no install, no adoption), and by a present event that made the selected object's copy; a selection of an object without a copy clears it, and `VSync_NoteFinishedPresent` ignores the finish of any swapchain that is not both the identity and the swap manager's selected one, so an unselected swapchain can neither count nor consume the one-shot. The counter keeps fired flag, generation and count in ONE atomic word: the scope that reaches 32 and the commit of the one-shot are one compare-exchange valid only for the generation it counted for, so a destroy or reselect in between refuses the commit without consuming the one-shot and the new generation starts its own run. The 32nd scope installs the pair ONCE through a `HookBatch` (`DxgiFallback`), logged at warning level with the count, and it is never removed or repeated (no timers). The typed install's enable is queued inside a batch and `FinalizeTypedEnables` settles `HookTarget::enabled` after the apply, never before. 'Not installed because the vtable entry carries the route' is a normal state in the diagnostics. Where the pair exists, nothing re-installs it when another module erases it, and teardown never disables it (`DisableAllHooksExcept` leaves the two DXGI targets enabled and passing through, since a prologue check cannot be made atomic with MinHook's write-back against another module's concurrent patch); `PrologueHoldsOurJump` is for diagnostics only. One native call has one body: both entries run through `PresentEntry` / `Present1Entry`, the outermost entry for an object on the thread (a thread-local list of `DedupNode`s on the detours' own stacks, any depth, no allocation; `PresentOutermost` / `Present1Outermost` unlink in a SEH `__finally`, so a structured exception caught by a caller never leaves the list pointing at a dead frame, and they hold no C++ object with a destructor, which a SEH unwind would not run) runs the VSync override, timeline, gate, readiness, probe, brackets and telemetry, and an inner entry for the same object passes straight to its original with the arguments the outer entry chose; a Present on another swapchain, or a recursion from inside the original for another object, is not suppressed. The vtable lock serializes install, destroy, reconcile and teardown and is never taken by the detours. Bindings (8) are never evicted: a published binding is kept until its object's destroy callback or teardown (a guess that its copy is gone races another module's unhook, and a later foreign replacement would look like an unseen vtable); when all are taken a new object is refused (logged once, inline-only); a binding dropped over a foreign vptr remembers that vptr first. One judge (`ReconcileLocked`) serves a selection and a present event for every address, with one binding per object address (never a second claim): a vptr that is one of OUR copies is adopted, never copied again (`IndexOfCopy` before any first-install path; an unbound object showing a copy takes the record's identity); the vptr our copy replaced is installed again on the SAME binding (an overlay's unhook, or a new object at an address whose destroy never came; at most 8 per lifetime, a selection resets it); any other vptr over a binding that had a copy is another module's: remembered, left alone. The installed copy's identity (`copy_vptr`, the vptr it replaced) stays on the binding through refused reinstalls until destroy or teardown, so a later restore, adoption or foreign note still finds it. This cannot layer copies: every install reads a vptr that is neither one of our copies (adoption catches those) nor a remembered foreign one (the history refuses them), so a copy is only ever made over a class vtable. Stopping is checked under the vtable lock in both entry points, serialised against the teardown's restoration. Teardown closes installer admission (`Hooks_BeginShutdown`) before collecting the DXGI targets to leave enabled, so a typed hook installed during shutdown is not missed.

## Concurrency and lifecycle

- Every worker needs an explicit owner, start condition, stop signal, wakeup path, join point, and final-drain behavior where applicable.
- Never stop ETW or join workers while under loader lock. Keep process-detach handling loader-lock safe.
- Preserve normal shutdown ordering: stop native PCL before removing hooks, then shut down telemetry and logging according to their existing ownership.
- Start-up evidence (`startup_breadcrumb.h/.cpp`, `Log_Init`): `Breadcrumb_Mark` and `Breadcrumb_PresentCompleted` are plain stores into a mapped page, with no lock, allocation, flush or log, because hook batches call them around `MH_ApplyQueued` while the process is frozen; keep them that way and keep every failure (open, map, read-only folder, a second live launch holding the file) a silent no-op. The record is a seqlock; one writer at a time, a contending mark is dropped. Every stage but the two batch stages is first-wins, `Running` (the 32nd present after the first-present block) is followed only by `Closed`. `Log_Init` moves the previous log to `relimiter_<exe>.prev.log` (a failure is not an error), attaches `relimiter_<exe>.crumb` in the log's folder and, after releasing the logger locks, logs one warning at warning level when the previous launch's record is valid and before `Running` and not `Closed`. A new stage needs the enum, `StageName`, the docs and a mark at its site; never rename a stage or reorder the record (the file layout is versioned).
- Use relaxed atomics only for independent snapshots. Use acquire/release ordering when publishing related data or transferring ring-buffer ownership.
- The callback guard (`runtime_lifecycle.h/.cpp`) counts admissions per thread: each thread claims a cache-line slot of a fixed table (128) at its first guarded call, a locked update on that slot is the whole cost of the guard (no shared line, no allocation, no loader call, no lock), the thread's exit releases the slot (a `thread_local` destructor; the slot keeps its word, the next owner continues from it) and threads beyond the table share one overflow slot (a locked update, the old shared counter's behaviour). The handshake is the Dekker pair of the single counter: the guard adds to its slot, then reads `s_stopping` (both sequentially consistent); shutdown stores `s_stopping` (sequentially consistent) before it reads any slot. `RuntimeLifecycle_WaitForCallbacks` and `RuntimeLifecycle_Initialize` read the slots as a double collect (`inside == 0` on the first read of every slot and an unchanged word on the second, `enters` only grows) and so see "no callback admitted" exactly when the single counter would have been zero at some instant of the call. A guard remembers its slot and leaves that one wherever it is destroyed; the `RuntimeLifecycle_EnterCallback`/`LeaveCallback` bracket leaves the calling thread's slot, so it must enter and leave on one thread. `s_stopping` is alone on a cache line nobody writes in steady state (Initialize, BeginShutdown and Shutdown only); keep every hot or frequently written variable off it. A new thread-hot guard path must not add a shared writable line. `test_runtime_lifecycle` runs the production unit.
- Keep telemetry producers nonblocking. Fixed SPSC buffers intentionally drop rows rather than stall render or ETW threads when full.

## Cross-surface changes

- A configuration field is not complete until its struct default, INI load, validation/clamping, save behavior, runtime application, OSD control, user documentation, and architecture guards agree.
- A telemetry field is not complete until row structures, CSV headers, formatting, producers, analysis consumers, and documentation agree.
- Preserve established CSV column order, especially the native-PCL prefix; append diagnostics unless a deliberate schema migration is requested.
- Keep high-frequency logging sparse. Log initialization, state transitions, feature decisions, and failures rather than every frame.

## Verification

- Use standalone tests for pure logic, but do not treat them as proof of production integration.
- Scheduler, hook, swapchain, loader, driver, ETW, and frame-generation changes require runtime verification on every affected API/path.
- Compare telemetry captures when changing pacing behavior and record units, filters, target FPS, refresh mode, API, and FG state used in the comparison.
