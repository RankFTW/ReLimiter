# AGENTS: ReLimiter production source

This file adds production-code rules under `src/`. Follow the root `AGENTS.md` as the shared baseline.

## Runtime and timing invariants

- Treat Present callbacks, marker hooks, scheduler enforcement, presentation-gate execution, fine sleep/spin paths, ETW callbacks, and CSV producer calls as latency-sensitive hot paths.
- Do not add routine blocking, heap allocation, file I/O, synchronous flushing, or contended mutex acquisition to a hot path. Move non-critical work to an existing worker or a clearly owned new worker.
- QPC is the timing authority. TSC-based timing is an acceleration hint and must retain calibration, fallback, and drift protection.
- Do not simplify or retune scheduler formulas, constants, state transitions, feedback, or call ordering without reading the surrounding rationale and producing capture-backed before/after evidence.
- Check all affected modes: VRR and fixed refresh, foreground and background, marker and Present fallback, and applicable FG/DMFG states.

## Pacing design constraints (user decisions, binding until the user changes them)

Rationale and evidence: the local work-item records (root `AGENTS.md`, Repository boundaries).

- Mechanisms must be general across games and systems. Do not tune a hold, release or fallback around a threshold or operating point found in one capture (a GPU load level, a budget value); a result that improves only at one point means a part of the problem is missing.
- Previously settled pacing must survive architectural changes: compare against the regression capture set in `.agents/skills/pacing-capture-analysis/references/capture-protocol.md` before and after any change to release timing, holds or the Reflex Sleep path. A change that trades long frames or cadence restarts for a few ms of latency is rejected by default; the user prefers smooth pacing and accepts about 4 ms of latency for it.
- No native Present hold as a pacing mechanism (it measured much worse frame-time jitter). Everything must work with hardware-accelerated GPU scheduling (HAGS) on.
- Output override **GPU wait** (`output_rung=gpu`) keeps its earlier behavior; new hold or release rules apply under Auto or to frames that are not held. GPU wait releases are timed against the next frame's heavy GPU work (or its Present call) with a fixed distance, never gated on GPU load or hold length; the collision guard stands aside only by the queue-order check, not by scaling a number.
- Prefer deterministic mechanisms over retries and backoff. Late-frame catch-up keeps the render queue (keep), it does not restart after a late frame.
- Cadence grid source lateness (`CadenceGrid::PlanNext` step 3): judge a source against S = T − min(L(n), L(n − 1)), the S its pre-wait aimed at. ReLimiter switching the lead (another output rung's or FG divisor's lead, a restarted lead) is not the game being late: judged against the new lead, the first frame after the FG input wait engaged restarted the cadence and moved T 4.4–10.5 ms later (CONTROL Resonant FG 2× at 130, lead 17.15 → 21.65 ms), a long displayed interval at every such switch, and the restart counted as evidence for the held GPU floor. Within a rung the lead moves at most one slew step per frame, so the rule only acts at those switches.
- One pacer: with the default **Bypass Reflex Sleep** the game's NvAPI Sleep returns without the driver whenever ReLimiter paces a positive cap, held or not (`Scheduler_PacesSource`, `NvAPI_ShouldBypassSleep`); only Dynamic MFG passthrough and the Reflex driver limiter use the driver's Sleep.
- Driver pacing inside `NvAPI_D3D12_SetAsyncFrameMarker`: under the Reflex Sleep bypass with DLSS-G the NVIDIA driver still paces, by sleeping the thread that calls the game's Present inside this call (Streamline's `sl.dlss_g`, through `sl.common`; the long calls are PRESENT_END, type 5). `Hook_SetAsyncFrameMarker` is pass-through timing only (telemetry `async_marker_wait_us`); never suppress, delay or alter that marker or its result. In Gears it sleeps when the game's PRESENT_START of frame n comes before about frame n − 1's Reflex GPU end (a heavy GPU frame n − 1, a fast render thread), and the slept real frame is misplaced far more often (9–21% against 1–2%). Do not chase it with a later release: the render thread absorbs most of the shift (PRESENT_START moves 0.22–0.34 ms per ms of release), so it would starve the GPU long before it removed the sleeps.
- Driver low latency mode under the bypass (developer A/B `bypass_low_latency_off`, `g_bypass_low_latency_off`, `UpdateLowLatencyOverride`, `ApplyCapturedSleepMode`, `s_low_latency_forced_off` in `nvapi_hooks.cpp`): the Sleep bypass removes the Sleep call, not the game's low latency mode, so the driver's own pacing, inside the Present (see above), remains a second pacer. With the key on, `Hook_Sleep` (presenting device only, after the Smooth Motion return) sends the captured game parameters with `bLowLatencyMode` and `bLowLatencyBoost` cleared on the first bypassed Sleep, and the game's parameters exactly on the first Sleep that is not (bypass off, cap off, driver limiter, passthrough, key off). Only the forwarded copy changes, never the captured game parameters; while applied, `Hook_SetSleepMode` forwards the game's calls the same way, and `RestoreGameSleepMode` (shutdown, limiter release) and a driver limiter apply clear the state. The state changes only after an `NVAPI_OK` driver call; a transition and the forwarding of the game's own SetSleepMode share `s_sleep_mode_forward_lock` (a transition only try-acquires it from the Sleep hook), so a game call can neither land between the driver call and the state change nor undo the override. A failed call or missing parameters retries on a later Sleep; log transitions only. Injected Reflex (`reflex_inject.cpp`) is outside it: it runs only without native Reflex markers, never reaches `Hook_Sleep` and is not bypassed. Measured in Gears (FG 2× at 120, GPU-paced): the in-Present sleep disappears (no async marker call above 0.1 ms), Reflex reports keep arriving on every frame, display jumps and jitter reach the driver's Sleep, PC Latency stays below it. CONTROL is not measured yet.
- Render handoff limit (`render_handoff.*`, `HandoffLimitApplies`): the render-thread offset (w + d) applies to frames **not held** only. On held frames it moved CONTROL's simulation into its render thread's command submission and regressed pacing; the queue in front of the render thread absorbs simulation variance for held frames. Stalls turn it off only before the render thread is seen taking a frame ahead of the next release, and only two in a row (`RenderHandoffStalled`); that evidence is checked at every planned frame, limited or not, so a block can lift while the limit is off. Never make a block depend on evidence only the limit itself produces: a game that runs ahead would keep it off for the session.
- Render handoff GPU floor (`LeadController::GpuFloor`, `OnGpuRenderEnd`, `OnReportPair`, `HandoffFloorQpc`): a frame not held, released at SIMULATION_START while the Sleep is bypassed, is released no earlier than Ĝ(n−1) − (P/2 + F + σ). P is the median GPU period of consecutive frames the GPU did not wait for (≤ 1 ms idle) and whose pace it set (the GPU-set classifier below), F the median first submission − RENDERSUBMIT_START of streaming pairs, σ the median release → RENDERSUBMIT_START of `source_only` frames; all from 32 samples. Ĝ is the later of the newest Reflex report's GPU end and the render thread's newest live PRESENT_END plus the Q5 of the reports' PRESENT_END → GPU end gap, each extrapolated by P; keep the live bound, since reports arrive about two frames after the GPU end and a stretched GPU frame otherwise cascades into the next four. Keep it deterministic and measured: do not reintroduce a term learned from held-back frames; it finds the edge by hitting it, and the first held-back frame of each run stutters. Keep the floor itself anchored to the newest GPU end rather than a free-running cadence at P, which follows a GPU change only through reports two frames old (the GPU-paced rhythm below smooths held releases inside a band the floor bounds; it does not replace the floor). Keep the stream proof: without it a game that submits a whole frame at the end of its window would read held back on every GPU-bound frame. Held frames get no floor unless `gpu_paced_cadence` is on, and then a floor bounded by the cap's own release (below). `OnReportPair` feeds F and the stream proof only.
- GPU-paced cadence (developer A/B `gpu_paced_cadence`, `GpuPacedHeldFloorApplies`, `SourceStage::GpuPacedRhythm`, `SourceStageRequest::gpu_floor_qpc`, `CadenceGridPlanInput::earliest_target_qpc`): one cadence takes the later of the cap and the GPU for every frame. Held frames get the GPU floor (no `w + d`) on a rhythm: after a consecutive frame it paced, release = previous release + mean of the newest 5 GPU periods (`RecentGpuPeriodUs`); the floor when that is not earlier (late starts idle the GPU: stretched 7–15% against 2–10%), else pulled 0.25 toward the floor, never earlier than floor − P/2 (early starts cost little: 4–8%). Keep it bounded by the floor on both sides and continued only from frames it paced: a free or symmetric phase tracker drifted 3–18 ms from the GPU at fast load changes in replays. `LeadController::GpuSetPace` classifies a frame as paced by the GPU (not held, or a queued wait the GPU reached after its Signal: the probe's pre-wait time, else readiness, later than the release; missing evidence counts as waited, and a probe read back after the report still decides). P counts only pairs whose two frames the GPU set, and the PRESENT_END → GPU end gaps only such frames: a held frame's GPU end follows ReLimiter's own Signal, so P measured the cadence and the floor, fed by it, released later every frame (Rogue Core with Adaptive cap at 130: 83–89 FPS, median P 11.77 ms against 7.4 ms of GPU work). `output_status` alone cannot classify: the GPU waits report every queued wait as held. Never switch the floor on and off per frame with the classifier: a held floor withheld after every GPU-waited frame read the floor's own early target as GPU lateness and alternated between two release depths 13.8 ms apart every 2–3 frames (CONTROL FG 2× at 130: 214 switches in 48 s, SIMULATION_START intervals of 23 then 7–8 ms, 171 display jumps per 1,000 against 2.7 with the cadence off; with the cadence off 24% of frames already read GPU-set there, so any per-frame choice between the two depths is bistable). The held floor is bounded by the cap's own release instead (`GpuFloorCap`, scheduler `HeldGpuFloor`): min(Ĝ(n−1) − (P/2 + F + σ), Ĝ(n−1) − ḡ + I − L − slack), ḡ the median readiness gap, L the cap's lead (the newest plan's), slack half the grid's late tolerance of I. With the predecessor held at its target it equals S(n) − slack, so the floor moves a release only by the GPU's lateness beyond the output's slack, and ReLimiter's own holds never move it. The floor's own depth P/2 + F + σ is Gears' operating point: CONTROL's cap runs a frame deeper (render thread start 14.7 ms before G(n−1) on the cap, 7.6 on the floor; simulation 4.4 / 8.9 ms p50 / p90 against 7.4 / 20), the effect for which the handoff limit is not applied to held frames. Never bound with a lead measured from frames the floor did not release (the median of anchor(m−1) + I − s_m): it stops once the floor releases every frame, and when L then rises the bound stays behind the floor for good (CONTROL FG 2× at 130: L 21 → 31–35 ms, the measured median stuck at 20–24 ms, the floor released 92–94% of frames, 8–11 display jumps per 1,000 against 1.6 with the cadence off). Until the cap held 32 frames in the producer epoch (`LeadController::CapHeldFrames`: the GPU waited at its Signal and the floor did not release the frame) the held floor applies unbounded only after a SourceLate or OutputLate restart of a held frame in the producer epoch (`NoteCadenceRestart`), else not at all (`GpuFloorEstimate::ineligible`); Gears, whose held frames the floor releases, keeps its unbounded floor this way. Never count restarts of frames not held: the first frame after an FG change lands late on the new grid while FG is not presenting yet, just after the floor's evidence was reset, and that restart alone made the floor apply unbounded once FG presented (CONTROL FG 2× at 130: for 13 s the floor released most frames while the cap held 15–23). The first held plan after the FG input wait engaged restarted the cadence the same way while the grid judged it against that rung's longer lead; the grid judges a source against the lead its pre-wait aimed at (`cadence_grid.h`, lead discontinuity). The plan and the pre-Sleep wait use the same `HeldGpuFloor`: with the unbounded floor the pre-Sleep wait aimed past S on 211 of 214 floor exits. A cap or FG divisor change restarts the floor's output-shaped windows, its restart and the rhythm (`SourceStage::ResetGpuFloor`), but P carries over until the new window holds 32 pairs (`GpuPeriodUs`): with P cold the floor stopped for those pairs, and where the GPU limits the new cap the cadence restarted on nearly every frame until the overload guard took the holds away (CONTROL at 130 after FG was turned off, 11.4 ms of GPU work for a 7.69 ms interval: 27 restarts in the 0.54 s before the floor returned, holds off for 4–7 s; an earlier build that kept P paced a 6.8 s FG-off stretch without that burst). With the switch, Ĝ also takes the readiness anchor (lead_controller.h): the newest frame's anchor (`ReadyAnchorQpc`: its GPU readiness, or for a queued GPU wait the later of readiness and release) + the median anchor → GPU end gap + P per frame, replacing the older report's extrapolation (reports are about four frames old at the release); it is an estimate, not a bound. The gap window (`RecordReadyGap`) takes every frame the GPU set, held or not, never only frames not held (that filter left the window empty and the anchor never engaged in Gears), and never a frame whose GPU waited at its Signal: on the GPU queue wait its measured GPU end does not follow the release, so its gap is ReLimiter's own hold. Keep the gap signed (within ±I): the GPU queue wait's pre-gate query runs after the game's measured GPU work (Rogue Core −0.21 ms, p10–p90 42 µs, in every capture since Phase 0; Gears without FG −0.34 ms) while the FG input prefix precedes frame generation (+1.45 to +1.75 ms); a positive-only gap rejected every GPU queue wait frame, so the anchor never engaged on that output. A frame whose GPU floor is later than the moment the game reached ReLimiter (its marker, or its Reflex Sleep entry for that grid index, `SourceStageRequest::sleep_entry_*`, before any wait in the hook) and whose earliest release is not later than the floor is on time by construction: the grid never judges its lateness, at its source or at its output (`LeadController::GpuFloorReleased` → `CadenceGrid::ObserveOutput` `gpu_paced`). Pass the raw floor as `gpu_floor_qpc` for that test, never the rhythm's release (a release earlier than the floor would otherwise turn frames arriving between them into SourceLate restarts, the v13 cascade). Its T ≥ its release + min(`LeadController::EarlyLeadUs`, L), so its S = T − L never lies after its release; the early lead is the `1 − q` quantile of the measured readiness (release → GPU ready on the GPU waits, never the hold-corrected sample) of the newest 128 frames the floor released (per output class and FG divisor; the bucket's early side until 32), and the grid follows a later T without an epoch. That early side lags a change from cap-held to GPU-limited frames (readiness 5–6 ms later after the release); judging such frames' outputs (the FG late-frame spacing moving the Signal past T + tol) restarted the cadence 13–47 times per 45 s capture and paused the holds. Each piece answers a capture where the GPU was the limit (Gears, FG 2× at 120): judging lateness while T had not moved, an early side from the bucket or from hold-corrected samples, and treating a pre-Sleep frame whose marker lands just after the floor as late each led to SourceLate restarts with a 6–10 ms GPU hold; releasing every frame at its floor copied GPU noise into the simulation-start interval that DLSS-G places real frames by. With `marker_forward_order=before_wait` the driver timestamps SIMULATION_START at the marker's arrival, before ReLimiter's trim to the release (0.45 ms earlier at the median, sd 0.38), so the smooth release reaches DLSS-G only partly. With the restarts and the driver's in-Present sleep gone (`bypass_low_latency_off`), `after_wait` puts the driver's SIMULATION_START on the release (+0.01 ms) and in one Gears session cut the misplaced real frames with a start-interval deviation above 1 ms from 40% to 11% (driver's Sleep 9%) and display jumps from 30.2 to 18.5 per 1,000 (driver 16.3). An earlier ABAB of the order showed no difference because OutputLate restarts dominated it. Never rebuild it as a restart rule: a restart at floor + E with S of the next frame still T + I − L cascaded (median one frame apart). Never move the grid to the GPU on frames the GPU finishes early: they keep the cap's T and are held, so the cap holds. The Present-end gate (a release no earlier than PRESENT_END(n−1)) was tried and removed: GPU period 17.2 → 18.4 ms and every pacing metric worse. Release smoothing (a second stage pulling releases toward the mean of 64 rhythm intervals, never earlier than floor − P) was removed: live ABAB jumps 21.1 against 17.8 per 1,000 (driver 9.7); releasing a render thread earlier than usual against G(n − 1) after a stall made Gears' render thread run only after the GPU finished frame n − 1 (GPU idle 11–13 ms). Do not deepen the queue after a stall again without knowing what the render thread waits on.
- Adaptive cap hold room of the FG input wait (`LeadController::GpuNeedQuantileUs(q, fg_divisor)`, `OnGpuReport`/`RecordGpuNeed`, scheduler `UpdatePeriodGovernor`; with `gpu_paced_cadence` only, until that switch is approved): the room is the Adaptive cap percentile of the newest 128 GPU needs of the frame's FG divisor slot (0 below 32 values, for another slot, or while that slot's Reflex reports are stale), with `adaptive_cap_hold_room` on and the Output rung on Auto. It replaced the hold margin A/B, a second interval floor beside the Adaptive cap's: one interval floor per rung, in the governor. The need is the frame's Reflex GPU execution time (GPU active + AI frame time, `gpu_service_us`), only from reports with execution evidence; a producer epoch or FG divisor change restarts the window. Never measure it between readinesses (frame n's readiness − frame n − 1's readiness or Signal): the Adaptive cap's own stretch enters that gap, because the game's render thread submits into the longer window, so the need follows the interval and feeds it back into itself (Gears FG 2× at 120, fit 75: that gap p50/p75 20.1/21.1 ms at an interval of 20.7 ms against an execution time of 17.7/17.9 ms; with the frame span demand below, the stretch held at +24% p50, 47.9 real FPS against 56.9 with the Adaptive cap off). The need must exclude ReLimiter's holds and the stretch, or it lowers the frame rate without bound. Active + AI overstates the saturated GPU period by 1.3–2.6% (frame generation overlaps the next frame), which errs toward holding. Gears FG 2× at 120 with the margin at Q75 (and release smoothing): 3.5 display jumps per 1,000 against 12.3 with the cadence alone, at −2% frame rate.
- DLSS-G display order (measured in Gears and CONTROL): the generated frame between real frames n − 1 and n is shown about 0.15 ms after frame n's Reflex GPU end (frame generation included), and real frame n about half an interval later, at a delay the driver sets. Under the Reflex Sleep bypass that delay follows half of frame n's SIMULATION_START interval (r 0.71–0.86), not the GPU gap it lands in, so the source release rhythm is an input to real-frame placement. The real/generated labels come from `PresentFrameGrouper` (present_association.h): the PCL marker lands on the first present of an app frame (the generated one), so the last present of a multi-present group is real. Captures before that fix have the labels swapped under DLSS-G.
- Reflex report ingestion (`TryIngestReflexLatency`): take every unseen report per poll, oldest first. Polls run once per frame, so one report per poll keeps any backlog for good (Gears' reports arrived 250 ms late), and every report-driven loop then acts on stale frames.
- Adaptive cap demand scale (`PeriodGovernor`, cause `release_failed`): a fall that fails raises a scale on the measured need instead of retrying the same level on a timer. Keep it deterministic: it changes only on a failed fall and on a reset. Attribute the failure: a fall is to blame only while the realized interval is below the level it fell from (`releasing_from_stretch_`), and k rises only when the need set the level it fell to (`release_need_us_` 0 for a fall to I_0; no raise while the hold room sets the realized interval). Rogue Core: a fall the room held at +39% was blamed for a loading hitch (k 1.547, 21 ms before a DLSS SR recreation), and two falls to I_0 at needs 4.6–5.5 ms set k 1.40 / 1.69; each held +18% for minutes or lifted a GPU-bound need to +59%. A fall to I_0 that fails is retried only after the recurring-load hold.
- Adaptive cap evidence (`PeriodGovernor::Track`, `previous_missed_`; `LeadStatistics::draining_late_samples`, scheduler `TakeLeadOutputs`): one late frame counts once. A run of consecutive missed frames is one restart for the restart pair, and a late frame less late than the late frame before it (grid index n − 1, sample emitted) is draining and not a late output. In Gears (FG 2×, Adaptive cap 99%) one 25 ms simulation hitch restarted the cadence on frames 3 and 4 after it and left five frames late: two restarts in 30 ms and six late outputs, each evidence alone, raised the interval +21 → +42% in 0.6 s. Replayed on that capture the late-output evidence after the hitch drops from 5–9 to 1–3 counted frames while the sustained stretches after failed falls keep 10–18. Keep the 10% window counting every missed frame: runs of restarts on every frame (26 runs of three or more in 154,000 Gears frames) rise through it within a second. Do not count lateness that is shrinking: it is the interval absorbing one late frame.
- Frame span demand (`SerialFrameDetector`, feedback `SerialFrameArrivalUs`, `ReflexOwnedWaits::arrival_qpc` from `SourceStageFrame::game_arrival_qpc`): a pair is serial when the game reached ReLimiter for frame n + 1 at or after frame n's PRESENT_END, before any wait of ReLimiter's own; a frame ReLimiter did not plan arrives at its simulation start. Never judge from the released simulation start: ReLimiter's own hold puts that after the previous Present for a pipelined game, and the Adaptive cap then measured the whole frame span (Gears FG 2× at 120: serial by the release 96% of pairs with the Adaptive cap, 58% without, CONTROL 96%; by the arrival 0% in all three; Rogue Core 100% either way). The frame span ran p90 19.5–21.4 ms in Gears against a GPU execution p90 of 18.3 ms. An arrival off the driver clock (clock map not stable) breaks the pair without judging it.
- Lateness ReLimiter accepts on purpose is not Adaptive cap evidence (`LeadGuardOutcome::reduction_us`; `EmitSample` adds it to the slack). The reduction includes the slew back up after the guard's limit relaxed.
- The slack is T − s + the guard's reduction − X, T the plan's output target (`LeadFrameStart::output_target_qpc`): whether the frame was ready by its target. Never L − X: that credits a frame released after S with time it never had (a source late within the grid's tolerance and source slack, a handoff-limited or floor release). With the GPU-paced cadence a floor-released frame counts against its target like any other; its target moved past the grid's only when even its earliest readiness came after it, so a late one kept no cap cadence, which is the Adaptive cap's evidence there (with the Adaptive cap and GPU-paced cadence together the restarts are gone). Judged against L its lateness depended on the lead estimator instead: CONTROL FG 2× at 130 and Rogue Core 130 with the cadence counted 78% and 99% of floor-released frames late (85% and 99.7% against T), Gears FG 2× at 120 1.7% at its 34.5 ms lead and 93% at the 28 ms own-work lead the replay predicts. Cadence-off captures: 0.1–0.3% of grid frames were late against T but not against L.
- A reset restarts windows, never the physics: frames released before it still explain the frames after them (`Previous`, decontamination, the anchors and Ĝ), but their later events add nothing to the windows it cleared. `ClearSlackEvidence` marks pending frames `slack_fenced` (their slack still makes the next frame draining); `ResetBuckets` finalizes them and gives up their C, D and σ (the old release point); `ResetGpuFloor` (and `ResetBuckets` through it) marks them `floor_fenced` and drops the pair with the newest report, so no P pairs across a cap or FG change. Without the fence every frame in flight at the reset (release → output point spans the lead, 1.3–2.7 intervals in CONTROL FG 2× at 130) became a sample of the new regime: the slack window's "a full window is fresh" assumption broke, and P, the gaps and the cap-held count mixed FG work per real frame across a divisor change.
- One collision model for the GPU queue wait (`CollisionGuardedLeadUs`, `CollisionOffsetUs`, `HoldRoomUs`, `BehindWait`): L ≤ I + Q10(D) − H (Reflex GPU times) or I + Q10(C) − M (without), H = `gpu_wait_headroom_us` (default 1.0 ms, developer key) and M = 2.5 ms fixed; the hold room is the same inequality solved for the interval, Q_fit(X) + h − (Q10(D) − H), h = 0.25 ms, from the guard's current distances. Do not learn H or M from late resumes and do not condition them on GPU load: the learned headroom widened to 1.75 ms on 10 of 123 resumes at a session's start and could never narrow (the guard keeps releases out of the region below the edge), so a slow section's margin stayed for the session; per-load-band learners were rejected in review because the heavy bands never collect the background a learner needs (235 and 1 resumes at ≥ 2 ms in the two heaviest bands across 47 Rogue Core captures, which hold half the late resumes) and the load gradient is composition (heavy sections hold briefly; with holds ≥ 500 µs late at 0.5–1 ms is 0.05–0.75% across loads). The GPU wait cap (lead ≤ median X + a cap lowered by late resumes) is removed for good: at a fixed distance short holds are the late ones (3.9% under 250 µs against at most 0.45%), so capping the hold pushed the wrong way. A relaxing limit returns the lead at the lead slew, never in one step (`Bucket::held_back`). The guard stands aside only while the heavy-work window is current (`WorkCurrent`); without reports no pair can show the queue order changing. Late resumes are measured and shown, never acted on.
- GPU waits' lead sample (`LeadController::SampleUs`, `BehindWait(rung, divisor)`, `RecordConcurrency`, `LeadSampleWaitsForReport`, `HandoffFirstWorkStreams`): where an output's queue order says the next frame's GPU work runs behind the wait (32 waited pairs, none concurrent, Reflex reports current; each GPU output keeps its own pairs, the FG input wait's "waited" is its readiness before the Signal), X = max(p, r − d) − s with d = max(0, f − w_c), f the GPU's pass of frame n − 1's gate (max(r_{n−1}, u_{n−1}), whether or not that frame waited), w_c = min(p, w + F); otherwise the measured max(p, r) − s. Behind the wait r_n = o_{n−1} + P_n, so a sample that keeps the wait for frame n − 1 is L + P_n − I and the lead is neutrally stable: it only ratchets up (CONTROL FG 2× at 130: 20 ms in light stretches, 39–43 ms after one heavier second and kept after the load fell; real-frame PC latency 58–61 ms at 40 ms against 38–39 ms at 20 ms, display jumps above 4 ms 1.3–1.6 against 0 per 1,000 in those lighter stretches). The former carried-delay chain removed that wait only after a frame whose GPU waited at its gate and only cumulatively; the 30% of frames after one that did not wait set Q99. Never apply d with concurrent or unknown order: the GPU then starts frame n's work beside the wait (Rogue Core), and an early start point turned ordinary overlap into a fictitious carried delay that kept the lead below X with most frames late. The invariant: a sample must not contain o_{n−1}. Q99 of 256 is the fourth-largest sample, so any branch that keeps such a sample (≈ L + r − T) on 1.2% of frames pins the lead at or above itself. A frame the cap released whose own submissions set its readiness keeps X, which then follows its release, not o_{n−1}: its report shows the GPU waited ≥ `LEAD_HANDOFF_GPU_IDLE_US` inside its work for its submissions (span − A − the FG input wait's hold inside the span; an unknown hold keeps d out) while its first work streamed (driverStartTime before the middle of its own render submission). Without that, Gears FG 2× at 120 with the Adaptive cap (cadence on or off) had cap-held frames that started their GPU work 1.6–1.8 ms after the gate and idled 2.6–3.1 ms in it, the render thread 5 ms after the release for 11.5 ms and readiness 12.6 ms after its last submission (X 28–31 ms p50); the sample S − d put the lead's fixed point at about (Q99(S) + I)/2, 29 ms with half the frames ready after their targets, and the Adaptive cap stretched to +19–43% to buy lead (real fps 48.8–50.9 against 56.3 with it off; jitter above 2 ms 91–101 per 1,000 against 17.8 at a 33.5 ms lead). Never keep X on starvation alone: with a long lead Gears' first work reached the driver only at frame n − 1's Signal (driverStart − o_{n−1} p10/p50/p90 −0.19/+0.10/+1.20 ms, 17–21 ms after RENDERSUBMIT_START against 0.7–0.9 ms when streaming), the GPU then caught up with the held submissions, and 3.7% of frames kept X − L of +0.25…+0.8 ms: the lead stayed at 45 ms for 30–40 s (PC latency +10 ms). The streaming test leaves 0.31% of frames of that section with X − L p50 −0.72 ms; CONTROL fires 0.00–0.02%. A frame the GPU floor released was released past S by the floor, so its starvation is the floor's, not the lead's: it never keeps X and its sample does not wait (cadence-only Gears would otherwise go 27 → 34.5 ms). A kept sample waits for the frame's report (about 2 intervals); a frame closed without one leaves d out (`report_missing_samples`). The outcome (slack, rings, room, handoff) stays at readiness. Residual: a frame whose first work streams but a later submission is held could still keep a sample that follows o_{n−1}; check the firing frames' RENDERSUBMIT_END − o_{n−1} for a constant. The slack (Adaptive cap evidence) and the hold room take the measured readiness, never the sample: behind the wait the sample hides GPU throughput lateness by design. The GPU-paced early side falls back to the GPU waits' measured readiness (`gpu_ready_rings_`), never to these samples (they put a floor-released frame's target earlier than it can be ready). Residual: at leads above about 32 ms in CONTROL the FG input call p is pinned about 4 ms after frame n − 1's release while the render thread's Present waits for it, so the sample keeps a slope of 0.2–0.25 on L there; it still falls.
- Adaptive cap hold room (`LeadController::HoldRoomUs`, `GovernorFrame::room_us`; developer A/B `adaptive_cap_hold_room`, default on, gated in `UpdatePeriodGovernor`): the interval at which the GPU queue wait can hold a frame at least h and still release it H before the next frame's heavy GPU work. It is not what frames need: when the GPU is the limit it buys GPU idle per frame. Rogue Core 130 (fit 75, with the old learned H 1.5 ms): GPU active 7.5 ms, GPU frame time 8.0 ms with Adaptive cap off (125 FPS), workload-report need plus margin 7.84 ms (+2%), hold room 9.4 ms (+22%, 106 FPS). When the GPU saturates, D includes queueing behind the previous frame (D p75 − p10 3.3 ms instead of 0.4 ms) and the room spiked to +47%. Whether holding is worth the room in GPU-bound scenes needs same-scene captures with the key off.
- Users do not tune: ship the recommended defaults (`config_version` migration), keep developer keys behind `developer_settings`, and keep user-facing text plain. The FPS cap exists to prevent the latency ReLimiter would otherwise add; never treat it as a latency source or lower it to hide a pacing defect.
- Latency conclusions need Reflex active (FG forces it on). An offline replay that keeps the game's render-thread timing as captured can reject a release rule but never approve one; approval needs a live capture.

## Hooks and external APIs

- Derive the active graphics API from the current presenting device during launcher, game, and swapchain transitions. Never reinterpret DX9, Vulkan, or OpenGL native handles as DXGI swapchains.
- Use typed MinHook trampolines, idempotent installation, and complete failure cleanup. Preserve each hook's established original-call ordering; some marker hooks intentionally call forward first.
- Keep SEH narrowly around unstable driver, game, COM/vtable, Streamline, NGX, or opaque-ABI access. Do not use a broad `__try` block to hide failures in ordinary project logic.
- Preserve late-load handling and data-only load filtering in loader hooks.
- Keep DLSS, FG, Streamline/PCL, NGX, Reflex, and other 64-bit-only integrations behind existing architecture boundaries. Shared code must continue to compile against Win32 stubs without referencing excluded symbols.

## Concurrency and lifecycle

- Every worker needs an explicit owner, start condition, stop signal, wakeup path, join point, and final-drain behavior where applicable.
- Never stop ETW or join workers while under loader lock. Keep process-detach handling loader-lock safe.
- Preserve normal shutdown ordering: stop native PCL before removing hooks, then shut down telemetry and logging according to their existing ownership.
- Use relaxed atomics only for independent snapshots. Use acquire/release ordering when publishing related data or transferring ring-buffer ownership.
- Keep telemetry producers nonblocking. Fixed SPSC buffers intentionally drop rows rather than stall render or ETW threads when full.

## Cross-surface changes

- A configuration field is not complete until its struct default, INI load, validation/clamping, save behavior, runtime application, OSD control, user documentation, and architecture guards agree.
- A telemetry field is not complete until row structures, CSV headers, formatting, producers, analysis consumers, and documentation agree.
- Preserve established CSV column order, especially the native-PCL prefix; append diagnostics unless a deliberate schema migration is requested.
- Keep high-frequency logging sparse. Log initialization, state transitions, feature decisions, and failures rather than every frame.

## Verification

- Use standalone tests for pure logic, but do not treat them as proof of production integration.
- Scheduler, hook, swapchain, loader, driver, ETW, and frame-generation changes require runtime verification on every affected API/path.
- Compare telemetry captures when changing pacing behavior and record units, filters, target FPS, refresh mode, API, and FG state used in the comparison.
