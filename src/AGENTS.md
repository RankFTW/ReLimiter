# AGENTS: ReLimiter production source

This file adds production-code rules under `src/`. Follow the root `AGENTS.md` as the shared baseline.

## Runtime and timing invariants

- Treat Present callbacks, marker hooks, scheduler enforcement, presentation-gate execution, fine sleep/spin paths, ETW callbacks, and CSV producer calls as latency-sensitive hot paths.
- Do not add routine blocking, heap allocation, file I/O, synchronous flushing, or contended mutex acquisition to a hot path. Move non-critical work to an existing worker or a clearly owned new worker.
- QPC is the timing authority. TSC-based timing is an acceleration hint and must retain calibration, fallback, and drift protection.
- Do not simplify or retune scheduler formulas, constants, state transitions, feedback, or call ordering without reading the surrounding rationale and producing capture-backed before/after evidence.
- Check all affected modes: VRR and fixed refresh, foreground and background, marker and Present fallback, and applicable FG/DMFG states.

## Pacing design constraints (user decisions, binding until the user changes them)

Rationale and evidence: the local work-item records (root `AGENTS.md`, Repository boundaries).

- Mechanisms must be general across games and systems. Do not tune a hold, release or fallback around a threshold or operating point found in one capture (a GPU load level, a budget value); a result that improves only at one point means a part of the problem is missing.
- Previously settled pacing must survive architectural changes: compare against the regression capture set in `.agents/skills/pacing-capture-analysis/references/capture-protocol.md` before and after any change to release timing, holds or the Reflex Sleep path. A change that trades long frames or cadence restarts for a few ms of latency is rejected by default; the user prefers smooth pacing and accepts about 4 ms of latency for it.
- No native Present hold as a pacing mechanism (it measured much worse frame-time jitter). Everything must work with hardware-accelerated GPU scheduling (HAGS) on.
- Output override **GPU wait** (`output_rung=gpu`) keeps its earlier behavior; new hold or release rules apply under Auto or to frames that are not held. GPU wait releases are timed against the next frame's heavy GPU work (or its Present call) with a fixed distance, never gated on GPU load or hold length; the collision guard stands aside only by the queue-order check, not by scaling a number.
- Prefer deterministic mechanisms over retries and backoff. Late-frame catch-up keeps the render queue (keep), it does not restart after a late frame.
- Cadence grid source lateness (`CadenceGrid::PlanNext` step 3): judge a source against S = T − min(L(n), L(n − 1)), the S its pre-wait aimed at. ReLimiter switching the lead (another output rung's or FG divisor's lead, a restarted lead) is not the game being late: judged against the new lead, the first frame after the FG input wait engaged restarted the cadence and moved T 4.4–10.5 ms later (CONTROL Resonant FG 2× at 130, lead 17.15 → 21.65 ms), a long displayed interval at every such switch, and the restart counted as evidence for the held GPU floor. Within a rung the lead moves at most one slew step per frame, so the rule only acts at those switches.
- One pacer: with the default **Bypass Reflex Sleep** the game's NvAPI Sleep returns without the driver whenever ReLimiter paces a positive cap, held or not (`Scheduler_PacesSource`, `NvAPI_ShouldBypassSleep`); only Dynamic MFG passthrough and the Reflex driver limiter use the driver's Sleep.
- Driver pacing inside `NvAPI_D3D12_SetAsyncFrameMarker`: under the Reflex Sleep bypass with DLSS-G the NVIDIA driver still paces, by sleeping the thread that calls the game's Present inside this call (Streamline's `sl.dlss_g`, through `sl.common`; the long calls are PRESENT_END, type 5). `Hook_SetAsyncFrameMarker` is pass-through timing only (telemetry `async_marker_wait_us`); never suppress, delay or alter that marker or its result. In Gears it sleeps when the game's PRESENT_START of frame n comes before about frame n − 1's Reflex GPU end (a heavy GPU frame n − 1, a fast render thread), and the slept real frame is misplaced far more often (9–21% against 1–2%). Do not chase it with a later release: the render thread absorbs most of the shift (PRESENT_START moves 0.22–0.34 ms per ms of release), so it would starve the GPU long before it removed the sleeps.
- Driver low latency mode under the bypass (developer A/B `bypass_low_latency_off`, `g_bypass_low_latency_off`, `UpdateLowLatencyOverride`, `ApplyCapturedSleepMode`, `s_low_latency_forced_off` in `nvapi_hooks.cpp`): the Sleep bypass removes the Sleep call, not the game's low latency mode, so the driver's own pacing, inside the Present (see above), remains a second pacer. With the key on, `Hook_Sleep` (presenting device only, after the Smooth Motion return) sends the captured game parameters with `bLowLatencyMode` and `bLowLatencyBoost` cleared on the first bypassed Sleep, and the game's parameters exactly on the first Sleep that is not (bypass off, cap off, driver limiter, passthrough, key off). Only the forwarded copy changes, never the captured game parameters; while applied, `Hook_SetSleepMode` forwards the game's calls the same way, and `RestoreGameSleepMode` (shutdown, limiter release) and a driver limiter apply clear the state. The state changes only after an `NVAPI_OK` driver call; a transition and the forwarding of the game's own SetSleepMode share `s_sleep_mode_forward_lock` (a transition only try-acquires it from the Sleep hook), so a game call can neither land between the driver call and the state change nor undo the override. A failed call or missing parameters retries on a later Sleep; log transitions only. Injected Reflex (`reflex_inject.cpp`) is outside it: it runs only without native Reflex markers, never reaches `Hook_Sleep` and is not bypassed. Measured in Gears (FG 2× at 120, GPU-paced): the in-Present sleep disappears (no async marker call above 0.1 ms), Reflex reports keep arriving on every frame, display jumps and jitter reach the driver's Sleep, PC Latency stays below it. CONTROL is not measured yet.
- Flip metering block (developer `flip_metering_off`, `InstallFlipMeteringBlock`, `Hook_QueryInterface` in `nvapi_hooks.cpp`): returns nullptr from `nvapi_QueryInterface` for `NvAPI_D3D12_SetFlipConfig` (ID 0xF3148C42), as Special K, OptiScaler and RenoDX Commander do, so DLSS Frame Generation runs as on a GPU without hardware flip metering. It reproduces that state on a Blackwell test machine; never default it on. It is installed during init, not with the deferred hooks, because frame generation resolves the function itself and a pointer resolved before the hook stays usable; interception ends with the addon's teardown (`DisableAllHooks`). The first hidden request logs its caller module; without that line the block did not reach frame generation. With metering, a capture shows `flip_delay_qpc` on every row and the real frame's display − `etw_ready_qpc` near its flip delay; without it, both are 0 and every frame is shown as soon as it is ready.
- SetFlipConfig observer (`Hook_SetFlipConfig` in `nvapi_hooks.cpp`, with the deferred NvAPI hooks): an inline pass-through hook on the function itself, so it also sees callers that resolved it earlier. It never alters the call, the configuration or the result; it logs the first configuration and each change of the batch size, presented frames, status and feedback (never per batch; at most 16 lines). It resolves the function through the block's trampoline whenever the block's hook exists, enabled or not (a reload can re-enable a retained hook): its own request must never reach the block, which would log it as the first hidden request. Under the block, frame generation that asks for the function afterwards never gets it; a line then comes from a caller that resolved it before the block. A user capture without flip delay where frame generation still issues each group's Presents within a few ms (the metered path) means metering was asked for and not applied; this line says whether the call was rejected, metering was off at the caller, or the driver reported `no_iflip` or `mirroring_detected`.
- Separate presenter (`fg_route_unsupported`; `SeparatePresenter`, `RecordSeparatePresent`, `RejectRoute`, `PublishSeparatePresenter` in `streamline_gpu_handoff.cpp`; `PacingCapability::FgSeparatePresenter`): without hardware flip metering DLSS-G presents each group from its own thread and queue after the worker's return Signal, overlapping the next cycle (Valor Mortis with `flip_metering_off`: every Present on one other thread and never on the worker's queue, 38% begun inside the worker interval). The worker-local Present contract never holds there, so the route reports unsupported, not pending. Only positive evidence turns `worker_signal_before_present` into `worker_present_on_other_queue`: a native Present of the bound swapchain outside any source scope, on another thread and a known other queue, recorded with the failing cycle's token (a stale Present can only miss a cycle; `present_queue_not_worker` also counts, an unknown queue does not). Keep qualification running under that reason (`FgRouteQualificationPending`); clear it on a completed cycle, a worker-local Present, a new route identity, an FG multiplier change or FG stopping, never on time. Do not relax the worker-present contract to hold such a presenter: another queue loses the queue-order proof that its Presents depend on the held work, and if that queue is the game's source queue the hold would stall the previous frame's Present. That needs a fence-chain proof first (a worker Signal the presenter's queue or thread waits on).
- Presenter probe (developer `fg_presenter_probe_us`, `GpuPresent_ExecutePresenterProbe` and `Ticket::probe` in `gpu_present_gate_d3d12.cpp`, called from both native Present hooks in `vsync_control.cpp`): an experiment, not a pacing mechanism. While the resolver reports `fg_route_unsupported`, it holds each native Present of the selected swapchain on its present queue (`present_queue`, from the ReShade present event) until call + the probe time, in alternating 4 s held / not-held blocks, to measure whether a released Present flips promptly while the game's GPU work runs and whether DLSS-G's pacer follows the held flips. Its tickets claim no plan (grid index 0, so `PushStage` drops their events) and `Current()` checks only the swapchain, settings and that the probe is still active. Its queue calls run inside `StreamlineQueueOwnedScope`, so the queue hooks never observe them. Remove it once the full-pacer decision is made.
- Priority probe (developer `gpu_priority_probe`, `gpu_priority_probe.cpp`, started and stopped in `dllmain.cpp` beside the GPU gate): an experiment, not a pacing mechanism. Its own thread creates a high and a normal priority DIRECT queue on the presenting device (`CreateCommandQueue1` with distinct creator IDs where available), each with a `GpuReadinessQueue` timestamp list and a CPU-signalled time fence, and alternates a queue Wait, a timestamp and a CPU signal on a 7.13 ms period; timestamp minus signal is the resume delay of that priority. A sample counts only when a snapshot at its signal confirms the probe's device presents (`PresentingIsProbeDevice`); it never stops on a device change, because a snapshot can be empty while the same device is republished or show a provisional device that never presents. Before exiting it signals every queued Wait and frees the queues only after their GPU work has completed (otherwise it retains them and `GpuPriorityProbe_Stop` returns false). Its queue calls run inside `StreamlineQueueOwnedScope`. Remove it once the full-pacer decision is made.
- Control file (developer `control_file`, `control_file.h/.cpp`, `Config_SetLiveKey` in `config.cpp`): the test harness's channel into ReLimiter. A poller thread reads `relimiter_control.txt` and queues new commands (`ControlFile_Parse`: complete lines, growing seq); `ControlFile_OnPresent`, after the presenter guard in `on_present_impl`, runs them under the config owner lock (`Config_TryLockOwner`), which both OSD callbacks (`DrawSettings`, `DrawOSD`) hold for their frame because every ReShade runtime runs them on its own present thread; when the lock is held the commands wait for a later present, so the paced thread never blocks on it. The poller writes `relimiter_control_status.txt`. The present callback touches only static queues, flags and counters, never a handle, so a callback still running at shutdown cannot use a closed one; `ControlFile_Start` empties the queues, so a retained module's reload runs nothing queued before it. `capture start` uses `FrameTimeline_StartCapture` (a new epoch even while capturing) and reports a rejected transition as a failure. `Config_SetLiveKey` covers exactly the keys the OSD changes at runtime and publishes them the way the OSD does (`ValidateConfig`, the cap atomics, `Config_ApplyPacingPipeline`); add a key there only when the OSD can change it live. It queues no save, but `AddonUninit` saves all settings, so the harness restores the INI after a session.
- Chain diagnostic (`ChainRecord`, `AggregateChain`, `ReportChain`, `StreamlineHandoff_RecordQueueFence` in `streamline_gpu_handoff.cpp`, called from `ObserveFence` before its Interested filter): counts only, no authority. It records the Signals and Waits of the FG worker's queue and the separate presenter's queue, for designing a hold for frame generation without hardware flip metering. Keep its lifetime model as it is: hooks only push records for queues the installer worker published, each tagged with one global epoch that every queue destroy advances, and the installer worker aggregates in push order, dropping older epochs and resetting both sides on a newer one. Per-queue lifetime schemes (lock-free tables, per-side lifetimes, last-seen tracking) each failed review on destroy races.
- Render handoff limit (`render_handoff.*`, `HandoffLimitApplies`): the render-thread offset (w + d) applies to frames **not held** only. On held frames it moved CONTROL's simulation into its render thread's command submission and regressed pacing; the queue in front of the render thread absorbs simulation variance for held frames. Stalls turn it off only before the render thread is seen taking a frame ahead of the next release, and only two in a row (`RenderHandoffStalled`); that evidence is checked at every planned frame, limited or not, so a block can lift while the limit is off. Never make a block depend on evidence only the limit itself produces: a game that runs ahead would keep it off for the session.
- Render handoff GPU floor (`LeadController::GpuFloor`, `OnGpuRenderEnd`, `OnReportPair`, `HandoffFloorQpc`): a frame not held, released at SIMULATION_START while the Sleep is bypassed, is released no earlier than Ĝ(n−1) − (P/2 + F + σ). P is the median GPU period of consecutive frames the GPU did not wait for (≤ 1 ms idle) and whose pace it set (the GPU-set classifier below), F the median first submission − RENDERSUBMIT_START of streaming pairs, σ the median release → RENDERSUBMIT_START of `source_only` frames; all from 32 samples. Ĝ is the later of the newest Reflex report's GPU end and the render thread's newest live PRESENT_END plus the Q5 of the reports' PRESENT_END → GPU end gap, each extrapolated by P; keep the live bound, since reports arrive about two frames after the GPU end and a stretched GPU frame otherwise cascades into the next four. Keep it deterministic and measured: do not reintroduce a term learned from held-back frames; it finds the edge by hitting it, and the first held-back frame of each run stutters. Keep the floor itself anchored to the newest GPU end rather than a free-running cadence at P, which follows a GPU change only through reports two frames old (the GPU-paced rhythm below smooths held releases inside a band the floor bounds; it does not replace the floor). Keep the stream proof: without it a game that submits a whole frame at the end of its window would read held back on every GPU-bound frame. Held frames get no floor unless `gpu_paced_cadence` is on, and then a floor bounded by the cap's own release (below). `OnReportPair` feeds F and the stream proof only.
- GPU-paced cadence (developer A/B `gpu_paced_cadence`, `GpuPacedHeldFloorApplies`, `SourceStage::GpuPacedRhythm`, `SourceStageRequest::gpu_floor_qpc`, `CadenceGridPlanInput::earliest_target_qpc`): one cadence takes the later of the cap and the GPU for every frame. Held frames get the GPU floor (no `w + d`) on a rhythm: after a consecutive frame it paced, release = previous release + mean of the newest 5 GPU periods (`RecentGpuPeriodUs`); the floor when that is not earlier (late starts idle the GPU: stretched 7–15% against 2–10%), else pulled 0.25 toward the floor, never earlier than floor − P/2 (early starts cost little: 4–8%). Keep it bounded by the floor on both sides and continued only from frames it paced: a free or symmetric phase tracker drifted 3–18 ms from the GPU at fast load changes in replays. `LeadController::GpuSetPace` classifies a frame as paced by the GPU (not held, or a queued wait the GPU reached after its Signal: the probe's pre-wait time, else readiness, later than the release; missing evidence counts as waited, and a probe read back after the report still decides). P counts only pairs whose two frames the GPU set, and the PRESENT_END → GPU end gaps only such frames: a held frame's GPU end follows ReLimiter's own Signal, so P measured the cadence and the floor, fed by it, released later every frame (Rogue Core with Adaptive cap at 130: 83–89 FPS, median P 11.77 ms against 7.4 ms of GPU work). `output_status` alone cannot classify: the GPU waits report every queued wait as held. Never switch the floor on and off per frame with the classifier: a held floor withheld after every GPU-waited frame read the floor's own early target as GPU lateness and alternated between two release depths 13.8 ms apart every 2–3 frames (CONTROL FG 2× at 130: 214 switches in 48 s, SIMULATION_START intervals of 23 then 7–8 ms, 171 display jumps per 1,000 against 2.7 with the cadence off; with the cadence off 24% of frames already read GPU-set there, so any per-frame choice between the two depths is bistable). The held floor is bounded by the cap's own release instead (`GpuFloorCap`, scheduler `HeldGpuFloor`): min(Ĝ(n−1) − (P/2 + F + σ), Ĝ(n−1) − ḡ + I − L − slack), ḡ the median readiness gap, L the cap's lead (the newest plan's), slack half the grid's late tolerance of I. With the predecessor held at its target it equals S(n) − slack, so the floor moves a release only by the GPU's lateness beyond the output's slack, and ReLimiter's own holds never move it. A game whose render thread runs ahead of the GPU releases bounded held frames at the cap's own release instead (`RenderCoupling`, `GpuFloorEstimate::release_floor_qpc`, `SourceStageRequest::release_floor_qpc`): R = own − φ(own − min(C, T(n − 1) + I − L − slack)), C the cap bound, once the later of frame n's RENDERSUBMIT_END and PRESENT_START came before frame n − 1's readiness on 32 of the newest 128 reported held frames (Coupled at none of a full window, unchanged between, Unknown after a reset). There the lateness term made no frame ready sooner and moved the SIMULATION_START interval by which DLSS-G places real frames (under `before_wait` the pre-Sleep wait carries the moved release to the marker): CONTROL FG 2× at 130, bounded, 6–18% of frames released 1.5–1.7 ms past S after a predecessor 3.5 ms late at p50, readiness unchanged at equal predecessor lateness (2.86 against 2.92 ms late), display jitter > 2 ms 23.9 against 12.2 per 1,000 with the cadence off in one session (none in another), PC latency 1–3.6 ms lower on those frames. Only the wait follows R: the floor still sets the GPU-late exemption, T′ and the rhythm, E's samples and the rhythm count from the floor's release (`LeadFrameStart::floor_pull_us`; from the earlier release E grows by the pull and moves T′ later on every such frame), a pulled frame's lead sample is the cap's (`FloorSetRelease`), and the pre-Sleep wait aims at the cap's S′. Never pull a render thread that waits on the GPU (Gears: 0 of 12,894 frames set the bit, p1 margin +0.12–0.14 ms): that is the deeper queue after a stall. Never slew-limit the shift instead (release smoothing) or keep it and move only the driver's SIMULATION_START (the game still simulates from the release). Replays must move SIMULATION_START through the pre-Sleep wait's end: shifting it by s − S directly predicted more jitter, because the pre-wait aims at the floor predicted at Sleep time; through it they predicted only part of the gain (23.9 → 21.8 per 1,000 against 12.2 with the cadence off). Live (CONTROL FG 2× at 130, Adaptive cap off, two cadence / cadence-off pairs in one session): the render thread read ahead of the GPU with 0 switches, 95–96% of floor frames were released at S′, release spacing p90 0.098 ms (0.100 off), SIMULATION_START intervals off by > 0.8 ms 15.5–15.6 against 11.9–14.1 per 1,000, display jitter > 2 ms 14.6 / 15.7 against 17.3 / 11.8 per 1,000 (no excess at equal predecessor lateness beyond the two cadence-off captures' own difference), jumps > 4 ms 4.2 / 4.1 against 5.1 / 3.4, animation error p90 0.93 / 0.88 against 0.93 / 0.91 ms, PC latency beyond the lead 0.3–0.5 ms lower (raw PC latency followed the lead's 35–41 ms swings within every capture). The floor's own depth P/2 + F + σ is Gears' operating point: CONTROL's cap runs a frame deeper (render thread start 14.7 ms before G(n−1) on the cap, 7.6 on the floor; simulation 4.4 / 8.9 ms p50 / p90 against 7.4 / 20), the effect for which the handoff limit is not applied to held frames. Never bound with a lead measured from frames the floor did not release (the median of anchor(m−1) + I − s_m): it stops once the floor releases every frame, and when L then rises the bound stays behind the floor for good (CONTROL FG 2× at 130: L 21 → 31–35 ms, the measured median stuck at 20–24 ms, the floor released 92–94% of frames, 8–11 display jumps per 1,000 against 1.6 with the cadence off). Which of the two depths applies comes from the newest 128 reported held frames (`LeadController::CapBound`, `NoteCapBoundEvidence`), each set when its GPU waited at its Signal and its plan did not move its target (`LeadFrameStart::gpu_target`), whoever released it: bounded at 32, the floor's own depth when the full window has none, unchanged between. Never decide it from frames the floor did not release: that evidence is what the own depth removes (CONTROL FG 2× at 130: 61–78% of held frames bounded, 5–7% under the own depth, while the waits at an unmoved Signal stayed at 50–63%), and the cumulative count of it (32 in the producer epoch) bound Gears for good: its render thread then started L − 19.7 ms before the GPU's need on the frames the floor released, with 850 held-first frames per minute at L 32 ms. Never exit at a share: at 16 of 128 CONTROL switched 12 times in one capture; at none, replayed on 24 captures, CONTROL left the bound once (0.9 s, every frame late with its GPU work above I) and Gears switched 2–6 times per capture at its section changes. Live (one capture per arm): CONTROL stayed bounded with 0 switches, its cadence capture within 0.1 display jumps per 1,000 of the cadence-off one; Gears with the cadence alone sat at its own depth 85% of the time, held-first frames 62 against 327 per minute, jumps 11.2 against 13.7 per 1,000, PC latency −2.4 ms, but in a heavy section the own depth starved the GPU inside frames whose render submission ran long (GPU stalls > 3 ms 107 against 57 per minute; that section's jumps unchanged). Do not size the own depth from the render submission to remove those stalls: Gears' submission of frame n never ends before the GPU finished rendering frame n − 1 (readiness; p1 margin 0.10–0.14 ms, under the driver's Sleep too), about 90% of a stalled frame's late last submission is its longer submission (content: stalls rise from 0 to 9.8% across simulation-length fifths at equal render-ahead), and an earlier release moves the late tail least (last submission against G(n−1): p50 −0.35, p95 −0.12, p99 0 ms per ms of render-ahead) while each millisecond pushes far more frames past the ~11 ms held-first edge (7.6% → 27.5% at +1 ms in the heavy section). A need measured as G(n) − w − A contains the depth itself (it moved 0.87 / 1.21 ms per ms at p50 / p90) and ratchets. The own depth already idles the GPU less than NVIDIA's Sleep in that game (in-span idle above 3 ms 133 against 148–196 per minute); the Adaptive cap removes most of it (133 → 15 per minute, jumps 11.2 → 5.0 per 1,000) at its fps cost. A switch moves the floor through a blend (`AdvanceCapBound`): Ĝ(n−1) − (P/2 + F + σ) − φΔ, Δ the gap back to the cap bound, φ stepping toward the mode by at most min(100 µs, I/64) of Δ per published held plan, never by Δ at once (CONTROL about 7 ms, Gears 2–4 ms; the rhythm passes a later floor straight through). φ is 1, the cap's release, after a reset and after every held plan without a floor (not eligible or not known), so a returning floor starts at the bound whenever the readiness gaps give one (with them cold, a restart still applies the own depth at once): holding φ through such a stretch brought a bound that had waited for readiness gaps after a restart back at the own depth (10.3 ms past the bound in a CONTROL-shaped test), and took Cold to the own depth in one step. Cold, the held floor applies at its own depth only after a SourceLate or OutputLate restart of a held frame in the producer epoch (`NoteCadenceRestart`), else not at all (`GpuFloorEstimate::ineligible`); bounded, not without warm readiness gaps and the cap's lead. Never count restarts of frames not held: the first frame after an FG change lands late on the new grid while FG is not presenting yet, just after the floor's evidence was reset, and that restart alone made the floor apply unbounded once FG presented (CONTROL FG 2× at 130: for 13 s the floor released most frames while the cap held 15–23). The first held plan after the FG input wait engaged restarted the cadence the same way while the grid judged it against that rung's longer lead; the grid judges a source against the lead its pre-wait aimed at (`cadence_grid.h`, lead discontinuity). The plan and the pre-Sleep wait use the same `HeldGpuFloor`: with the unbounded floor the pre-Sleep wait aimed past S on 211 of 214 floor exits. A cap or FG divisor change restarts the floor's output-shaped windows, its restart, the cap bound's window and the rhythm (`SourceStage::ResetGpuFloor`), but P carries over until the new window holds 32 pairs (`GpuPeriodUs`): with P cold the floor stopped for those pairs, and where the GPU limits the new cap the cadence restarted on nearly every frame until the overload guard took the holds away (CONTROL at 130 after FG was turned off, 11.4 ms of GPU work for a 7.69 ms interval: 27 restarts in the 0.54 s before the floor returned, holds off for 4–7 s; an earlier build that kept P paced a 6.8 s FG-off stretch without that burst). With the switch, Ĝ also takes the readiness anchor (lead_controller.h): the newest frame's anchor (`ReadyAnchorQpc`: its GPU readiness, or for a queued GPU wait the later of readiness and release) + the median anchor → GPU end gap + P per frame, replacing the older report's extrapolation (reports are about four frames old at the release); it is an estimate, not a bound. The gap window (`RecordReadyGap`) takes every frame the GPU set, held or not, never only frames not held (that filter left the window empty and the anchor never engaged in Gears), and never a frame whose GPU waited at its Signal: on the GPU queue wait its measured GPU end does not follow the release, so its gap is ReLimiter's own hold. Keep the gap signed (within ±I): the GPU queue wait's pre-gate query runs after the game's measured GPU work (Rogue Core −0.21 ms, p10–p90 42 µs, in every capture since Phase 0; Gears without FG −0.34 ms) while the FG input prefix precedes frame generation (+1.45 to +1.75 ms); a positive-only gap rejected every GPU queue wait frame, so the anchor never engaged on that output. A frame whose GPU floor is later than the moment the game reached ReLimiter (its marker, or its Reflex Sleep entry for that grid index, `SourceStageRequest::sleep_entry_*`, before any wait in the hook) and whose earliest release is not later than the floor is on time by construction: the grid never judges its lateness, at its source or at its output (`LeadController::GpuFloorReleased` → `CadenceGrid::ObserveOutput` `gpu_paced`). Pass the raw floor as `gpu_floor_qpc` for that test, never the rhythm's release (a release earlier than the floor would otherwise turn frames arriving between them into SourceLate restarts, the v13 cascade). Its T ≥ its release + min(`LeadController::EarlyLeadUs`, L), so its S = T − L never lies after its release; the early lead is the `1 − q` quantile of the measured readiness (release → GPU ready on the GPU waits, never the hold-corrected sample) of the newest 128 frames the floor released (per output class and FG divisor; the bucket's early side until 32), and the grid follows a later T without an epoch. That early side lags a change from cap-held to GPU-limited frames (readiness 5–6 ms later after the release); judging such frames' outputs (the FG late-frame spacing moving the Signal past T + tol) restarted the cadence 13–47 times per 45 s capture and paused the holds. Each piece answers a capture where the GPU was the limit (Gears, FG 2× at 120): judging lateness while T had not moved, an early side from the bucket or from hold-corrected samples, and treating a pre-Sleep frame whose marker lands just after the floor as late each led to SourceLate restarts with a 6–10 ms GPU hold; releasing every frame at its floor copied GPU noise into the simulation-start interval that DLSS-G places real frames by. With `marker_forward_order=before_wait` the driver timestamps SIMULATION_START at the marker's arrival, before ReLimiter's trim to the release (0.45 ms earlier at the median, sd 0.38), so the smooth release reaches DLSS-G only partly. With the restarts and the driver's in-Present sleep gone (`bypass_low_latency_off`), `after_wait` puts the driver's SIMULATION_START on the release (+0.01 ms) and in one Gears session cut the misplaced real frames with a start-interval deviation above 1 ms from 40% to 11% (driver's Sleep 9%) and display jumps from 30.2 to 18.5 per 1,000 (driver 16.3). An earlier ABAB of the order showed no difference because OutputLate restarts dominated it. Never rebuild it as a restart rule: a restart at floor + E with S of the next frame still T + I − L cascaded (median one frame apart). Never move the grid to the GPU on frames the GPU finishes early: they keep the cap's T and are held, so the cap holds. The Present-end gate (a release no earlier than PRESENT_END(n−1)) was tried and removed: GPU period 17.2 → 18.4 ms and every pacing metric worse. Release smoothing (a second stage pulling releases toward the mean of 64 rhythm intervals, never earlier than floor − P) was removed: live ABAB jumps 21.1 against 17.8 per 1,000 (driver 9.7); releasing a render thread earlier than usual against G(n − 1) after a stall made Gears' render thread run only after the GPU finished frame n − 1 (GPU idle 11–13 ms). Do not deepen the queue after a stall again without knowing what the render thread waits on.

A stamp is keyed by the complete `MarkerStampKey` (marker domain, producer epoch, frame ID: `PacingFrameKey`'s fields), frozen by the hook at ENTRY (`MarkerStamps_Capture`, before any admission step that can be descheduled across a lifetime change: the device check, and in the PCL hook the flow-timeout rotation, the token `GetFrameID`, which can begin an epoch itself, and the marker log: the PCL capture is the first step after the QPC read, a call whose own rotation changed the epoch publishes nothing, and the first marker of a resumed PCL lifetime, a SIMULATION_START, therefore has no stamp) together with the ring's reset generation and the arrival sample, and published once the marker is admitted (`MarkerStamps_Publish`), which drops the stamp when the producer epoch is no longer the captured one (`MarkerStamps_Record` drops it when the generation is not): a call suspended across another lifetime never stamps its frame ID into the new one. Key off: the capture is one relaxed load and a branch not taken, nothing else is touched; the reader (`FillMarkerStamps` in `pacing_telemetry.cpp`) asks for the complete key. Never look a stamp up by the frame ID alone: the two hooks have their own ID spaces and a synthetic ID restarts with the producer epoch. `MarkerStamps_Reset` runs where `ApplyLifecycle` resets the source stage (a generation bump, wait-free). A marker stamped twice for one frame keeps the sample with the latest QPC, whole (an older sample from a thread that was descheduled before it claimed the slot changes nothing; QPC, cycles and thread ID are never mixed). The ring has 256 slots, one sequence word per slot: a writer claims it by compare-exchange and retries up to 256 times with a pause and then drops the stamp rather than wait, a reader retries 4 times and then reports nothing, a later frame takes the slot over. Do not copy the stamps into the Source record when it is pushed: that record is built at the frame's SIMULATION_START release, before the frame's own SIMULATION_END exists, so every cell would be empty; `FillMarkerStamps` reads them when the row completes. The rate (`MarkerRateCalibration`, driven one step per telemetry worker cycle by `MarkerCycles_CalibrateStep`) is the TSC's from clean clock pairs, never from spinning: each pair is `__rdtsc` between two QPC reads and is rejected when the bracket is wider than 5 µs (a preemption inside a pair shifts the TSC against the QPC and would publish a rate off by tens of percent, which the later agreement check cannot see; 5 µs bounds the pair's time error to 2.5 µs, 5e-5 of a 50 ms interval), its time is the bracket's middle; three pairs with intervals of at least 50 ms must give two interval rates that agree within 0.1% (else the oldest pair is dropped and the next waited for, 4 times), and the rate is only used with an invariant TSC (CPUID 0x80000007 EDX bit 8) and after one busy section of about 5 ms on the worker shows `QueryThreadCycleTime` counting TSC ticks within 5% (low readings, which can be lost CPU time, are retried up to 3 times; high ones refuse the rate): the documentation calls it a cycle counter, not a clock, so the equivalence is checked on the machine, never assumed, and without it the CPU cells stay empty. ## Hooks and external APIs

- Derive the active graphics API from the current presenting device during launcher, game, and swapchain transitions. Never reinterpret DX9, Vulkan, or OpenGL native handles as DXGI swapchains.
- Use typed MinHook trampolines, idempotent installation, and complete failure cleanup. Preserve each hook's established original-call ordering; some marker hooks intentionally call forward first.
- Install hooks in batches, one per site (`HookBatch` in `hooks.h`; every MinHook enable freezes the process, and two engines' freezes can deadlock each other, so a site makes one freeze, not one per hook). A batch is lazy: constructing or destroying one takes no lock and calls nothing, the first install inside it takes `HookInstallGuard`, and the lock is held from that first create to the apply (`Apply` and `Hooks_FlushBatch` release it), so an idle batch never blocks another installer and no site lengthens a lock the present thread waits on; a site whose own code creates hooks (`FocusLock_Install`, `NGXHooks_TryInstall`) holds its own `HookInstallGuard` around that code. Inside a batch `InstallHook`, `InstallHookPublished` and `Hooks_EnableOrQueue` create, publish the trampoline and `MH_QueueEnableHook`, and their `MH_OK` means queued, never enabled. The sites: `Init` (`DoInit`: the flip-metering block and `NGXHooks_Init`, one batch around both), `FirstPresent` (the first present event: the four LoadLibrary hooks and the NvAPI hooks), `LoaderScan` (one scan of the loader-install worker, closed before its 250 ms wait, so discovery, factory probing and drains never run under the install lock for the batch; `NGXHooks_TryInstall` outside the worker opens its own), `FocusLock` (`FocusLock_Install`: `MH_CreateHook` x4, then `Hooks_EnableOrQueue`) and `DxgiFallback` (the DXGI `Present` / `Present1` pair, only when the vtable route is absent). Anything that logs a hook as installed, begins a producer epoch or sets a state flag reads `Hooks_TargetEnabled` AFTER the apply (`NvAPIHooks_ReportInstalled`, `ReportFlipMeteringBlock` and `LoadLibraryHooks_ReportInstalled` run after the batch; the installers call them themselves outside a batch). A group that cannot continue without the enable result (the Streamline hooks, the proxy and queue hooks, the FG input and queue hooks, the NGX transaction, which retains or rolls back on it) calls `Hooks_FlushBatch()` once after its installs: the same apply with the batch still open. `MH_ApplyQueued` is not a transaction: it stops at its first failure with the earlier hooks enabled, so a failed apply enables every hook still queued one by one with `MH_EnableHook`, logs each failure once at warning and leaves the failing hook created and not queued (nothing stays queued, so a later apply never enables it behind its owner's back). Nested batches on one thread are no-ops that queue into the outer one; an empty batch calls MinHook not at all; a refused admission (shutdown) makes installs fail with `MH_ERROR_DISABLED` as before. A retained load's records stay: installing the same target again queues it, and `EnableAllHooks` (`MH_EnableHook(MH_ALL_HOOKS)`) enables the queue too, settles every record to enabled and, when it stops at a failing hook, enables the rest one by one. Never call `MH_EnableHook` per hook inside a batch scope, and never hold a batch across a wait. Every call that freezes (the apply and the one-by-one enables, a single enable or disable, enable-all, the teardown disable) goes through hooks.cpp, never a raw `MH_EnableHook` / `MH_DisableHook` / `MH_ApplyQueued` elsewhere (`Hooks_DisableHook` for a hook's own disable): those run on the hook installer thread (`Hooks_StartInstallerThread` from `DoInit`, key `hook_installer_thread`, default true, a compatibility switch read once; `Hooks_StopInstallerThread` inside `DisableHooksForShutdown`, after the last freezing call). It is created with a security descriptor that denies `THREAD_SUSPEND_RESUME | THREAD_GET_CONTEXT | THREAD_SET_CONTEXT` to Everyone in front of the token's default DACL, so another engine's `OpenThread` for it is refused and the two freezes cannot wait for each other; at its start it opens itself for a suspend, which must fail (a debug privilege bypasses the descriptor), else it is `Unprotected` and every call runs on the requester. Only raw MinHook calls run on it: no ReLimiter lock, no log, no allocation; the requester keeps the install lock, takes the single job slot's lock, posts and waits with no timeout for the job event or the thread handle. `HookInlineOnlyScope` is the explicit way for code in DllMain or a loader callback (none today) to keep a call inline; so are the kill switch, a thread that is not `Ready` yet, and a stopped thread. If the thread ends before it took the job, the requester runs the job; if it ends with a job in flight MinHook is unusable for the rest of the process (`Hooks_MinHookUnusable`: admission closed, every later freezing call `MH_ERROR_DISABLED`, nothing replayed or terminated), and so is every other MinHook call of the product: none is made outside hooks.cpp (`Hooks_Initialize`, `Hooks_CreateHook`, `Hooks_RemoveHook` and the internal queue calls all return `MH_ERROR_DISABLED` without touching MinHook, whose lock the dead thread may hold), and a caller treats that status as "leave the record retained, do not retry". The batch stages record whether the installer ran the apply and whether it is protected in the high bits of the crumb's site byte (`kBreadcrumbInstaller*`). `Hooks_ForgetTarget` after `MH_RemoveHook` of a `Hooks_EnableOrQueue` target.
- Keep SEH narrowly around unstable driver, game, COM/vtable, Streamline, NGX, or opaque-ABI access. Do not use a broad `__try` block to hide failures in ordinary project logic.
- Preserve late-load handling and data-only load filtering in loader hooks.
- Keep DLSS, FG, Streamline/PCL, NGX, Reflex, and other 64-bit-only integrations behind existing architecture boundaries. Shared code must continue to compile against Win32 stubs without referencing excluded symbols.
- Native Present entry (`vtable_copy.h/.cpp` pure rules, `vsync_control.cpp` install and detours): the route's entry is a private copy of the native swapchain object's vtable, not the inline patch. The copy is VERBATIM: the entries from index -1 (the RTTI locator) as far as they are readable, at most 512, never judged and never zero-filled (entries past the vtable's real end are whatever follows it in memory and are never called); every read first queries the region (`VirtualQuery`) and stops at anything that is not committed, readable memory without PAGE_GUARD, so a guard page is never touched (the SEH stays for races); it must cover the whole IDXGISwapChain4 interface (slots 0 to 40) or nothing is installed (logged). Before the copy is published every module that supplies a callable entry of slots 0 to 40 is pinned (`GetModuleHandleEx` FROM_ADDRESS with PIN); ANY of those slots pointing outside every loaded module is code whose lifetime cannot be held (a hook's private thunk its owner frees), so no vtable entry is installed (inline patch only, logged with the slot index). A copy goes only over a vptr inside a loaded module's image (a class vtable), never over a vptr in private memory. The copy names the detours in slots 8 and 22 and the object's vptr points at it. Each copy has an immutable forwarding record (the original vptr and the slot values read at copy time, shared by identical vtable images) and one detour pair, so a detour's record is its template index and the Present path searches nothing; a record is never retargeted. Another module replacing the vptr AFTER our copy is left alone (`VSync_ObserveNativeVptr`: one load and one compare on an ordinary frame; counted, logged once, shown in the `NativeGate vtable route:` line): never a second copy over a foreign vtable (its hook can save our entry and a later copy would chain into a cycle), no vptr write against it, no timers, no retries. A process-global, never-freed `VptrHistory` (16) keeps the vptrs we replaced and the foreign vptrs seen over our copy: a vptr in the foreign history is left alone on every later selection of ANY object (destroy and init of the same native object do not forget it; this is what stops a resize from re-layering over a foreign chain); a full history refuses a new vptr (logged). Install at the swap manager's selection of the object (`VSync_OnNativeSelected`), restore on its destroy event only if the vptr still equals our copy (`VSync_OnNativeDestroyed`), at teardown restore what is still ours before the hooks are disabled; copies, records and detours are never freed (the module is retained). The inline patch on DXGI's `Present` / `Present1` is NOT installed where the vtable entry carries the route (every MinHook enable freezes the process, and two engines' freezes can deadlock each other; the overlay can also erase the bytes for good): `VSync_InstallDXGIHooksImpl` installs it, in one hook batch, only when the copy was refused (all bindings taken, a foreign vptr, an unsupported object). While the copy carries the route, `VSync_NoteFinishedPresent` (ReShade's finish_present of the selected native swapchain) counts consecutive completed scopes in which no vtable entry ran (`vtable_copy::FallbackCounter`, 32, reset by any scope with an entry, any thread). The evidence is the selected object's alone: `s_selected_vtable_entries` counts only entries whose body ran for the swap manager's selected object (another object's entries never count or reset the run; the all-entries counter is diagnostics), and the run's baseline is snapshotted whenever it is reset. The fallback's selected identity (object + generation, `PublishFallbackIdentity`) is published on every actual selection, also when an existing binding keeps its copy (no install, no adoption), and by a present event that made the selected object's copy; a selection of an object without a copy clears it, and `VSync_NoteFinishedPresent` ignores the finish of any swapchain that is not both the identity and the swap manager's selected one, so an unselected swapchain can neither count nor consume the one-shot. The counter keeps fired flag, generation and count in ONE atomic word: the scope that reaches 32 and the commit of the one-shot are one compare-exchange valid only for the generation it counted for, so a destroy or reselect in between refuses the commit without consuming the one-shot and the new generation starts its own run. The 32nd scope installs the pair ONCE through a `HookBatch` (`DxgiFallback`), logged at warning level with the count, and it is never removed or repeated (no timers). The typed install's enable is queued inside a batch and `FinalizeTypedEnables` settles `HookTarget::enabled` after the apply, never before. 'Not installed because the vtable entry carries the route' is a normal state in the diagnostics. Where the pair exists, nothing re-installs it when another module erases it, and teardown never disables it (`DisableAllHooksExcept` leaves the two DXGI targets enabled and passing through, since a prologue check cannot be made atomic with MinHook's write-back against another module's concurrent patch); `PrologueHoldsOurJump` is for diagnostics only. One native call has one body: both entries run through `PresentEntry` / `Present1Entry`, the outermost entry for an object on the thread (a thread-local list of `DedupNode`s on the detours' own stacks, any depth, no allocation; `PresentOutermost` / `Present1Outermost` unlink in a SEH `__finally`, so a structured exception caught by a caller never leaves the list pointing at a dead frame, and they hold no C++ object with a destructor, which a SEH unwind would not run) runs the VSync override, timeline, gate, readiness, probe, brackets and telemetry, and an inner entry for the same object passes straight to its original with the arguments the outer entry chose; a Present on another swapchain, or a recursion from inside the original for another object, is not suppressed. The vtable lock serializes install, destroy, reconcile and teardown and is never taken by the detours. Bindings (8) are never evicted: a published binding is kept until its object's destroy callback or teardown (a guess that its copy is gone races another module's unhook, and a later foreign replacement would look like an unseen vtable); when all are taken a new object is refused (logged once, inline-only); a binding dropped over a foreign vptr remembers that vptr first. One judge (`ReconcileLocked`) serves a selection and a present event for every address, with one binding per object address (never a second claim): a vptr that is one of OUR copies is adopted, never copied again (`IndexOfCopy` before any first-install path; an unbound object showing a copy takes the record's identity); the vptr our copy replaced is installed again on the SAME binding (an overlay's unhook, or a new object at an address whose destroy never came; at most 8 per lifetime, a selection resets it); any other vptr over a binding that had a copy is another module's: remembered, left alone. The installed copy's identity (`copy_vptr`, the vptr it replaced) stays on the binding through refused reinstalls until destroy or teardown, so a later restore, adoption or foreign note still finds it. This cannot layer copies: every install reads a vptr that is neither one of our copies (adoption catches those) nor a remembered foreign one (the history refuses them), so a copy is only ever made over a class vtable. Stopping is checked under the vtable lock in both entry points, serialised against the teardown's restoration. Teardown closes installer admission (`Hooks_BeginShutdown`) before collecting the DXGI targets to leave enabled, so a typed hook installed during shutdown is not missed.

## Concurrency and lifecycle

- Every worker needs an explicit owner, start condition, stop signal, wakeup path, join point, and final-drain behavior where applicable.
- Never stop ETW or join workers while under loader lock. Keep process-detach handling loader-lock safe.
- Preserve normal shutdown ordering: stop native PCL before removing hooks, then shut down telemetry and logging according to their existing ownership.
- Start-up evidence (`startup_breadcrumb.h/.cpp`, `Log_Init`): `Breadcrumb_Mark` and `Breadcrumb_PresentCompleted` are plain stores into a mapped page, with no lock, allocation, flush or log, because hook batches call them around `MH_ApplyQueued` while the process is frozen; keep them that way and keep every failure (open, map, read-only folder, a second live launch holding the file) a silent no-op. The record is a seqlock; one writer at a time, a contending mark is dropped. Every stage but the two batch stages is first-wins, `Running` (the 32nd present after the first-present block) is followed only by `Closed`. `Log_Init` moves the previous log to `relimiter_<exe>.prev.log` (a failure is not an error), attaches `relimiter_<exe>.crumb` in the log's folder and, after releasing the logger locks, logs one warning at warning level when the previous launch's record is valid and before `Running` and not `Closed`. A new stage needs the enum, `StageName`, the docs and a mark at its site; never rename a stage or reorder the record (the file layout is versioned).
- Use relaxed atomics only for independent snapshots. Use acquire/release ordering when publishing related data or transferring ring-buffer ownership.
- Keep telemetry producers nonblocking. Fixed SPSC buffers intentionally drop rows rather than stall render or ETW threads when full.

## Cross-surface changes

- A configuration field is not complete until its struct default, INI load, validation/clamping, save behavior, runtime application, OSD control, user documentation, and architecture guards agree.
- A telemetry field is not complete until row structures, CSV headers, formatting, producers, analysis consumers, and documentation agree.
- Preserve established CSV column order, especially the native-PCL prefix; append diagnostics unless a deliberate schema migration is requested.
- Keep high-frequency logging sparse. Log initialization, state transitions, feature decisions, and failures rather than every frame.
