# AGENTS: ReLimiter production source

This file adds production-code rules under `src/`. Follow the root `AGENTS.md` as the shared baseline.

## Runtime and timing invariants

- Treat Present callbacks, marker hooks, scheduler enforcement, presentation-gate execution, fine sleep/spin paths, ETW callbacks, and CSV producer calls as latency-sensitive hot paths.
- Do not add routine blocking, heap allocation, file I/O, synchronous flushing, or contended mutex acquisition to a hot path. Move non-critical work to an existing worker or a clearly owned new worker.
- QPC is the timing authority. TSC-based timing is an acceleration hint and must retain calibration, fallback, and drift protection.
- Do not simplify or retune scheduler formulas, constants, state transitions, feedback, or call ordering without reading the surrounding rationale and producing capture-backed before/after evidence.
- Check all affected modes: VRR and fixed refresh, foreground and background, marker and Present fallback, and applicable FG/DMFG states.

## Pacing design constraints (user decisions, binding until the user changes them)

Rationale and evidence: the local work-item records (root `AGENTS.md`, Repository boundaries).

- Mechanisms must be general across games and systems. Do not tune a hold, release or fallback around a threshold or operating point found in one capture (a GPU load level, a budget value); a result that improves only at one point means a part of the problem is missing.
- Previously settled pacing must survive architectural changes: compare against the regression capture set in `.agents/skills/pacing-capture-analysis/references/capture-protocol.md` before and after any change to release timing, holds or the Reflex Sleep path. A change that trades long frames or cadence restarts for a few ms of latency is rejected by default; the user prefers smooth pacing and accepts about 4 ms of latency for it.
- No native Present hold as a pacing mechanism (it measured much worse frame-time jitter). Everything must work with hardware-accelerated GPU scheduling (HAGS) on.
- Output override **GPU wait** (`output_rung=gpu`) keeps its earlier behavior; new hold or release rules apply under Auto or to frames that are not held. GPU wait releases are timed against the game's next Present with a lead margin, never gated on GPU load or hold length; the GPU wait budget's open top is decided by the queue-order check, not by scaling a number.
- Prefer deterministic mechanisms over retries and backoff. Late-frame catch-up keeps the render queue (keep), it does not restart after a late frame.
- One pacer: with the default **Bypass Reflex Sleep** the game's NvAPI Sleep returns without the driver whenever ReLimiter paces a positive cap, held or not (`Scheduler_PacesSource`, `NvAPI_ShouldBypassSleep`); only Dynamic MFG passthrough and the Reflex driver limiter use the driver's Sleep.
- Driver pacing inside `NvAPI_D3D12_SetAsyncFrameMarker`: under the Reflex Sleep bypass with DLSS-G the NVIDIA driver still paces, by sleeping the thread that calls the game's Present inside this call (Streamline's `sl.dlss_g`, through `sl.common`; the long calls are PRESENT_END, type 5). `Hook_SetAsyncFrameMarker` is pass-through timing only (telemetry `async_marker_wait_us`); never suppress, delay or alter that marker or its result. In Gears it sleeps when the game's PRESENT_START of frame n comes before about frame n − 1's Reflex GPU end (a heavy GPU frame n − 1, a fast render thread), and the slept real frame is misplaced far more often (9–21% against 1–2%). Do not chase it with a later release: the render thread absorbs most of the shift (PRESENT_START moves 0.22–0.34 ms per ms of release), so it would starve the GPU long before it removed the sleeps.
- Driver low latency mode under the bypass (developer A/B `bypass_low_latency_off`, `g_bypass_low_latency_off`, `UpdateLowLatencyOverride`, `ApplyCapturedSleepMode`, `s_low_latency_forced_off` in `nvapi_hooks.cpp`): the Sleep bypass removes the Sleep call, not the game's low latency mode, so the driver's own pacing, inside the Present (see above), remains a second pacer. With the key on, `Hook_Sleep` (presenting device only, after the Smooth Motion return) sends the captured game parameters with `bLowLatencyMode` and `bLowLatencyBoost` cleared on the first bypassed Sleep, and the game's parameters exactly on the first Sleep that is not (bypass off, cap off, driver limiter, passthrough, key off). Only the forwarded copy changes, never the captured game parameters; while applied, `Hook_SetSleepMode` forwards the game's calls the same way, and `RestoreGameSleepMode` (shutdown, limiter release) and a driver limiter apply clear the state. The state changes only after an `NVAPI_OK` driver call; a transition and the forwarding of the game's own SetSleepMode share `s_sleep_mode_forward_lock` (a transition only try-acquires it from the Sleep hook), so a game call can neither land between the driver call and the state change nor undo the override. A failed call or missing parameters retries on a later Sleep; log transitions only. Injected Reflex (`reflex_inject.cpp`) is outside it: it runs only without native Reflex markers, never reaches `Hook_Sleep` and is not bypassed. Measured in Gears (FG 2× at 120, GPU-paced): the in-Present sleep disappears (no async marker call above 0.1 ms), Reflex reports keep arriving on every frame, display jumps and jitter reach the driver's Sleep, PC Latency stays below it. CONTROL is not measured yet.
- Render handoff limit (`render_handoff.*`, `HandoffLimitApplies`): the render-thread offset (w + d) applies to frames **not held** only. On held frames it moved CONTROL's simulation into its render thread's command submission and regressed pacing; the queue in front of the render thread absorbs simulation variance for held frames. Stalls turn it off only before the render thread is seen taking a frame ahead of the next release, and only two in a row (`RenderHandoffStalled`); that evidence is checked at every planned frame, limited or not, so a block can lift while the limit is off. Never make a block depend on evidence only the limit itself produces: a game that runs ahead would keep it off for the session.
- Render handoff GPU floor (`LeadController::GpuFloor`, `OnGpuRenderEnd`, `OnReportPair`, `HandoffFloorQpc`): a frame not held, released at SIMULATION_START while the Sleep is bypassed, is released no earlier than Ĝ(n−1) − (P/2 + F + σ). P is the median GPU period of consecutive frames the GPU did not wait for (≤ 1 ms idle), F the median first submission − RENDERSUBMIT_START of streaming pairs, σ the median release → RENDERSUBMIT_START of `source_only` frames; all from 32 samples. Ĝ is the later of the newest Reflex report's GPU end and the render thread's newest live PRESENT_END plus the Q5 of the reports' PRESENT_END → GPU end gap, each extrapolated by P; keep the live bound, since reports arrive about two frames after the GPU end and a stretched GPU frame otherwise cascades into the next four. Keep it deterministic and measured: do not reintroduce a term learned from held-back frames; it finds the edge by hitting it, and the first held-back frame of each run stutters. Keep the floor itself anchored to the newest GPU end rather than a free-running cadence at P, which follows a GPU change only through reports two frames old (the GPU-paced rhythm below smooths held releases inside a band the floor bounds; it does not replace the floor). Keep the stream proof: without it a game that submits a whole frame at the end of its window would read held back on every GPU-bound frame. Held frames get no floor unless `gpu_paced_cadence` is on. `OnReportPair` feeds F and the stream proof only.
- GPU-paced cadence (developer A/B `gpu_paced_cadence`, `GpuPacedHeldFloorApplies`, `SourceStage::GpuPacedRhythm`, `SourceStageRequest::gpu_floor_qpc`, `CadenceGridPlanInput::earliest_target_qpc`): one cadence takes the later of the cap and the GPU for every frame. Held frames get the GPU floor (no `w + d`) on a rhythm: after a consecutive frame it paced, release = previous release + mean of the newest 5 GPU periods (`RecentGpuPeriodUs`); the floor when that is not earlier (late starts idle the GPU: stretched 7–15% against 2–10%), else pulled 0.25 toward the floor, never earlier than floor − P/2 (early starts cost little: 4–8%). Keep it bounded by the floor on both sides and continued only from frames it paced: a free or symmetric phase tracker drifted 3–18 ms from the GPU at fast load changes in replays. With the switch, Ĝ also takes the readiness anchor (lead_controller.h): the newest frame's anchor (`ReadyAnchorQpc`: its GPU readiness, or for a queued GPU wait the later of readiness and release) + the median anchor → GPU end gap + P per frame, replacing the older report's extrapolation (reports are about four frames old at the release); it is an estimate, not a bound. Record the gap from every frame, never only from frames not held: the GPU waits report every queued wait as held, whether or not the GPU reached it first, so that filter left the window empty and the anchor never engaged in Gears. A frame whose GPU floor is later than the moment the game reached ReLimiter (its marker, or its Reflex Sleep entry for that grid index, `SourceStageRequest::sleep_entry_*`, before any wait in the hook) and whose earliest release is not later than the floor is on time by construction: the grid never judges its lateness, at its source or at its output (`LeadController::GpuFloorReleased` → `CadenceGrid::ObserveOutput` `gpu_paced`). Pass the raw floor as `gpu_floor_qpc` for that test, never the rhythm's release (a release earlier than the floor would otherwise turn frames arriving between them into SourceLate restarts, the v13 cascade). Its T ≥ its release + `LeadController::EarlyLeadUs`, the `1 − q` quantile of the measured readiness (release → GPU ready on the GPU waits, never the hold-corrected sample) of the newest 128 frames the floor released (per output class and FG divisor; the bucket's early side until 32), and the grid follows a later T without an epoch. That early side lags a change from cap-held to GPU-limited frames (readiness 5–6 ms later after the release); judging such frames' outputs (the FG late-frame spacing moving the Signal past T + tol) restarted the cadence 13–47 times per 45 s capture and paused the holds. Each piece answers a capture where the GPU was the limit (Gears, FG 2× at 120): judging lateness while T had not moved, an early side from the bucket or from hold-corrected samples, and treating a pre-Sleep frame whose marker lands just after the floor as late each led to SourceLate restarts with a 6–10 ms GPU hold; releasing every frame at its floor copied GPU noise into the simulation-start interval that DLSS-G places real frames by. With `marker_forward_order=before_wait` the driver timestamps SIMULATION_START at the marker's arrival, before ReLimiter's trim to the release (0.45 ms earlier at the median, sd 0.38), so the smooth release reaches DLSS-G only partly. With the restarts and the driver's in-Present sleep gone (`bypass_low_latency_off`), `after_wait` puts the driver's SIMULATION_START on the release (+0.01 ms) and in one Gears session cut the misplaced real frames with a start-interval deviation above 1 ms from 40% to 11% (driver's Sleep 9%) and display jumps from 30.2 to 18.5 per 1,000 (driver 16.3). An earlier ABAB of the order showed no difference because OutputLate restarts dominated it. Never rebuild it as a restart rule: a restart at floor + E with S of the next frame still T + I − L cascaded (median one frame apart). Never move the grid to the GPU on frames the GPU finishes early: they keep the cap's T and are held, so the cap holds. The Present-end gate (a release no earlier than PRESENT_END(n−1)) was tried and removed: GPU period 17.2 → 18.4 ms and every pacing metric worse.
- GPU-paced hold margin (developer A/B `gpu_paced_hold_margin`, `PacingHoldMargin`, `GpuPacedHoldIntervalUs`, `s_gpu_paced_hold_us`, `LeadController::GpuNeedQuantileUs`, `NoteReadyAnchor`/`RecordGpuNeed`): on VRR, for frames `GpuPacedHeldFloorApplies` accepts, the grid interval is the later of the cap's interval and the Q75 or Q90 of the newest 128 GPU needs D, slewed like the Adaptive cap's realized interval (+3% up, −1% down per frame); the cap interval is the lower bound and every frame that does not apply, a cold window (32) or a reset clears the state back to the cap. D = readiness of frame n − the readiness anchor of frame n − 1 (the later of readiness and Signal for a held frame): it excludes ReLimiter's own holds and must keep doing so, because a period that includes them feeds the interval back into itself and lowers the frame rate without bound. `period_change` stays keyed to the cap (`period_identity_us`), so the margin is a silent rebase. It is an A/B for a frame-rate-for-smoothness trade (a replay estimated −2 to −6% frame rate for about 0.3–1 ms of hold); never enable it by default without the user's decision.
- GPU-paced release smoothing (developer A/B `gpu_paced_release_smoothing`, `GPU_PACED_SMOOTHING_GAIN`, `GpuPacedRhythmRelease::rhythm_qpc`, `SourceStageRequest::gpu_paced_rhythm_qpc`, `SourceStage::SmoothingPeriodUs`): a second stage after the GPU-paced rhythm. Release = previous actual release + mean of the newest 64 rhythm release intervals, pulled 0.25 toward the rhythm's release, never later than it and never earlier than floor − P (cold below 32). The rhythm continues from the release it would have made (the later of its release and the actual one), never from the smoothed release, so with the switch off nothing changes; its intervals fill the window either way. Why: in Gears 68–91% of display jumps sat within four frames after the game's own GPU starvations, and the rhythm followed each later floor within about three frames, changing the start intervals DLSS-G places real frames by (0.5–0.8 misplaced real frames per starvation against 0.1–0.2 under the driver's Sleep, which keeps its start interval and lets the queue deepen). A replay (releases never later than captured, GPU timeline fixed) put the cost at 0.4–0.6 ms mean, 1.8–3.3 ms p95 extra lead. It rejected a constant extra lead (start intervals unchanged) and slow drains (gains 0.1–0.02, p95 up to 17 ms, no further gain). The bound is a full period, not the rhythm's P/2: live with P/2, a stall longer than P/2 moved the floor past it, and the game, arriving late after its own render-thread hitch, was held about 7 ms more, so the second frame after every big stall started 21–30 ms after the previous one (deviation p50 +3.7 to +5.0 ms; driver +0.04). Live with the full period (ABAB) that frame kept its rhythm (0.7–1.0 ms), but the smoothing was net worse (jumps 21.1 against 17.8 per 1,000, driver 9.7): a render thread released earlier than usual against G(n − 1) after a stall (RENDERSUBMIT_START − G(n − 1) below about −11 ms, normally −9.5) made Gears' render thread run only after the GPU finished frame n − 1 (25–30 ms windows with normal simulation, 6–9× as often as off in two sessions, GPU idle 11–13 ms). Not depth alone: the driver's Sleep starts 24 ms ahead all the time and serializes far less at the same depth; the cause is unknown. Do not deepen the queue after a stall again without knowing what the render thread waits on. Keep it never later than the rhythm: a later release idles the GPU. Keep it inside the floor band (one more frame queued at most): a free phase tracker drifted in replays.
- DLSS-G display order (measured in Gears and CONTROL): the generated frame between real frames n − 1 and n is shown about 0.15 ms after frame n's Reflex GPU end (frame generation included), and real frame n about half an interval later, at a delay the driver sets. Under the Reflex Sleep bypass that delay follows half of frame n's SIMULATION_START interval (r 0.71–0.86), not the GPU gap it lands in, so the source release rhythm is an input to real-frame placement. The real/generated labels come from `PresentFrameGrouper` (present_association.h): the PCL marker lands on the first present of an app frame (the generated one), so the last present of a multi-present group is real. Captures before that fix have the labels swapped under DLSS-G.
- Reflex report ingestion (`TryIngestReflexLatency`): take every unseen report per poll, oldest first. Polls run once per frame, so one report per poll keeps any backlog for good (Gears' reports arrived 250 ms late), and every report-driven loop then acts on stale frames.
- Adaptive cap demand scale (`PeriodGovernor`, cause `release_failed`): a fall that fails raises a scale on the measured need instead of retrying the same level on a timer. Keep it deterministic: it changes only on a failed fall and on a reset.
- Adaptive cap evidence (`PeriodGovernor::Track`, `previous_missed_`; `LeadStatistics::draining_late_samples`, scheduler `TakeLeadOutputs`): one late frame counts once. A run of consecutive missed frames is one restart for the restart pair, and a late frame less late than the late frame before it (grid index n − 1, sample emitted) is draining and not a late output. In Gears (FG 2×, Adaptive cap 99%) one 25 ms simulation hitch restarted the cadence on frames 3 and 4 after it and left five frames late: two restarts in 30 ms and six late outputs, each evidence alone, raised the interval +21 → +42% in 0.6 s. Replayed on that capture the late-output evidence after the hitch drops from 5–9 to 1–3 counted frames while the sustained stretches after failed falls keep 10–18. Keep the 10% window counting every missed frame: runs of restarts on every frame (26 runs of three or more in 154,000 Gears frames) rise through it within a second. Do not count lateness that is shrinking: it is the interval absorbing one late frame.
- Lateness ReLimiter accepts on purpose is not Adaptive cap evidence (`LeadGuardOutcome::reduction_us` for the collision guard, `cap_reduction_us` for the GPU wait cap; `EmitSample` judges the slack against L plus both). The GPU wait cap is median X + cap, so the share it lets run late does not fall with a longer interval; in Rogue Core (130, fit 75) X grows with the interval (8.75 → 10.2 ms from a 10 to a 12 ms interval), the cap bound 86% of leads, lateness against the capped lead rose 2.2 → 6.0% with the interval (0.7–0.8% against the uncapped lead at every interval), and the Adaptive cap sat at +45–60%, its demand scale climbing 1.20 → 1.89 over seven failed falls. The hold room keeps judging against the lead the wait ran with (`guarded_slack_us`): a frame late against it is the overload's, not the hold's.
- Adaptive cap hold room (`LeadController::HoldRoomUs`, `GovernorFrame::room_us`; developer A/B `adaptive_cap_hold_room`, default on, gated in `UpdatePeriodGovernor`): R = X − (Q10(D) − H) = A + H + (D − Q10(D)), the interval at which the GPU queue wait can hold a frame and still release it H before the next frame's heavy GPU work. It is not what frames need: when the GPU is the limit it forces H of idle GPU per frame. Rogue Core 130 (fit 75, H 1.5 ms): GPU active 7.5 ms, GPU frame time 8.0 ms with Adaptive cap off (125 FPS), workload-report need plus margin 7.84 ms (+2%), hold room 9.4 ms (+22%, 106 FPS), 76% of frames held against 0% off, display jitter p99 1.0 ms held at +22% against 0.2–0.3 ms unheld (316 frames only). When the GPU saturates, D includes queueing behind the previous frame (D p75 − p10 3.3 ms instead of 0.4 ms) and the room spiked to +47%. Whether holding is worth the room in GPU-bound scenes needs a same-scene capture with the key off.
- Users do not tune: ship the recommended defaults (`config_version` migration), keep developer keys behind `developer_settings`, and keep user-facing text plain. The FPS cap exists to prevent the latency ReLimiter would otherwise add; never treat it as a latency source or lower it to hide a pacing defect.
- Latency conclusions need Reflex active (FG forces it on). An offline replay that keeps the game's render-thread timing as captured can reject a release rule but never approve one; approval needs a live capture.

## Hooks and external APIs

- Derive the active graphics API from the current presenting device during launcher, game, and swapchain transitions. Never reinterpret DX9, Vulkan, or OpenGL native handles as DXGI swapchains.
- Use typed MinHook trampolines, idempotent installation, and complete failure cleanup. Preserve each hook's established original-call ordering; some marker hooks intentionally call forward first.
- Keep SEH narrowly around unstable driver, game, COM/vtable, Streamline, NGX, or opaque-ABI access. Do not use a broad `__try` block to hide failures in ordinary project logic.
- Preserve late-load handling and data-only load filtering in loader hooks.
- Keep DLSS, FG, Streamline/PCL, NGX, Reflex, and other 64-bit-only integrations behind existing architecture boundaries. Shared code must continue to compile against Win32 stubs without referencing excluded symbols.

## Concurrency and lifecycle

- Every worker needs an explicit owner, start condition, stop signal, wakeup path, join point, and final-drain behavior where applicable.
- Never stop ETW or join workers while under loader lock. Keep process-detach handling loader-lock safe.
- Preserve normal shutdown ordering: stop native PCL before removing hooks, then shut down telemetry and logging according to their existing ownership.
- Use relaxed atomics only for independent snapshots. Use acquire/release ordering when publishing related data or transferring ring-buffer ownership.
- Keep telemetry producers nonblocking. Fixed SPSC buffers intentionally drop rows rather than stall render or ETW threads when full.

## Cross-surface changes

- A configuration field is not complete until its struct default, INI load, validation/clamping, save behavior, runtime application, OSD control, user documentation, and architecture guards agree.
- A telemetry field is not complete until row structures, CSV headers, formatting, producers, analysis consumers, and documentation agree.
- Preserve established CSV column order, especially the native-PCL prefix; append diagnostics unless a deliberate schema migration is requested.
- Keep high-frequency logging sparse. Log initialization, state transitions, feature decisions, and failures rather than every frame.

## Verification

- Use standalone tests for pure logic, but do not treat them as proof of production integration.
- Scheduler, hook, swapchain, loader, driver, ETW, and frame-generation changes require runtime verification on every affected API/path.
- Compare telemetry captures when changing pacing behavior and record units, filters, target FPS, refresh mode, API, and FG state used in the comparison.
