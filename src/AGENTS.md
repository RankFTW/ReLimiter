# AGENTS: ReLimiter production source

This file adds production-code rules under `src/`. Follow the root `AGENTS.md` as the shared baseline.

## Runtime and timing invariants

- Treat Present callbacks, marker hooks, scheduler enforcement, presentation-gate execution, fine sleep/spin paths, ETW callbacks, and CSV producer calls as latency-sensitive hot paths.
- Do not add routine blocking, heap allocation, file I/O, synchronous flushing, or contended mutex acquisition to a hot path. Move non-critical work to an existing worker or a clearly owned new worker.
- QPC is the timing authority. TSC-based timing is an acceleration hint and must retain calibration, fallback, and drift protection.
- Do not simplify or retune scheduler formulas, constants, state transitions, feedback, or call ordering without reading the surrounding rationale and producing capture-backed before/after evidence.
- Check all affected modes: VRR and fixed refresh, foreground and background, marker and Present fallback, and applicable FG/DMFG states.

## Pacing design constraints (user decisions, binding until the user changes them)

Rationale and evidence: the local work-item records (root `AGENTS.md`, Repository boundaries).

- Mechanisms must be general across games and systems. Do not tune a hold, release or fallback around a threshold or operating point found in one capture (a GPU load level, a budget value); a result that improves only at one point means a part of the problem is missing.
- Previously settled pacing must survive architectural changes: compare against the regression capture set in `.agents/skills/pacing-capture-analysis/references/capture-protocol.md` before and after any change to release timing, holds or the Reflex Sleep path. A change that trades long frames or cadence restarts for a few ms of latency is rejected by default; the user prefers smooth pacing and accepts about 4 ms of latency for it.
- No native Present hold as a pacing mechanism (it measured much worse frame-time jitter). Everything must work with hardware-accelerated GPU scheduling (HAGS) on.
- GPU wait releases are timed against the next frame's heavy GPU work (or its Present call) with a fixed distance, never gated on GPU load or hold length; the collision guard stands aside only by the queue-order check, not by scaling a number.
- Prefer deterministic mechanisms over retries and backoff. Late-frame catch-up keeps the render queue (keep), it does not restart after a late frame.
- Cadence grid source lateness (`CadenceGrid::PlanNext` step 3): judge a source against S = T − min(L(n), L(n − 1)), the S its wait aimed at. ReLimiter switching the lead (another output rung's or FG divisor's lead, a restarted lead) is not the game being late: judged against the new lead, the first frame after the FG input wait engaged restarted the cadence and moved T 4.4–10.5 ms later (CONTROL Resonant FG 2× at 130, lead 17.15 → 21.65 ms), a long displayed interval at every such switch. Within a rung the lead moves at most one slew step per frame, so the rule only acts at those switches.
- One pacer: the Reflex Sleep bypass is not a setting. The game's NvAPI Sleep returns without the driver whenever ReLimiter paces a positive cap (`Scheduler_PacesSource`, `NvAPI_ShouldBypassSleep`, `PacingPipeline_SleepBypass()`, true exactly while the effective `pacing_test_mode` is off); only pass-through frames (Dynamic MFG, uncapped, no presenting swapchain) and the test modes use the driver's Sleep.
- Driver pacing inside `NvAPI_D3D12_SetAsyncFrameMarker`: under the Reflex Sleep bypass with DLSS-G the NVIDIA driver still paces, by sleeping the thread that calls the game's Present inside this call (Streamline's `sl.dlss_g`, through `sl.common`; the long calls are PRESENT_END, type 5). `Hook_SetAsyncFrameMarker` is pass-through timing only (telemetry `async_marker_wait_us`); never suppress, delay or alter that marker or its result. In Gears it sleeps when the game's PRESENT_START of frame n comes before about frame n − 1's Reflex GPU end (a heavy GPU frame n − 1, a fast render thread), and the slept real frame is misplaced far more often (9–21% against 1–2%). Do not chase it with a later release: the render thread absorbs most of the shift (PRESENT_START moves 0.22–0.34 ms per ms of release), so it would starve the GPU long before it removed the sleeps.
- In-band frame id and the FG route's cross-thread hand-off (`StreamlineHandoff_RecordInbandFrame`, `marker_slot` (a `CrossThreadRing`, `cross_thread_slot.h`) and `StreamlineInputScope` in `streamline_gpu_handoff.cpp`): after the original call has returned, `Hook_SetAsyncFrameMarker` also states each known marker's frame id to the route; never before the call, and never altering, suppressing or delaying the marker or its result. A proxy Present on a thread without a marker of its own (Gears sends PRESENT_START on the render thread and presents on another) is pending and claims a marker only by identity: the marker whose frame id equals the id an async PRESENT_START (type 4) or out-of-band PRESENT_START (type 11) states on that thread, inside that outermost scope. No id, no claim: `inband_frame_unknown` when no marker of that id is in the ring, `inband_frame_late` when the Present's first fence call came before any id, `inband_frame_absent` when it ended without one; each is recorded in `present_admission` once and rejects a tracked binding like a Present without a marker. "The newest marker" is never a claim: while a scene loads the Present runs behind the next frame's marker. The ring keeps 8 markers keyed by frame id, a rejected marker is a tombstone that withdraws no older one, and a same-thread marker is claimed by sequence exactly as before (Phantom Blade Zero is untouched). A Present with `DXGI_PRESENT_TEST` presents nothing, so its scope is inert: it masks the calls inside it as any scope does, but takes neither marker (the thread's own or the probe's), claims nothing, records no admission and rejects no binding (counted as `test_presents`). 007 First Light asks one between a frame's PRESENT_START and that frame's Present on the same thread; when the test Present took the thread's marker, every Present after it was markerless, the frame id its in-band PRESENT_START named had been consumed (every claim `unknown`, two Present-stage records per frame, one Present per frame reaching the native swap chain without FG) and the route never qualified. The route does not consult `NativeGate_CrossThreadVerified()`: the ETW flag stays the native gate's and the telemetry's check, and the GPU queue probe keeps its own latest-wins slot. Counters (relaxed atomics, formatted by the installer worker only): `Streamline GPU: in-band frame claims=… unknown=… late=… absent=… match=… mismatch=… test_presents=…` in the 5 s admission report and `inband=claims/unknown/late/absent/match/mismatch` at the end of the `qualified` line, which is where a healthy session shows them; match and mismatch compare the later in-band ids of a Present that claimed a marker with the claimed frame and change nothing. A pending Present's first fence call reaches the handoff whether or not a binding is tracked (`StreamlineHandoff_Interested`): `StreamlineHandoff_BeforeFence`, or `StreamlineHandoff_RejectQueueMethods` on a queue whose methods the hooks do not match, resolves the Present as `inband_frame_late` before the call is classified, so an id that comes after that call claims nothing and the marker it names stays in the ring.
- Flip metering block (developer `flip_metering_off`, `InstallFlipMeteringBlock`, `Hook_QueryInterface` in `nvapi_hooks.cpp`): returns nullptr from `nvapi_QueryInterface` for `NvAPI_D3D12_SetFlipConfig` (ID 0xF3148C42), as Special K, OptiScaler and RenoDX Commander do, so DLSS Frame Generation runs as on a GPU without hardware flip metering. It reproduces that state on a Blackwell test machine; never default it on. It is installed during init, not with the deferred hooks, because frame generation resolves the function itself and a pointer resolved before the hook stays usable; interception ends with the addon's teardown (`DisableAllHooks`). The first hidden request logs its caller module; without that line the block did not reach frame generation. With metering, a capture shows `flip_delay_qpc` on every row and the real frame's display − `etw_ready_qpc` near its flip delay; without it, both are 0 and every frame is shown as soon as it is ready.
- SetFlipConfig observer (`Hook_SetFlipConfig` in `nvapi_hooks.cpp`, with the deferred NvAPI hooks): an inline pass-through hook on the function itself, so it also sees callers that resolved it earlier. It never alters the call, the configuration or the result; it logs the first configuration and each change of the batch size, presented frames, status and feedback (never per batch; at most 16 lines). It resolves the function through the block's trampoline whenever the block's hook exists, enabled or not (a reload can re-enable a retained hook): its own request must never reach the block, which would log it as the first hidden request. Under the block, frame generation that asks for the function afterwards never gets it; a line then comes from a caller that resolved it before the block. A user capture without flip delay where frame generation still issues each group's Presents within a few ms (the metered path) means metering was asked for and not applied; this line says whether the call was rejected, metering was off at the caller, or the driver reported `no_iflip` or `mirroring_detected`.
- Separate presenter (`fg_route_unsupported`; `SeparatePresenter`, `RecordSeparatePresent`, `RejectRoute`, `TagSeparate`, `PublishSeparatePresenter`, `Authorize`, `Cycle::separate`, `Route::separate` in `streamline_gpu_handoff.cpp`; `PacingCapability::FgSeparatePresenter`): without hardware flip metering DLSS-G presents each group from its own thread and queue after the worker's return Signal, overlapping the next cycle (Valor Mortis with `flip_metering_off`: every Present on one other thread and never on the worker's queue, 38% begun inside the worker interval; Phantom Blade Zero the same). The worker-local Present contract never holds there. Positive evidence only turns `worker_signal_before_present` into `worker_present_on_other_queue`: a native Present of the bound swapchain outside any source scope, on another thread and a known other queue, recorded with the failing cycle's token (a stale Present can only miss a cycle; `present_queue_not_worker` also counts, an unknown queue does not), or present-first ordering established on the route's source queue (`FgPresentOrder_Orders`, which is false while the key `fg_present_order` is off), which does not depend on a Present falling into a cycle's span. Keep qualification running under that reason (`FgRouteQualificationPending`); clear it on a cycle completed with a worker-local Present, such a Present, a new route identity, an FG multiplier change or FG stopping, never on time. With the developer A/B switch `fg_separate_presenter_hold` on (default on), a cycle without a worker-local Present stands while ordering holds the source queue (`WorkerSignalRejection`), which keeps the binding tracked, and the binding is first authorized (`Authorize`) only once the fence chain is proven too (`ChainProven(route.source)`: the presenter's queue is neither the source queue nor the worker's and waits on a fence the worker's queue signals, never at a value below the worker's newest Signal by as much as the generated frames a real one: at 3x and 4x the presenter waits for a frame's later generations after the worker has signalled them all). An authorized binding is not ended by a proof that lapses: the hold is admitted only while the proof holds at that moment (`StreamlineHandoff_IsCurrent` reads `ChainProven` for a separate binding) and resumes when the chain is proven again. Without the chain another queue loses the queue-order proof that its Presents depend on the held work, and if the presenter's queue were the game's source queue the hold would stall the previous frame's Present; without the ordering the generated frame's Present runs behind the next frame's work whatever the hold does. Do not replace either by timing, counts of Presents or module identity. A binding is of one kind: a worker-local Present in a separate binding, or the reverse, rejects it (`cycle_presenter_changed`). `CheckDevices` accepts a compute queue for the worker of a separate binding only. The switch is on by default together with the breaks (Render breaks), because the hold alone made the display less even there: it evens the batch starts (Present call interval SD 1.8 to 0.7 ms) and leaves the render queue without gaps, so the real frame's Present waits longer behind it (0.4 to 1.5 ms at the median), and the breaks give that Present room; and the breaks and the trailing release without the hold made a cap worse than the ordering alone. Only a cycle without a worker-local Present reads the key (`WorkerSignalRejection`), and the key counts only while the ordering holds the source queue (`FgPresentOrder_ProvesSeparatePresenter`), so with hardware flip metering (the worker presents) and without frame generation it does nothing; with it off the cap applies at the source (`fg_route_unsupported`) and the state line in `PublishSeparatePresenter` says so. Measured together with the trailing release and the breaks (final build, 2×, flip metering hidden, two runs an arm; the ordering alone against the three together): Phantom Blade Zero at a cap of 104, 1% low 65.3 to 69.5 fps and hitches 33 to 19 a minute, PC Latency 46.0 to 46.9 → 51.7 to 52.2 ms (+5 to +6; +4.7 to +5.2 over NVIDIA's limiter) with 88% of frames held; at a cap of 60, 1% low 41.0 to 46.3 fps, hitches 8 to 5, PC Latency 56.5 → 66.4 ms (+9.9: the frames are held 6.6 to 8.2 ms at the median, because the lead covers the slowest 1% of frames and the game's own frame times spread by about 7.5 ms); at no cap the hold holds 0.1% of frames; Gears of War at a cap of 90, 57.2 to 60.8 fps and 22 to 12, PC Latency 52.3 → 54.9 ms (+2.7; +2.3 over NVIDIA's limiter) with 79 to 89% held. The breaks and the trailing release without the hold (Phantom Blade Zero at 104, a fourth launch): 1% low 64.7 to 63.3 fps, hitches 37 to 48 a minute and displayed frame-to-frame change 1.69 to 1.96 ms against the ordering alone, where the three together gave 71.1 fps, 14 and 1.22 ms; the cause is not established, the three ship together. 3x and 4x: see Frame generation at 3x and 4x. Not measured: another game, a GPU that really lacks the hardware (both games ran with its flip metering hidden). The GPU deadline routes need the display in variable refresh: a session started with the monitor asleep ran with `context_supported=0` and reported `fg_unqualified` throughout.
- Present-first ordering (`fg_present_order.h/.cpp`, rule in `fg_present_order_rule.h`, tested in `tests/test_fg_present_order_rule.cpp`; key `fg_present_order`, default on, live, and the developer A/B switch `fg_present_order_trailing`, default on, live; 64-bit DX12; compiled into the add-on only through `RELIMITER_FG_PRESENT_ORDER`, every other target gets the header's no-op forms): where DLSS-G presents from its own thread, its return Signal releases the game's render queue and the generated frame's Present together, and the render queue's backlog reaches the GPU first (Phantom Blade Zero: the Present 2 ms late as a rule, a frame late in 4 to 8% of frames). Right behind DLSS-G's Wait on the render queue (`FgPresentOrder_AfterWait` in `ObserveWait`, through the original Signal and Wait, in front of the queue probe's release Signal) the unit enqueues a Signal of its own marker fence and, once the rule says so, a Wait on its own order fence; the selected swapchain's outermost Present that presented (`PresentBody`, `Present1Body` in `vsync_control.cpp`, result `S_OK`, no `DXGI_PRESENT_TEST`; never a nested entry, another swapchain or a failed call) signals the order fence from the CPU when it was made by another thread than DLSS-G's worker, a watchdog at a deadline a share of the frame time after its own wake for the marker (an eighth, 0.5 to 2 ms, `FgPresentOrderRule::BoundUs`; counted from that wake, not from the GPU's completion of the marker). Keep these properties: the queue never waits without evidence, judged in blocks of sixteen markers by one measure (at most two left to the watchdog start the waiting, more than eight stop the unit for 240 frames, from a probe or while ordering; with hardware flip metering the worker presents before its return Signal and nothing ever waits); an order Wait is enqueued only while the watchdog runs and the marker's event exists (`ReadyLocked`), and a watchdog that ended is replaced at the next bind; a release whose CPU Signal failed advances nothing and is tried again (`ReleaseOrder`); the worker thread is the one that signals the followed Wait's fence and its Presents release nothing; the fences are the unit's own and are let go, after every enqueued wait was released, at the queue's destruction, at shutdown, and by `FgPresentOrder_Service` (the installer's worker, every pass of `StreamlineHandoff_Service`) when the key is turned off, frame generation stops presenting or its multiplier changes (not instantly: the worker waits up to about 250 ms between passes, so an established binding can outlive frame generation by about that long, and the trailing release and the breaks still act on it meanwhile); nothing is bound while the key is off, the runtime stops or frame generation does not present (`BindLocked`, checked under the exclusive lock, so a bind cannot follow the shutdown's drop), and a queue whose fences could not be created is not tried again until it is destroyed or frame generation starts again; no log line and no blocking call under `lock`, `release_lock` or `window_lock` (order: `lock`, then `release_lock` or `window_lock`); the unit starts again after `FgPresentOrder_Shutdown`, which `StopOwnedProducers` also calls at start-up lifecycle changes. `g_fg_present_order_queue` names the queue that is made to wait and, with the key on, is the handoff's second proof for a separate presenter (`FgPresentOrder_Orders`). With `fg_present_order_trailing` on (default on; published as `g_fg_present_order_trailing`, 64-bit; rule `FgPresentOrderTrailingRule` in `fg_present_order_rule.h`, tested in the same test file) the unit observes whether DLSS-G's presenting thread submits work right after that Present: that thread's first outermost `ExecuteCommandLists` after the Present is the anchor (`FgPresentOrder_AfterExecute`, in the Execute detour directly behind the native call; a bare Signal of the thread is none, so a presenter that only signals after its Present would qualify and pay for nothing), and the Present is followed when its anchor came before the deadline the watchdog applies to that marker (its wake for the marker plus the bound), on a queue of the render queue's device that is not the render queue. After a block of sixteen Presents of which at least fourteen were followed, all on one queue, the release is deferred (off, and while observing, it is made when the generated frame's native Present has returned): behind the anchor, on its queue, the unit enqueues a Signal of its own fence `trailed` with the marker's value, and the render queue is released when that has completed on the GPU (the unit's thread, woken by the fence's event, signals the order fence from the CPU), or by the watchdog at its unchanged deadline. A deferred release left to the watchdog is missing (no anchor before the deadline) or late (the anchor came and the Signal behind it had not completed): the third in a block of sixteen sends the unit back to releasing at the return and observing, and three late ones, or the third such return in a row with no clean block of sixteen deferred releases in between, stop deferring until the binding, the presenting queue or the key changes; the ordering rule's own transitions do not clear that (a queue whose work waits for the render queue, or a presenter whose submission comes in time only while the render queue runs, shows only while deferring, and observing it again would enter again for good). Keep: `trailed` is written by Signals of one queue only, with rising values, each taken and enqueued as one step and a new queue only once everything signalled has completed; the order fence only from the CPU under the release lock; no Present releases anything while a release is deferred, but one that returns meanwhile is still told to the breaks (nothing is deferred at 3x and 4x: see Frame generation at 3x and 4x). Key off: nothing is made at the bind and the gate behind an outermost Execute (`FgPresentOrder_AfterExecute`) pays one relaxed load and a branch (two loads where the unit orders, its queue being tested first). Key on (default): the bind also makes the `trailed` fence (once per binding, on the game's thread inside the proxy Present) and, the first time, its event; that gate pays one relaxed load and a branch while the unit does not order (it tests `g_fg_present_order_queue` first) and, while it orders, a call, a thread id read and a compare until a Present's release awaits an anchor (`FgPresentOrder_AfterExecuteActive` returns at its first test); and the unit's own thread publishes a deadline at each marker wake and takes its locks at its deadline instead of trying them. Defaults: the trailing release, the breaks (Render breaks) and the hold (Separate presenter) are on by default and act only once this unit has established the ordering (`g_fg_present_order_queue`): with hardware flip metering the worker presents and the ordering never establishes (every marker goes to the watchdog, nothing waits), so the three never enqueue a break, a hold or an ordering Wait; but the unit still binds and probes there (a marker in 16 of every 256 frames), and that costs: each of the two Execute gates (`FgPresentOrder_BeforeExecute` in front of an outermost Execute, `FgPresentOrder_AfterExecute` behind it; both test `g_fg_present_order_queue` first) one relaxed load and a branch, so two loads and two branches per Execute in all, not one; at each bind the `trailed` fence and, the first time, its event, on the game's thread inside the proxy Present; for each probe marker `BreakFrameStart` on that thread (the break settings read, `window_lock`, the frame's and its windows' records, `window_live`); and on the unit's own thread, for each, the deadline publication, the trailing planning and the blocking lock acquisition at the deadline. Without frame generation, or without Streamline's proxy Present, nothing binds (`FgPresentOrder_Service`) and nothing is paid beyond the two gate loads (the Signal and Wait detours' load of `fg_present_order` is older). Why: in Phantom Blade Zero (packet traces) the presenting thread submits one more packet and queues two Signals 36 to 56 µs after the Present returns in 97% of frames; the packet lands behind the render queue's batch that the release has just let go and sits 2.2 ms on the hardware (in one launch until the render queue runs dry in 26% of frames), and the real frame's Present queues behind it. Measured (final build, 2×, flip metering hidden, two runs an arm; the game alone against the ordering alone, no cap): Phantom Blade Zero 116.3 to 118.0 fps, 1% low 48.2 to 69.7, hitches 325 to 79 a minute, displayed frame-to-frame change 3.43 to 2.05 ms; Gears of War 98.0 to 94.0 fps, 36.9 to 63.3, 185 to 18, 2.64 to 1.14 ms. In Gears the ordering is established 0.3 s after frame generation presents, the trailing release defers, none is left to the watchdog for want of a submission and one to two markers per 10 s go to it. What the trailing release, the breaks and the hold add to the ordering: see Render breaks and Separate presenter. 3x and 4x: see Frame generation at 3x and 4x. Not measured: another game, a GPU that really lacks the hardware, the cost on the Present thread.
- Render breaks (developer live keys `fg_render_break_every`, 1 = on (default), 0 = off, 2–64 = every n-th submission of a window, for comparison, and `fg_render_break_window`, −1 (default) = placed by the rule, 0 = every n-th submission of the whole frame, 1–32 = that half-width; rule in `fg_break_window_rule.h`, tested in `tests/test_fg_break_window_rule.cpp`; `breaker`, `BreakFrame`, `BreakFrameStart`, `BreakFrameReleased`, `BreakLaterPresentShared` and `FgPresentOrder_BeforeExecuteActive` in `fg_present_order.cpp`). What the real frame's Present waits for (packet traces): the GPU is handed the render queue's work up to twelve submissions ahead; a presenter's packet that arrives meanwhile is served neither at the next boundary between render packets nor when that queue blocks, but after a delay of the GPU's own (1 to 2 ms at the median) amid the committed work, although DLSS-G's queue has the higher priority. Where the render queue has nothing on the hardware it is served at once (0.14 ms). A break makes such a moment: in front of a submission of the ordered render queue (in `ObserveExecute`, behind the queue probe's entry, so the break's time is never read as the submission before it) the unit enqueues a Signal of its own fence and a Wait for that value. The Wait is unsatisfied when enqueued, so the hardware gets nothing past it until the GPU is there, and the Signal then releases it; no thread, no watchdog. A break costs about 50 µs of frame time, so they go only where frame generation's later Presents arrive. A frame is the work submitted behind one ordering marker; its first Present releases the marker and every later Present of another thread than the worker until the next release is one of its other outputs (2x: the real frame's; 3x and 4x: more generated frames first), each with a window of submissions of its own and one instance of the rule (`FgBreakOutputs`: the number two frames in a row agree on, up to five). The rule: the centre follows the GPU (when that Present has returned, the breaks the GPU has reached say at which submission it was: `FgBreakWindowRule::Locate` over the frame's recorded breaks, so a skipped break or a frame that ended early does not shift the reading; inside the window one submission towards it, outside half the half-width); the half-width follows the spread (of every 128 such Presents, 24 or more outside widen it by one, 8 or fewer narrow it); the windows of a frame together never exceed what one break per 1.85 ms of frame time pays for, shared evenly (the 2.7% of frame rate the owner accepted; `frame_us` is the smoothed interval of the ordering's markers); and a window at the budget that more than half of a block's Presents miss gets no breaks for 512 frames and is then placed again. The breaks are never thinned: for the same number, a dense narrow window does more than a wide one with gaps (replay). A frame's keys and windows are fixed when its marker is enqueued (`BreakFrameStart`) and everything about a frame, its submission count included, is read and written under `window_lock`. Invariants: one submitter at a time enqueues a pair (values must rise in queue order, or a Wait would stand above the fence's value for good); the Wait is enqueued only after its Signal succeeded; `window_lock` is held for loads and stores only and never around `lock`. A queue Wait is decided when it is enqueued (a Wait on a fence already at its value is gone at once, even behind an unsatisfied Wait), so a gate held from the CPU cannot stop work the GPU is about to take. A break is enqueued only on the ordered queue (`FgPresentOrder_BeforeExecute`: `g_fg_present_order_queue` the submitting queue, tested first, then the key above 0 and `fg_present_order` on), so with hardware flip metering and without frame generation no break is enqueued; that gate, in front of an outermost Execute, costs one relaxed load and a branch there (the trailing release's gate behind it costs another, see Present-first ordering), and where frame generation runs with hardware flip metering the unit's probes (16 markers in every 256 frames) also run `BreakFrameStart` for each probe marker on the game's thread inside the proxy Present (the settings read, `window_lock`, the frame's and its windows' records, `window_live`). Measured with one window (an earlier build, Phantom Blade Zero, no cap, half-width 4, which is what the rule gives there): display jitter 2.20 to 1.51 ms, hitches 88 to 49 a minute, 1% low 64.0 to 65.8, for 2.7% frame rate and 0.6 ms latency; half-width 6: 1.42 ms for 3.7%; every 4th submission of the whole frame: 1.78 for 3.5%; every submission: 1.42 for 13.7%. At a cap of 104 breaks alone do not help; with `fg_separate_presenter_hold`: 1.82 to 1.17 ms, 1% low 61.0 to 66.1, for 4.9 ms latency (3.7 of it the hold's), which the owner accepted. They are on by default together with the trailing release and the hold, which only the three together were measured with (final build, 2×, flip metering hidden, two runs an arm; the ordering alone against the three together): Phantom Blade Zero at no cap 118.0 to 115.5 fps, 1% low 69.7 to 70.0, hitches 79 to 48 a minute, displayed frame-to-frame change 2.05 to 1.47 ms (the trailing release and the breaks without the hold: 115.5 fps, 69.2, 60, 1.48 ms), at a cap of 104 103.9 to 103.7 fps, 65.3 to 69.5, 33 to 19, 1.76 to 1.19 ms, the Present calls' change 1.33 to 0.44 ms, PC Latency +5 to +6 ms with 88% of frames held; Gears of War at no cap 94.0 to 93.7 fps, 63.3 to 62.0, 18 to 17, 1.14 to 1.16 ms, at a cap of 90 89.56 to 89.19 fps, 57.2 to 60.8, 22 to 12, 1.49 to 0.89 ms, the Present calls' change 1.10 to 0.50 ms, +2.7 ms with 79 to 89% held, and about 90% of the later Presents found the GPU inside their window. In a fourth launch at a cap of 104 the trailing release and the breaks without the hold were worse than the ordering alone (1% low 64.7 to 63.3 fps, hitches 37 to 48 a minute; see Separate presenter). A wait of the render queue for the real frame's Present (`fg_real_yield`) was tried before the breaks and removed: the same jitter for more frame rate and latency. 3x and 4x (several windows a frame): see Frame generation at 3x and 4x. Not measured: the cost on the submitting thread, another game, a GPU that really lacks the flip metering hardware. The breaks are not shown to the queue probe.

Three fences, ONE writer each (the gate's and `fg_present_order`'s convention: a fence written by a queue and by the CPU can be set back and strand a Wait): `issued` by P right after the native Present of a frame the plan ordered and the gate committed a Wait for returned S_OK, `reached` by R in front of the order Wait, `order` from the CPU by the release thread when `issued` reached the value (the Present is runnable), at once when the hold's target has come while R has not reached that value's Wait or has none yet (`GpuHoldOrderBook::Late`, counted as `late`: a frame that is late for its slot has no hold left to protect and does not pay the Present's service time; a value R already stands at waits for `issued`), or at the deadline, the watchdog (the later of the hold's target and the moment `reached` got there, plus a quarter of the interval, 1 to 4 ms; it does not run while R has not reached the Wait, so a frame that is late on the GPU is no watchdog case; a release while the gate has not released the hold is the gate's delay and no trip, see the rule). Boundary check (why the Wait cannot make the queue wait for itself): the Present's dependencies are the outermost Waits of P its thread made in front of the gate's own, on fences one other queue signals (a Present with none, with fences of more than one queue, or with more Waits than the thread remembers has no dependency and is not ordered); its edge is judged at R's next outermost `ExecuteCommandLists`, before that Execute is counted and before the probe's `ExecuteEnter`, and the Wait is enqueued there only when, for EVERY Wait of P for that Present on a fence R signals, R has signalled the fence with a value at least the one P waited for, and no Execute on R followed the latest of those first such Signals (one per Wait); otherwise nothing is enqueued and the cause is counted. A game that signals one fence after every submission (Rogue Core: 13 Signals a frame, values rising) has a later Signal with nothing behind it in mid-frame, so counting from the newest Signal was a defect, found before the first build. The Signals of each fence the Present waits for are kept in a short history (`GpuHoldOrderHistory`, 32 records, its oldest never counts as the first because an older Signal may have satisfied the Wait earlier; `GpuHoldOrderEvidence` takes the latest over the Waits; both in the rule header, tested), and a Signal's record takes R's Execute count from before the native Signal (`GpuHoldOrder_BeforeSignal` gives the mark, `GpuHoldOrder_AfterSignal(queue, fence, value, mark)` records it), so an Execute another thread counts while the Signal is being enqueued is behind it. Once the Wait is on the queue the Executes R's other threads counted since the judgement are looked at: the Wait stays and is released like any other, but a frame one of them passed in front of is counted as raced and not as qualified. Rule (`GpuHoldOrderRule`): Probe, 16 held frames that all qualified → Ordering (`Able()`, what the scheduler reads, with a binding, a running release thread, no frame generation presenting and the GPU queue wait rung: the unit is able); a frame that does not qualify → Probe; a trip is a watchdog release of a Wait whose hold the gate had released (the Present did not become runnable within the bound although the hold was over and R stood at the Wait): it counts in every state but Off (a Wait enqueued in Ordering and released after the rule fell to Probe counts too) and leads to Probe, or stays there; the third trip → Off until a new binding, the key toggled or a restart, unless clean running forgave the trips. A watchdog release while the gate's own release of the hold is not recorded is no trip: the runtime can hold the gate worker's own CPU Signal of its time fence for tens of milliseconds (Phantom Blade Zero at a game hitch: 30 ms), so the Present could not run whatever R did and the order is not what stalled; the Wait is let go at the bound (R must not stand at it past it), counted (`gate_late`, a part of the watchdog releases) and said, and the rule is told nothing (no trip, no fall to Probe); a value with no side data cannot be shown to be the gate's delay and stays a trip. Trips are forgiven by clean running (`GpuHoldOrderRule::OnReleased`, `kForgive` = 256): each ordered frame's Wait that its Present released (not a late release, not the watchdog's; counted in Probe too and across a fall to Probe) counts, and 256 in a row with no trip between set the trips back to 0, because a cycle the boundary check cannot see recurs with the frames (every entry into Ordering stalls at once, with no ordered frame released by its Present in between, so its trips follow within a few blocks of 16 frames) and a hitch does not; three trips with fewer than 256 such releases after each of them turn the rule Off, a long session of ordinary hitches does not; Off stays Off. ## Hooks and external APIs

- Derive the active graphics API from the current presenting device during launcher, game, and swapchain transitions. Never reinterpret DX9, Vulkan, or OpenGL native handles as DXGI swapchains.
- Use typed MinHook trampolines, idempotent installation, and complete failure cleanup. Preserve each hook's established original-call ordering; some marker hooks intentionally call forward first.
- Install hooks in batches, one per site (`HookBatch` in `hooks.h`; every MinHook enable freezes the process, and two engines' freezes can deadlock each other, so a site makes one freeze, not one per hook). A batch is lazy: constructing or destroying one takes no lock and calls nothing, the first install inside it takes `HookInstallGuard`, and the lock is held from that first create to the apply (`Apply` and `Hooks_FlushBatch` release it), so an idle batch never blocks another installer and no site lengthens a lock the present thread waits on; a site whose own code creates hooks (`FocusLock_Install`, `NGXHooks_TryInstall`) holds its own `HookInstallGuard` around that code. Inside a batch `InstallHook`, `InstallHookPublished` and `Hooks_EnableOrQueue` create, publish the trampoline and `MH_QueueEnableHook`, and their `MH_OK` means queued, never enabled. The sites: `Init` (`DoInit`: the flip-metering block and `NGXHooks_Init`, one batch around both), `FirstPresent` (the first present event: the four LoadLibrary hooks and the NvAPI hooks), `LoaderScan` (one scan of the loader-install worker, closed before its 250 ms wait, so discovery, factory probing and drains never run under the install lock for the batch; `NGXHooks_TryInstall` outside the worker opens its own), `FocusLock` (`FocusLock_Install`: `MH_CreateHook` x4, then `Hooks_EnableOrQueue`) and `DxgiFallback` (the DXGI `Present` / `Present1` pair, only when the vtable route is absent). Anything that logs a hook as installed, begins a producer epoch or sets a state flag reads `Hooks_TargetEnabled` AFTER the apply (`NvAPIHooks_ReportInstalled`, `ReportFlipMeteringBlock` and `LoadLibraryHooks_ReportInstalled` run after the batch; the installers call them themselves outside a batch). A group that cannot continue without the enable result (the Streamline hooks, the proxy and queue hooks, the FG input and queue hooks, the NGX transaction, which retains or rolls back on it) calls `Hooks_FlushBatch()` once after its installs: the same apply with the batch still open. `MH_ApplyQueued` is not a transaction: it stops at its first failure with the earlier hooks enabled, so a failed apply enables every hook still queued one by one with `MH_EnableHook`, logs each failure once at warning and leaves the failing hook created and not queued (nothing stays queued, so a later apply never enables it behind its owner's back). Nested batches on one thread are no-ops that queue into the outer one; an empty batch calls MinHook not at all; a refused admission (shutdown) makes installs fail with `MH_ERROR_DISABLED` as before. A retained load's records stay: installing the same target again queues it, and `EnableAllHooks` (`MH_EnableHook(MH_ALL_HOOKS)`) enables the queue too, settles every record to enabled and, when it stops at a failing hook, enables the rest one by one. Never call `MH_EnableHook` per hook inside a batch scope, and never hold a batch across a wait. Every call that freezes (the apply and the one-by-one enables, a single enable or disable, enable-all, the teardown disable) goes through hooks.cpp, never a raw `MH_EnableHook` / `MH_DisableHook` / `MH_ApplyQueued` elsewhere (`Hooks_DisableHook` for a hook's own disable): those run on the hook installer thread (`Hooks_StartInstallerThread` from `DoInit`, key `hook_installer_thread`, default true, a compatibility switch read once; `Hooks_StopInstallerThread` inside `DisableHooksForShutdown`, after the last freezing call). It is created with a security descriptor that denies `THREAD_SUSPEND_RESUME | THREAD_GET_CONTEXT | THREAD_SET_CONTEXT` to Everyone in front of the token's default DACL, so another engine's `OpenThread` for it is refused and the two freezes cannot wait for each other; at its start it opens itself for a suspend, which must fail (a debug privilege bypasses the descriptor), else it is `Unprotected` and every call runs on the requester. Only raw MinHook calls run on it: no ReLimiter lock, no log, no allocation; the requester keeps the install lock, takes the single job slot's lock, posts and waits with no timeout for the job event or the thread handle. `HookInlineOnlyScope` is the explicit way for code in DllMain or a loader callback (none today) to keep a call inline; so are the kill switch, a thread that is not `Ready` yet, and a stopped thread. If the thread ends before it took the job, the requester runs the job; if it ends with a job in flight MinHook is unusable for the rest of the process (`Hooks_MinHookUnusable`: admission closed, every later freezing call `MH_ERROR_DISABLED`, nothing replayed or terminated), and so is every other MinHook call of the product: none is made outside hooks.cpp (`Hooks_Initialize`, `Hooks_CreateHook`, `Hooks_RemoveHook` and the internal queue calls all return `MH_ERROR_DISABLED` without touching MinHook, whose lock the dead thread may hold), and a caller treats that status as "leave the record retained, do not retry". The batch stages record whether the installer ran the apply and whether it is protected in the high bits of the crumb's site byte (`kBreadcrumbInstaller*`). `Hooks_ForgetTarget` after `MH_RemoveHook` of a `Hooks_EnableOrQueue` target.
- Keep SEH narrowly around unstable driver, game, COM/vtable, Streamline, NGX, or opaque-ABI access. Do not use a broad `__try` block to hide failures in ordinary project logic.
- Preserve late-load handling and data-only load filtering in loader hooks.
- Keep DLSS, FG, Streamline/PCL, NGX, Reflex, and other 64-bit-only integrations behind existing architecture boundaries. Shared code must continue to compile against Win32 stubs without referencing excluded symbols.
- Native Present entry (`vtable_copy.h/.cpp` pure rules, `vsync_control.cpp` install and detours): the route's entry is a private copy of the native swapchain object's vtable, not the inline patch. The copy is VERBATIM: the entries from index -1 (the RTTI locator) as far as they are readable, at most 512, never judged and never zero-filled (entries past the vtable's real end are whatever follows it in memory and are never called); every read first queries the region (`VirtualQuery`) and stops at anything that is not committed, readable memory without PAGE_GUARD, so a guard page is never touched (the SEH stays for races); it must cover the whole IDXGISwapChain4 interface (slots 0 to 40) or nothing is installed (logged). Before the copy is published every module that supplies a callable entry of slots 0 to 40 is pinned (`GetModuleHandleEx` FROM_ADDRESS with PIN); ANY of those slots pointing outside every loaded module is code whose lifetime cannot be held (a hook's private thunk its owner frees), so no vtable entry is installed (inline patch only, logged with the slot index). A copy goes only over a vptr inside a loaded module's image (a class vtable, whose module is pinned as well), never over a vptr in private memory. The copy names the detours in slots 8 and 22 and the object's vptr points at it. Each copy has an immutable record (the class vtable it replaced and the slot values read at copy time, shared by identical vtable images) and one detour pair, so a detour's record is its template index; a record is never retargeted. The detours call the class vtable's slot 8 / 22 as it is at each call (`vtable_copy::Forward` via `ForwardOf`: one guarded load and a compare against the records' detours), not the value read at copy time: another module's hook written into the class vtable in place is called while it is there and no longer once that module takes it out, exactly as for an object without our copy. REFramework hooks the class slot until its first Present, then takes it out and puts its own vtable on the object, saving our detour as its original; a copy-time value kept calling its retracted hook from below its own vtable on every frame, its depth guard returned `S_OK` without presenting, and the game showed a black screen (Resident Evil Requiem). A slot that names one of our detours, or a failed read, falls back to the copy-time value. Another module replacing the vptr AFTER our copy is left alone (`VSync_ObserveNativeVptr`: one load and one compare on an ordinary frame; counted, logged once, shown in the `NativeGate vtable route:` line): never a second copy over a foreign vtable (its hook can save our entry and a later copy would chain into a cycle), no vptr write against it, no timers, no retries. A process-global, never-freed `VptrHistory` (16) keeps the vptrs we replaced and the foreign vptrs seen over our copy, each foreign one with the class vtable our copy had replaced (`ClassOf`): a vptr in the foreign history is left alone on every later selection of ANY object (destroy and init of the same native object do not forget it; this is what stops a resize from re-layering over a foreign chain); a full history refuses a new vptr (logged). Install at the swap manager's selection of the object (`VSync_OnNativeSelected`), restore on its destroy event only if the vptr still equals our copy (`VSync_OnNativeDestroyed`), at teardown restore what is still ours before the hooks are disabled; copies, records and detours are never freed (the module is retained). The inline patch on DXGI's `Present` / `Present1` is NOT installed where the vtable entry carries the route (every MinHook enable freezes the process, and two engines' freezes can deadlock each other; the overlay can also erase the bytes for good): `VSync_InstallDXGIHooksImpl` installs it, in one hook batch, only when the copy was refused (all bindings taken, a foreign vptr, an unsupported object). It goes only on the implementation's own functions (`vtable_copy::NativeTarget` via `ResolveNativeTargets`): code in the module of the object's class vtable (the one its copy replaced; for a foreign vtable seen over our copy the one in the history, also after a resize dropped the binding), the earliest record's slot first, then the live slot; never another module's hook in those slots and never one of our detours; when none is known nothing is patched (`VSync: the Present slot of swapchain … names …`, one warning per slot). While the copy carries the route, `VSync_NoteFinishedPresent` (ReShade's finish_present of the selected native swapchain) counts consecutive completed scopes in which no vtable entry ran (`vtable_copy::FallbackCounter`, 32, reset by any scope with an entry, any thread). The evidence is the selected object's alone: `s_selected_vtable_entries` counts only entries whose body ran for the swap manager's selected object (another object's entries never count or reset the run; the all-entries counter is diagnostics), and the run's baseline is snapshotted whenever it is reset. The fallback's selected identity (object + generation, `PublishFallbackIdentity`) is published on every actual selection, also when an existing binding keeps its copy (no install, no adoption), and by a present event that made the selected object's copy; a selection of an object without a copy clears it, and `VSync_NoteFinishedPresent` ignores the finish of any swapchain that is not both the identity and the swap manager's selected one, so an unselected swapchain can neither count nor consume the one-shot. The counter keeps fired flag, generation and count in ONE atomic word: the scope that reaches 32 and the commit of the one-shot are one compare-exchange valid only for the generation it counted for, so a destroy or reselect in between refuses the commit without consuming the one-shot and the new generation starts its own run. The 32nd scope installs the pair ONCE through a `HookBatch` (`DxgiFallback`), logged at warning level with the count, and it is never removed or repeated (no timers). The typed install's enable is queued inside a batch and `FinalizeTypedEnables` settles `HookTarget::enabled` after the apply, never before. 'Not installed because the vtable entry carries the route' is a normal state in the diagnostics. Where the pair exists, nothing re-installs it when another module erases it, and teardown never disables it (`DisableAllHooksExcept` leaves the two DXGI targets enabled and passing through, since a prologue check cannot be made atomic with MinHook's write-back against another module's concurrent patch); `PrologueHoldsOurJump` is for diagnostics only. One native call has one body: both entries run through `PresentEntry` / `Present1Entry`, the outermost entry for an object on the thread (a thread-local list of `DedupNode`s on the detours' own stacks, any depth, no allocation; `PresentOutermost` / `Present1Outermost` unlink in a SEH `__finally`, so a structured exception caught by a caller never leaves the list pointing at a dead frame, and they hold no C++ object with a destructor, which a SEH unwind would not run) runs the VSync override, timeline, gate, readiness, probe, brackets and telemetry, and an inner entry for the same object passes straight to its original with the arguments the outer entry chose; a Present on another swapchain, or a recursion from inside the original for another object, is not suppressed. The vtable lock serializes install, destroy, reconcile and teardown and is never taken by the detours. Bindings (8) are never evicted: a published binding is kept until its object's destroy callback or teardown (a guess that its copy is gone races another module's unhook, and a later foreign replacement would look like an unseen vtable); when all are taken a new object is refused (logged once, inline-only); a binding dropped over a foreign vptr remembers that vptr first. One judge (`ReconcileLocked`) serves a selection and a present event for every address, with one binding per object address (never a second claim): a vptr that is one of OUR copies is adopted, never copied again (`IndexOfCopy` before any first-install path; an unbound object showing a copy takes the record's identity); the vptr our copy replaced is installed again on the SAME binding (an overlay's unhook, or a new object at an address whose destroy never came; at most 8 per lifetime, a selection resets it); any other vptr over a binding that had a copy is another module's: remembered, left alone. The installed copy's identity (`copy_vptr`, the vptr it replaced) stays on the binding through refused reinstalls until destroy or teardown, so a later restore, adoption or foreign note still finds it. This cannot layer copies: every install reads a vptr that is neither one of our copies (adoption catches those) nor a remembered foreign one (the history refuses them), so a copy is only ever made over a class vtable. Stopping is checked under the vtable lock in both entry points, serialised against the teardown's restoration. Teardown closes installer admission (`Hooks_BeginShutdown`) before collecting the DXGI targets to leave enabled, so a typed hook installed during shutdown is not missed.
- Per-call cost on the game's threads (base cost with Reflex alone; keep these shapes): hotkeys are NOT polled on a game thread: `hotkey_poller.h/.cpp` is polled by the blackout service thread (`Hotkeys_Poll` every `kHotkeyPollPeriodMs` = 8 ms from a high-resolution waitable timer; the thread's window and OLED work keeps its 16 ms cadence on every second wake) with the pure edge detector `hotkey_edge.h` (`Step` = the old `PollHotkey`, its key reads lazy); `DrawOSDImpl` (every frame the overlay event fires, visible or not, so hotkeys work with the overlay hidden and the game focused) only publishes the parsed bindings (`ParseKeybind` runs when a binding STRING changes, `PublishHotkeyBinding`), reports capture suppression (`Hotkeys_SetSuppressed`, latched so a window shorter than a poll still suppresses) and applies the latched triggers (`Hotkeys_Take`) on the thread that owns `g_config` under the config owner lock; a changed binding, a capture and suppression each require seeing the key released before it fires; a press is seen at most 8 ms (plus about 1 ms timer granularity) after it starts and applied by the callback's next run, a press shorter than the period can be missed, two presses before the callback runs are one trigger. A trigger carries the transition generation its poll started under (`s_generation`, advanced by a capture beginning or ending, a rearm, a binding change) and `Hotkeys_Take` rejects one from an older generation, so a poll in flight across a capture cannot apply a press made during it. If the service thread cannot be created, `Blackout_Init` logs one warning and the OSD callback polls per frame on the presenting thread (`Hotkeys_PollFallback`, which does nothing while `Hotkeys_SetServiceThreadPolling(true)` holds, so the two never both poll). Never put `GetAsyncKeyState` back on a game thread otherwise (it blocks in `NtUserGetAsyncKeyState`).
- Module presence (`module_presence.h/.cpp`): the per-frame hooks never ask the loader (`GetModuleHandleW` / `GetModuleHandleExW`) whether `nvpresent64.dll` (`IsNvSmoothMotionActive`), a frame generation runtime (`IsFGDllLoaded`: `nvngx_dlssg.dll`, `_nvngx_dlssg.dll`, `sl.dlss_g.dll`, `dlss-g.dll`) or `RTSSHooks64.dll` (the RTSS caller check of `Hook_SetLatencyMarker`) is loaded. `ModulePresence_Scan` publishes them as atomics: first thing in every pass of the loader-install worker (`loadlib_hooks.cpp` `InstallWorker`: a LoadLibrary* notification starts a pass, else the 250 ms timeout) and once on first use. Staleness bound: a hooked LoadLibrary load is seen at the worker's next pass (one event wake plus the pass in progress), every other load and every unload at most one 250 ms timeout later (a module that unloads reads as present for at most that long); the readers are relaxed/acquire loads. The RTSS check is a range test of the return address against the module's published image range (packed in one word; an unknown size asks the loader as before), so there is no per-address cache to invalidate when another module unloads and another loads into the same range. Win32 never has these modules (the header's inline stubs).
- Identity checks that run per Present and per marker take no COM call to learn that nothing changed: `PublishSwapchain` (`correlator.cpp`) returns at once when the incoming swapchain is the published one (the destination owns a reference, so the address cannot have been reused); `ResolveIncomingDevice` (`nvapi_hooks.cpp`, one look per hook call) answers "is this the presenting device / the published feedback device" for the game's own pointer from values: the pointer equals the publication's native or its alias (`s_feedback_alias`, the ReShade proxy named in the native's private data, captured with the publication; never dereferenced) under an unchanged transition sequence, and the canonical native is compared with `SwapMgr_PresentingDeviceIdentity()`; any other pointer (a foreign wrapper) is unwrapped once per call. `FeedbackIsPresenting` re-checks a token without an incoming pointer. Do not cache an answer on a borrowed pointer alone.
- ReShade's device lock (a launch hang, fixed once; keep it fixed). ReShade runs the `init_device` and `destroy_device` events and add-on unload while it holds one process-wide, non-recursive mutex (`g_d3d12_adapter_mutex`, `deps/reshade/source/d3d12/d3d12_device.cpp`), and every `AddRef`/`Release` of a ReShade device proxy, and `QueryInterface` for the proxy's own interfaces or `IUnknown`, takes the same mutex; `IID_UnwrappedObject` and unknown IIDs do not. So ReLimiter never calls `AddRef`, `Release` or `QueryInterface` (other than `IID_UnwrappedObject`) on a device pointer that a game or plugin passed in: it unwraps it once (`DeviceIdentity_AcquireNative`, `feedback_device_identity.h`), owns and compares NATIVE devices only (the canonical `IUnknown` identity of the native object: the feedback publication `s_feedback_native`, the presenting device of `swapchain_manager.cpp`), and keeps the incoming pointer as an alias that is only compared by value. Four identity namespaces are never mixed: the raw native handle (`get_native()`), the canonical identity (`QueryInterface(IUnknown)` on a native object), the incoming pointer, and the publication sequence. `E_NOINTERFACE` from the unwrap query does not prove an object native: a wrapper that swallows it is terminal and is never captured unless its canonical identity is the presenting device's. Callback rule: `on_init_device`, `on_destroy_device`, `SwapMgr_OnInitDevice/OnDestroyDevice` and `NvAPI_OnDeviceDestroyed` make no call on a device proxy (they compare stored values, or values derived from `get_native()` by calls on the native object) and return for an unrelated device before the selection lock, which a Present holds for a whole frame (`DeviceInitMayChangeSelection`, `ClassifyDestroyedDevice` in `swapchain_selection_policy.h`). Add-on unload can run under the same lock at game exit (destroy_device, then unload_addons): `AddonUninit` and `RollbackInitialization` call nothing on an object ReShade can hook, so the read-back buffer of `gpu_readiness_d3d12_queue.cpp` is released while mapped, never `Unmap`ped. Tests: `test_feedback_device_identity` (a fake process-wide lock; proxies in strict mode fail on any AddRef/Release/own-interface query) and ctest `feedback_device_lock_fixture` (the fixture fails at once instead of hanging).
- The Streamline `SetOptions`, `GetState` and compat `SetOptions` detours keep their `RuntimeLifecycle_EnterCallback`/`LeaveCallback` bracket in a thin `__try`/`__finally` wrapper around an out-of-line body and leave the block by falling through: a `return` from inside a `__try`/`__finally` runs `_local_unwind` -> `RtlUnwind` on every call. ## Concurrency and lifecycle

- Every worker needs an explicit owner, start condition, stop signal, wakeup path, join point, and final-drain behavior where applicable.
- Never stop ETW or join workers while under loader lock. Keep process-detach handling loader-lock safe.
- Preserve normal shutdown ordering: stop native PCL before removing hooks, then shut down telemetry and logging according to their existing ownership.
- ReShade unloads every add-on when the game releases its last device and loads them again with its next device, in the same process. `AddonUninit` must leave the add-on unregistered: ReShade refuses a second registration of a module it still lists. ReShade's header helpers keep the add-on and ReShade module handles in function-local statics that their first call fixes, so `AddonInit` seeds both before anything can log (the logger forwards warnings and errors through `reshade::log::message`); call no `reshade::` helper ahead of that. `test_addon_reload` (ctest `addon_reload`) runs the cycle on the built add-on in a fake host.
- Start-up evidence (`startup_breadcrumb.h/.cpp`, `Log_Init`): `Breadcrumb_Mark` and `Breadcrumb_PresentCompleted` are plain stores into a mapped page, with no lock, allocation, flush or log, because hook batches call them around `MH_ApplyQueued` while the process is frozen; keep them that way and keep every failure (open, map, read-only folder, a second live launch holding the file) a silent no-op. The record is a seqlock; one writer at a time, a contending mark is dropped. Every stage but the two batch stages is first-wins, `Running` (the 32nd present after the first-present block) is followed only by `Closed`. `Log_Init` moves the previous log to `relimiter_<exe>.prev.log` (a failure is not an error), attaches `relimiter_<exe>.crumb` in the log's folder and, after releasing the logger locks, logs one warning at warning level when the previous launch's record is valid and before `Running` and not `Closed`. A new stage needs the enum, `StageName`, the docs and a mark at its site; never rename a stage or reorder the record (the file layout is versioned).
- Stall report (`hang_report.h/.cpp`, `hang_report_policy.h/.cpp`, `hang_progress.h`, `lock_owner_diag.h`, `log_level_state.h`; keys `hang_report` (default off), `hang_report_dump` (default true; false = text report only, dbghelp never loaded) and developer `hang_report_test_after_s`; the last two are in `Config_DeveloperOverrides`/`Config_ResetDeveloperSettings`): a watchdog thread created with the installer thread's descriptor (`Hooks_BuildProtectedThreadSecurity`; the thread checks on itself that opening it for suspend is actually refused, because the debug privilege bypasses the descriptor, and the report says "built" and "effective" separately) wakes once a second, keeps the process CPU time of the last interval (`GetProcessTimes`), evaluates the pure policy (armed after a completed present event, or 60 s after the first swapchain init; report at 20 s without a completed present event, again at 90 s, progress re-arms, at most three per process) and writes `relimiter_<exe>.hang.txt` then `.hang.dmp` next to the log (the temporary folder with one warning when the names next to the log would exceed MAX_PATH). The text step uses only static buffers, `WriteFile`, `OpenThread`/`SuspendThread`/`GetThreadContext`/`ResumeThread` (a thread is resumed before anything else touches it), `ReadProcessMemory`, the Nt calls resolved at start (kernel thread states are parsed from `SystemProcessInformation` by its record layout, bounds-checked, with the pid and first ClientId validated) and a few user32 window queries that send nothing: no heap, CRT stream, logger, loader call or ReLimiter lock until the file is closed, because the process may be stuck holding any of them. Keep it so. The dump step is entered only when the text file was created, written, flushed and closed; the log lines and `HangReportResult` state the per-file outcome. The producers are plain relaxed stores (`g_hang_progress` at the present events, the native Present entry, the Reflex Sleep and latency marker hooks; `LockOwnerDiag` for the selection lock and the hook install lock; the trail kinds in the crumb ring, `TrailKind`); nothing is added to a queue detour but one relaxed load and a not-taken branch per call (`Breadcrumb_TrailFirst`). `HangReport_Start` begins a logger floor (`Log_BeginLevelFloor`, at least info) that the watchdog ends 120 s after it started; `Log_SetLevel` stores the requested level whatever the floor says (`LogLevelState`: request and floor in one atomic word, `Log_Write`'s rejected path is still one load), so a level requested during the window is never overwritten. A new trail kind needs the enum, `Breadcrumb_TrailKindName`, the report's decoder in `PutTrailEntry` and a mark at its site. Off means inert: `hang_report_state.h` holds one process-lifetime flag (`HangReport_Active`), set once in `DoInit` right after `LoadConfig` and before any hook or callback can run a mark (the key is launch-only); `HangReport_Start` returns false and starts nothing when the key is off (no thread, no log-level floor); every progress counter, trail append (`Breadcrumb_Trail`, `Breadcrumb_TrailFirst`, the trail part of `Breadcrumb_Mark`), lock-owner note (`LockOwnerDiag`) and every clock read that feeds them (`NowQpc` in `hooks.cpp` and `swapchain_manager.cpp`, the present, native Present, Sleep and latency-marker sites) starts with one relaxed load of that flag and a branch that is not taken. New report marks on a hot path take the same gate; the one-record start-up breadcrumb (stage at offset 0) does not depend on it.
- Use relaxed atomics only for independent snapshots. Use acquire/release ordering when publishing related data or transferring ring-buffer ownership.
- The callback guard (`runtime_lifecycle.h/.cpp`) counts admissions per thread: each thread claims a cache-line slot of a fixed table (128) at its first guarded call, a locked update on that slot is the whole cost of the guard (no shared line, no allocation, no loader call, no lock), the thread's exit releases the slot (a `thread_local` destructor; the slot keeps its word, the next owner continues from it) and threads beyond the table share one overflow slot (a locked update, the old shared counter's behaviour). The handshake is the Dekker pair of the single counter: the guard adds to its slot, then reads `s_stopping` (both sequentially consistent); shutdown stores `s_stopping` (sequentially consistent) before it reads any slot. `RuntimeLifecycle_WaitForCallbacks` and `RuntimeLifecycle_Initialize` read the slots as a double collect (`inside == 0` on the first read of every slot and an unchanged word on the second, `enters` only grows) and so see "no callback admitted" exactly when the single counter would have been zero at some instant of the call. A guard remembers its slot and leaves that one wherever it is destroyed; the `RuntimeLifecycle_EnterCallback`/`LeaveCallback` bracket leaves the calling thread's slot, so it must enter and leave on one thread. `s_stopping` is alone on a cache line nobody writes in steady state (Initialize, BeginShutdown and Shutdown only); keep every hot or frequently written variable off it. A new thread-hot guard path must not add a shared writable line. `test_runtime_lifecycle` runs the production unit.
- Keep telemetry producers nonblocking. Fixed SPSC buffers intentionally drop rows rather than stall render or ETW threads when full.

## Cross-surface changes

- A configuration field is not complete until its struct default, INI load, validation/clamping, save behavior, runtime application, OSD control, user documentation, and architecture guards agree.
- A telemetry field is not complete until row structures, CSV headers, formatting, producers, analysis consumers, and documentation agree.
- The OSD's Jitter line and Frame Pacing block read one worker snapshot (`PacingTelemetrySnapshot`, `pacing_telemetry.h`). Its window takes one sample source at a time, in the order ETW, DXGI frame statistics (no frame generation), the flip gate's flips (`PacingTelemetry_PushFlip` from `GateClock`: one lock-free push per flip on the gate's own clock thread and one relaxed store per gated Present's return on DLSS-G's presenting thread, `gate_presented`, so a flip let go for a Present that did not present is left out; nothing on a thread of the game, nothing where the gate does not run), and the real frames at the FG input (`pacing_sample_sources.h`, from the gate and ready records the worker drains anyway; fed only while, in the last 500 ms, the driver accepted a `NvAPI_D3D12_SetFlipConfig` of two or more frames a batch with no obstacle in its feedback: `g_flip_metering_accepted_qpc`, one relaxed store per such call in the hook; a game without frame generation sends a batch of ONE in every frame with status 0, which is not metering). A change of source empties the window, the in-process samples leave it as soon as ETW flows or DXGI is active again, and the snapshot names the source the window holds (`window_source`), never the one that was fresh last. Jitter is the window's MEAN change between adjacent intervals and hitches are intervals over 1.5 times the window's median; do not bring back a score built on the 99th percentile (it read 64 to 79% for the best pacing measured and moved between 36 and 81 from window to window, while the mean is 0.15 to 0.26 ms for good pacing against 1.2 to 1.7 ms for bad). A sample that does not directly follow the one before it (a flip the gate did not time, a frame without a readiness, another binding) is a gap in the chain and never an interval; real frames follow each other only by consecutive frame IDs, and a frame whose release may have been overwritten is left out. The worker takes a cycle's readiness records off their queue BEFORE it drains the gate queue and adds them after it: a frame is emitted at the next frame's readiness and its release, pushed before that by the same thread, must be in by then. Do not feed the FG input source where frame generation presents by itself without the gate: per 5 s the real frames follow the displayed ones under hardware flip metering (r 0.88 to 0.99, reading about 0.1 ms lower in calm scenes) but not there (0.1 to 0.7 ms where the displayed frames changed by 1.4 to 1.6 ms), so that route reads `not timed` and needs ETW. The samples of the two in-process sources are not CSV rows: a snapshot event whose `snapshot_display_source` is 3 or 4 cannot be recomputed from the rows, and the analyzer skips it (`in_process_source`).
- Telemetry runs on demand only (`g_pacing_telemetry_demand`, `pacing_telemetry.h`): a CSV capture or a shown pacing readout (the OSD's Jitter/Frame Pacing, or the settings panel's open **Details**; `PacingTelemetry_SetOsdReadout`) makes it active, and the native route's cross-thread evidence keeps only the Present spans it needs. With no consumer the worker, the DXGI frame-statistics polls, the snapshot summaries and the CSV writer wake for nothing, and producers skip records that only telemetry reads (`PacingTelemetry_Active()` / `PacingTelemetry_NeedsPresent()`: one relaxed load at the push site). A new reader must publish demand; a new producer of telemetry-only records must check it. Nothing the pacer reads may depend on that demand.
- No ReLimiter thread wakes on a fixed period without work to do: workers wait on their inputs (events, `WaitOnAddress`) and keep a timeout only for an obligation that needs it (a ready GPU queue's heartbeat, pending readiness rows, probe calibration recovery), stated in the code. Driver calls (display, DRS, hardware sensors) run on change or on demand, never as a periodic re-assert.
- G-Sync means the game's frames are refreshed variably, not that the display can do it (N.172, measured with vblank waits). The deciding answer is the driver's per-game `bFsVrr` from `NvAPI_D3D_GetSleepStatus`, the flag Reflex and DLSS Frame Generation pace by. It counts only while `bFullscreenIFlip` is 1, and only for the published feedback device while it presents and while its publication is unchanged across the query. It comes from the game's own calls through `Hook_GetSleepStatus` (another device's answer neither decides nor stops ReLimiter's read), or from ReLimiter's read in the Reflex Sleep at most once a second when the game did not ask within that second. Once known it decides both ways and survives swapchain changes. The display worker (`display_worker.cpp`, one event, wakes only when the answer changes) applies it, because the change can stop the vblank worker. Until then each swapchain resolve decides from `NvAPI_Disp_GetVRRInfo` `bIsVRREnabled || bIsDisplayInVRRMode` (the first poll sets the mode even when inactive, warns then, and sets the first launch's cap). `bIsVRRPossible` is only a capability: a launch whose display slept at its start reads `possible=1 displayInVRR=1` while its frames are scanned out at a fixed rate, and only `enabled` and `bFsVrr` say so, and neither of them at the resolve. Each change of the per-game answer logs one default-level line with the display's flags beside it. `PollGSyncState`, the worker and the resolver's teardown (`DisplayState_RetireDisplay`) serialize on one lock. The mode decides more than the cadence: Fixed mode makes the native context unsupported (`NativeGate_GetContext`), which under frame generation leaves the queue law without frames (N.170, finding 1033).
- Preserve established CSV column order, especially the native-PCL prefix; append diagnostics unless a deliberate schema migration is requested. A column leaves the header only when no producer writes it any more, and the capture-analysis tools keep the older header as a historical profile.
- Keep high-frequency logging sparse. Log initialization, state transitions, feature decisions, and failures rather than every frame.
