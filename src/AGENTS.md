# AGENTS: ReLimiter production source

This file adds production-code rules under `src/`. Follow the root `AGENTS.md` as the shared baseline.

## Runtime and timing invariants

- Treat Present callbacks, marker hooks, scheduler enforcement, presentation-gate execution, fine sleep/spin paths, ETW callbacks, and CSV producer calls as latency-sensitive hot paths.
- Do not add routine blocking, heap allocation, file I/O, synchronous flushing, or contended mutex acquisition to a hot path. Move non-critical work to an existing worker or a clearly owned new worker.
- QPC is the timing authority. TSC-based timing is an acceleration hint and must retain calibration, fallback, and drift protection.
- Do not simplify or retune scheduler formulas, constants, state transitions, feedback, or call ordering without reading the surrounding rationale and producing capture-backed before/after evidence.
- Check all affected modes: VRR and fixed refresh, foreground and background, marker and Present fallback, and applicable FG/DMFG states.

## Pacing design constraints (user decisions, binding until the user changes them)

Rationale and evidence: the local work-item records (root `AGENTS.md`, Repository boundaries).

- Mechanisms must be general across games and systems. Do not tune a hold, release or fallback around a threshold or operating point found in one capture (a GPU load level, a budget value); a result that improves only at one point means a part of the problem is missing.
- Previously settled pacing must survive architectural changes: compare against the regression capture set in `.agents/skills/pacing-capture-analysis/references/capture-protocol.md` before and after any change to release timing, holds or the Reflex Sleep path. A change that trades long frames or cadence restarts for a few ms of latency is rejected by default; the user prefers smooth pacing and accepts about 4 ms of latency for it.
- No native Present hold as a pacing mechanism (it measured much worse frame-time jitter). Everything must work with hardware-accelerated GPU scheduling (HAGS) on.
- GPU wait releases are timed against the next frame's heavy GPU work (or its Present call) with a fixed distance, never gated on GPU load or hold length; the collision guard stands aside only by the queue-order check, not by scaling a number.
- Prefer deterministic mechanisms over retries and backoff. Late-frame catch-up keeps the render queue (keep), it does not restart after a late frame.
- Cadence grid source lateness (`CadenceGrid::PlanNext` step 3): judge a source against S = T − min(L(n), L(n − 1)), the S its wait aimed at. ReLimiter switching the lead (another output rung's or FG divisor's lead, a restarted lead) is not the game being late: judged against the new lead, the first frame after the FG input wait engaged restarted the cadence and moved T 4.4–10.5 ms later (CONTROL Resonant FG 2× at 130, lead 17.15 → 21.65 ms), a long displayed interval at every such switch. Within a rung the lead moves at most one slew step per frame, so the rule only acts at those switches.
- One pacer: the Reflex Sleep bypass is not a setting. The game's NvAPI Sleep returns without the driver whenever ReLimiter paces a positive cap (`Scheduler_PacesSource`, `NvAPI_ShouldBypassSleep`, `PacingPipeline_SleepBypass()`, true exactly while the effective `pacing_test_mode` is off); only pass-through frames (Dynamic MFG, uncapped, no presenting swapchain) and the test modes use the driver's Sleep.
- Driver pacing inside `NvAPI_D3D12_SetAsyncFrameMarker`: under the Reflex Sleep bypass with DLSS-G the NVIDIA driver still paces, by sleeping the thread that calls the game's Present inside this call (Streamline's `sl.dlss_g`, through `sl.common`; the long calls are PRESENT_END, type 5). `Hook_SetAsyncFrameMarker` is pass-through timing only (telemetry `async_marker_wait_us`); never suppress, delay or alter that marker or its result. In Gears it sleeps when the game's PRESENT_START of frame n comes before about frame n − 1's Reflex GPU end (a heavy GPU frame n − 1, a fast render thread), and the slept real frame is misplaced far more often (9–21% against 1–2%). Do not chase it with a later release: the render thread absorbs most of the shift (PRESENT_START moves 0.22–0.34 ms per ms of release), so it would starve the GPU long before it removed the sleeps.
- Flip metering block (developer `flip_metering_off`, `InstallFlipMeteringBlock`, `Hook_QueryInterface` in `nvapi_hooks.cpp`): returns nullptr from `nvapi_QueryInterface` for `NvAPI_D3D12_SetFlipConfig` (ID 0xF3148C42), as Special K, OptiScaler and RenoDX Commander do, so DLSS Frame Generation runs as on a GPU without hardware flip metering. It reproduces that state on a Blackwell test machine; never default it on. It is installed during init, not with the deferred hooks, because frame generation resolves the function itself and a pointer resolved before the hook stays usable; interception ends with the addon's teardown (`DisableAllHooks`). The first hidden request logs its caller module; without that line the block did not reach frame generation. With metering, a capture shows `flip_delay_qpc` on every row and the real frame's display − `etw_ready_qpc` near its flip delay; without it, both are 0 and every frame is shown as soon as it is ready.
- SetFlipConfig observer (`Hook_SetFlipConfig` in `nvapi_hooks.cpp`, with the deferred NvAPI hooks): an inline pass-through hook on the function itself, so it also sees callers that resolved it earlier. It never alters the call, the configuration or the result; it logs the first configuration and each change of the batch size, presented frames, status and feedback (never per batch; at most 16 lines). It resolves the function through the block's trampoline whenever the block's hook exists, enabled or not (a reload can re-enable a retained hook): its own request must never reach the block, which would log it as the first hidden request. Under the block, frame generation that asks for the function afterwards never gets it; a line then comes from a caller that resolved it before the block. A user capture without flip delay where frame generation still issues each group's Presents within a few ms (the metered path) means metering was asked for and not applied; this line says whether the call was rejected, metering was off at the caller, or the driver reported `no_iflip` or `mirroring_detected`.
- Separate presenter (`fg_route_unsupported`; `SeparatePresenter`, `RecordSeparatePresent`, `RejectRoute`, `TagSeparate`, `PublishSeparatePresenter`, `Authorize`, `Cycle::separate`, `Route::separate` in `streamline_gpu_handoff.cpp`; `PacingCapability::FgSeparatePresenter`): without hardware flip metering DLSS-G presents each group from its own thread and queue after the worker's return Signal, overlapping the next cycle (Valor Mortis with `flip_metering_off`: every Present on one other thread and never on the worker's queue, 38% begun inside the worker interval; Phantom Blade Zero the same). The worker-local Present contract never holds there. Positive evidence only turns `worker_signal_before_present` into `worker_present_on_other_queue`: a native Present of the bound swapchain outside any source scope, on another thread and a known other queue, recorded with the failing cycle's token (a stale Present can only miss a cycle; `present_queue_not_worker` also counts, an unknown queue does not), or present-first ordering established on the route's source queue (`FgPresentOrder_Orders`, which is false while the key `fg_present_order` is off), which does not depend on a Present falling into a cycle's span. Keep qualification running under that reason (`FgRouteQualificationPending`); clear it on a cycle completed with a worker-local Present, such a Present, a new route identity, an FG multiplier change or FG stopping, never on time. With the developer A/B switch `fg_separate_presenter_hold` on (default off), a cycle without a worker-local Present stands while ordering holds the source queue (`WorkerSignalRejection`), which keeps the binding tracked, and the binding is first authorized (`Authorize`) only once the fence chain is proven too (`ChainProven(route.source)`: the presenter's queue is neither the source queue nor the worker's and waits on a fence the worker's queue signals, never at a value below the worker's newest Signal). An authorized binding is not ended by a proof that lapses: the hold is admitted only while the proof holds at that moment (`StreamlineHandoff_IsCurrent` reads `ChainProven` for a separate binding) and resumes when the chain is proven again. Without the chain another queue loses the queue-order proof that its Presents depend on the held work, and if the presenter's queue were the game's source queue the hold would stall the previous frame's Present; without the ordering the generated frame's Present runs behind the next frame's work whatever the hold does. Do not replace either by timing, counts of Presents or module identity. A binding is of one kind: a worker-local Present in a separate binding, or the reverse, rejects it (`cycle_presenter_changed`). `CheckDevices` accepts a compute queue for the worker of a separate binding only. The switch is off by default because the hold alone made the display less even there (N.102): it evens the batch starts (Present call interval SD 1.8 to 0.7 ms) and leaves the render queue without gaps, so the real frame's Present waits longer behind it (0.4 to 1.5 ms at the median). The GPU deadline routes need the display in variable refresh: a session started with the monitor asleep ran with `context_supported=0` and reported `fg_unqualified` throughout.
- Present-first ordering (`fg_present_order.h/.cpp`, rule in `fg_present_order_rule.h`, tested in `tests/test_fg_present_order_rule.cpp`; key `fg_present_order`, default on, live; 64-bit DX12; compiled into the add-on only through `RELIMITER_FG_PRESENT_ORDER`, every other target gets the header's no-op forms): where DLSS-G presents from its own thread, its return Signal releases the game's render queue and the generated frame's Present together, and the render queue's backlog reaches the GPU first (Phantom Blade Zero: the Present 2 ms late as a rule, a frame late in 4 to 8% of frames). Right behind DLSS-G's Wait on the render queue (`FgPresentOrder_AfterWait` in `ObserveWait`, through the original Signal and Wait, in front of the queue probe's release Signal) the unit enqueues a Signal of its own marker fence and, once the rule says so, a Wait on its own order fence; the selected swapchain's outermost Present that presented (`PresentBody`, `Present1Body` in `vsync_control.cpp`, result `S_OK`, no `DXGI_PRESENT_TEST`; never a nested entry, another swapchain or a failed call) signals the order fence from the CPU when it was made by another thread than DLSS-G's worker, a watchdog after a share of the frame time (an eighth, 0.5 to 2 ms, `FgPresentOrderRule::BoundUs`). Keep these properties: the queue never waits without evidence, judged in blocks of sixteen markers by one measure (at most two left to the watchdog start the waiting, more than eight stop the unit for 240 frames, from a probe or while ordering; with hardware flip metering the worker presents before its return Signal and nothing ever waits); an order Wait is enqueued only while the watchdog runs and the marker's event exists (`ReadyLocked`), and a watchdog that ended is replaced at the next bind; a release whose CPU Signal failed advances nothing and is tried again (`ReleaseOrder`); the worker thread is the one that signals the followed Wait's fence and its Presents release nothing; the fences are the unit's own and are let go, after every enqueued wait was released, at the queue's destruction, at shutdown, and by `FgPresentOrder_Service` (the installer's worker, every pass of `StreamlineHandoff_Service`) when the key is turned off, frame generation stops presenting or its multiplier changes; nothing is bound while the key is off, the runtime stops or frame generation does not present (`BindLocked`, checked under the exclusive lock, so a bind cannot follow the shutdown's drop), and a queue whose fences could not be created is not tried again until it is destroyed or frame generation starts again; no log line and no blocking call under `lock`, `release_lock` or `window_lock` (order: `lock`, then `release_lock` or `window_lock`); the unit starts again after `FgPresentOrder_Shutdown`, which `StopOwnedProducers` also calls at start-up lifecycle changes. `g_fg_present_order_queue` names the queue that is made to wait and, with the key on, is the handoff's second proof for a separate presenter (`FgPresentOrder_Orders`). Measured with the rule of sixteen in a row and a 2 ms bound (N.100): 1% low 46 to 68, hitches 511 to 85 a minute, display jitter 4.1 to 2.1 ms for 3.7% frame rate under the pacer. Not measured: the block rule and the bound as a share of the frame time (written after the review of N.106, not run in a game), its cost on the Present thread, 3x and 4x, another game.
- Render breaks (developer live keys `fg_render_break_every`, 0 = off (default), 1 = on, and `fg_render_break_window`, −1 (default) = placed by the rule, 0 = every n-th submission of the whole frame, 1–32 = that half-width; rule in `fg_break_window_rule.h`, tested in `tests/test_fg_break_window_rule.cpp`; `breaker`, `BreakFrame`, `BreakFrameStart`, `BreakFrameReleased`, `BreakLaterPresentShared` and `FgPresentOrder_BeforeExecuteActive` in `fg_present_order.cpp`). What the real frame's Present waits for (N.103, packet traces): the GPU is handed the render queue's work up to twelve submissions ahead; a presenter's packet that arrives meanwhile is served neither at the next boundary between render packets nor when that queue blocks, but after a delay of the GPU's own (1 to 2 ms at the median) amid the committed work, although DLSS-G's queue has the higher priority. Where the render queue has nothing on the hardware it is served at once (0.14 ms). A break makes such a moment: in front of a submission of the ordered render queue (in `ObserveExecute`, behind the queue probe's entry, so the break's time is never read as the submission before it) the unit enqueues a Signal of its own fence and a Wait for that value. The Wait is unsatisfied when enqueued, so the hardware gets nothing past it until the GPU is there, and the Signal then releases it; no thread, no watchdog. A break costs about 50 µs of frame time, so they go only where frame generation's later Presents arrive. A frame is the work submitted behind one ordering marker; its first Present releases the marker and every later Present of another thread than the worker until the next release is one of its other outputs (2x: the real frame's; 3x and 4x: more generated frames first), each with a window of submissions of its own and one instance of the rule (`FgBreakOutputs`: the number two frames in a row agree on, up to five). The rule: the centre follows the GPU (when that Present has returned, the breaks the GPU has reached say at which submission it was: `FgBreakWindowRule::Locate` over the frame's recorded breaks, so a skipped break or a frame that ended early does not shift the reading; inside the window one submission towards it, outside half the half-width); the half-width follows the spread (of every 128 such Presents, 24 or more outside widen it by one, 8 or fewer narrow it); the windows of a frame together never exceed what one break per 1.85 ms of frame time pays for, shared evenly (the 2.7% of frame rate the owner accepted; `frame_us` is the smoothed interval of the ordering's markers); and a window at the budget that more than half of a block's Presents miss gets no breaks for 512 frames and is then placed again. The breaks are never thinned: for the same number, a dense narrow window does more than a wide one with gaps (replay, N.106). A frame's keys and windows are fixed when its marker is enqueued (`BreakFrameStart`) and everything about a frame, its submission count included, is read and written under `window_lock`. Invariants: one submitter at a time enqueues a pair (values must rise in queue order, or a Wait would stand above the fence's value for good); the Wait is enqueued only after its Signal succeeded; `window_lock` is held for loads and stores only and never around `lock`. A queue Wait is decided when it is enqueued (a Wait on a fence already at its value is gone at once, even behind an unsatisfied Wait; N.104 finding 456), so a gate held from the CPU cannot stop work the GPU is about to take. Measured with one window (N.104 to N.106, Phantom Blade Zero, no cap, half-width 4, which is what the rule gives there): display jitter 2.20 to 1.51 ms, hitches 88 to 49 a minute, 1% low 64.0 to 65.8, for 2.7% frame rate and 0.6 ms latency; half-width 6: 1.42 ms for 3.7%; every 4th submission of the whole frame: 1.78 for 3.5%; every submission: 1.42 for 13.7%. At a cap of 104 breaks alone do not help; with `fg_separate_presenter_hold`: 1.82 to 1.17 ms, 1% low 61.0 to 66.1, for 4.9 ms latency (3.7 of it the hold's), which the owner accepted. The breaks stay off by default until they are checked in Gears and another game, at 3x and 4x, and reviewed again. A wait of the render queue for the real frame's Present (`fg_real_yield`) was tried before the breaks and removed: the same jitter for more frame rate and latency (N.102, N.104). Not measured: several windows a frame, the rest of a window that misses and the per-frame records (written after the review of N.106, not run in a game), the cost on the submitting thread, a GPU without the flip metering hardware. The breaks are not shown to the queue probe.
- Control file (developer `control_file`, `control_file.h/.cpp`, `Config_SetLiveKey` in `config.cpp`): the test harness's channel into ReLimiter. A poller thread reads `relimiter_control.txt` and queues new commands (`ControlFile_Parse`: complete lines, growing seq); `ControlFile_OnPresent`, after the presenter guard in `on_present_impl`, runs them under the config owner lock (`Config_TryLockOwner`), which both OSD callbacks (`DrawSettings`, `DrawOSD`) hold for their frame because every ReShade runtime runs them on its own present thread; when the lock is held the commands wait for a later present, so the paced thread never blocks on it. The poller writes `relimiter_control_status.txt`. The present callback touches only static queues, flags and counters, never a handle, so a callback still running at shutdown cannot use a closed one; `ControlFile_Start` empties the queues, so a retained module's reload runs nothing queued before it. `capture start` uses `FrameTimeline_StartCapture` (a new epoch even while capturing) and reports a rejected transition as a failure. `Config_SetLiveKey` covers exactly the keys the OSD changes at runtime and publishes them the way the OSD does (`ValidateConfig`, the cap atomics, `Config_ApplyPacingPipeline`); add a key there only when the OSD can change it live. It queues no save, but `AddonUninit` saves all settings, so the harness restores the INI after a session.
- Chain diagnostic (`ChainRecord`, `AggregateChain`, `ReportChain`, `ChainProven`, `VoidChain`, `StreamlineHandoff_RecordQueueFence`, `StreamlineHandoff_ChainCallFailed` in `streamline_gpu_handoff.cpp`, called from `ObserveFence`, the record before its Interested filter): counts, and one authority: the fence-chain proof of the separate presenter's route (see "Separate presenter"), computed by the installer worker from the aggregate on every pass. It records the Signals and Waits of the FG worker's queue and the separate presenter's queue. The proof is the pair `chain.proof_source` and `chain.proof_epoch`, published together and read by `ChainProven`, which holds only while `chain.epoch` still equals the proof's epoch; so everything that advances the epoch voids it at once, until the facts are observed again: any queue destroy, a record that could not be pushed (`PushChain`), and a native Signal or Wait on the worker's or presenter's queue that failed after its record was made (`StreamlineHandoff_ChainCallFailed`). The wait evidence is judged per pass: a presenter wait below the worker's newest Signal voids the proof for that pass, a pass with waits only at or above it proves, a pass without waits leaves it as it was. Keep its lifetime model as it is: hooks only push records for queues the installer worker published, each tagged with one global epoch, and the installer worker aggregates in push order, dropping older epochs and resetting both sides on a newer one. Per-queue lifetime schemes (lock-free tables, per-side lifetimes, last-seen tracking) each failed review on destroy races.
- DLSS-G display order (measured in Gears and CONTROL): the generated frame between real frames n − 1 and n is shown about 0.15 ms after frame n's Reflex GPU end (frame generation included), and real frame n about half an interval later, at a delay the driver sets. Under the Reflex Sleep bypass that delay follows half of frame n's SIMULATION_START interval (r 0.71–0.86), not the GPU gap it lands in, so the source release rhythm is an input to real-frame placement. The real/generated labels come from `PresentFrameGrouper` (present_association.h): the PCL marker lands on the first present of an app frame (the generated one), so the last present of a multi-present group is real. Captures before that fix have the labels swapped under DLSS-G.
- Reflex report ingestion (`TryIngestReflexLatency`): take every unseen report per poll, oldest first. Polls run once per frame, so one report per poll keeps any backlog for good (Gears' reports arrived 250 ms late), and every report-driven loop then acts on stale frames.
- Lockstep credit (`GatedHoldTicks`, later frames' waits inside [s, p]): keep the whole credit on the GPU waits too, even when the frame's readiness is its output point. In a pipelined engine the next frame's wait overlaps frame n's render submission, so the credit hides GPU-throughput lateness (Gears FG 2× at 120 11.2–12.5 ms on 53–100% of frames, 0.2–1.4% of the 12–28% late frames counted), but bounding it by the frame's GPU idle inside its span changed no display measure beyond the run-to-run spread.
- Frame span demand (`SerialFrameDetector`, feedback `SerialFrameArrivalUs`, `ReflexOwnedWaits::arrival_qpc` from `SourceStageFrame::game_arrival_qpc`): a pair is serial when the game reached ReLimiter for frame n + 1 at or after frame n's PRESENT_END, before any wait of ReLimiter's own; a frame ReLimiter did not plan arrives at its simulation start. Never judge from the released simulation start: ReLimiter's own hold puts that after the previous Present for a pipelined game, and the detector then read the whole frame span (Gears FG 2× at 120: serial by the release on 58–96% of pairs, CONTROL 96%; by the arrival on 0%; Rogue Core 100% either way). The frame span ran p90 19.5–21.4 ms in Gears against a GPU execution p90 of 18.3 ms. An arrival off the driver clock (clock map not stable) breaks the pair without judging it.
- A reset restarts windows, never the physics: frames released before it still explain the frames after them (`Previous`, decontamination, the anchors), but their later events add nothing to the windows it cleared. `ResetBuckets` finalizes pending frames and gives up their C and D (the old release point). Without that every frame in flight at the reset (release → output point spans the lead, 1.3–2.7 intervals in CONTROL FG 2× at 130) became a sample of the new regime.
- One collision model for the GPU queue wait (`CollisionGuardedLeadUs`, `CollisionOffsetUs`, `BehindWait`): L ≤ I + Q10(D) − H (Reflex GPU times) or I + Q10(C) − M (without), H = 1.0 ms (`kPacingGpuWaitHeadroomDefaultUs`) and M = 2.5 ms, both fixed. Do not learn H or M from late resumes and do not condition them on GPU load: a learned headroom widened to 1.75 ms on 10 of 123 resumes at a session's start and could never narrow (the guard keeps releases out of the region below the edge), so a slow section's margin stayed for the session; per-load-band learners fail because the heavy bands never collect the background a learner needs (235 and 1 resumes at ≥ 2 ms in the two heaviest bands across 47 Rogue Core captures, which hold half the late resumes) and the load gradient is composition (heavy sections hold briefly; with holds ≥ 500 µs late at 0.5–1 ms is 0.05–0.75% across loads). Do not cap a GPU wait's lead (lead ≤ median X + a cap lowered by late resumes): at a fixed distance short holds are the late ones (3.9% under 250 µs against at most 0.45%), so capping the hold pushes the wrong way. A relaxing limit returns the lead at the lead slew, never in one step (`Bucket::held_back`). The guard stands aside only while the heavy-work window is current (`WorkCurrent`), or for a frame planned with present-first ordering while the Reflex reports are (below); without reports no pair can show the queue order changing. Late resumes are measured and shown, never acted on.
- Collision model evidence (`LeadController::RecordWorkStart`, `RecordCallTime`, `GpuGateVerdict`, `GpuGateEvidence`, `PendingFrame::gpu_wait_lead`, `OnSourceRelease`, `OnGpuReport`, `WorkCurrent`): D is sampled only after a predecessor (grid index − 1, same lifecycle = identity domain + producer epoch + controller generation, same FG divisor, a sampled GPU queue wait frame) whose GPU waited at its gate (probe at or before the Signal, else readiness before the Signal); a not-waited, missing, other-lifecycle or other-divisor predecessor adds none, since D after it does not measure a release the wait could collide with. For a GPU queue wait frame with a resume probe expected, the verdict stays pending until the probe event arrives (`GpuGateVerdict`); readiness decides only when no probe time is available (no pre-wait time) or the slot closed. A pending verdict defers the sample and the successor is revisited on any event of the predecessor (GpuReady, GpuResume, OutputRelease) and on its source release. Only paths that seal a decision once (the D samples) wait for the probe; consumers that read a frame's gate at one event (the FG input wait's queue-order pair) take `GpuGateEvidence`, the evidence present then. C (`RecordCallTime`) is unchanged: every GPU-wait sample, the D-less fallback. The work age counts every frame planned with the GPU wait's lead (`gpu_wait_lead`: held) in `OnSourceRelease` and resets on any Reflex report of such a frame in `OnGpuReport`, with or without a D sample (mirror of `fg_report_age_frames_`); never reset it inside `RecordWorkStart`: an age reset only by D samples ages in every stretch without waited releases (a pause, GPU-bound frames) although reports keep arriving. There is no cold guard while no window is warm.
- Late state of the collision model (`LeadController::LateOffsetUs`, `LateWindow`, `LeadRequest::late_us` / `late_index` / `late_guard` / `late_observe`, `LeadGuardOutcome::late_state` / `release_limit_us`, `PacingFramePlan::lead_limit_us`, `Decide` in `gpu_present_gate_d3d12.cpp`; developer A/B switch `gpu_wait_late_guard`, default off, and `gpu_wait_ab_interleave_s`): a game that is slower than its slot for CPU reasons arrives after its planned start, its frames are released I + lateness apart, none is held, so D gets no sample and the window (current by the rule above) keeps the limit it learned at the cap. Rogue Core with `r.OneFrameThreadLag=0`: the limit stood at 10.33 ms for 110 s (Q10 of samples 10 s older, 3.64 ms) while frames were ready 14 to 17 ms after release and the GPU idled 1.5 to 4.5 ms before the next frame's heavy work; the replay of the guard matches the logged lead to 0.04 ms at the 99th percentile (N.109). With the switch on, while the heavy-work window is warm and current, the guard applies, and each of the newest 64 consecutive planned frames arrived more than 100 µs late: L ≤ I + (their least arrival lateness) + (the least D of the newest 64 reported frames, whatever their predecessor but an ordered one) − H. Keep these properties: one collision model (heavy work and H; the Present-call form inside the state left 0.4 to 1.1 ms before the heavy work and was rejected in review); lateness from the game's arrival against the planned start, never the release (the hard limit's wait and a late wake are ReLimiter's); minima, not the window's quantile (a D delayed behind a predecessor is larger and so cannot raise a minimum); a frame after a predecessor planned with present-first ordering adds no D to the ring (`RecordWorkStart`: its heavy work waited for that Present, so its D carries the order's delay and a limit built from it would be looser than the heavy work allows); one frame on time ends the state in that plan; a frame planned in the state gives its successor no sample in the heavy-work window (it stays on-time evidence, so the limit after the state is the one before it); the rings are cleared with the bucket and by a gap in the plans. 64 is `LEAD_WORK_STALE_FRAMES`, the horizon of the guard's own evidence: do not shorten it from replay figures (16 held half again as many frames and about doubled the holds that end within 0.5 ms of the next heavy work). The guard's limit also bounds the resolved target: the spacing floor lifts a target past the limit when the lead drops by more than its slack in one plan (the end of a state), and a hold that ends inside the next frame's heavy work is displayed about 1.5 ms late (91% of such holds in the capture; 29% at 0 to 0.5 ms before it; 0.2% at 0.5 to 1 ms). `up_flags` 0x80000000 marks a frame planned in the state, 0x100000 one that met the condition in an off period of the interleave. Status: replay on two captures only; not approved by a capture, so the switch stays off.
- Present-first ordering (developer A/B switch `gpu_wait_present_first`, default off, live, with `gpu_wait_ab_interleave_s`; 64-bit Direct3D 12, compiled into the add-on only (the `RELIMITER_FG_PRESENT_ORDER` pattern, other targets get no-op forms); the unit `gpu_hold_order.h/.cpp`, its rule, books, Signal history and boundary evidence `gpu_hold_order_rule.h` (tested in `tests/test_gpu_hold_order_rule.cpp`); design `project-docs/002_unified_pacing_timing/foundation/design_present_first_hold.md`): in a game whose render queue R is not its presenting queue P (Rogue Core through Streamline's proxy, no frame generation presenting) the next frame's heavy work runs beside a hold, and a hold that ends inside that work or within 0.5 ms before it is displayed 1 to 1.5 ms late (68% and 43% of cases, N.117). Every limit on the lead learned from evidence either starved or collided (the idle-GPU evidence this replaced was rejected by its capture and removed), because when that work starts depends on when frame n was ready. The unit orders the GPU instead: R's work for frame n + 1 waits until frame n's Present is runnable. Three fences, ONE writer each (the gate's and `fg_present_order`'s convention: a fence written by a queue and by the CPU can be set back and strand a Wait): `issued` by P right after the native Present of a frame the plan ordered and the gate committed a Wait for returned S_OK, `reached` by R in front of the order Wait, `order` from the CPU by the release thread when `issued` reached the value (the Present is runnable), at once when the hold's target has come while R has not reached that value's Wait or has none yet (`GpuHoldOrderBook::Late`, counted as `late`: a frame that is late for its slot has no hold left to protect and does not pay the Present's service time; a value R already stands at waits for `issued`), or at the deadline, the watchdog (the later of the hold's target and the moment `reached` got there, plus a quarter of the interval, 1 to 4 ms; it does not run while R has not reached the Wait, so a frame that is late on the GPU is no watchdog case; a release while the gate has not released the hold is the gate's delay and no trip, see the rule). Boundary check (why the Wait cannot make the queue wait for itself): the Present's dependencies are the outermost Waits of P its thread made in front of the gate's own, on fences one other queue signals (a Present with none, with fences of more than one queue, or with more Waits than the thread remembers has no dependency and is not ordered); its edge is judged at R's next outermost `ExecuteCommandLists`, before that Execute is counted and before the probe's `ExecuteEnter`, and the Wait is enqueued there only when, for EVERY Wait of P for that Present on a fence R signals, R has signalled the fence with a value at least the one P waited for, and no Execute on R followed the latest of those first such Signals (one per Wait); otherwise nothing is enqueued and the cause is counted. A game that signals one fence after every submission (Rogue Core: 13 Signals a frame, values rising) has a later Signal with nothing behind it in mid-frame, so counting from the newest Signal was a defect, found before the first build. The Signals of each fence the Present waits for are kept in a short history (`GpuHoldOrderHistory`, 32 records, its oldest never counts as the first because an older Signal may have satisfied the Wait earlier; `GpuHoldOrderEvidence` takes the latest over the Waits; both in the rule header, tested), and a Signal's record takes R's Execute count from before the native Signal (`GpuHoldOrder_BeforeSignal` gives the mark, `GpuHoldOrder_AfterSignal(queue, fence, value, mark)` records it), so an Execute another thread counts while the Signal is being enqueued is behind it. Once the Wait is on the queue the Executes R's other threads counted since the judgement are looked at: the Wait stays and is released like any other, but a frame one of them passed in front of is counted as raced and not as qualified. Rule (`GpuHoldOrderRule`): Probe, 16 held frames that all qualified → Ordering (`Able()`, what the scheduler reads, with a binding, a running release thread, no frame generation presenting and the GPU queue wait rung: the unit is able); a frame that does not qualify → Probe; a trip is a watchdog release of a Wait whose hold the gate had released (the Present did not become runnable within the bound although the hold was over and R stood at the Wait): it counts in every state but Off (a Wait enqueued in Ordering and released after the rule fell to Probe counts too) and leads to Probe, or stays there; the third trip → Off until a new binding, the key toggled or a restart, unless clean running forgave the trips. A watchdog release while the gate's own release of the hold is not recorded is no trip: the runtime can hold the gate worker's own CPU Signal of its time fence for tens of milliseconds (Phantom Blade Zero at a game hitch: 30 ms), so the Present could not run whatever R did and the order is not what stalled; the Wait is let go at the bound (R must not stand at it past it), counted (`gate_late`, a part of the watchdog releases) and said, and the rule is told nothing (no trip, no fall to Probe); a value with no side data cannot be shown to be the gate's delay and stays a trip. Trips are forgiven by clean running (`GpuHoldOrderRule::OnReleased`, `kForgive` = 256): each ordered frame's Wait that its Present released (not a late release, not the watchdog's; counted in Probe too and across a fall to Probe) counts, and 256 in a row with no trip between set the trips back to 0, because a cycle the boundary check cannot see recurs with the frames (every entry into Ordering stalls at once, with no ordered frame released by its Present in between, so its trips follow within a few blocks of 16 frames) and a hitch does not; three trips with fewer than 256 such releases after each of them turn the rule Off, a long session of ordinary hitches does not; Off stays Off. The hooks order a frame whose plan said so while `Orders()` (not Off and not tripped since the rule last entered Ordering), not only while `Able()`: a plan is made before the edge of the frame before it is judged, so a frame planned ordered just before the rule fell to Probe is still ordered, and its own boundary check keeps it safe. ## Hooks and external APIs

- Derive the active graphics API from the current presenting device during launcher, game, and swapchain transitions. Never reinterpret DX9, Vulkan, or OpenGL native handles as DXGI swapchains.
- Use typed MinHook trampolines, idempotent installation, and complete failure cleanup. Preserve each hook's established original-call ordering; some marker hooks intentionally call forward first.
- Install hooks in batches, one per site (`HookBatch` in `hooks.h`; every MinHook enable freezes the process, and two engines' freezes can deadlock each other, so a site makes one freeze, not one per hook). A batch is lazy: constructing or destroying one takes no lock and calls nothing, the first install inside it takes `HookInstallGuard`, and the lock is held from that first create to the apply (`Apply` and `Hooks_FlushBatch` release it), so an idle batch never blocks another installer and no site lengthens a lock the present thread waits on; a site whose own code creates hooks (`FocusLock_Install`, `NGXHooks_TryInstall`) holds its own `HookInstallGuard` around that code. Inside a batch `InstallHook`, `InstallHookPublished` and `Hooks_EnableOrQueue` create, publish the trampoline and `MH_QueueEnableHook`, and their `MH_OK` means queued, never enabled. The sites: `Init` (`DoInit`: the flip-metering block and `NGXHooks_Init`, one batch around both), `FirstPresent` (the first present event: the four LoadLibrary hooks and the NvAPI hooks), `LoaderScan` (one scan of the loader-install worker, closed before its 250 ms wait, so discovery, factory probing and drains never run under the install lock for the batch; `NGXHooks_TryInstall` outside the worker opens its own), `FocusLock` (`FocusLock_Install`: `MH_CreateHook` x4, then `Hooks_EnableOrQueue`) and `DxgiFallback` (the DXGI `Present` / `Present1` pair, only when the vtable route is absent). Anything that logs a hook as installed, begins a producer epoch or sets a state flag reads `Hooks_TargetEnabled` AFTER the apply (`NvAPIHooks_ReportInstalled`, `ReportFlipMeteringBlock` and `LoadLibraryHooks_ReportInstalled` run after the batch; the installers call them themselves outside a batch). A group that cannot continue without the enable result (the Streamline hooks, the proxy and queue hooks, the FG input and queue hooks, the NGX transaction, which retains or rolls back on it) calls `Hooks_FlushBatch()` once after its installs: the same apply with the batch still open. `MH_ApplyQueued` is not a transaction: it stops at its first failure with the earlier hooks enabled, so a failed apply enables every hook still queued one by one with `MH_EnableHook`, logs each failure once at warning and leaves the failing hook created and not queued (nothing stays queued, so a later apply never enables it behind its owner's back). Nested batches on one thread are no-ops that queue into the outer one; an empty batch calls MinHook not at all; a refused admission (shutdown) makes installs fail with `MH_ERROR_DISABLED` as before. A retained load's records stay: installing the same target again queues it, and `EnableAllHooks` (`MH_EnableHook(MH_ALL_HOOKS)`) enables the queue too, settles every record to enabled and, when it stops at a failing hook, enables the rest one by one. Never call `MH_EnableHook` per hook inside a batch scope, and never hold a batch across a wait. Every call that freezes (the apply and the one-by-one enables, a single enable or disable, enable-all, the teardown disable) goes through hooks.cpp, never a raw `MH_EnableHook` / `MH_DisableHook` / `MH_ApplyQueued` elsewhere (`Hooks_DisableHook` for a hook's own disable): those run on the hook installer thread (`Hooks_StartInstallerThread` from `DoInit`, key `hook_installer_thread`, default true, a compatibility switch read once; `Hooks_StopInstallerThread` inside `DisableHooksForShutdown`, after the last freezing call). It is created with a security descriptor that denies `THREAD_SUSPEND_RESUME | THREAD_GET_CONTEXT | THREAD_SET_CONTEXT` to Everyone in front of the token's default DACL, so another engine's `OpenThread` for it is refused and the two freezes cannot wait for each other; at its start it opens itself for a suspend, which must fail (a debug privilege bypasses the descriptor), else it is `Unprotected` and every call runs on the requester. Only raw MinHook calls run on it: no ReLimiter lock, no log, no allocation; the requester keeps the install lock, takes the single job slot's lock, posts and waits with no timeout for the job event or the thread handle. `HookInlineOnlyScope` is the explicit way for code in DllMain or a loader callback (none today) to keep a call inline; so are the kill switch, a thread that is not `Ready` yet, and a stopped thread. If the thread ends before it took the job, the requester runs the job; if it ends with a job in flight MinHook is unusable for the rest of the process (`Hooks_MinHookUnusable`: admission closed, every later freezing call `MH_ERROR_DISABLED`, nothing replayed or terminated), and so is every other MinHook call of the product: none is made outside hooks.cpp (`Hooks_Initialize`, `Hooks_CreateHook`, `Hooks_RemoveHook` and the internal queue calls all return `MH_ERROR_DISABLED` without touching MinHook, whose lock the dead thread may hold), and a caller treats that status as "leave the record retained, do not retry". The batch stages record whether the installer ran the apply and whether it is protected in the high bits of the crumb's site byte (`kBreadcrumbInstaller*`). `Hooks_ForgetTarget` after `MH_RemoveHook` of a `Hooks_EnableOrQueue` target.

Teardown closes installer admission (`Hooks_BeginShutdown`) before collecting the DXGI targets to leave enabled, so a typed hook installed during shutdown is not missed.
- Per-call cost on the game's threads (base cost with Reflex alone; keep these shapes): hotkeys are NOT polled on a game thread: `hotkey_poller.h/.cpp` is polled by the blackout service thread (`Hotkeys_Poll` every `kHotkeyPollPeriodMs` = 8 ms from a high-resolution waitable timer; the thread's window and OLED work keeps its 16 ms cadence on every second wake) with the pure edge detector `hotkey_edge.h` (`Step` = the old `PollHotkey`, its key reads lazy); `DrawOSDImpl` (every frame the overlay event fires, visible or not, so hotkeys work with the overlay hidden and the game focused) only publishes the parsed bindings (`ParseKeybind` runs when a binding STRING changes, `PublishHotkeyBinding`), reports capture suppression (`Hotkeys_SetSuppressed`, latched so a window shorter than a poll still suppresses) and applies the latched triggers (`Hotkeys_Take`) on the thread that owns `g_config` under the config owner lock; a changed binding, a capture and suppression each require seeing the key released before it fires; a press is seen at most 8 ms (plus about 1 ms timer granularity) after it starts and applied by the callback's next run, a press shorter than the period can be missed, two presses before the callback runs are one trigger. A trigger carries the transition generation its poll started under (`s_generation`, advanced by a capture beginning or ending, a rearm, a binding change) and `Hotkeys_Take` rejects one from an older generation, so a poll in flight across a capture cannot apply a press made during it. If the service thread cannot be created, `Blackout_Init` logs one warning and the OSD callback polls per frame on the presenting thread (`Hotkeys_PollFallback`, which does nothing while `Hotkeys_SetServiceThreadPolling(true)` holds, so the two never both poll). Never put `GetAsyncKeyState` back on a game thread otherwise (it blocks in `NtUserGetAsyncKeyState`).
- Module presence (`module_presence.h/.cpp`): the per-frame hooks never ask the loader (`GetModuleHandleW` / `GetModuleHandleExW`) whether `nvpresent64.dll` (`IsNvSmoothMotionActive`), a frame generation runtime (`IsFGDllLoaded`: `nvngx_dlssg.dll`, `_nvngx_dlssg.dll`, `sl.dlss_g.dll`, `dlss-g.dll`) or `RTSSHooks64.dll` (the RTSS caller check of `Hook_SetLatencyMarker`) is loaded. `ModulePresence_Scan` publishes them as atomics: first thing in every pass of the loader-install worker (`loadlib_hooks.cpp` `InstallWorker`: a LoadLibrary* notification starts a pass, else the 250 ms timeout) and once on first use. Staleness bound: a hooked LoadLibrary load is seen at the worker's next pass (one event wake plus the pass in progress), every other load and every unload at most one 250 ms timeout later (a module that unloads reads as present for at most that long); the readers are relaxed/acquire loads. The RTSS check is a range test of the return address against the module's published image range (packed in one word; an unknown size asks the loader as before), so there is no per-address cache to invalidate when another module unloads and another loads into the same range. Win32 never has these modules (the header's inline stubs).
- Identity checks that run per Present and per marker take no COM call to learn that nothing changed: `PublishSwapchain` (`correlator.cpp`) returns at once when the incoming swapchain is the published one (the destination owns a reference, so the address cannot have been reused); `ResolveIncomingDevice` (`nvapi_hooks.cpp`, one look per hook call) answers "is this the presenting device / the published feedback device" for the game's own pointer from values: the pointer equals the publication's native or its alias (`s_feedback_alias`, the ReShade proxy named in the native's private data, captured with the publication; never dereferenced) under an unchanged transition sequence, and the canonical native is compared with `SwapMgr_PresentingDeviceIdentity()`; any other pointer (a foreign wrapper) is unwrapped once per call. `FeedbackIsPresenting` re-checks a token without an incoming pointer. Do not cache an answer on a borrowed pointer alone.
- ReShade's device lock (a launch hang, fixed once; keep it fixed). ReShade runs the `init_device` and `destroy_device` events and add-on unload while it holds one process-wide, non-recursive mutex (`g_d3d12_adapter_mutex`, `deps/reshade/source/d3d12/d3d12_device.cpp`), and every `AddRef`/`Release` of a ReShade device proxy, and `QueryInterface` for the proxy's own interfaces or `IUnknown`, takes the same mutex; `IID_UnwrappedObject` and unknown IIDs do not. So ReLimiter never calls `AddRef`, `Release` or `QueryInterface` (other than `IID_UnwrappedObject`) on a device pointer that a game or plugin passed in: it unwraps it once (`DeviceIdentity_AcquireNative`, `feedback_device_identity.h`), owns and compares NATIVE devices only (the canonical `IUnknown` identity of the native object: the feedback publication `s_feedback_native`, the presenting device of `swapchain_manager.cpp`), and keeps the incoming pointer as an alias that is only compared by value. Four identity namespaces are never mixed: the raw native handle (`get_native()`), the canonical identity (`QueryInterface(IUnknown)` on a native object), the incoming pointer, and the publication sequence. `E_NOINTERFACE` from the unwrap query does not prove an object native: a wrapper that swallows it is terminal and is never captured unless its canonical identity is the presenting device's. Callback rule: `on_init_device`, `on_destroy_device`, `SwapMgr_OnInitDevice/OnDestroyDevice` and `NvAPI_OnDeviceDestroyed` make no call on a device proxy (they compare stored values, or values derived from `get_native()` by calls on the native object) and return for an unrelated device before the selection lock, which a Present holds for a whole frame (`DeviceInitMayChangeSelection`, `ClassifyDestroyedDevice` in `swapchain_selection_policy.h`). Add-on unload can run under the same lock at game exit (destroy_device, then unload_addons): `AddonUninit` and `RollbackInitialization` call nothing on an object ReShade can hook, so the read-back buffer of `gpu_readiness_d3d12_queue.cpp` is released while mapped, never `Unmap`ped. Tests: `test_feedback_device_identity` (a fake process-wide lock; proxies in strict mode fail on any AddRef/Release/own-interface query) and ctest `feedback_device_lock_fixture` (the fixture fails at once instead of hanging).
- The Streamline `SetOptions`, `GetState` and compat `SetOptions` detours keep their `RuntimeLifecycle_EnterCallback`/`LeaveCallback` bracket in a thin `__try`/`__finally` wrapper around an out-of-line body and leave the block by falling through: a `return` from inside a `__try`/`__finally` runs `_local_unwind` -> `RtlUnwind` on every call. Keep any new per-call `__finally` that way. `MarkerCycles_ThreadCycles` (`QueryThreadCycleTime`) is read only through `MarkerStamps_Capture`, which is gated by `unified_queue_upstream` (default 0; the consumer is the pacing CSV's render-stage and span CPU columns) and by the four stamped marker types.

## Concurrency and lifecycle

- Every worker needs an explicit owner, start condition, stop signal, wakeup path, join point, and final-drain behavior where applicable.
- Never stop ETW or join workers while under loader lock. Keep process-detach handling loader-lock safe.
- Preserve normal shutdown ordering: stop native PCL before removing hooks, then shut down telemetry and logging according to their existing ownership.
- Start-up evidence (`startup_breadcrumb.h/.cpp`, `Log_Init`): `Breadcrumb_Mark` and `Breadcrumb_PresentCompleted` are plain stores into a mapped page, with no lock, allocation, flush or log, because hook batches call them around `MH_ApplyQueued` while the process is frozen; keep them that way and keep every failure (open, map, read-only folder, a second live launch holding the file) a silent no-op. The record is a seqlock; one writer at a time, a contending mark is dropped. Every stage but the two batch stages is first-wins, `Running` (the 32nd present after the first-present block) is followed only by `Closed`. `Log_Init` moves the previous log to `relimiter_<exe>.prev.log` (a failure is not an error), attaches `relimiter_<exe>.crumb` in the log's folder and, after releasing the logger locks, logs one warning at warning level when the previous launch's record is valid and before `Running` and not `Closed`. A new stage needs the enum, `StageName`, the docs and a mark at its site; never rename a stage or reorder the record (the file layout is versioned).
- Stall report (`hang_report.h/.cpp`, `hang_report_policy.h/.cpp`, `hang_progress.h`, `lock_owner_diag.h`, `log_level_state.h`; keys `hang_report` (default off), `hang_report_dump` (default true; false = text report only, dbghelp never loaded) and developer `hang_report_test_after_s`; the last two are in `Config_DeveloperOverrides`/`Config_ResetDeveloperSettings`): a watchdog thread created with the installer thread's descriptor (`Hooks_BuildProtectedThreadSecurity`; the thread checks on itself that opening it for suspend is actually refused, because the debug privilege bypasses the descriptor, and the report says "built" and "effective" separately) wakes once a second, keeps the process CPU time of the last interval (`GetProcessTimes`), evaluates the pure policy (armed after a completed present event, or 60 s after the first swapchain init; report at 20 s without a completed present event, again at 90 s, progress re-arms, at most three per process) and writes `relimiter_<exe>.hang.txt` then `.hang.dmp` next to the log (the temporary folder with one warning when the names next to the log would exceed MAX_PATH). The text step uses only static buffers, `WriteFile`, `OpenThread`/`SuspendThread`/`GetThreadContext`/`ResumeThread` (a thread is resumed before anything else touches it), `ReadProcessMemory`, the Nt calls resolved at start (kernel thread states are parsed from `SystemProcessInformation` by its record layout, bounds-checked, with the pid and first ClientId validated) and a few user32 window queries that send nothing: no heap, CRT stream, logger, loader call or ReLimiter lock until the file is closed, because the process may be stuck holding any of them. Keep it so. The dump step is entered only when the text file was created, written, flushed and closed; the log lines and `HangReportResult` state the per-file outcome. The producers are plain relaxed stores (`g_hang_progress` at the present events, the native Present entry, the Reflex Sleep and latency marker hooks; `LockOwnerDiag` for the selection lock and the hook install lock; the trail kinds in the crumb ring, `TrailKind`); nothing is added to a queue detour but one relaxed load and a not-taken branch per call (`Breadcrumb_TrailFirst`). `HangReport_Start` begins a logger floor (`Log_BeginLevelFloor`, at least info) that the watchdog ends 120 s after it started; `Log_SetLevel` stores the requested level whatever the floor says (`LogLevelState`: request and floor in one atomic word, `Log_Write`'s rejected path is still one load), so a level requested during the window is never overwritten. A new trail kind needs the enum, `Breadcrumb_TrailKindName`, the report's decoder in `PutTrailEntry` and a mark at its site. Off means inert: `hang_report_state.h` holds one process-lifetime flag (`HangReport_Active`), set once in `DoInit` right after `LoadConfig` and before any hook or callback can run a mark (the key is launch-only); `HangReport_Start` returns false and starts nothing when the key is off (no thread, no log-level floor); every progress counter, trail append (`Breadcrumb_Trail`, `Breadcrumb_TrailFirst`, the trail part of `Breadcrumb_Mark`), lock-owner note (`LockOwnerDiag`) and every clock read that feeds them (`NowQpc` in `hooks.cpp` and `swapchain_manager.cpp`, the present, native Present, Sleep and latency-marker sites) starts with one relaxed load of that flag and a branch that is not taken. New report marks on a hot path take the same gate; the one-record start-up breadcrumb (stage at offset 0) does not depend on it.
- Use relaxed atomics only for independent snapshots. Use acquire/release ordering when publishing related data or transferring ring-buffer ownership.
- The callback guard (`runtime_lifecycle.h/.cpp`) counts admissions per thread: each thread claims a cache-line slot of a fixed table (128) at its first guarded call, a locked update on that slot is the whole cost of the guard (no shared line, no allocation, no loader call, no lock), the thread's exit releases the slot (a `thread_local` destructor; the slot keeps its word, the next owner continues from it) and threads beyond the table share one overflow slot (a locked update, the old shared counter's behaviour). The handshake is the Dekker pair of the single counter: the guard adds to its slot, then reads `s_stopping` (both sequentially consistent); shutdown stores `s_stopping` (sequentially consistent) before it reads any slot. `RuntimeLifecycle_WaitForCallbacks` and `RuntimeLifecycle_Initialize` read the slots as a double collect (`inside == 0` on the first read of every slot and an unchanged word on the second, `enters` only grows) and so see "no callback admitted" exactly when the single counter would have been zero at some instant of the call. A guard remembers its slot and leaves that one wherever it is destroyed; the `RuntimeLifecycle_EnterCallback`/`LeaveCallback` bracket leaves the calling thread's slot, so it must enter and leave on one thread. `s_stopping` is alone on a cache line nobody writes in steady state (Initialize, BeginShutdown and Shutdown only); keep every hot or frequently written variable off it. A new thread-hot guard path must not add a shared writable line. `test_runtime_lifecycle` runs the production unit.
- Keep telemetry producers nonblocking. Fixed SPSC buffers intentionally drop rows rather than stall render or ETW threads when full.

## Cross-surface changes

- A configuration field is not complete until its struct default, INI load, validation/clamping, save behavior, runtime application, OSD control, user documentation, and architecture guards agree.
- A telemetry field is not complete until row structures, CSV headers, formatting, producers, analysis consumers, and documentation agree.
- Preserve established CSV column order, especially the native-PCL prefix; append diagnostics unless a deliberate schema migration is requested. A column leaves the header only when no producer writes it any more, and the capture-analysis tools keep the older header as a historical profile.
- Keep high-frequency logging sparse. Log initialization, state transitions, feature decisions, and failures rather than every frame.

## Verification

- Use standalone tests for pure logic, but do not treat them as proof of production integration.
- Scheduler, hook, swapchain, loader, driver, ETW, and frame-generation changes require runtime verification on every affected API/path.
- Compare telemetry captures when changing pacing behavior and record units, filters, target FPS, refresh mode, API, and FG state used in the comparison.
