# AGENTS: ReLimiter tests

This file adds rules for project-owned tests under `tests/`. Dependency test trees under `deps/` are not ReLimiter tests.

## Test model constraints

- Most C++ test executables compile selected production `.cpp` files from `src/` (see `tests/CMakeLists.txt`) and stub the rest; a few are standalone copied models. A pass proves the compiled unit's logic, not its integration with hooks, threads or drivers.
- Stubs stand in for production APIs (for example `test_feedback_device_identity.cpp` stubs the `Scheduler_*` functions the NvAPI hooks call). When a stubbed API's name, signature or contract changes, update the stub in the same change; a stub that still links against an old contract hides the regression it should catch.
- Pacing-core unit tests prove their pure units only. `test_lead_controller` covers the 99% lead, the collision guard and its start term (ordered plans only, the render queue's resume and its staleness, a long stretch of holds that give no pair, windows, pairs (a pair needs the unit's word and not the probe's stamp, and the term stands aside with no probe report at all), stand-aside evidence, delivery order, resets, the plan), the spike floor, the render queue correction (the FG input wait always, the GPU queue wait with its developer key), the queue-wait mode, the cold start and the joins; `test_cadence_grid`, `test_source_stage` and `test_pacing_resolver` cover the grid, the source stage's present and unified planners (with the collision guard's switches and the limit and arrival a plan carries) and the resolver's decisions; `test_unified_pacer` and `test_unified_queue_law` cover the start law and the queue law; `test_pacing_test_mode` pins each test mode's pipeline decision, Sleep policy and observer state. `test_period_governor` covers `LfcHysteresis`, `PeriodGovernor_LfcIntervalUs`, the `GovernorCause` text and the VRR choices (`PacingPipeline_VrrIntervalUs`, `PacingPipeline_VrrTargetFps`); `test_rung_feasibility` covers the `FeasibilityCause` values and text. `test_pacing_csv` and `test_pacing_join` cover the 197-column rows header, the events header and the join. `test_scheduler_passthrough.cpp` models the dispatcher and does not prove it; its live counterpart is the manual procedure `tests/test_scheduler_passthrough.md`.
- The pacing capture schema is one checked-in fixture, `tests/data/pacing_schema.txt` (line based: the 197-column rows header, the 112-column events header (the 86 columns every build before the flip gate's rows wrote, then the `flip_*` columns), and every value-to-name table the analyzer keeps, with values no build produces any more marked `retired`). `test_pacing_schema` (ctest `pacing_schema`) compares it with the real CSV writer's headers and `event_type` text and with the `*_Text` functions over every value 0..255, and lists the enumerators of the enums that have no text (a new enumerator does not compile until it is listed); `test_analyze_pacing.py` compares the same file with the analyzer's headers and tables. A schema change (a column, an enumerator, a name) updates the fixture in the same change; no test reads `src/` text for it.
- `test_pacing_sample_sources` (ctest `pacing_sample_sources`) includes the real `src/pacing_sample_sources.h` and links `pacing_metrics.cpp`: which flips of the flip gate and which real frames at the FG input follow each other, when a real frame entered frame generation, and the window's mean jitter and hitch count over such samples. It does not prove the gate's stamps, the GPU readbacks, the worker's choice between sources, or that a source's figure matches what the display showed; those need a capture with ETW display times next to the source.
- `test_fg_present_places` (ctest `fg_present_places`) includes the real `src/fg_present_places.h`: which Present was in progress on a thread at a time, the ring's bounds and what an overwritten entry gives, on one thread. `test_present_association` covers `PresentFrameGrouper::AddPlaced`: a placed present's role, the head it takes where its frame's marker was on a present of its own cycle, of the cycle before or on none, and the change to and from grouping by marker order. Neither proves that the unit writes a place for the right Present, that the place's times bracket the start ETW records, that the frame id is the one PresentMon carries, or the collector's lookup across threads: those need a capture. `test_pacing_csv` writes one `flip_gate` event through the real writer and reads its cells back; what the clock thread fills them with is not tested.
- `test_gpu_queue_glue` (ctest `gpu_queue_glue`, `gpu_queue_glue_rule`) and `bench_gpu_queue_hooks` (not a ctest) link the REAL probe glue (`src/gpu_queue_probe_d3d12.cpp`, `src/streamline_queue_hooks.cpp`, core, borrow, dependency) against fake D3D12 queue/fence/device COM objects (`gpu_queue_glue_support.h/.cpp`, x64 only). The fakes' vtable slots are verified against the SDK at test start; the stubs there (logger, hook installation, Streamline handoff, telemetry, law feed, queue reference) and the test seam (`src/gpu_queue_probe_test_seam.h`, `RELIMITER_GLUE_TEST_SEAM`, set only by those two targets: two native-method checks accept the fake methods and the render-queue adoption can be started without the dependency rule's 64-frame window) follow the same rule as other stubs: update them with the contract they stand for. They do not prove a real driver's completion timing, the real D3D12 runtime's cost, MinHook installation or the Streamline handoff.
- Glue test seams (`src/gpu_queue_probe_test_seam.h`, `RELIMITER_GLUE_TEST_SEAM` only): adoption of the render queue, `Running`/`Dead`/adopted queue and role, the dependency table entry time read-back, the core's untrusted-marker count, and `GpuQueueProbeTest_SetBindPause` (a function called on a Signal detour's binder thread at four points of `BindMarker`; `test_gpu_queue_glue --bind-race-*` hold a binder there). Each `--...` mode of `test_gpu_queue_glue` ends its session in its own way and is its own ctest process; when a pause point or a seam function moves in the glue, move it in the same change.
- More glue test seams (same header and macro): the pause points of `GpuQueueProbeTest_SetBindPause` also include 4 (the claim, before it releases the Signal lock), 5 and 6 (the lock-timeout taker after its Submit is built and after Lost is published), 7 (the worker's tail read after the cursor and `issued` loads) and 8 (after the tag of a slot above the cursor, never reached for a consumed one); `GpuQueueProbeTest_SetPushObserver` (every Submit a taker pushes, exactly as pushed: bind, lose, settle), `GpuQueueProbeTest_SetClaimObserver` (each claim's index, saved event and claim epoch) and `GpuQueueProbeTest_SetArmObserver` (the planner's armed k per fence); `GpuQueueProbeTest_Orphaned`; `GpuQueueProbeTest_ConsumedCursor` (the worker's consumed slot cursor: a test that classifies a tail read as stale waits for it first); and the fake queue's Signal gate (`Queue::signal_gate`, `signal_gate_fence`, `signals_blocked` in `gpu_queue_glue_support.h`), which holds the game's native Signal of one fence after the probe's bind. A pause hold that expires (30 s) is recorded by the test's dispatcher and fails the test at the next release and at the end of the run; it is never a pause that worked. Tests of a slot-ownership rule assert the pushed Submit's identity against the claim observer, not only counts.
- `test_addon_reload` (ctest `addon_reload`) loads the built add-on into a fake ReShade host (the test executable exports the add-on API, following `deps/reshade/source/addon_manager.cpp`) and runs ReShade's unload and reload over two devices: registration, unregistration at `AddonUninit`, registration again, and the add-on's module on every forwarded message. A crumb record of a launch that ended during start-up forces a warning before registration. It runs the add-on's whole initialization and shutdown, but no device, swapchain or present. It writes its log and crumb next to the test executable and stages the add-on in `addon_reload\` beside it.
- For a copied model, never claim that a pass proves production behavior. Verify that the model still matches current production conditions, defaults, formulas, thresholds, and ordering, and update it in the same change as the production logic it copies, or document why it no longer applies.
- Python tests (`test_*.py`, `python -m unittest discover -s tests`) cover the capture-analysis scripts under `.agents/skills/pacing-capture-analysis/scripts/` and the offline simulators under `tools/` when present, with synthetic inputs; the configuration's save policy, key set, migration and presets are covered by `test_config_async.cpp` (the real `config.cpp` against fake profile I/O), not by Python. The capture tests pin the current 197-column rows header and its 195-, 193- and 192-column prefixes: absent lead terms are unavailable, absent start limit columns and `plan_ordered` read as 0. They also pin the pre-removal 199-column header, its historical prefixes and the unchanged events header, so earlier captures keep parsing. They prove the tools' arithmetic and rules, never pacing behavior.
- Tests assert behavior, values, wire formats and schema headers, never the wording of log, OSD or document text.
- Prefer directly testing genuinely platform-independent production logic when practical, but do not distort a latency-sensitive runtime design solely to make it unit-testable.
- Keep randomized/property tests replayable. Accept or fix a seed, and print the seed and failing input when a failure depends on generated data.
- Keep manual verification documents synchronized with current config names, OSD controls, telemetry columns, and runtime paths.

## Validation

- Build the smallest affected test target, then run it through CTest from the architecture's `tests` build directory.
- Report the architecture and configuration used for each run.
- Hooks, swapchains, driver APIs, ETW, loader behavior, and pacing quality still require live runtime or capture-based validation.
