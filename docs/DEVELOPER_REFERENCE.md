# ReLimiter Developer Reference

This document covers the settings, status lines and log lines that exist for A/B testing and capture analysis. Normal users never need it: ReLimiter ships the recommended defaults and the [User Guide](USER_GUIDE.md) covers everything a player has to know.

It describes current behavior only. Release notes are in [`CHANGELOG.md`](../CHANGELOG.md).

**Scope.** 64-bit DirectX 12 with NVIDIA Reflex is the supported and tested configuration; other APIs with Reflex run the same pacer untested; games without Reflex and all 32-bit games get a plain frame-rate cap. The present route that caps those games is retained and covered by unit tests; it has not been validated in a game, and nothing validates DirectX 11, Vulkan or 32-bit pacing.

[Frame Pacing](FRAME_PACING.md) explains the mechanisms these settings and lines refer to (cadence grid, lead, output points, protections), with diagrams.

## Enabling Developer Settings

The **Developer diagnostics** group appears in the **Advanced** section only when both of these are true:

- `developer_settings=true` is set under `[FrameLimiter]` in `relimiter.ini` (default `false`; edit it with the game closed).
- **Enable advanced settings** is checked.

Every control in the group can make pacing worse on purpose. The group's **Reset to defaults** button returns all of them to their recommended defaults. While any of them differs from its default, the main view shows an amber `N developer setting(s) changed from the defaults` line with a **Reset** button, whether or not the group is shown, so a forgotten test setting does not go unnoticed. When comparing, change one setting at a time and capture the same scene, cap and frame-generation mode, and start each run from a fresh game launch.

The developer keys are also read from the INI when `developer_settings` is `false`; the setting only controls whether the overlay shows the controls. The one exception is `pacing_test_mode`, which counts only while `developer_settings` is `true`.

## Developer Diagnostics

Defaults are the shipped values. Settings marked 64-bit are not available in the 32-bit addon.

### GPU Wait Probes

`gpu_present_gate_probes` (default on, 64-bit). Applies only to the `gpu_queue_wait` output. It places GPU timestamps immediately before and after the queue wait; the pacing CSV records them as `gate_pre_wait_qpc` and `gate_post_wait_qpc`, and the lead uses them. The same measurements supply the late-resume count shown on the Details lines and in telemetry. Nothing acts on that count: the release headroom and the release margin of the collision-aware release are fixed.

Turning it off removes two command lists and two fence signals per frame from the game's GPU queue; the Details lines then have no late-resume count. The guard itself does not change (headroom 1.0 ms, margin 2.5 ms).

### Pacing test mode

`pacing_test_mode` (`off`, the default; `reflex_only`; `driver_limiter`) says who paces, for a comparison capture. It is honoured only with `developer_settings=true`: without it the effective mode is `off` whatever the INI says (the saved value stays in the INI and in `g_config`, and a warning says it is ignored). It is never in the user's panel and never entered automatically: no saved key, old or new, and no migration sets it. It has no parameter of its own (it uses `target_fps`). It is a live key (`set pacing_test_mode reflex_only`), counts in the developer overrides, and the developer reset returns it to `off`.

| Mode | What runs |
|------|-----------|
| `off` | ReLimiter paces: the unified pacer on 64-bit (the queue-based law in DirectX 12, the report-based rule elsewhere) and the Present route on 32-bit and in games without Reflex markers. |
| `reflex_only` | ReLimiter paces nothing, whatever the saved cap (the cap is not overwritten): the pipeline resolves to mode `off`, placement `none`, reason `passthrough`, the scheduler passes every frame through, and the game's own Sleep calls and Sleep mode are forwarded untouched (the Reflex Sleep bypass is off while a test mode is on, so a positive saved cap does not skip the driver's Sleep). |
| `driver_limiter` | The Reflex driver limiter paces the source: placement `driver_limiter`, output `source_only` with reason `override`, no hold and no start plan of ReLimiter's. ReLimiter sets the driver's `minimumIntervalUs` to the cap's interval, converted for frame generation (divided by the FG multiplier, once). |

The owner is derived once: `unified` is true on 64-bit with the effective mode `off` and false otherwise, and every reader of the owner reads that one value; it is not a setting. A change of the effective mode is an ownership transition with every effect of a hand-over: old plans, mailbox and feed state retired, outstanding holds released, the queue law reset, the Sleep-mode epoch bumped. While a test mode is on `unified` is false, so the queue law and its feed are off and the queue probe follows `gpu_queue_probe` alone. The status file has `pacing_test_mode=` (the effective mode) next to `placement=`, and the `Pacing pipeline:` log line carries it.

A test mode is a foreground instrument and never falls into a pacing path:

- `driver_limiter` where the driver's limiter cannot apply (the game calls no Reflex Sleep, the route is not NvAPI markers, the driver refused the limiter, a 32-bit process) restores the game's behaviour: mode `off`, placement `none`, reason `driver_limiter_unavailable`. The OSD says so.
- An idle cap (background, FG-off cap, OLED Care) passes through in either mode (`reflex_only`: reason `passthrough`; `driver_limiter`: `driver_limiter_unavailable`).
- `reflex_only` passes through on every display, a fixed-refresh one included: ReLimiter applies no cap of its own.

### Fixed values

The pacing behavior that no setting selects is fixed in the code: the lead covers 99% of recent frames plus a 0.5 ms allowance, the output point is always resolved, and the frame interval comes from the cap (the unified pacer also applies the VRR ceiling, the game's own limit and the GPU term, see *Unified pacer* below). The render queue time stays in the GPU queue wait's lead, and the driver's Sleep status is polled once a second. The Reflex Sleep bypass is derived: `PacingPipeline_SleepBypass()` is true exactly when the effective test mode is `off`, and it skips the driver's Sleep only for a Sleep that is not the unified start wait (the first Sleep after start or after a second without one, a frame-start marker other than SIMULATION_START, a Sleep while the placement is `present`) while ReLimiter paces a positive cap; the unified start wait is always followed by the driver's Sleep. The constants that remain in `src/pacing_resolver.h`:

| Constant | Value | Fixed behavior |
|----------|-------|----------------|
| `kPacingLeadCoverage` | `PacingLeadCoverage::Q99` | The lead covers 99% of frames. |
| `kPacingFgLateSpacing` | `true` | The FG input wait floors the frame after a late one. |
| `kPacingLeadSpikeFloor` | `true` | A GPU wait's lead covers the game's rare long simulation frames. |
| `kPacingGpuWaitHeadroomDefaultUs` | `1000.0` | The collision-aware release's headroom, 1.0 ms. |
| `kPacingUnifiedEveryFrameServiceDefault` | `true` | The unified law's GPU service estimate takes a sample from every reported frame. |
| `kPacingUnifiedQueueTargetDefaultUs` | `2000.0` | The report-based rule's queue target, 2 ms. |

## Developer INI Keys

Settings belong under `[FrameLimiter]`. Leave these at their defaults for normal play. The overlay shows them only with `developer_settings=true`; its main view warns while any differs from its default and offers **Reset**.

| Key | Default | Values / purpose |
|-----|---------|------------------|
| `developer_settings` | false | INI-only. Shows **Developer diagnostics** in the Advanced section. |
| `gpu_present_gate_probes` | true | 64-bit, `gpu_queue_wait` only. `false` removes the GPU timestamps around the queue wait; the pacing CSV then has no `gate_pre_wait_qpc` or `gate_post_wait_qpc` and the Details lines have no late-resume count. The collision-aware release does not change (headroom and margin are fixed). |
| `flip_metering_off` | false | 64-bit, DLSS Frame Generation on GPUs with hardware flip metering (RTX 50). `true` or `false` (**Flip metering off (next launch)**): `true` hides `NvAPI_D3D12_SetFlipConfig` from the game's later NvAPI requests, so frame generation that asks for it afterwards never turns flip metering on and runs as on a GPU without it. The log names the first module it was hidden from; without that line the block did not reach frame generation. Confirm in a capture: no flip delay on any row, and each frame shown as soon as it is ready. Applies from the next launch. Smooth Motion needs flip metering. Developer diagnostic, off by default. |
| `fg_present_order_trailing` | false | 64-bit, Direct3D 12, DLSS Frame Generation presenting from its own thread without hardware flip metering, with present-first ordering established (`fg_present_order`, on by default). `true` or `false`: a developer A/B switch for when the render queue is released. Off, it is released when the generated frame's native Present has returned. On, ReLimiter observes whether frame generation's presenting thread submits work (`ExecuteCommandLists`) right after that Present, before the watchdog's deadline for that marker. After a block of sixteen Presents of which at least fourteen were followed by such a submission on one queue, the release is deferred: behind that submission ReLimiter enqueues a Signal of its own fence on that queue, and the render queue is released when it has completed on the GPU (relayed by ReLimiter's own thread to the CPU-written order fence), or by the watchdog at its unchanged deadline. A deferred release left to the watchdog is missing (no submission in time) or late (the Signal behind it had not completed); at the third in a block of sixteen ReLimiter goes back to releasing at the return and observes again, and if three were late, or it went back three times in a row with no clean block of sixteen in between, it stops deferring until the binding, the presenting queue or the key changes. In Phantom Blade Zero (packet traces of 2026-11-14, N.121) the presenting thread submits one more packet and queues two Signals 36 to 56 µs after the Present returns in 97% of frames; the packet lands behind the render queue's batch and sits 2.2 ms on the hardware, in one launch until the render queue runs dry in 26% of frames, and the real frame's Present queues behind it. With the key off nothing new is made at the bind and an outermost Execute pays one load and a branch. Not measured yet in a game; at 3x and 4x only the first generated frame's trailing work can go in front. Read from the INI and a live key (`set fg_present_order_trailing true` through the control file); never saved, not in the overlay and not counted in the developer overrides. Developer diagnostic, off by default. |
| `gpu_wait_late_guard` | false | GPU queue wait with the unified pacer. `true` or `false`: a developer A/B switch for how the GPU queue wait's lead is limited while the game is slower than its slot for CPU reasons. Off, the limit is the interval plus what the collision guard learned about the next frame's heavy GPU work while frames were held at the cap; in a stretch where every frame arrives late none is held, so that figure is not renewed and no frame is held although the GPU idles before the next frame's work. On, while each of the newest 64 frames arrived late for its planned start, the limit is the interval plus their least lateness plus the earliest heavy GPU work of the newest 64 reported frames minus the release headroom, and the GPU queue wait resolves no target past the guard's limit. One frame on time ends it. Frames planned this way carry `0x80000000` in `up_flags`. The log warns at launch while it is on. Not approved by a capture yet; off by default. |
| `gpu_wait_present_first` | true | 64-bit, Direct3D 12, GPU queue wait with the unified pacer, no frame generation presenting. `true` or `false`: on by default, a held frame is presented ahead of the next frame's GPU work in a game whose render queue is not its presenting queue (Rogue Core through Streamline's proxy, Phantom Blade Zero without frame generation); `false` turns it off and leaves the collision guard's limit on the lead alone, as before. ReLimiter orders only where its own evidence qualifies (the render queue is not the presenting queue, no frame generation presents, the output is the GPU queue wait); in every other game the key does nothing. It stays a developer switch: it turns the order off, and with `gpu_wait_start_limit` off it is the subject of the A/B interleave (`gpu_wait_ab_interleave_s`). Off, the next frame's heavy GPU work runs beside a hold, and a hold that ends inside that work, or within 0.5 ms before it, is displayed 1 to 1.5 ms late (68% and 43% of such holds, 2026-11-14 capture); the collision guard limits the lead from what it learned about that work, and no limit separates safe holds from unsafe ones, because when that work starts depends on when the previous frame was ready. On, ReLimiter orders the GPU instead of predicting it: the render queue's work for frame n + 1 waits until frame n's Present has become runnable, so a held frame is released onto an idle GPU and the next frame's work starts behind its Present. No game thread is blocked and no time is predicted. The order uses three fences of ReLimiter's own, each signalled by one writer only (the presenting queue right after the native Present of an ordered frame, the render queue in front of its Wait, and a release thread from the CPU), and the Wait is enqueued only at the frame's edge on the render queue: for every Wait the Present made on a fence the render queue signals, that queue has already signalled the fence with a value at least the one waited for, and nothing was executed on it after the latest of the first such Signals, so the Wait sits behind everything the Present waits for (a game that signals one fence after every submission has later Signals with nothing behind them in mid-frame, so the newest Signal is not the one to count from); an Execute that another thread gets in front of the Wait counts the frame as raced and not as qualified; a frame that fails the check is not ordered and costs nothing. The release thread frees a Wait when the Present has become runnable; at once when the hold's target has come while the render queue has not reached that Wait (the late-frame release: a frame that is late for its slot has no hold left to protect and does not pay the Present's service time; a Wait the render queue already stands at waits for the Present); and at a deadline, the later of the hold's target and the moment the render queue reached the Wait plus a quarter of the interval (1 to 4 ms), for what the check cannot see. A release by the deadline counts as a trip when the gate had released the hold, in every state but off: it stops the ordering until 16 held frames all qualify again, and the third switches the unit off until the game's queues change, the key is toggled or the game restarts. While the gate has not released the hold the Present cannot run whatever the render queue does (measured in Phantom Blade Zero at a game hitch: the gate's own Signal of its time fence blocked in the runtime for 30 ms), so such a release frees the render queue at the deadline, tells the rule nothing and is only counted as a late gate. Trips are forgiven by clean running: 256 ordered frames in a row whose Wait the Present released set the trips back to 0, because a cycle the check cannot see recurs with the frames (every entry into ordering stalls at once) and a hitch does not; once the unit is off it stays off. The unit is bound to one presenting queue, render queue, device and swapchain; another one releases every outstanding Wait and starts the rule again. A frame is ordered when its plan says so (key on, the unit able to order, and with `gpu_wait_start_limit` off the interleave's period on), and one planned just before the unit fell back to probing is still ordered, behind its own check, unless the unit has tripped; then the collision guard stands aside for it while the Reflex reports are current and the frames ordered so show no concurrent pair, and the lead sample of the frame after it leaves out the wait carried from its gate. The row of every ordered frame carries `plan_ordered` = 1 in the pacing CSV (column 193). The evidence of ordered frames and of the others is kept apart, so with the interleave each period shows what its rule alone does. Cost: the GPU's budget per frame is the interval minus the Present's service time (0.3 to 0.75 ms); where the GPU is the limit the order cost 0.35 ms a frame (3%) in the first run below, which had no late-frame release, and PC Latency rose 0.35 ms at the cap. Every ten seconds while it is on, and only when a count changed, the log (info level) counts the held frames, the ordered frames, the frames not ordered by cause, the edges judged and how many Executes of the render queue followed the Signal the Present waits for, the frames an Execute of another thread got in front of the Wait (raced), the Waits released by the Present, by the deadline (and how many of those found the gate late) and by the late-frame release, the Wait's duration (mean and most), the unit's state and trips, the failures of its own queue calls, the holds dropped (told, but their Present failed, was not theirs or never came) and the edges lost (never judged: the render queue made no Execute for four frames, or its fences were no longer its own); each release by the deadline that counted as a trip says one info line of its own with the times (how long the render queue stood at the Wait, how far after the hold's target, whether and when the gate released the hold, how far the Present had got), at most three a binding, and a release with the gate late says one too (the first four of a binding at info level, the rest at debug); the first time it orders in a binding, the switch-off after the third trip, a binding let go and why, and a stop (with totals) are info lines too. At launch it warns only when the key is off, or when `gpu_wait_ab_interleave_s` is not 0 with `gpu_wait_start_limit` off and ordering therefore acts in alternate periods only; with the defaults it says nothing. First run in Rogue Core (the build before the review fixes, no alternation, compared with the built rule in another session): 82,860 of 82,861 edges qualified, 99.94% of the held frames were ordered, no Wait was released by the deadline, and the collision classes were empty (no hold ended inside the next frame's heavy work, and none that ended within 0.5 ms before it was displayed late); the display step against the release step was 2.33 ms at the 99th percentile with ordering against 3.71 ms with the built rule, and the 0.1% low 76.5 against 44.5 fps. In Phantom Blade Zero without frame generation (the render queue is found by dependency there too), three runs an arm, interleaved, on build `1a07a37b9d1c1690`, differences against NVIDIA's limiter with their standard errors where given: at a cap of 60 the shipped defaults hold 0% of the frames and equal NVIDIA's limiter (the display's frame-to-frame change 1.66 against 1.76 ms); with the switch on 81% are held, the frame-to-frame change is 0.42 ms (1.34 ± 0.06 ms lower), the displayed-interval SD 0.69 against 1.49 ms, the 1% low 4.5 ± 0.15 fps higher, hitches 1.5 against 5.6 a minute, PC Latency 5.1 ± 0.6 ms higher (4.5 ms over the shipped defaults), and the cap holds; at a cap of 72 (the edge) the switch on against the shipped defaults gives a 1% low 2.2 fps higher, a frame-to-frame change of 0.82 against 1.52 ms, 5 hitches a minute fewer, 0.9 fps (1.3%) less and PC Latency 4.6 ms higher; without a cap, where the GPU is the limit (measured on the earlier build `b3efbbe50ccef779`), the switch costs 0.7 fps (1%) and changes nothing else. With frame generation presenting the unit does not bind: Phantom Blade Zero at a cap of 120 and Gears at a cap of 90 are the same with the switch on and off. Before a pair whose frame lost its GPU render end (about 0.2% of the driver's Reflex reports lack it) was left out of the collision guard's evidence, the same scene at a cap of 60 held 52 to 58% of the frames and gave 0.88 ms: one false pair brought the guard back for 9 to 16 s of every run. It is on by default since 2026-11-15 because of these two sets of captures (Rogue Core, Phantom Blade Zero). Not yet measured: Rogue Core inside one session on the final build (the alternating capture), the cost where the GPU is the limit there, a render-thread-limited scene with the key on, and Gears without frame generation. Live key; counted in the developer overrides when it is off. |
| `gpu_wait_start_limit` | true | 64-bit, Direct3D 12, GPU queue wait with the unified pacer, for plans made on present-first ordering (`gpu_wait_present_first`). `true` or `false`: on by default, the collision guard's second limit on the GPU queue wait's lead, `2 I − (W + G)` with the render queue's resume `W` after the hold's release and the game's turnaround `G`, keeps a held frame from delaying the game's start of the frame two ahead, which showed as a saw-tooth in the frame-time graph at a cap; `false` leaves the guard as it was. | `gpu_queue_probe` | true | 64-bit, Direct3D 12. `true` or `false`: a developer measurement of what the game's presenting queue does, per frame; telemetry only, no pacing decision reads it (the unified queue law reads its records only with `unified_queue_law`). A submission's start is derived from the releases of the Waits in front of it; nothing is signalled in front of submissions. Marker stamps (`unified_queue_upstream` at 1, telemetry only: nothing in the pacer reads the stamps; `src/marker_stamps.h/.cpp`). ReLimiter stamps the game's own SIMULATION_END, RENDERSUBMIT_START and RENDERSUBMIT_END in its marker hooks, on the thread that sends them, at arrival (NvAPI `SetLatencyMarker` before the driver call, Streamline's `slPCLSetMarker` at hook entry; the markers ReLimiter injects for games without Reflex and RTSS's markers are not stamped), because the driver's report of the same markers reaches ReLimiter 2.5–3 frames late. A stamp belongs to a frame named by its complete key, the marker domain (NvAPI or PCL), the producer epoch and the frame ID, all frozen at the hook's entry, before any admission step that can be descheduled, together with the ring's reset generation, and checked again at publication (in the Streamline PCL hook the capture is the first step after the clock read, before the frame token is resolved, so a call whose own token step rotated the epoch publishes nothing: the first marker of a resumed PCL lifetime, a SIMULATION_START, has no stamp); a reader (the pacing row) asks for the complete key, so an ID of the other domain or of another producer epoch finds nothing, and a hook that was suspended across a controller lifecycle reset or a producer epoch change publishes nothing into the new lifetime (it is dropped when the generation or the epoch is no longer the captured one). A marker stamped twice for one frame keeps the sample with the latest QPC, whole (its QPC, cycles and thread ID together). The ring holds 256 slots; a writer claims a slot with one compare-exchange and drops the stamp rather than wait, a reader gets a consistent copy or nothing, a later frame takes a slot over, and the ring is cleared at every controller lifecycle reset. A frame's stamps are read when its pacing row completes, not when its Source record is pushed (that record is built at the SIMULATION_START release, before any of the three exists). A stamp is one clock read and a few atomic operations, no lock and no allocation; with the key at 0 a marker call pays one relaxed load and a branch not taken.

Thread CPU time of the marker spans (`unified_queue_upstream` at 1; recorded only, nothing reads it yet). The same hooks also read the sending thread's CPU cycle counter (`QueryThreadCycleTime`) and thread ID at SIMULATION_START, SIMULATION_END, RENDERSUBMIT_START and RENDERSUBMIT_END. A span's CPU time is the cycle difference of its end and start marker divided by the cycle rate; it exists only when both markers came from the same thread and the rate is known. The rate is the TSC's, from clean clock pairs read one per cycle on the telemetry worker (no spinning for it, never on a marker call): each pair is the TSC read between two QPC reads and is rejected when that bracket is wider than 5 µs (a preemption inside a pair would shift the TSC against the QPC and publish a rate off by tens of percent; at the usual 10 MHz QPC the bracket is 0–2 ticks, and the 5 µs bound limits the pair's time error to 2.5 µs, 5e-5 of a 50 ms interval); the pair's time is the bracket's middle. Three pairs, each interval at least 50 ms, give two interval rates that must agree within 0.1%, otherwise the oldest pair is dropped and the next one waited for (4 times, then no rate); the rate is that of the whole span. It is used only when CPUID reports an invariant TSC (leaf 0x80000007, EDX bit 8) and when the thread cycle counter is verified to count TSC ticks: `QueryThreadCycleTime` is documented as a cycle counter, not a clock, so once, on the worker, a busy section of about 5 ms compares its thread-cycle delta with the TSC delta of the same section and the two must agree within 5% (a reading below that can be lost CPU time and is tried again, up to 3 times; above it the counter is not the TSC's). Without that the rate stays unknown and the CPU cells are empty for the launch. The span's duration minus its CPU time is how long the submitting thread waited inside its own span (for the render thread: for the GPU or a lock rather than building commands). The pacing row carries `render_submit_cpu_us` and `sim_cpu_us`, the START markers' thread IDs `render_submit_tid` and `sim_tid`, and the END markers' `render_submit_end_tid` and `sim_end_tid`, so a game that sends a span's markers from two threads is visible (its CPU cell is then empty); every cell is empty with the key at 0 or when a value is missing.

`gpu_queue_probe` mechanism and cost. The adopted queue is the queue the game's frames are submitted on: without frame generation the presenting queue (the queue of ReShade's present event), with frame generation the source queue of the frame generation input; never Streamline's presenter queue. One real frame is one boundary, at the point where ReLimiter's present-time work for the frame is enqueued, reached whether or not readiness or the gate is eligible (so also with the pacer passing through). Without frame generation it is the readiness site of the Present (`GpuReadinessCall`, in front of its eligibility checks; the presenting queue is noted for it by `GpuReadiness_OnPresent`, which runs for every Present of the selected D3D12 swapchain), tagged with the (swapchain generation, present sequence) of the Present's span, which the Present's pacing row carries; a Present without a span has no identity (its frames would be untagged and never emitted), so it neither adopts a queue nor delimits a frame. With frame generation it is the real frame's input, delivered by the Streamline handoff independently of the gate's demand and policy (the gate's own input, `GpuPresent_BeginFgInput`, delivers the same boundary when it runs; a repeated frame key is dropped, so one boundary per real frame): the frame's marker is recorded whenever the key is on (`ProbeRecordMarker`: frame, producer and controller present, frame generation observed by the native gate, producer epoch and controller of the current context, one input per frame), the outermost proxy Present scope takes it if it is fresh (within 250 ms) and still current (the same checks again), and the first queue `Signal` inside the scope (seen by the shared queue detour, `StreamlineHandoff_ProbeSourceSignal`) names the source queue and delivers the boundary there. The marker is the scope thread's own (claimed) or, when the engine hands its markers over across threads (Gears), the newest one another thread published into the probe's own hand-off slot (taken exactly once by the game's outermost proxy Present, which frame generation never calls): this does not use the gate's cross-thread verification, which is lost while frame generation is on, so what the probe leaves unverified is the one thing that verification checks (that Present(n) takes marker n and not n - 1); the key it uses is the one the Present's pacing row takes from the same newest marker, so a frame is attributed to the row the pipeline itself attributes that Present to. What the gate additionally requires (the qualified fences, the plugin site, the binding epoch, a readiness demand) is not required. The boundary is tagged with the frame's key (`PacingFrameKey` NvApiFrame, producer epoch, source frame id: what the pacing row of the real frame carries; the joiner matches it first) and, as the secondary identity, the input's swapchain generation. The readiness-site boundary is not used while frame generation is on (the native gate's frame generation observation or the frame generation flags), because that Present is Streamline's presenter, twice per real frame; nor within one second of the last frame generation input boundary (it neither adopts nor asks for another adoption: the flags can lag, and every flip of the adopted queue between the presenting queue and the source queue is a teardown and an adoption that yields only invalid frames; the frame generation input boundary may always switch the adopted queue), so the first non-frame-generation frames after frame generation stops can be lost for up to one second. The gate's hold `Wait` enqueue is not a second boundary while a keyed boundary is open (one logical boundary per real frame): a submission another thread enqueued between the keyed boundary and the hold's `Wait` marks the frame (an overlap submission invalidates it) instead of splitting it, and a hold `Wait` with no keyed boundary before it delimits the frame by itself (untagged). The first boundary with the key on claims the session start atomically (compare-exchange Idle to Starting, so one thread initialises even when the Present thread and a frame generation callback both see Idle), takes a COM reference on the queue and its device, logs the adoption once (queue, which site adopted it, device) and starts one thread, which makes sure the native queue detours are installed (once per process, by the same installer the Streamline queue hooks use: `StreamlineQueue_EnsureHooks`, the one owner of the detours of the native `ID3D12CommandQueue::ExecuteCommandLists`, `Signal` and `Wait`, vtable slots 10, 14 and 15; the probe only adds calls to them and never hooks anything of its own), creates the probe's own fences and a calibration helper thread, calibrates, and only then publishes the queue to the detours. For any other queue, for the adopted queue with the key off, for a nested call (ReLimiter's own submissions inside the gate's owned scope or the Streamline handoff's) and for ReLimiter's own timestamp submission, the probe's calls in the detours return after one load and a compare; a queue `Wait` on any other queue touches no state (it is only counted). A `Wait` on the adopted queue for a fence value that was already reached (`GetCompletedValue` at the call) is satisfied: it never becomes a queue packet and cannot block, so it is counted and sets no state (fence values are monotonic; the one edge is a CPU Signal of a lower value, which can lower the completed value). Every unsatisfied `Wait` on the adopted queue is a Wait event: its enqueue time is read at the detour's entry, the original runs, and right after it returns the probe signals one value of its fence (the Wait fence), whose completion stamp is the Wait's release (the queue reached it, because the Signal is queued behind the Wait); the event carries the number of submissions issued before it, the entry QPC, the release value and the QPC after that Signal returned, the waited fence and its value; a Wait whose Signal was not issued (lock timeout or a failed Signal) carries release value 0. The gate reports ReLimiter's own hold `Wait` (and the frame generation input tickets') when it releases it (`GpuQueueProbe_OnHoldRelease`, from the CPU Signal of the time fence on the gate's worker, with the QPC at which the Wait was enqueued and the release QPC), a Hold event that pairs with the Wait event of the same fence and value; with the key off the gate pays a load and a branch at each of its two sites. On the adopted queue, for the outermost `ExecuteCommandLists` call, the probe takes a per-queue flag, reads the QPC (`enq`), lets the original run, signals the done value right behind it (before the Streamline handoff's own post-call work), and pushes one event into a bounded wait-free ring; there is no fence in front of a submission any more (the Wait fences replace it: a submission's start is derived from the releases of the Waits in front of it); nothing blocks and nothing is allocated. All probe fence values (done and Wait) are claimed and signalled under one lock, so the value order is the Signal order on the queue; a Signal that cannot take the lock within 50 µs (a QPC deadline) is lost and counted, and the boundary publication has the same bound. A second submitting thread finds the flag taken and goes through untouched: that call is a lost event for the core, is tracked until its native call returns (a boundary published meanwhile is `overlap`), and when a boundary fell between its entry and its return it also invalidates the frame it lands in. Every publication carries the session generation and is dropped when the session changed meanwhile. The rundown at the end of a session waits (bounded) for the in-flight submission, for the tracked contended calls, and for the boundary callbacks, hold releases and unsatisfied Waits, which are admitted into the session by a counter incremented before their session checks, revalidated against the session generation after admission, held through publication and released last; a Wait that returns after the session changed publishes nothing into the new one. Ordering between threads is a non-blocking protocol: a boundary is published between two increments of a sequence (odd while in progress) and is `overlap` when a submission is in flight; a submission records that sequence and the queue Wait sequence when it enters and when it leaves, and the number of Waits in flight when it enters, and is `overlap` when a boundary or a Wait could have fallen inside it; a Wait event is `overlap` when a submission was in flight or issued, or a boundary published, between its entry and its fence. The completion thread (TIME_CRITICAL, named) waits on one auto-reset event, the calibration event and a stop event, at most 100 ms, never on a poll of the fence; the fence values are registered on the event at least 32 ahead of the producer. Before it blocks it drains an event that is already set and reads `GetCompletedValue`; on a wake it reads `GetCompletedValue` again, then takes one QPC, and stamps every outstanding value up to the completed one: only the lowest value, after a wait that blocked, woken by the event, for a value that was incomplete when it was registered and when the thread was about to block, is event-awaited (lateness: the calibrated latency; a completion between that last read and the block, the thread being descheduled in between, is the residual case); every other value is a late pickup, whose lateness bound is derived from the entry QPC of the submission or Wait and the completion lower bound of the value before it; `gq_stamp_late_us` reports the maximum per frame. The calibration is the wake latency of a blocked thread: the worker arms a value of a private fence on the calibration event and blocks, the helper thread (normal priority, bounded timed waits on the stop event) takes a QPC immediately before signalling that value from the CPU, and the worker's wake stamp minus that QPC is a sample (it includes the Signal call, so it is conservative; a sample whose event was already set when the worker was about to block is dropped); 16 samples are taken 1 ms apart before the probe runs, then one every ~31 ms; the nearest-rank p95 and the maximum of the last 16 go to the core. The pure core (`gpu_queue_probe_core.h`) does the accounting; the thread drains it and pushes each finished frame record to the pacing telemetry and, when the queue law's feed is on (`g_gpu_queue_law_feed`, one load and a branch otherwise), to the law's feed (`GpuQueueLawFeed_Push`). The detours stay installed once installed (with the key off the probe's part is one load and a branch, and the thread ends within 100 ms). A changed adopted queue, a destroyed queue, key off or shutdown ends the session: the probe's calls stop, an in-flight one is waited for up to 200 ms, the helper is joined, the open frames are flushed incomplete, and the references are released once the GPU has reached the last fence value (retained when it has not). A device removal, or a failed Signal, fence, `SetEventOnCompletion` or hook install, ends the probe for the session with one log line. The cost summary is logged once per session when it ends (key off, shutdown, a failure, another queue) and, when the session's thread had not got to it, by the shutdown call itself: the boundaries, submissions (and submissions per frame), contended calls, the fences by kind (done, Wait release), the queue Waits on the adopted queue (satisfied and ignored, unsatisfied and fenced), the Waits on other queues (ignored), the fences lost, the ambiguous cases by reason, the frames emitted to the telemetry (the number joined to a row is the joiner's and not known to the probe), the invalid frames by reason (overlap, incomplete, untagged, lost events), the calibration and the core's counters. Expected for a game that submits about 47 packets per frame with about 9 unsatisfied queue Waits per frame: about 47 submissions, about 45 done fences and about 9 Wait fences per frame, one boundary per real frame.

Cost of `gpu_queue_probe`, measured with a throw-away benchmark (a real NVIDIA RTX PRO 6000 Blackwell, an idle GPU, empty command lists on one direct queue, no game and no Streamline pass except where stated; the figures are means unless a percentile is named): `QueryPerformanceCounter` 0.015 µs; `ExecuteCommandLists` of one empty list 0.08 µs; `Signal` 1.04 µs (p99 4.8 µs); `Wait` on a fence already reached 2.6 µs; `GetCompletedValue` 0.03 µs; `SetEventOnCompletion` 0.86 µs for a value 32 ahead and 0.97 µs for a completed one, with at most 64 registrations pending. The probe signals one fence value behind every submission (done) and one behind every unsatisfied queue `Wait` (Wait release), nothing in front of a submission: about 54 fences per frame for a game with 47 submissions and about 9 unsatisfied Waits (the measured figure for the earlier scheme with a front fence was 5.7 µs per submission and 251 µs per frame with 87 fences). In the benchmark a frame of 47 submissions with 54 fences costs the producer about 60 µs against about 11 µs without them, so the fences add about 0.05 ms per frame (about 1 µs per Signal; the ring push and the QPC reads are inside it); modelling the extra `ObserveSignal` pass of the shared detour (callback guard, depth, last error) for each of its Signals adds about 2 µs per frame. This holds only while no thread waits for the fence: with the completion thread registered and woken for every completion, the Signal call itself rises to about 7.5 µs (p50 6.5 µs) and the same frame costs the producer 0.42 ms (0.49 ms in another run), that is about 0.4 ms per frame more, four times the 0.1 ms budget; the live figure (5.7 µs per submission) is in that range. Registering without waiting costs 0.09 ms; waking the thread only every 2 ms brings the frame to 0.28 ms but the stamps are then 0.3 to 2.8 ms late; registering only the next value does not help (0.40 ms). The Signal lock the fences are serialised by is a bounded spin of at most 50 µs (a QPC deadline) that is paid only when another thread is inside a probe Signal (a hold of about 1 to 8 µs); a contender that exceeds it loses its fence (counted, the frame invalidated) instead of waiting longer. The wake latency of a TIME_CRITICAL thread blocked in `WaitForMultipleObjects`, CPU-signalled fence to event: p50 3.9 µs, p95 7.7 µs, max 16 µs when idle; p50 19 µs, p95 41 µs, max 74 µs with a submitting thread and four spinning normal-priority threads. For a GPU-signalled done value on an idle GPU, the completion thread's stamp minus the return of the Signal call is p50 9.6 µs, p95 48 µs, max 306 µs. The completion thread's own work per wake after the stamp is about 0.1 µs. Gaps: the GPU was idle (a busy GPU delays the completion, not the call), no game or driver load on the other cores, empty command lists, no real Streamline hooks; the larger cost with the thread waiting was not explained further than the Signal call getting slower while an event is registered and woken on the same fence, so whether it also appears under a game's load is unmeasured.

`gpu_queue_probe` ordering and cost details. Every probe Signal on the adopted queue (the done fence in the `ExecuteCommandLists` detour and the Wait-release fence behind an unsatisfied `Wait`) runs inside the queue hook's recursion suppression: the Wait-release Signal runs in the forward call of `ObserveFence`, before its depth guard ends, so neither `ObserveFence` nor the Streamline handoff sees it (outside the guard it would be an outermost application Signal, which the handoff takes for a repeated source Signal of the proxy Present and so invalidates the frame generation route); the calibration signals a CPU fence, which no queue hook sees. The probe is invisible to the handoff. ReLimiter's own hold `Wait` is announced to the probe (`GpuQueueProbe_OnHoldAnnounce`: fence, wait value, enqueue QPC) before the `Wait` is enqueued, so that a frame is not resolved before the hold's release arrives (`GpuQueueProbe_OnHoldRelease`, after the CPU Signal that releases it; the call also takes the plan's key and grid index, empty for the gate's own holds and given by the present-first unit for a frame its order was in effect for, see the order report below); the stamp the gate keeps for them is written before the ticket is published as armed and cleared when the ticket is freed, never at the release. Two `Wait` sections of different threads on the adopted queue that overlap (one still open when the other begins, or opened or closed between a Wait's entry and its fence) mark the Wait events they affect `overlap`, because the first Wait's fence could then measure the second's release; the core invalidates the frames. Each pushed frame record carries the probe's session generation (not in the CSV). Nothing else on a submitting thread waits on anything the completion thread or the driver can hold: the boundary publication wait is the same 50 µs bound, the rundown and teardown waits are on the completion thread only, and `GetCompletedValue` is a read.

`gpu_queue_probe` order report (the probe's answer to the present-first unit, `gpu_wait_present_first`). The unit tells the probe, never the pacer: the release of its order Wait on the render queue goes through the same `GpuQueueProbe_OnHoldRelease` as the gate's (fence, wait value, enqueue QPC, release QPC, from the unit's release thread after its lock) and carries two more arguments, the plan's key and grid index, which the gate handed to the unit with the hold. They are given only for a frame the order was in effect for: its order Wait went on the render queue, nothing of another thread's passed in front of it, the render queue stood at the Wait, and the Wait was let go because the Present had become runnable. Every other release, and every release the gate makes for its own holds, passes an empty key and 0. The identity travels in the Hold event into the core's hold record. When the core accounts the Wait that matches the hold it queues one report, the key, the grid index and the upper end of the Wait's release interval (the render queue passed the Wait at or before that time), if the accounting is valid for the frame: a known predecessor, every Wait of the submission trusted with a release marker, and a frame that is neither dropped nor overlapped. A hold without an identity, a release that never arrived, an untrusted or failed Wait marker (a lock timeout), an abandoned frame, a hold evicted from the pool and a lost ring event report nothing. The queue holds 32 reports; a full one drops the new report and counts it (`order_passed_dropped`, next to `order_passed_reported`). The completion thread hands what each drain accounted to `GpuPresent_PushOrderPassed` (every pass of its loop and the session's end, no lock held), which pushes the stage event `OrderPassed` for the plan (GPU queue wait rung, status unknown): the stamp the collision guard's start term reads as the render queue's resume. The report is not made at the release: it waits for the first read that saw the Wait's marker complete and for the accounting of the submission behind the Wait (frame closed, markers bounded, hold event in), so in normal play it comes about a frame after the release (not measured). It needs the probe on (`gpu_queue_probe`, forced on by the unified queue law) and the render queue adopted as role 3 (`gpu_queue_probe_source` 1, by the dependency rule): the announce and release calls return at once for any other queue, so with the probe off, the source at 0, before the adoption or with another queue adopted, the unit still orders and nothing is reported (the start term then has no telling pair). The unit's ten-second line ends with a count, still labelled "Presents told to the pacer as processed": it is the number of releases that carried an identity to the probe, not of reports (the probe may report fewer, or none).

`gpu_queue_probe_source` (developer live key, 0 or 1, default 1, 64-bit; effective only with the probe on). Without frame generation the probe watched the queue of ReShade's present event, which is not the render queue where Streamline's swapchain proxy makes the presenting queue a separate queue: it submits a few command lists per frame and Waits once per frame on a fence the main render queue signals, so the probe's GPU side was the proxy's copy queue. At 1 the probe finds the queue by a dependency rule (`src/gpu_queue_dependency.h/.cpp`, pure). The shared queue detours record, for every queue and only with the key on, its outermost `Signal` (fence, value, queue, QPC), its `Wait`s (queue, fence, value, QPC, thread; for a Wait of the presenting queue on the Present thread the id of the Present scope it belongs to: the scope between ReShade's present event and finish_present, or the next one when the Wait was enqueued in front of it, as when the swapchain proxy waits for the render queue and then calls the native Present) into two tables of 512 entries each, and its command lists (eight queue slots); ReLimiter's own Signals and the probe's own run nested in the detour and are not recorded. The tables serve the adoption decision, not the per-frame record, so they are plain arrays behind ONE small spin lock (`Tables`), and EVERY path that takes it, on any thread, takes it with the same bounded spin (`Tables::kSpinBound` = 512 test-and-set iterations with a pause, never a kernel wait; there is no unbounded acquisition): the Signal, Wait and Execute detours (game threads) DROP and COUNT an event that does not get it (`events dropped on a lock time-out` in the summary); the evaluator's pull is SKIPPED and COUNTED (`pulls skipped`); a decision publication that does not get it is DISCARDED and counted (`decisions discarded`, `lock time-outs`); a clear is never lost (below). The evaluating thread, the detours' game threads and the probe thread all use the one bound (a pull or a publication holds the lock for a short copy or a few instructions, so a time-out is rare and the cost of one is one frame's evaluation deferred, not a stall). Cost per Signal or Wait detour call with the key on: uncontended one interlocked exchange, one epoch load, the record write and one release store (about 20-30 ns; an Execute of a queue whose row exists takes no lock, see the per-call cost paragraph below); worst case the spin bound (a few microseconds up to roughly 20 on a CPU with a long pause instruction), after which the event is dropped. With the key off (or the probe off) the lock is never taken: the call sites are one relaxed load and a not-taken branch, and queue destruction (which clears) is gated on the probe being on, the key being on and something having been recorded. ONE epoch (`Tables::Epoch`, distinct from the frame counter entries age by) is advanced by every clear (swapchain, presenting queue or queue lifetime change, any destroyed queue, the key turned off at teardown), which may run on a game thread (the thread that releases a queue) or the probe thread: `Clear` advances the epoch at once with an atomic add every reader sees and resets the tables if the lock comes free within the spin bound; otherwise the reset is a pending clear (`clears applied later`): the next successful lock holder, a detour writer or the pull, notices that the epoch it holds the tables for is behind and resets the tables before its own work, once, so a clear is neither lost nor repeated. A published decision carries the epoch it was computed for and is valid only while that epoch is current, so a clear invalidates it at once, before the tables are reset. A window whose epoch changed restarts and adopts nothing. An evaluation never runs under the lock: `Reader::Pull` copies only the entries recorded since its previous successful pull (about 512 at most; more than a table holds between two pulls are counted as lost) and the command list rows under it, then the resolver and the evaluator run on that copy, and the lock is taken again only to publish the decision; a submitting thread's detour never waits behind an evaluation. A skipped pull keeps per-frame resolution exact: the cursors do not move, the frames stay in the consumer's backlog (eight frames, each with its own scope, window and key), and the next successful pull, which copies the entries of every frame since the previous one (none lost, none twice), resolves the backlog in order with each frame's own scope and window, so a frame is never evaluated with a part of its Signals missing and never counted as having zero; eight skipped pulls in a row restart the window (`backlog overflows`). A window in which any Signal, Wait or command list record was dropped or lost (a lock time-out, a queue beyond the eight rows, entries overwritten before they were copied) does not qualify for any queue (reason `records were dropped or lost`): the loss counter is snapshotted BEFORE the window's first frame (the value the previous frame carried), so a drop inside the first frame counts, and a lost record can never hide a second boundary or change the winner. A pull that finds new loss poisons every window any affected frame belongs to (`Evaluator::BeginPull(loss, pending_frames)`): the loss belongs to a frame that was current when the pull saw it (its events were not all recorded, the NEXT pull resolves it, production's one-frame lag) or to a frame still waiting for resolution (a backlog can cross a window boundary), and one counter cannot tell them apart, so each of the next `pending_frames + 1` frames resolved, the backlog and the one current at the pull, poisons the window it belongs to, and the poison outlives the pull that saw the loss. Each frame is resolved once the following Present's boundary (the readiness site) has pushed it: the presenting queue's Waits of that Present scope, each matched to the Signal of the SAME fence and value (not the newest Signal of the fence) by another queue, add that queue; its Waits inside the frame's window add the next (3 hops at most); a fence no other queue signals (a CPU or kernel sync object) ends the branch, a (fence, value) signalled by two queues is counted as an ambiguous Signal (and as an ambiguity of the join when it is one of the presenting queue's own Waits). Fence lifetime: no hook on fence release and no fence is retained (an AddRef while a table entry names the fence would delay a game that waits for the fence's reference count or reports live objects at device teardown). Instead a Signal joins a Wait only with the same fence address and value, recorded within two windows of 64 frames of now and within 4 frames of the Wait, and the tables, counters and window are cleared on a swapchain, presenting queue or queue lifetime change (a session watching by the rule is stopped). Accepted residual risk and why it cannot adopt a wrong queue: a fence pointer reused for a CPU-signalled fence joins a stale Signal only when the reused address carries the same value within 4 frames; that adds one edge in one frame. Adoption needs one Signal and one first-hop edge on the same fence in every frame of a 64-frame window (and the dependency queue reached in every frame), so a false join can at most make a window not qualify (the law then runs on its fallback for that window), never adopt a different queue (tested); the argument also rests on the core invalidating the frame after an irregular boundary (a boundary or tag that does not match, counted as `irregular_boundary_events`), so a split frame is never reported as valid. At the end of a window of 64 frames the candidates reached in every frame are compared by command lists per frame: the most wins, a tie (among the dependency candidates, or with the presenting queue) and no dependency give the presenting queue (adopted at once, role 1, the boundary at the readiness site as before). A queue reached in only some frames of the window with AT LEAST as many command lists as the best full candidate (a tie included) leaves nothing adopted for the window (`NotQualifiedPartial`: its dependency is missing or ambiguous in the other frames, a lost Signal, a false or ambiguous join), rather than falling back to a queue with less work or letting an equally busy full candidate win; a partial candidate never wins. A winner that is not the presenting queue (role 3, `render queue by dependency`) is adopted only when its boundary can be joined to the frame identity: it is one hop away, the presenting queue reaches it through exactly one dependency (fence, value) per frame (a deeper queue may be reached through several: a multiple dependency, not an ambiguity), always the same fence, the adopted queue Signals that fence exactly once per real frame (EVERY Signal of that fence by that queue between the previous frame's matched Signal and this frame's, whatever its value, is counted, so a repeated Signal of an older value is seen; otherwise a frame would be split by its Signals while only one is waited on), the matched value rises from frame to frame (a separate check), and the presenting queue's Wait of it belonged to the Present scope of a Present that carried the frame's key every frame. Otherwise nothing is adopted: the probe reports no frames (the law runs on its report fallback, not on the presenting queue), one log line per transition names the reason. For role 3 the frame boundary is the adopted queue's own `Signal` of the dependency fence (a boundary event with the value as its id and no identity) and the presenting queue's `Wait` of the same fence and value pushes the tag (generation, present sequence, key; at the Wait when the Present's identity is known, else at the readiness site); the core defers a frame until its tag arrives. Each boundary and tag reads the session generation before its role, fence and queue checks and is checked again after admission into the session (session generation, role, fence, queue), so a call that paused in between never publishes into a replacement session. The decision is re-evaluated at window ends only: another queue wins, the dependency disappears or an unjoinable winner stops the session (the session generation changes, the law's window restarts) and the next window decision is adopted without further hysteresis. An adoption continues otherwise: the destruction of a queue that is neither the adopted nor the presenting one restarts the evaluation window (the epoch advances) but does not retire the adoption, because it says nothing about the adopted queue, whose boundary and tag mechanism does not use the tables, so its samples stay valid and stopping the law's feed for a window would disturb pacing for nothing; the adoption lasts until a completed window decides otherwise or the adopted queue, the presenting queue or the swapchain goes away. With a frame generation input adoption is unchanged (role 2); the rule is evaluated at the readiness site of those Presents for a diagnostic and logged once when its answer differs from the adopted source queue. The held output of the gate stays on the presenting queue: its announce, release and enqueue calls are no-ops for any other queue (no pool entry, no deferral), so a role 3 record's hold_block is only ReLimiter's own order Wait on that queue (present-first ordering, announced by `gpu_hold_order.cpp`; 0 without the order), which the queue law takes out of the sample's cycle, and the law uses its report-based rule for the credit there (`queue_role`, CSV `gq_queue_role`). The hold's announce (`GpuQueueProbe_OnHoldAnnounce(native_queue, fence, wait_value, wait_enq_qpc, law_hold_sequence)`) carries the sequence the queue law assigned to the grant of the hold (0 = not a law hold; a zero-length hold never has one) and the core attaches the sequence of the hold a frame was queued behind (the hold that gives its hold_block) to that frame's record (`law_hold_sequence`, not in the CSV; 0 when no hold matched or the hold had none), whatever the record's valid bits, so the law can settle an invalid or irregular frame's hold. A teardown with nothing ever recorded (the key never on) clears nothing and writes nothing. Log: the adoption line names the role, the hops and the command lists per frame of each candidate; the per-window line and the session summary give the windows, the frames evaluated, the frames with an ambiguous join (the presenting queue's own dependency: a first-hop queue reached through several (fence, value) pairs, or one of its Waits signalled by two queues), the frames where a deeper queue was reached through several fence values (a multiple dependency, not an ambiguity), the frames with a missing join, the frames with the dependency fence not Signalled exactly once, the records dropped or lost in the window, the Waits no queue signals, the ambiguous Signals, the events dropped on a lock time-out per table and for command lists, the queues beyond the rows, the decisions discarded (a changed epoch or a lock time-out), the Present thread pulls skipped, the backlog overflows, the clears applied later by the next lock holder, the boundaries and tags pushed and the core's join counters (`join_ambiguous`, `join_missing`, `untagged_boundaries`, `tags_unmatched`, `irregular_boundary_events`, `frames_invalidated_by_irregular_boundary`). Open points: a winner two or three hops from the presenting queue cannot be joined (only the presenting queue's Wait has the Present's identity) and is reported as not adoptable; whether the proxy's Wait is enqueued on the Present thread (inside or in front of the Present scope) is not verified: a Wait of another thread has no scope and shows as a missing join; the frame of an evaluated Present is assigned by Present scope for the presenting queue and by the time window between two readiness sites for the others, which is approximate for deeper hops; a game with more than eight queues loses the command lists of the rest (counted as overflow, so no window qualifies); any destroyed queue restarts the evaluation window (the epoch advances); the first frame after a reset has no previous edge to count Signals against; the first 64 frames of a session carry no data (the window).

`gpu_queue_probe_source`, pending frames and counts (refinements of the paragraph above). The evaluator's mirror of the tables keeps the newest 512 entries of each; before every pull it is told the oldest time an unresolved frame still needs (`Reader::SetNeededSince`: the oldest pending frame's window begin, or the previous edge's Signal when that is older), and a full mirror overwriting an entry at or after it counts that as loss (a crowded game with hundreds of Signals per frame would otherwise lose the early extra Signal of the frame being resolved and let a window with two dependency Signals per frame qualify): the pull that evicts it poisons the frames it resolves and the current one like any other loss. A backlog overflow (eight skipped pulls) restarts the window but keeps the previous successful pull's loss baseline (`Evaluator::pull_loss`), so loss the overflowing pull discovers still poisons the retained frames and the current one. The command list counts of a window are the difference of boundary snapshots: each frame carries the command list counters of its own boundary (one bounded locked copy taken when the boundary pushed it; `Evaluator::CountAlign::Exact`), a window starts where the previous frame ended and ends at its last frame's snapshot, so a burst in the window's first frame is counted and a pull-time count that includes the next frame's work is not. The first frame after a reset (or an epoch or presenting queue change) is a BASELINE only: its end counters and first-hop edges seed the next frame, it is not one of the window's frames, and the 64 frames that follow are evaluated, so the first window divides by 64 over 64 frames like every other (a poison that touches the baseline frame carries to the first window). A frame whose boundary snapshot did not get the lock takes the counters of the pull that resolves it (`Inexact`): EVERY such frame poisons its window, an interior one too, and the window that starts after it does not qualify either (reason `records were dropped or lost`). Adoption acts on one immutable copy: the Present thread that holds the evaluator guard copies the decision (queue, role, fence, hops, candidates) together with the published queue into a `dq::AdoptionSnapshot` before it releases the guard (`MakeAdoptionSnapshot`, valid only for the published, current, adoptable winner), and `Boundary` and `Adopt` use only that copy (never a later read of the evaluator's decision, which another Present thread may reset on a lifetime change); a Present thread that did not take the guard has no snapshot and adopts nothing that frame.

`gpu_queue_probe_source`, the rule's own per-call cost and where it evaluates. Detour side. `Tables::NoteExecute` (every outermost Execute of every queue) takes no lock when the queue's row exists in the current epoch: it loads the epoch, the row count, the row's queue word and its packed counter word `[tag:20 low bits of the epoch][calls:16][lists:28]` and adds the call with ONE compare-exchange (at most `Tables::kFastAttempts` lost races, then the locked path). The tag makes the add fail against a row that a clear re-created for another queue, so an add of one queue never lands in another queue's row (a caller that loaded the epoch before a clear is ordered before it: its add lands in a row the reset discards); a pending clear (epoch advanced, tables not reset yet) sends the call to the locked path, which applies it first; a field about to overflow (65535 calls, 2^28 lists, one call above 2^28) is spilled into the exact 64-bit base counters by a lock holder, so `Row::lists` and `Row::calls` seen by `Reader::Pull` and `Tables::SnapshotRows` stay exact and unbounded. Anything new (a queue's first Execute in an epoch, a ninth queue, a spill, a pending clear) takes the old bounded-spin locked path, where the drop-and-count rules are unchanged (`DroppedLists`, `RowOverflow`); a known row never drops, so a window loses few records under a held lock. Cost per Execute: four loads, a scan up to the queue's row and one compare-exchange, no lock (the locked path costs one interlocked exchange, a row scan of up to eight rows, two stores and a release store). `RecordSignal` and `RecordWait` keep the lock on purpose: they log EVERY Signal and Wait (the resolver matches (fence, value) and counts every Signal), cost one interlocked exchange (the lock), the entry write and a release store, no row scan, and a claim-and-write ring would still need a second read-modify-write to keep a writer that was preempted across a clear and a lap from tearing a newer entry. Evaluation. The Present thread's part per real frame is `DependencyBoundary` (`FrameFeed::OnBoundary`): the scope's identity and tag push, the three-boundary ring, the frame the Present closes with the command list counters of its own boundary (`Tables::SnapshotRows`: one bounded locked copy of at most eight rows, inexact when the lock does not come free) and the loss counter of that moment (`Tables::Lost()`, lock-free), pushed into a bounded queue of `FrameFeed::kBacklog` (8) frames. The evaluation (`FrameFeed::Evaluate`: the pull of the tables, `ResolveFrame`, the evaluator, the publication, `DependencyOnDecision`) runs on ONE thread at a time (the evaluator guard): the probe's worker at the end of every step (`DependencyDrainOnWorker`, outside the step's timing) while a session runs; in every other phase (no session before the first adoption, starting, stopping, dead: there is no worker) the Present thread itself, right after its boundary (`DependencyEvaluateAfterBoundary`), so the rule works before any worker exists and the first adoption is decided by the Present thread's own evaluation; while a session runs the Present thread evaluates only when `FrameFeed::kHelpAt` (4) frames wait (the worker blocks up to `kWaitMs` between wakes). No new thread. Nothing is pulled when no boundary is new. The windows of 64 frames, the loss handling (a batch of frames is resolved as one pull at the Present that pushed its last frame: that Present's loss counter, poison of the batch plus one frame, counters of each frame's own boundary, the frame counter its entries age against taken at its Present), the epoch/clear protocol, the retain gate and the adoption snapshot taken under the evaluator guard work as described above, whichever thread evaluates; frames of an older generation or older tables epoch are discarded, never evaluated against cleared tables. A producer that finds the 8-slot queue full drops that frame and the window restarts; it needs a consumer eight frames behind. Tests (`tests/test_gpu_queue_dependency.cpp`): the Execute fast path against a model of the locked path under a randomised script and under concurrent writers with clears (never mixes queues, exact sums, exact spill), and `FrameFeed` against the per-Present evaluation modelled by `PullHarness` and against itself evaluated every 2, 3 or 7 Presents and on another thread. Only a game shows the per-call cost on the submission thread and the marker thread.

`gpu_queue_probe_source`, running adoption and queue lifetime (refinements). A window that does not qualify carries no evidence and changes nothing: while a queue is adopted it keeps the adoption (session, role, records and the law's feed continue, no stop, no role change; `dq::ApplyDecision` returns `KeepUnqualified`); only a QUALIFIED window with another result (another queue, role or fence) stops the session to adopt the new one, and the adopted queue's destruction, or the presenting queue or swapchain going away, ends it. Without an adoption an unqualified window adopts nothing. Such a window is logged at most once per session (info) and counted (`windows that did not qualify while a queue was adopted` in the dependency summary). The queue an adoption acts on is held by an owned reference taken together with the lifetime check: the Present thread that holds the evaluator guard copies the decision and takes the reference (`dq::RetainGate::RetainAtEpoch`: counted in flight, epoch re-read, then the AddRef) into an RAII ticket released on every exit path unless the session takes it over, and the queue's destroy callback (which runs before its final native Release) advances the epoch FIRST and then waits, bounded (2048 pauses; `queue destructions that stopped waiting` counts a give-up), for retainers inside that window, so a reference taken at the decision's epoch is on a live object and a queue destroyed since is never touched. If the wait gives up (a retainer descheduled inside its few-instruction window), the destroy callback takes one native reference of the queue itself and NEVER releases it (`dq::RetainGate::WaitOrLeak`): a deliberate, counted leak of one object (the references leaked are in the dependency summary), so the retainer's later AddRef always lands on a live object. With the source rule on, a boundary without a valid ticket adopts nothing (except the frame generation source, role 2), so a running-only call that finds the session idle after a stop cannot adopt the presenting queue with role 1. When the adopted queue is destroyed the law's session is retired explicitly (`GpuQueueLawFeed_RetireSession` with the session generation: the scheduler's drain empties the law's window, settles its outstanding grants and drops records of that session that are still in flight).

`gpu_queue_probe` borrowing the game's own marker (role 3 only: the render queue found by the dependency rule; roles 1 and 2 are unchanged and never take the path; no key). The probe's done marker of a submission is, by default, a Signal of its own fence issued behind the `ExecuteCommandLists` call (42 per frame in a measured game, about 0.3 ms per frame on a submission thread that is the limit). When the game itself queues a Signal directly behind every submission, that Signal is the same marker for free, and the probe only binds (fence, value) to the submission. Code: the pure rules in `src/gpu_queue_borrow.h/.cpp` (tested by `tests/test_gpu_queue_borrow.cpp`), the glue in `gpu_queue_probe_d3d12.cpp` and the Signal/Execute hooks of `streamline_queue_hooks.cpp`. The core stays keyed by the probe's own value sequence k; borrowing only changes who marks k and what the worker waits on. Mechanism: with borrowing active an Execute leave claims k without a Signal and publishes it as `pending` (a word holding k, the thread and a borrowed bit, plus a per-k slot for the worker); the Submit event is pushed when the pending marker is settled. The game's outermost Signal on the adopted queue binds it (the Signal detour calls `GpuQueueProbe_BorrowSignal` right before forwarding, after the Streamline handoff's own calls) when it comes from the same thread, of the one fence the last whole frame used, with a value strictly above the last bound value (a Signal of another fence in between does not matter). Whatever reaches the queue first instead (an Execute enter, nested ones included, a Wait, the role-3 boundary, a claim of another probe value, another Execute that entered since this one or an open Wait at the leave) SETTLES it before that call is forwarded: the probe's own Signal for k, issued under the Signal lock so a lower value is never signalled after a higher one, the frame invalid (the Submit event carries `overlap`), borrowing off until a whole frame shows the pattern again; a compare-exchange on the word gives exactly one winner between the bind and the repair, and a settle that cannot get the Signal lock gives the value up (the worker skips it, the submission is pushed without a done). A frame borrows only when the previous frame was whole: every submission followed, before the next Execute or Wait, by a same-thread Signal of ONE fence with strictly increasing values, and no Signal of that fence from another queue seen by the dependency tables (an optimisation gate, not proof: the pending protocol keeps a wrong guess harmless); the session starts with the probe's own Signals. The first bind takes ONE reference on the game's fence (the dependency tables never retain one: this is the single, documented exception), released by the worker with the session on every end path (session end, queue destruction, another adoption, failure). The worker arms an event on that fence with ONE registration outstanding per fence and waits for the newest marker only, own or borrowed (the tail stamps paragraph below); a borrowed marker issued more than the stamp guard after the Execute returned, or completed within the guard of its issue, is a late pickup (the core's existing late bound); one found complete BEFORE it was issued (someone else advanced the fence) has an inconsistent interval: the core makes it untrusted, its frame is invalid and the done chain breaks there. Waits' release Signals stay. The probe's own Signals now call the original method directly (they no longer re-enter the Signal detour, nor appear in the dependency tables). Counters in the summary line `GPU queue probe borrowing:` (marked by the game / the probe, repairs by reason, frames on the game's markers, frames invalid by a repair, late markers, completions before their issue, registrations on the game's fence, references taken and released); two info lines: when borrowing first becomes active and when it is turned off for the session (with the reason). The per-frame count of borrowed submissions is `PacingGpuQueueRecord::borrowed_submits` (CSV column `up_ql_rt_spread_us`, 0 when the probe marked all). Hardened rules. (1) Another queue signalling the pattern's or the bound fence (the dependency hook, BEFORE the Signal is forwarded; `BorrowForeignSignal`) ends borrowing for the SESSION: when a borrowed marker can be affected (borrowing active, a word pending, or a borrowed value the worker has not stamped), under the Signal lock the gate goes off and the foreign epoch rises, a pending word is settled with the probe's own Signal, and an `Invalidate` event invalidates the frame in progress and the one still open to a tag; every marker CLAIMED before the epoch rose is untrusted (the core makes a marker whose claim epoch differs from the epoch of an observation untrusted wherever one is applied, and the worker hands the rest to the core with `OnUntrusted`), so its frame is invalid and the done chain breaks there. The reason is logged once and counted in the summary line. A CPU `ID3D12Fence::Signal` of the game's fence is not observed; the bind-time check of the tail stamps paragraph below and the core's inconsistent-interval rule are the guards against it. (2) A marker between its Execute and its Submit event is visible to a boundary: writers that take the pending word (a bind, a repair, a claim's settle) raise `InFlight` BEFORE the take and drop it after pushing the Submit, and a boundary overlaps (like a busy Execute: both frames invalid) when the word is pending or a writer is in flight (`MarkerInFlight`: word first, then the count). (3) Slots: the producer claims a borrowed marker only when the worker has read the value that used the slot (`SlotAvailable`, the worker publishes its cursor); otherwise the probe's own Signal marks the value, the gate goes off and `slot reuse refused` counts it; a slot found reused by the worker (`KMode::Overwritten`, a breach) is untrusted and consumed at once (its frame invalid), never taken for an own marker, so the cursor always advances. (4) An untrusted marker whose Submit has not been processed yet is parked together with its bounds in ONE entry (64 entries; a full table drops the smallest k as a watermark, and every k at or below it without an entry is untrusted, counted, never dropped silently) and applied when the Submit arrives. (5) A value that completed before its registration has no event and calibration wakes restart the wait, so the worker runs its step on EVERY wake (event, calibration sample, timeout, stale event) and after every (re)registration, a refused one too, not only on event wakes. (6) The binding of the game's fence is closed for good by the session end (`BoundFence::Release` from any state; Closing/Released are terminal): nobody spins; a binder that is inside its retain when it closes releases its own reference when the AddRef completes (the only Release on a game thread); a second binder meeting a binder in progress gets `Busy` and its marker is settled with the probe's own Signal. (7) The claim publishes its pending word BEFORE the Signal lock is dropped (and settles a previous word under the lock), so an unsatisfied Wait on another thread can only signal an own value after the repair of this one: own values reach the queue in order. (8) Before a reference is held a whole frame only NOMINATES the fence (by address); the first observed marker of the nominated fence takes the ONE reference (a game thread AddRef, once per session) and makes the frame in progress unclean, so the whole frame that starts borrowing is of the object actually bound (a destroyed fence and a new one at the same address cannot pass as one candidate). (9) The pending word holds the full 32-bit thread id (`k` has 31 bits: past 2^31 values in a session nothing is borrowed any more). Live validation still needed: that the pattern holds in the game, the cost on the submission thread, and the equality of the records with the probe's own Signals.

`gpu_queue_probe` tail stamps. A queue runs empty only when its newest item completes, so the worker waits for the NEWEST marker only and everything else is known as an interval. Marker sequence: one sequence in probe order k across both fences (the game's borrowed Signal behind a submission, and the probe's own Signals behind unsatisfied Waits, holds, repairs and as the fallback marker); own k and game fence values are different namespaces and always go through the slot mapping. Observations are free: (completed value of the game fence, completed value of the own fence, QPC before the reads, QPC after) taken on the submission thread at every Execute enter and Wait begin on the adopted queue (`ObserveInto`: two user-mode `GetCompletedValue` reads and one extra QPC read, no lock, no allocation, no kernel call; role 3 reads both fences, roles 1 and 2 the own fence) and carried inside that item's Submit/Wait event (`obs_*` fields) so the core applies them in ring order, and by the worker at every wake and after every registration. Worker step (`gq::WorkerStep`, the pure planner in `gpu_queue_borrow.h`, driven by the worker loop in `gpu_queue_probe_d3d12.cpp`), at every wake (armed event, calibration, timeout, stale event) in this order: read T (the newest marker whose (fence, value) is fully published, never a reserved slot), take an observation, give the ARMED marker (stored explicitly: fence, value, k, session generation, registration QPC) its awaited interval only when it is covered and the wake is its own event (any other wake certifies nothing: the armed marker gets an observation interval like the rest), every other newly covered marker gets `[latest QPC it was seen incomplete, this observation's QPC]`, then register: ONE outstanding registration per fence, never re-registering a fence whose registration has not fired; with a marker pending arm T on its fence, drained arm completed+1 on each fence's event; observe again after registering and, when the armed value is already covered, treat it as a late pickup and go round again without sleeping (bounded number of immediate rounds per wake). Every wake, calibration included, and every (re)registration, a refused one too, runs the step first. The core (`OnObservation`, `OnAwaited`, `OnUntrusted`) evaluates the unchanged accounting walk on intervals: scalar fields keep their names and carry the lower ends, `empty_hi_us`, `boundary_idle_hi_us` and `min_margin_free_hi_us` the upper ends; an untrusted marker (foreign Signal, overwritten slot, lost marker) invalidates its frame and breaks the done chain until a trusted completion. A slot is consumed once its interval is closed (the worker pins no slot waiting for a stamp). Another queue's Signal of the bound game fence (or of the nominated pattern fence before the reference is taken) ends borrowing FOR THE SESSION (the hardened rules of the borrowing paragraph above); every borrowed marker claimed before the foreign epoch rose is handed to the core as untrusted when the worker closes it. Counters in the summary line `GPU queue probe borrowing:`: registrations on each fence, worker wakes by cause (armed event, late pickup, calibration, timeout, stale event), markers awaited against markers closed by observation, untrusted markers, the core's parked-table watermark hits. `PacingGpuQueueRecord::registrations` is the number of registrations the worker made since the previous record was popped (CSV 190 high part). Per submission the hooks add: role 3 with a bound fence one game fence read, and the own fence read only while an own marker is outstanding; roles 1 and 2 one own fence read; the clock reads as below; no lock beyond the existing sequencing lock, no allocation, no kernel call. Clock reads: ONE per hook entry. An Execute and its borrowed Signal read the clock twice in all: the enq at Execute enter (also the observation's `before`) and the game's Signal hook's entry read (`GpuQueueProbe_Now`, taken once in streamline_queue_hooks.cpp), which the bind uses as the marker's issue time AND as the observation's `after` (stamped when the Submit is pushed, so it is later than the fence reads by the Execute's own duration: a valid, looser upper bound) and which the dependency observer uses as its table time (it takes none of its own). A borrowed Execute leave reads no clock; an own marker reads one at leave (the issue lower bound before the probe's own Signal, also the observation's `after`). An unsatisfied Wait reads the clock three times: the detour's entry (shared with the dependency observer; the Wait's enq and the observation's `before`), the observation's `after` and the release Signal's issue time; a satisfied one reads none of its own. The probe's own fence is read at Execute enter only while an own marker is outstanding (`own_issued` above `own_seen`, what the producer last saw complete); the game fence read stays; one `GetCurrentThreadId` per Execute and Signal pair. The hooks keep no per-section cost counters or per-frame cost marks (timing the Leave section would take two clock reads and a dozen stores per submission and never covers the Enter observation); the hooks' cost is measured by the benchmark and by profiles. Statistics are not counted on the bind path (`marked_game` / `marked_probe` are counted by the worker from the slots, the frames on the game's markers from the popped records' `borrowed_submits`). Kept per submission, each for its protocol: `submissions_total` (the race check: another Execute's enter between this Execute's enter and leave), `busy` (the producer flag and the boundary's in-flight read), the Signal lock exchange (the sequencing lock: the claim and the pending word are published under the sequencing lock), the callback admission pair (the closing handshake: the rundown waits for it), the `binds_inflight` pair and the pending word's compare-exchange (the in-flight bracket: a boundary sees a marker in flight; exactly one winner of the word), the pattern tracker's counters (the gate's whole-frame test), the core ring's occupancy and head claim (the multi-producer bound). Every observation carries the foreign epoch read after its fence reads and every borrowed Submit its claim epoch (the core checks them wherever an observation is applied). When the session rundown times out (`detour_left` false) the reference on the game's fence is NOT released: it is retained with the queue, the device and the probe fence and the session goes dead; no bind can open (the active queue is cleared). At the bind, a borrowed marker whose own Execute-enter observation of the game fence already stood at or above the value being bound (a CPU `ID3D12Fence::Signal` by the game, or another writer, before the Execute) is foreign-writer evidence: the winner of the pending word (which owns the slot while it is Pending: the saved observation is read only by it, the Submit is built whole in a local before the slot's value is published, and pushed without touching the slot again) pushes the marker as usual and ends borrowing for the session through the foreign-Signal path (epoch up, so the marker is untrusted when the worker closes it; frame invalid; Invalidate event), and the core makes such a marker untrusted by itself when it sees one. Slot ownership (the comment above `BorrowSlot`): a slot's plain fields and claim metadata are read only by the claim that initialises it and by the one thread that took its pending word, and only while its value is Pending; every taker (bind, settle, lock-timeout loss) builds its whole Submit into a local before it publishes a non-Pending value and never touches the slot afterwards; the worker reads only the atomics of slots above its own consumed cursor (the tail read returns an unknown tail at or below it); `binds_inflight` and `callbacks_inflight` are visibility for the boundary and the rundown and pin no slot. Layout by writer: the probe's globals are laid out in cache lines by the thread that writes them, each group starting on a line of its own (`alignas(64)`) and checked by `static_assert`: `g` (gpu_queue_probe_d3d12.cpp: S0 read-mostly gate state written at adoption only, S1 cold session handles, S2 the producer's call-order counters, S3 its rare statistics, S4 the submission being taken, S5 the sequencing lock and value counters, S6 the Wait hooks' counters, S7 the boundary thread's, S8 the worker's, S9 the calibration helper's), `bw` (B0 the gate, B1 the bound fence and the foreign epoch, B2 the pending word, in-flight count and pattern tracker, B3 the slots, B4 rare hook statistics, B5 the worker's), `dep` (the tables' own groups in `Tables`: lock, read-mostly epoch / row count / decision, rows, logs, counters; then the read-by-every-hook scope state, the boundary's and the evaluator's) and the ring of `GpuQueueProbeCore` (producers' occupancy and head, the rarely written drop counter, the slots, then the consumer's state). The Wait hooks' statistics (`waits_seen`, `waits_satisfied`, `waits_ignored`, `fences_wait`) are counted per thread and added to the totals in blocks of 64 (the summary line is short by the unflushed remainder). The locked instructions left per submission each have a protocol: `submissions_total` and `busy` (the race check), the Signal lock (the sequencing lock), the callback admission and in-flight pairs (the closing handshake and the in-flight bracket), the pending word's compare-exchange (one winner), the tracker's value compare-exchange (monotonic gate), the ring's occupancy and head (multi-producer bound) and the dependency table's lock on a Signal or Wait record. Frame boundary markers: the last submission of a frame is no tail while the next frame's work is queued behind it, so the cycle would inherit its lateness; the worker therefore also waits for the OLDEST OPEN FRAME BOUNDARY's closing marker (`GpuQueueProbeCore::OldestOpenBoundaryMarker`, read after the drain and before the observation, passed as `WakeInput::boundary`; it may sit on either fence, armed on its own fence, one registration outstanding per fence) and `SetArmed` tells the core which markers are armed so that an armed marker is accounted only after its wake was processed. The awaited interval's bound is the MAX of a 256-sample trailing window of the wake-latency calibration (`GuardTicksOf`, floored at 20 us; the start burst still takes 16 samples), the Wait guard keeps p95. The per-session event handles are REUSED when no registration of the ended session can still fire (`ClassifyEvents`: every registered value reached; the probe's own fence is CPU-signalled to its outstanding value once the GPU has caught up, the game's fence never); only a registration still outstanding on the game's fence retires that one handle unclosed (a leak in that rare case only). Live validation still needed: the pattern and the registration count per frame in the game, the submission thread cost, record containment against the probe's own Signals.

The per-frame probe record protects itself against an irregular boundary sequence (a boundary that expired untagged, a boundary id lower than one already seen, a second boundary with one id, a tag for a frame that already finished, a tag whose boundary never appeared): each such event clears every valid bit of exactly one following emitted frame, because its cycle and occupancy span the broken frame, and is counted in the probe summary (`irregular_boundary_events`, `frames_invalidated_by_irregular_boundary`).

Sleep status instrumentation limit. The game's own `NvAPI_D3D_GetSleepStatus` calls are observed (for `driver_sleep_interval_us` and `driver_use_game_sleep`) only while `developer_settings` is on; with it off the hook only forwards and logs the call and does not touch the feedback device, and the two columns stay empty. The observation takes its feedback-device snapshot without waiting and without draining retired device references, so with it on, a retired reference may be released late, at the next draining acquisition (a marker or Sleep hook) or retirement; at device loss or shutdown it can stay retained until then.

Unified pacer. The pacer that paces 64-bit games; code in `src/unified_pacer.h` and `src/unified_pacer.cpp`, the Sleep hook and the Sleep-mode tuple in `src/nvapi_hooks.cpp`. It is no setting: the owner `unified` is derived (64-bit and the effective `pacing_test_mode` `off`, see [Pacing test mode](#pacing-test-mode)), and while it paces the pipeline uses the fixed values above (the output point resolved, 99% lead coverage, the lead spike floor and FG late-frame spacing on, the render queue kept); the frame interval I(n) is the largest of the cap's interval (the idle interval under an idle cap), the VRR ceiling's, the game's own Sleep-mode interval and the GPU term, each times the frame generation factor; the source placement is `unified` while the game calls the Reflex Sleep, else `marker`, never the driver limiter. The output point is limited only by the physical blockers (Present route, architecture, API, fixed refresh, no native route, frame generation qualification). ReLimiter manages the Sleep-mode parameters the driver sees (low latency off, interval 0; with Dynamic MFG the game's own). The status file has `unified_driver_pacing` (1 while the self-check sees the driver's own Sleep pacing, flag `2048`) and its `placement` reads `unified`. The pacing CSV has the twenty-three `up_` columns (142–155, 171–176 and 180–182, below).

The status file also has `cross_thread_verified` (1 once ETW frame IDs have verified this game's cross-thread PRESENT_START hand-off, else 0).

## Pacing Preference

The user key `pacing_preference` (`latency`, `balanced` or `smooth`; default `balanced`; live key `set pacing_preference smooth`; an unknown text is refused or loads as `balanced`; the OSD combo **Pacing preference**) sets two developer keys' effective values for the queue-based pacer (64-bit, Direct3D 12):

| Position | `unified_queue_rank` | `unified_hold_share` |
|----------|----------------------|----------------------|
| `balanced` | the key's value | the key's value |
| `latency` | 4 | the key's value |
| `smooth` | the key's value | 1/32 (0.03125) |

**Precedence.** Each lever is resolved on its own, once, in `Config_ApplyPacingPipeline`: a developer key at its default cannot override the preference; a developer key that differs from its default decides its own value whatever the preference (to force an exact developer pair, select `balanced` first). `latency` leaves a developer share alone and `smooth` leaves a developer rank alone. The preference is not a developer setting: it is not counted in the developer overrides and the developer reset leaves it. The INI and `g_config` keep the raw developer keys; the pipeline carries the effective pair, and the 32-bit forcing of `unified_hold_share` runs after it (the share is 0 on 32-bit). The OSD notes when a developer key overrides the selected position.

The two levers act through the keys they change: `unified_hold_share` (under the queue law the share part of the law's refill is bounded by the median frame generation time of the used reports, 0 without frame generation or once the reports are expired; a decrease of the share drops a positive hold credit to 0) and `unified_queue_rank` (rank 4 instead of 2). See their rows under [Developer INI Keys](#developer-ini-keys). The effective pair is logged on the `Pacing pipeline:` line (`pacing_preference=`, `queue_rank=`, `hold_share=`).

## Pacing Details Lines

The main view shows one plain status line; the technical lines are under **Details**, a collapsed node below it. Each line below appears under the condition given. The [User Guide](USER_GUIDE.md#reading-the-status) has the one-line meanings; this section adds the technical detail.

**Route.** `Reflex markers`, `Present-based`, or `waiting for a presenting swapchain`.

**Mode | Output | Reason.** `vrr` or `fixed` from the display, `idle` while an idle cap (Background FPS, FG-Off Cap, OLED Care) is active, or `off` when ReLimiter is not pacing. Output is one of `gpu_queue_wait`, `fg_input_wait`, `marker_hold`, `source_only` (`native_hold`, which nothing produces now, appears only in captures of older builds). Reason is listed under [Fallback Reasons](#fallback-reasons).

**Placement.**
- `unified` is the pacer's own wait inside the game's Reflex Sleep call, `marker` waits at the game's frame-start marker (a game that does not call the Reflex Sleep), `present` at the Present call, `none` means ReLimiter is not pacing.
- `Reflex driver limiter (x.xx ms)` shows the presented-frame interval applied in the test mode `driver_limiter`; an orange `Reflex driver limiter (not applied)` can appear briefly while the driver limit is not in effect. Where the limiter cannot apply, the game runs as it is (reason `driver_limiter_unavailable`).

**Lead | Grid epoch.**
- Lead is how far ahead of each output target the game is released, whether it is still `warming` (fewer than 32 samples, using a starting estimate) or `warm`, and how many recent frames it is based on. It shows `-` until the source wait has run. The lead is limited to three frame intervals; `, at budget` after the sample count means the lead it wanted was longer and was clamped, so those frames are likely to miss their targets.
- `Lead spike floor: F ms = arrival tail T + GPU G | own quantile Q ms` follows while the spike floor applies (a GPU wait behind the wait, its memories warm), with `| sets the lead` while it is above the lead's own target.
- Grid epoch is a counter that increases each time the cadence restarts: after a cap or FG multiplier change (an LFC change too on the Present route of a 32-bit game), a mode change, a new swapchain or API, or, on the Present route, a late source (a late output too on a 32-bit game).

**Release headroom / Release margin.** Shown on `gpu_queue_wait` while the collision-aware release is active.
- `Release headroom H ms | limit L ms | guarded P% | late n/N`: the release is measured against the next frame's heavy GPU work (needs NVIDIA Reflex latency reports). Shows the headroom (fixed, 1.00 ms), the newest lead limit (one frame interval, plus the game's short release-to-heavy-GPU-work time, minus the headroom), the share of leads the limit lowered (including the frames the lead is still returning up to its unguarded value), and how many waited GPU resumes came more than 1 ms after the release. The late count is a measurement only; nothing acts on it, and it needs **GPU Wait Probes**.
- `Release margin M ms | limit L ms | guarded P% | late n/N`: the same line while the release is measured against the next frame's Present call instead (no Reflex GPU active time within the newest 64 releases). The margin is fixed at 2.50 ms.
- `limit - (measuring)` until 32 frames are measured.
- `Release headroom H ms | guard off (next frame's GPU work waits behind the gate, N pairs)` when the guard has found that the next frame's GPU work runs behind the wait.
- The counts run since the last controller reset.

**Driver Sleep: `x.xx` ms.** The average time the game's Reflex Sleep call spends in the driver, shown while a GPU wait is the output. A readout only; ReLimiter does not act on it.

**Dynamic frame generation: pacing passthrough.** Shown below the status line itself, not under **Details**, while frame pacing is left to the driver.

## Mechanisms Behind the Details Lines

The output point stays the best one the game supports (the GPU waits where available); the lead and the collision-aware release adjust the holds.

### Lead and late frames

For each frame ReLimiter plans a *source wait* (when the game is released) and an *output point* (the target at which the finished frame should pass on). The lead covers 99% of recent frames, plus 0.5 ms, and is limited to three frame intervals.

- **Late frames.** A frame that reaches its output point after its target is never held. If it is late by more than a quarter interval (at least 0.5 ms), the cadence restarts from that late frame and the grid epoch increases. The same applies when the game itself arrives late for its source wait, but only if it is late by more than a quarter interval plus the frame's *slack*: the lead minus the median time from release to the output point. A frame within the slack is released at once and keeps the cadence.
- **Skipped holds.** Holds that would be unusually long, such as a marker hold of more than 1.5 intervals, are skipped rather than performed.
- **Measurement on the GPU waits.** For `gpu_queue_wait` and `fg_input_wait`, each frame's measurement is its time to readiness. When the next frame's GPU work runs behind the wait (each GPU wait checks this from the Reflex reports: the next frame submits before the release, but its GPU work starts only after it), the measurement leaves out how long the frame's GPU work waited for the GPU to finish the previous frame, counted from where its first GPU work reached the driver (RENDERSUBMIT_START plus the measured first-submission delay). Otherwise a frame's readiness follows ReLimiter's own release of the previous frame, the measurement grows with the lead, and the lead could only rise: in CONTROL Resonant with FG 2× at 130 FPS it went from 20 to 39–43 ms after one heavier second and stayed there. A frame the cap released keeps its full measurement when its own late submissions set its readiness: its Reflex report shows its GPU waited 1 ms or more inside its work for its submissions while its first work reached the driver in the first half of its render submission. In Gears of War: E-Day with FG 2× at 120 FPS, leaving that wait out held the lead at 29 ms with half of those frames ready after their targets. A frame whose first work reached the driver only late in its render submission (in Gears, at the previous frame's Signal when the lead is long) keeps the wait left out even when its GPU waited: its submissions were held by the previous frame, and keeping its measurement held the lead at 45 ms. Behind the wait such a frame's measurement is taken when its Reflex report arrives, about two frames later. Where the GPU starts the next frame's work beside the wait (Deep Rock Galactic: Rogue Core), or while the order is not known, the measurement is the measured readiness. Whether a frame was late always uses the measured readiness, at once. The log shows the FG input wait's order with `Lead: the next frame's GPU work runs behind the FG input wait ...`, the GPU queue wait's with `Collision guard: stands aside ...`.
- **Render queue time.** On `fg_input_wait`, the measurement also leaves out the time a finished frame waited for the game's render thread while that thread was still inside the previous frame's Present (from the frame's SIMULATION_END marker to the previous frame's PRESENT_END marker, at most until its RENDERSUBMIT_START). Without this, a game that simulates a frame ahead of rendering keeps a lead one frame too long. `source_only`, the CPU holds and `gpu_queue_wait` keep the full measurement.
- **Spike floor.** While the next frame's GPU work runs behind the wait, the lead is at least the arrival tail plus the GPU's time from starting a frame to its readiness. The arrival is how long after its release a frame's first GPU work reached the driver, without the time its finished simulation waited for the render thread; the tail is the second-largest of the longest arrivals of the newest 32 blocks of 64 frames (about 31 s of frames: every arrival of that time but the longest is covered), the GPU time the median of the newest 32 frames. The lead's own 99th percentile leaves a game's rare long simulation frames out, and while the GPU runs back to back such a frame leaves the GPU waiting and every later frame inherits the lost time: in CONTROL Resonant with FG 2× at 130 FPS, simulations above 15 ms came 11–23 times per minute, the GPU waited more than 3 ms for a frame 8–18 times per minute at the own lead of 29.5 ms, and display jumps above 4 ms rose to 5.2–9.5 per 1,000 from 1.3–1.6 at an earlier lead of 40 ms. Covering all but the fourth-largest cut those waits to 2.4 per minute and jitter above 2 ms from 25.1 to 10.4 per 1,000 for about 2.5 ms of PC latency, but left the game's 22–25 ms simulations; the second-largest covers more of them for about 1–4 ms more lead in such scenes. The floor applies only after 4 blocks and 32 GPU times, enters the lead's target (so it moves at the lead slew) and never counts as a lead at budget. It is cleared with the lead buckets (for example at an enforcement marker change) and kept at cap and FG multiplier changes. The log reports `Lead spike floor: on at ...` when it first sets the lead and `off (...)` after 256 frames without.

### Collision-aware release

Applies on `gpu_queue_wait` only. The GPU wait releases each frame at its target. If the next frame's heavy GPU work has already started on the GPU when the work after the wait becomes ready, that work waits for it, and the resume comes more than 1 ms late. The game's own long command buffers run on the same GPU engine as the work after the wait and are not interrupted for it.

- **The limit.** The lead is `L = min(Q_q(X) + allowance, I + Q10(D) − H)`: the plain lead, at most one frame interval `I`, plus the game's short release-to-heavy-GPU-work time `D` (the 10th percentile of the newest 256 frames), minus the **release headroom** `H`. The heavy work is measured as a frame's GPU ready time minus its GPU active render time from its Reflex latency report. A frame adds a `D` sample only when the frame before it was a GPU wait frame whose GPU waited at its gate (only a waited release can collide with the next frame's heavy work). While that verdict is pending (the readback probe of the predecessor's resume has not arrived) the sample is deferred and added when the verdict is known; readiness decides only when no probe time is available. A frame after one that was not waited for, or that belongs to another lifecycle or FG multiplier, adds none. The limit applies once 32 frames are measured. Without Reflex latency reports (no GPU active time within the newest 64 frames planned with the GPU wait's lead), the release-to-Present time `C` (every GPU wait frame adds one) and the **release margin** `M` take their place: `I + Q10(C) − M`.
- **Frames that need more lead.** A frame that would need a longer lead reaches its GPU wait a little after the release and is shown when it is ready. Its slack is judged against the lead before the limit. No mode switch, timer or GPU-load threshold is involved.
- **A relaxing limit does not jump the lead.** A tighter limit applies at once. When it relaxes, or the guard stands aside, the lead returns to the unguarded lead at the lead slew (100 µs per frame, at most `I`/64), never in one step. The frames the slew still holds back count as the guard's own reduction.
- **Release headroom and margin are fixed.** `H` is 1.0 ms (`kPacingGpuWaitHeadroomDefaultUs`): the headroom the lead limit keeps between the release and the next frame's heavy GPU work (its 10th-percentile time), used with Reflex GPU active times. `M` is 2.5 ms: the margin it keeps before the next frame's Present call, used without them. Nothing widens or narrows either. Late resumes (more than 1 ms after the release) are measured and shown on the Details lines and in telemetry, but nothing acts on them. Across about 1.35 million waited GPU resumes with probes and Reflex GPU times in Deep Rock Galactic: Rogue Core, late resumes were 0.00–0.05% per 250 µs distance bin from 1 ms on, and 99.2% of all late resumes were closer than 1 ms.
- **Games that run the next frame's GPU work behind the wait.** For each frame whose GPU waited at the gate, ReLimiter asks whether the next frame had started submitting before the release and whether that frame's GPU work (the GPU start in its Reflex latency report) began more than 0.1 ms before the release. The limit stands aside only while at least 32 such pairs exist, none of the newest 64 began earlier, and the heavy-work window is current (a Reflex GPU active time arrived within the newest 64 frames planned with the GPU wait's lead). Every frame planned with the GPU wait's lead ages that window, whether it was held; any Reflex report of such a frame resets the age, with or without a new `D` sample, so the age is not tied to `D` samples. Without current Reflex reports no new pair can show the order changing, so the Present-call margin guard applies until a report arrives. A single pair that began earlier brings the limit back at once, until that pair is no longer among the newest 64. Without **GPU Wait Probes** or Reflex latency reports there are no pairs and the limit stays. The pairs are kept across controller resets until the game closes; after a lifecycle reset the guard waits for a warm heavy-work window (32 frames) before standing aside again.
- **The start term** (developer key `gpu_wait_start_limit`, on by default, 64-bit). A second limit on the same lead, for every plan made on present-first ordering with the GPU wait's lead while the guard is on, whether or not the limit above judged it; a plan that is not ordered gets none, because without the order a hold on the presenting queue does not block the render queue. What it limits: the lead, the distance from the release to the hold's target, is at most `2 I − (W + G)`, and at least 0. With the order the render queue's next frame waits for the held frame's Present, and the game's own frame sync ties its next frames to the render queue: its PRESENT_END comes with the render queue's next start, the release of the order's Wait, which follows the hold's release, and it asks for its next frame right behind that end. So a hold released later than that delays the game's start of the frame two ahead; on every second frame it is a saw-tooth in the frame-time graph, which plots the interval between starts. The limit above hid it by ending holds far earlier, and present-first ordering made that limit stand aside. What it measures: `W` is the render queue's resume after the release: for a held frame, the time from the hold's release to the moment the render queue passed the order's Wait behind the frame's Present (the hold order unit's stamp, the upper end of the GPU queue probe's interval for the Wait's release), the 99th percentile over the newest 256 held frames. It is counted from the release alone: the game waits for the render queue, and when the GPU finishes a frame after its release that wait is longer by the lateness. The unit gives the stamp only for a frame the order was in effect for and only once the probe resolved the Wait, so it arrives after the release, typically within the next frame, and a frame without it gives no sample; a sample below 0 or above three intervals is left out. The sample is taken from every such frame, whether or not the game's next Present arrived before the release: where holds end before it, which is where the limit puts them, there is no pair of the game's own wait to measure, and a measure taken from such pairs went stale behind its own effect. The resume is in use from 32 samples on, while one arrived within the newest 64 frames planned with the GPU wait's lead; else `W` is the release headroom `H`, the fallback. `G` is the 99th percentile of the game's turnaround over the newest 256 frames, from a frame's PRESENT_END to the game's arrival for the next one (the Reflex Sleep's arrival, or the marker's: never the release of ReLimiter's own wait), 0 until there is one, and a turnaround above three intervals is left out. When it stands aside: on the game's own times only. A *free pair* among the newest 64 telling pairs (frame `n` held, the order in effect for it, and its release after frame `n + 1`'s native Present arrived, while frame `n + 1`'s Present ended before that release: the game does not wait for a held Present) or an *untied start* among the newest 64 frames (the game asked for frame `n + 1` before frame `n`'s Present ended: a game thread running a frame ahead, where the frame a hold reaches is a later one) puts it aside, with no limit and an empty `plan_start_limit_us`; it is back when none is left among the newest 64. A frame the unit gave no stamp for gives no pair, telling or free: a hold the order did not release behind its Present says nothing of the order's chain. A pair is judged once, between consecutive frames of one lifecycle, rung and FG multiplier, and only for frames the executor held. Like the limit above it tightens at once and relaxes at the lead slew, and the lead is cut to the lower of the two; it also reaches the output executor, which resolves no target past it (`PacingFramePlan::lead_limit_us`; the late state's limit joins it as the lower one while `gpu_wait_late_guard` is on), so the spacing floor cannot lift a target back past it when the lead drops by more than its slack in one plan. A limit that would be below 0 is 0 for the lead and the pacing CSV, but the executor is then given 1 µs, never 0, which it reads as no limit: a lead of 0 does not guarantee no hold, because the previous output can lift the spacing floor above the frame's release, and a hold past the limit would follow. The log says `Start limit: applies, ...` and `Start limit: stands aside (...)`.
- **When the GPU is busy most of the interval.** The release can then come only shortly after the frame reaches the wait, and few frames wait at all.

## Hook Installation

MinHook's enable freezes the process: it suspends every other thread, patches, and resumes. Two engines whose suspend loops overlap can deadlock each other (other injectors in the process use MinHook too), so ReLimiter installs its hooks in as few freezes as it can, one batch per site.

**Batch.** `HookBatch` (`hooks.h`) is lazy: constructing or destroying one takes no lock and calls nothing. The first install inside it takes the install lock and keeps it until the apply, which releases it, so an idle batch never blocks another installer (the present thread's first-present install, the focus lock and the DXGI fallback wait on that lock while the swap-chain selection lock is held). Inside the batch every install creates the hook, publishes its trampoline into the caller's original slot, then queues the enable (`MH_QueueEnableHook`); the apply is one `MH_ApplyQueued`. An install's `MH_OK` inside a batch means *queued*: whatever acts on a hook, logs it as installed or sets a state flag from it reads `Hooks_TargetEnabled` after the apply. A batch nests on one thread (the inner one is a no-op that queues into the outer), applies in its destructor if `Apply` was not called, and an empty batch calls MinHook not at all (no freeze). Outside a batch an install is create, publish, enable, as before. A group that cannot continue without the result (the Streamline hooks, the proxy and queue hooks, the FG input and queue hooks, the NGX transaction) calls `Hooks_FlushBatch()` once after its installs: the same apply (it releases the lock too), batch still open.

| Site | Hooks in the batch |
|------|--------------------|
| `Init` | The flip-metering block (`flip_metering_off`) and the NGX hooks, in `DoInit`. |
| `FirstPresent` | The first present event: the four LoadLibrary hooks and up to nine NvAPI hooks (about 13 freezes become one). The selection lock's hold gains no work. |
| `LoaderScan` | One scan of the loader-install worker: the Streamline hooks, the proxy and queue hooks, the FG input and queue hooks, NGX when its modules appear. The batch closes before the worker's 250 ms wait; discovery, factory probing and drains run without the lock, which is held only from a group's first create to its flush. NGX installed outside the worker (the OSD's retry) opens its own. |
| `FocusLock` | The four user32 hooks of the focus lock. |
| `DxgiFallback` | The DXGI `Present` / `Present1` inline pair, installed only when the native swap chain's vtable route is absent. |

**A failed apply.** `MH_ApplyQueued` is not a transaction: it stops at its first failure with the earlier hooks enabled and the later ones pending. ReLimiter then enables every hook still queued one by one with `MH_EnableHook`, logs one warning for the failed apply and one for each hook that still fails (`Hooks: ... MH_ApplyQueued failed (...)`, `Hooks: the hook at ... could not be enabled (...)`, both with MinHook's status), and leaves such a hook created and not queued, so no later apply enables it behind its owner's back. `Hooks_TargetEnabled` reports what is really enabled. The site lines say so too: `FG input: Present installation status=... enabled=...`, `FocusLock: installed on HWND ... (N of 4 hooks enabled)`, `NvAPI: ... hook installed|not installed`.

**A retained load.** The hook records survive an addon unload and load. Installing a retained target again queues it (no second `MH_CreateHook`); `EnableAllHooks` (`MH_EnableHook(MH_ALL_HOOKS)`) enables every hook, the queued ones too, so nothing stays queued, and when it stops at a failing hook it enables the rest one by one before it returns the failure.

**The installer thread.** MinHook's freeze suspends every other thread; another engine's freeze that overlaps it can suspend the thread that is freezing, and the two wait for each other for good (two ordinary freezers deadlocked within a second in a stand-alone program). ReLimiter therefore runs its freezing calls on one installer thread created at initialisation, outside the loader lock, with a security descriptor that denies `THREAD_SUSPEND_RESUME`, `THREAD_GET_CONTEXT` and `THREAD_SET_CONTEXT` to Everyone in front of the process token's default DACL (nothing else is granted). Another engine's `OpenThread` for it then fails with access denied and it skips the thread, so ReLimiter's freeze no longer waits for anything another engine can suspend. At its start the thread opens itself for a suspend; that must fail. If it succeeds (a process with the debug privilege enabled bypasses the descriptor) the thread is *unprotected* and every call runs on the requester as before. Only the raw MinHook calls that freeze run on it (the batch apply and the one-by-one enables after a failed one, a single enable or disable outside a batch, the enable-all of a reactivation, the disable at teardown); creating, publishing, queueing and every log stay on the requester, which keeps the install lock and waits, without a timeout, for the job or for the thread's death. The thread cannot be suspended by other engines, so neither can a crash-dump writer read its context; it is idle between jobs. Calls run on the requester when `hook_installer_thread` is `false`, before the thread reports ready, after teardown stopped it and inside a `HookInlineOnlyScope` (the explicit mark for code in `DllMain` or a loader callback; no call site is one today). If the thread ends before it took a job, the requester runs the job; if it ends with a job in flight MinHook's internal lock may be held for good, so MinHook is not used again in this process (every later freezing call fails with `MH_ERROR_DISABLED`, install admission closes) and nothing is replayed or terminated; creating, removing, queueing and initialising hooks make no MinHook call either (they take the same internal lock), and a hook that could not be removed stays retained. Other engines can still deadlock each other: this removes ReLimiter from that cycle, not the cycle.

`hook_installer_thread` (default **true**, both addons, `[FrameLimiter]`, restart required) is a compatibility switch, not a tuning option: `false` turns the thread off for a game or tool that does not tolerate a thread with a restricted descriptor (some anti-cheat or anti-tamper software, an unusual crash handler). The log says which applies (`Hooks: installer thread created` at start, `ready (protected)` or `unprotected` at the first present).

**Evidence.** The apply is bracketed by the `BatchApplyEntered` / `BatchApplyLeft` crumb stages with the site number (1 `Init`, 2 `FirstPresent`, 3 `LoaderScan`, 4 `FocusLock`, 5 `DxgiFallback`), so a hang inside a freeze is named by the next launch (see **Start-up evidence** below). The site byte's high bits also say whether the installer thread ran the apply, whether it was protected but not used for that call, or unprotected.

**Start-up evidence.** `Log_Init` first moves the previous log to `relimiter_<exe>.prev.log` in the same folder (`MoveFileEx` with replace; a failure, such as a log a second live launch still holds, is ignored and the new log opens as before), then opens the new log (next to the game executable, else next to the addon, else `%TEMP%`). `src/startup_breadcrumb.h/.cpp` keeps `relimiter_<exe>.crumb`, a 4 KB file in the log's folder mapped for the life of the process, holding one 40-byte record: magic, version, process ID, launch time, sequence numbers, the stage reached, the QPC at the stage and a site ID (a hook batch's `HookBatchSite` for the two batch stages). A mark is plain stores into the mapped page (no lock, allocation, flush or log), so it is safe around a MinHook freeze, and the page survives a killed or frozen process. The sequence number is odd while a record is written and equal at both ends when it is whole; a reader rejects any other record. Stages, in the order they are normally reached: `InitBegun`, `InitEnded` (DoInit), `BatchApplyEntered`, `BatchApplyLeft` (a hook batch around its `MH_ApplyQueued`, with the site), `FirstPresentEvent`, `FirstNativePresentEntered`, `FirstNativePresentReturned`, `FirstGateWaitEnqueued`, `FirstGateSignal`, `Running` (the 32nd completed present of the selected swapchain, after the first-present block ran) and `Closed` (clean shutdown, both teardown paths). Every stage except the two batch stages is first-wins, only `Closed` follows `Running` (a hook batch applied later in the session is not start-up), and a mark that finds another thread writing is dropped, never waited for. After the new log is open, `Breadcrumb_Attach` reads the previous record before it resets the file, and the logger writes ONE warning, at warning level so the default level shows it: `the previous launch ended during start-up; last stage: <stage>[ (site <name>)]` (it says ended, not hung). Nothing is logged when the previous record reached `Running` or `Closed`, or is missing, short, from another version, has a bad magic or is torn. The file is opened as the only writer (`FILE_SHARE_READ`): a second live launch of the same executable, or a read-only folder or file, makes the open fail and the process runs without marks and without a report, so a live launch's record is never reported or overwritten; a dead process holds nothing, so its record is read. A reload of the addon in the same process keeps the mapping, judges its record and resets it.

## Capture Files

Turn on **Telemetry Logging** (Advanced) to record a capture; the User Guide describes the steps. Files are written next to the addon and named with the game's process name, process ID, a session number and the capture number.

**`relimiter_pacing_`** has one row per displayed frame, or per Present call when no display time is available, with 195 columns (column names are in the header row; empty cells mean the value was unavailable, not zero). Present records come only from the DXGI `Present` and `Present1` hooks, so a capture of a game that does not present through DXGI has the header and no rows. Groups:

- ReLimiter's release and frame plan: cadence epoch and index, output target, lead, output point and its outcome.
- The game's Present call, GPU wait and readiness timing, Reflex timing.
- The display time and its source (ETW or DXGI), and Display Pacing measurements.
- Columns this build no longer writes. The header of this build has 195 columns; the pre-removal header has 199 and carries seven that this build does not write: `predicted_render_us`, `governor_step`, `governor_interval_us` (the removed period governor's step and interval), `plan_signal_advance_us`, `pre_sleep_margin_us` (the margin of the removed pre-Sleep placement) and `gpu_first_submit_qpc` and `gpu_start_qpc` (the stamps of the removed GPU start probe); it has no `plan_ordered`, `plan_start_limit_us` or `plan_start_applied` (below). An older capture carries them with their old meaning and the analysis tools read both headers. In `source_flags` the bits 4 `gpu_paced`, 64 `overload` and 128 `stall_injected` are never set by this build; an older capture can carry them.
- `gate_pre_wait_qpc` and `gate_post_wait_qpc`, the GPU queue wait's GPU time before and after the wait (with **GPU Wait Probes**; empty when unknown).
- PC Latency (with PC latency collection).

- GPU queue probe columns (developer key `gpu_queue_probe`, 156–170 and 192), what the game's presenting queue did for the frame's submissions, a frame being the `ExecuteCommandLists` calls between ReLimiter's own Present-time enqueues. **Frame generation labels.** Under DLSS-G one app frame produces several presents on one swapchain, with the game's PC latency simulation marker on the first, the generated frame shown as soon as frame generation has computed it. The PC latency collector groups presents per swapchain from one marker present to the next: the last present of a group of several is the real frame and takes the app frame's identity (frame ID, simulation start, input ping, Present start), so its row joins ReLimiter's release and carries PC Latency; the earlier presents are generated and carry no frame identity. Presents that PresentMon types (Application, Repeated, XeFG, AFMF) are never reassigned. A present's display and PC Latency samples are published when the next marker present arrives (at most 250 ms or 8 presents later). Captures from builds before this grouping have the real and generated labels swapped under DLSS-G.
