# ReLimiter Developer Reference

This document covers the settings, status lines and log lines that exist for A/B testing and capture analysis. Normal users never need it: ReLimiter ships the recommended defaults and the [User Guide](USER_GUIDE.md) covers everything a player has to know.

It describes current behavior only. Release notes are in [`CHANGELOG.md`](../CHANGELOG.md).

[Frame Pacing](FRAME_PACING.md) explains the mechanisms these settings and lines refer to (cadence grid, lead, output points, protections), with diagrams.

## Enabling Developer Settings

The **Developer diagnostics** group appears in the **Advanced** section only when both of these are true:

- `developer_settings=true` is set under `[FrameLimiter]` in `relimiter.ini` (default `false`; edit it with the game closed).
- **Enable advanced settings** is checked.

Every control in the group can make pacing worse on purpose. The group's **Reset to defaults** button returns all of them to their recommended defaults. While any of them differs from its default, the main view shows an amber `N developer setting(s) changed from the defaults` line with a **Reset** button, whether or not the group is shown, so a forgotten test setting does not go unnoticed. When comparing, change one setting at a time and capture the same scene, cap and frame-generation mode, and start each run from a fresh game launch.

The developer keys are also read from the INI when `developer_settings` is `false`; the setting only controls whether the overlay shows the controls. Developer-only status lines (**A/B interleave**, **Stalls injected**) appear only while their setting is on.

## Developer Diagnostics

Defaults are the shipped values. Settings marked 64-bit are not available in the 32-bit addon.

### Smoothing

`smoothing` (`on` or `off`, default **On**). On holds each frame's output to the cap cadence at the best available output point and releases the game early enough for 99% of recent frames plus 0.5 ms. Off holds nothing after the source wait (output `source_only`, reason `smoothing_off`) and only places the shared target; the lead still covers 99% of recent frames, with no extra allowance. It is the only way to turn smoothing off.

### Output override

`output_rung` (default **Auto**) forces an output point: **Source only (no hold)** (`source`), **Marker hold** (`marker`), **Native Present hold** (`native`) or **GPU wait** (`gpu`). Available in both addons; GPU wait needs the 64-bit addon.

- An override whose requirements are not met falls back one step: GPU wait or native hold to marker hold, marker hold to source only. With frame generation, a GPU wait override without a qualified FG input route gives source only. The status then shows the reason `override`.
- Smoothing Off, idle caps and Present-based routes still take precedence.
- Only **Auto** uses the overload fallback and the collision-aware release (see [Mechanisms Behind the Details Lines](#mechanisms-behind-the-details-lines)). A **GPU wait** override bypasses both: its lead is the plain lead (the 99th percentile of the time from release to readiness plus the allowance, at most three intervals) with no limit on top. An override is never changed to another output point by ReLimiter.
- `native_hold` (the CPU holds at the native Present call) can only be selected here.

### GPU Wait Probes

`gpu_present_gate_probes` (default on, 64-bit). Applies only to the `gpu_queue_wait` output. It places GPU timestamps immediately before and after the queue wait; the pacing CSV records them as `gate_pre_wait_qpc` and `gate_post_wait_qpc`, and the lead uses them. The same measurements supply the late-resume count shown on the Details lines and in telemetry. Nothing acts on that count: the release headroom and the release margin of the collision-aware release are fixed.

Turning it off removes two command lists and two fence signals per frame from the game's GPU queue; the Details lines then have no late-resume count. The guard itself does not change (headroom 1.0 ms by default, margin 2.5 ms). The overload fallback is unaffected.

### GPU wait release headroom

`gpu_wait_headroom_us` (default 1000 µs, 500–3000 µs, 64-bit, `gpu_queue_wait` with **Output override** **Auto**). The distance the collision-aware release keeps between a frame's release and the next frame's heavy GPU work (**GPU wait release headroom** in the OSD's developer settings). It exists to reproduce a report without a rebuild; users never change it.

- A shorter headroom lets more frames run their full lead and leaves more of them resuming behind the next frame's long command buffers; a longer one lowers more leads.
- It also sets the Adaptive cap hold room (see [Adaptive cap](#adaptive-cap)), which solves the same limit for the interval.
- The release margin to the next Present call (2.5 ms, used without current Reflex GPU active times) is not configurable.
- Values outside the range are clamped with a log warning; 0, negative and non-finite values load as 1000.
- The log records the value in the `Pacing pipeline:` line (`gpu_wait_headroom_us=`).
- An old `gpu_wait_budget_us` key in the INI is ignored and dropped on the next save; the GPU wait has no cap any more.

### GPU wait A/B blocks

`gpu_wait_interleave_s` (default 0 = Off, 1–10 s, 64-bit, **Output override** **Auto** only). With it on, the `gpu_queue_wait` output alternates held and not-held blocks, each 0.75–1.25 times this length (lengths vary so blocks do not line up with periodic game events). The first block after turning it on is held.

- The overload guard and the collision-aware release stay on in held blocks.
- Not-held blocks keep the GPU wait's lead, so switching blocks does not jump the frame timing; the render handoff limit applies in them, as to every frame that is not held.
- Each block starts a `rung_feasibility` event (`ab_held` or `ab_not_held`) in the pacing events file, so a capture can compare both outputs at the same loads. The Details lines show `A/B interleave`.
- **Pacing switches every block on purpose.** Set it back to Off for normal play.

### Stall injector and Stall period

`stall_inject_ms` (default 0 = Off, 0–200 ms) and `stall_inject_period_s` (default 5, 1–60 s). **Deliberately hitches the game:** once per period ReLimiter sleeps the configured time after the source wait, to test how pacing recovers from a stall. The OSD shows **Stalls injected**, the pacing events file records each `stall_injected` event and the log warns while it is on. Set it back to Off after testing.

### Bypass Reflex Sleep

`reflex_sleep_bypass` (default **on**, 64-bit). While an FPS cap is set and ReLimiter's own wait paces the game, held or not, the game's Reflex Sleep call returns immediately without reaching the driver. Reflex markers and the game's Reflex mode are still forwarded.

- The Sleep reaches the driver as before with the cap off and whenever ReLimiter does not pace the game: before a presenting swapchain exists, while pacing is suspended, in the background with Background FPS off, with the **Reflex driver limiter** placement, and in Dynamic MFG passthrough, where the driver paces the game.
- Frames that are not held (the overload pause, **Output override** **Source only**) use the render handoff limit instead of Reflex's queue management.
- With [pre-Sleep placement](#pre-sleep-placement), ReLimiter still waits inside the bypassed Sleep call before it returns.
- The **Reflex driver limiter** placement needs the driver's Sleep, so with the bypass on that placement cannot apply.
- The log records each change. The 32-bit addon has no Reflex hooks, so the setting has no effect there.
- Turning the bypass off returns to the driver's Sleep, which can favor latency over smooth pacing near the GPU's limit.
- With DLSS Frame Generation the driver still paces inside `NvAPI_D3D12_SetAsyncFrameMarker`, which Streamline's `sl.dlss_g` calls through `sl.common`: it can sleep the thread that calls the game's Present although the Sleep is bypassed. ReLimiter only times that call (the `async_marker_wait_us` column) and never suppresses, delays or alters it.

### Marker forward order

`marker_forward_order` (default **Before wait**, 64-bit, NvAPI marker games only) sets when the game's SIMULATION_START reaches the driver. **Before wait** passes it on as soon as the game sends it, then ReLimiter waits. **After wait** passes it on after ReLimiter's wait, as the Streamline PCL path already does, so the driver, DLSS Frame Generation and PC Latency see the paced frame start. PC Latency then counts from the paced start, so compare it with care. The Adaptive cap's workload measurement stops removing ReLimiter's wait from the simulation stage, because that stage no longer contains it.

### GPU queue wait render queue

`gpu_queue_wait_render_queue` (default **Keep**, 64-bit, `gpu_queue_wait` only). Controls whether the lead includes the time a finished frame waited for the game's render thread to leave the previous frame's Present.

- **Keep** measures the lead with that time.
- **Remove** leaves it out, as `fg_input_wait` always does, so the lead and latency can shrink in games that simulate a frame ahead.
- **Remove after held** leaves it out only when the previous frame's GPU waited at ReLimiter's gate, the case in which ReLimiter's own wait can cause the queue.
- Removing it can come with late GPU resumes, so compare late GPU resumes, grid restarts, long frames and PC Latency at a cap the game can reach, one setting per capture in the same scene. The log warns while it is not **Keep**.

### Lead coverage

`lead_coverage` (default **99%**, all holds). The share of frames the lead releases early enough to reach their hold in time: the lead is that percentile of the measured release-to-ready times plus the allowance.

- **99%** (default) leaves about 1 frame in 100 ready after its target. Such frames are shown when ready; with frame generation each one moves two or more displayed frames.
- **95%** leaves about 1 in 20, for a shorter lead and a little less latency: in CONTROL Resonant captures about 2–2.6 ms less lead at the median with frame generation, about 0.5 ms in Rogue Core.
- **90%**, **75%** and **50%** leave about 1 in 10, 4 and 2. They map the trade between the hold's latency and the frames it can no longer hold: a frame is released the lead before its target and needs only its own time, so the hold costs about the distance from the game's typical frame time to the covered percentile.
- The lead spike floor still applies below 99% and can then set the lead instead (with it, 95% kept about 1 ms more PC latency in the same game); turn `lead_spike_floor` off to compare coverages.
- Measured in Phantom Blade Zero with DLSS frame generation 2× (hardware flip metering) at a 100 FPS cap the GPU reaches with room, spike floor off, each against NVIDIA's Reflex limiter at the same cap in the same session (about 30 displayed intervals per minute over 1.5 times the median, 74 steps over 4 ms per 1,000 displayed frames):

  | Lead coverage | PC latency | Long intervals per minute | Steps over 4 ms per 1,000 |
  |---|---|---|---|
  | 50% | +0.8 ms | −6 | −38 |
  | 75% | +1.8 ms | −12 | −53 |
  | 90% | +2.0 ms | −19 | −61 |
  | 95% | +2.9 ms | −19 | −60 |
  | 99% | +4.9 ms | −21 | −62 |
  | 99% with the spike floor (default) | +4.8 ms | −20 | −65 |

  Two to four one-minute runs per row on one route; long intervals vary by about 5 per minute between runs.
- Frames late because the GPU or the game's render thread was still busy with the previous frame are not helped; the extra lead only adds latency there. At a cap the GPU barely reaches (the same game at 120 FPS) 90% had 2–4 ms less PC latency than the default with no measurable difference in long intervals or steps.
- The render handoff limit keeps 95% whatever the coverage. Compare long frames, jitter, frames ready after their target and PC Latency, one setting per capture in the same scene. The log warns while it is not **99%**.

### FG late-frame spacing

`fg_late_spacing` (default **on**, 64-bit, `fg_input_wait` only). When a real frame reaches the FG input wait after its release time, it enters frame generation when its GPU work finishes, and frame generation shows most of that delay on one displayed interval. On, ReLimiter records the late frame where it actually passed and holds the next real frame at least one frame interval minus an eighth of the displayed interval after it, so each displayed interval is shortened by at most about an eighth, the same share the outputs without frame generation allow ([No catch-up burst](FRAME_PACING.md#no-catch-up-burst)). Off (developer A/B), the next real frame is released on its original target, so the displayed interval after the late one is short by most of the same amount: in CONTROL Resonant at 60 FPS with 2×, the worst displayed error after a game hitch was 5.6 ms off against 1.7 ms on (median).

- Only releases after a late frame move, and only later; the late frame itself is unchanged. Recovering from a long hitch takes a few more frames, each held a little later.
- **Never while the game's render thread waits.** If the game's render thread is still inside a frame's Present when the frame's original target arrives (its PRESENT_END marker has not come), holding the frame longer would also hold the render thread, and the next frame would wait behind it. That frame is then released at its original target. This is what happens when the GPU is the limit (CONTROL Resonant at 157 FPS with 2×: the next frame was late after 42% of such holds against 3% of the others); with headroom (60 FPS with 2×) the render thread had always left. Without PRESENT_END markers nothing is moved.
- A release moved more than the late tolerance (a quarter of the real-frame interval) restarts the cadence, as a late release does on the other outputs; such restarts count for the overload pause and the Adaptive cap.
- A frame that reaches the FG input after its original target can be held to the moved target instead of passing late.
- Compare jitter above 2 and 4 ms, long frames and PC Latency, one setting per capture in the same scene. The log warns while it is off and logs at INFO the first moved release and the first release kept at its target because the render thread was still in the Present.

### GPU-paced cadence

`gpu_paced_cadence` (default **off**, 64-bit, direct NvAPI Reflex markers; the held GPU floor below needs the Sleep bypass on with pre-Sleep or marker placement, the driver-released rule needs the Sleep kept with pre-Sleep placement). A developer A/B for games whose GPU is the limit at the cap, such as Gears of War: E-Day at 120 FPS with FG 2× (GPU active plus frame generation time 16.8–17.6 ms per real frame against a 16.67 ms interval). Without it ReLimiter keeps the cap's cadence: frames drift later than it until the cadence restarts, a restart puts the next targets ahead of frames the GPU cannot finish sooner, and the output hold then holds a GPU that has no idle time, so the frame after it stretches. In such a game the held frames' restarts count for the [overload guard](#overload-guard), which can then take the holds away and give them back every few seconds.

The cadence is not a fix for overload and does not change what the guard counts. Its held floor drops out when the game's back-pressured arrival passes it: in a game that runs its frames one after another, the next frame reaches ReLimiter after the previous frame's Present has ended, so its arrival drifts later than `S` by the GPU's back-pressure, past any floor that only delays a release. Holds in such GPU-bound stretches stay on because the guard ignores restarts that taking the holds away could not change, with this switch on or off.

On, one cadence takes the later of the two limits for every frame:

- **Held frames get the GPU floor.** A held frame released at SIMULATION_START by marker or pre-Sleep placement while the driver's Sleep does not run is released no earlier than about `Ĝ(n−1) − (P/2 + F + σ)`, the floor frames that are not held already use ([Render handoff limit](#render-handoff-limit)), without the render-thread offset `w + d`, and on a rhythm (below). The pre-Sleep wait for the next frame aims for the rhythm's release.
- **Bounded by the cap's own release.** A held frame's floor is at most the cap's own release of it plus how late the GPU finished the previous frame, beyond the output's slack: `min(Ĝ(n−1) − (P/2 + F + σ), Ĝ(n−1) − ḡ + I − L − slack)`, with `ḡ` the median readiness gap (below), `L` the cadence's current lead (the newest frame's), and `slack` half the cadence's late tolerance of `I`. While the previous frame is held at its target the bound is the cadence's own release minus the slack, so ReLimiter's holds never move the floor; only the GPU's lateness does. The floor's own depth, `P/2 + F + σ`, is where Gears of War: E-Day's render thread runs; CONTROL Resonant's cap runs a frame deeper (its render thread starts 14.7 ms before the previous GPU end when the cap holds it, 7.6 ms on the floor), and an unbounded floor there sat 13.8 ms past the cadence's release. The bound takes the lead the cadence uses, not one measured from the frames the floor did not release: such a measurement stops once the floor releases every frame, and in CONTROL at 130 with FG 2× the lead then rose from 21 to 31–35 ms while the measured one stayed at 20–24 ms, so the floor released 92–94% of frames (8–11 display jumps above 4 ms per 1,000 against 1.6 without the switch). Which of the two depths applies follows the newest 128 reported held frames: a frame counts when the GPU waited at its release and its own plan did not move its target, whichever limit released it. The bound applies once 32 of them did, the floor's own depth once none of a full 128 did, and the depth stays between the two. A switch moves the floor toward the other depth by at most 0.1 ms (or a 64th of the interval) per held frame, never in one step. After a reset, and after any held frame that got no floor, the floor starts again from the cadence's own release, so once the readiness gaps are warm a floor that returns never lands at a depth no frame was released at. Counting only frames the floor did not release made the choice one-way: under the floor's own depth the floor releases most frames, and in Gears the first 32 such frames kept the bound for the rest of the session, so in its GPU-limited sections the render thread ran as far ahead as the lead allowed. Before the window decides, the floor applies at its own depth once the cadence restarted on a held frame in this producer epoch (a late source or output), and not before. A restart of a frame that is not held does not count: the first frame after a frame-generation change lands late on the new cadence while frame generation is not presenting yet, and in CONTROL that restart alone let the floor release most frames for 13 s once frame generation presented. The GPU frame period and the PRESENT_END → GPU end gaps count only frames whose pace the GPU set (not held, or reaching the queued wait after the release; for the period both frames of a pair): a held frame's GPU end follows ReLimiter's own release, so the period otherwise measured ReLimiter's cadence and the floor followed it (Deep Rock Galactic: Rogue Core at a 130 FPS cap with Adaptive cap fell to 83–89 FPS, median period 11.77 ms against 7.4 ms of GPU work). That classification never switches the floor off for a frame: an earlier test build did, and in CONTROL at 130 with FG 2× the floor came and went every 2–3 frames between two release depths 13.8 ms apart (171 display jumps above 4 ms per 1,000 against 2.7 without the switch), because the floor's own early target made its frames read as limited by the GPU. A cap or frame-generation change restarts these windows and the rhythm; the GPU frame period in use carries over until 32 new pairs exist. Without it the floor stopped for those pairs, and where the GPU limits the new cap the cadence restarted on nearly every frame until the overload pause took the holds away (CONTROL at 130 after frame generation was turned off, 11.4 ms of GPU work for a 7.69 ms interval: 27 restarts in the half second before the floor returned, then 4–7 s without holds). The floor of frames not held ([Render handoff limit](#render-handoff-limit)) takes no bound.
- **A render thread ahead of the GPU is released at the cadence's release.** The bound still moves a held frame's release by the previous frame's lateness beyond the slack. In a game whose render thread runs ahead of the GPU that delay makes no frame ready sooner, and the moved release becomes the simulation-start interval by which the driver places the real frame (the pre-Sleep wait carries it to the marker too). In CONTROL Resonant at 130 with FG 2× the floor moved 6–18% of releases 1.5–1.7 ms past the cadence's, after a previous frame 3.5 ms late at the median; at equal lateness of the previous frame those frames were ready no sooner, and display jitter above 2 ms followed them (23.9 against 12.2 per 1,000 without the switch in one session). So once the newest reported held frames show such a render thread (its last submission, the later of RENDERSUBMIT_END and PRESENT_START, came before the previous frame's GPU readiness on 32 of the newest 128; 66–96% of frames in CONTROL, none of 12,894 in Gears of War: E-Day), a bounded held frame is released at the cadence's own release, or at its arrival when that is later. The floor still decides everything else: the frame is still on time by construction, its target still follows the floor's release plus the early side, the rhythm and the early side count from the floor's release, and the pre-Sleep wait aims at the cadence's release. A full 128 without such a submission returns to the floor's release. A render thread that waits on the GPU never gets it: releasing its late frames earlier deepens the queue after a stall. At the floor's own depth nothing changes. With it, in two pairs of captures in one CONTROL session (Adaptive cap off), display jitter above 2 ms was 14.6 and 15.7 per 1,000 against 17.3 and 11.8 without the switch, release spacing and simulation-start intervals matched the switch-off captures, and PC Latency beyond the lead was 0.3–0.5 ms lower.
- **The rhythm.** With frame generation, the driver shows each real frame about half of that frame's simulation-start interval after its generated frame. Releasing every frame exactly at its floor copies the GPU's frame-to-frame noise into that interval, because the floor follows the newest GPU end. So after a frame it paced, the next frame's release is the previous release plus the mean of the newest five GPU frame periods (consecutive frames the GPU did not wait for). If that is not earlier than the floor, the release is the floor: a late start leaves the GPU idle. Otherwise it is pulled a quarter of the way toward the floor and is never earlier than the floor minus half the median GPU frame period. After a frame the rhythm did not pace, or a frame gap, it starts again at the floor.
- **Fresher GPU end.** With this switch, the expected GPU end `Ĝ` also comes from the GPU waits' own readback of each frame's GPU readiness: the FG input timestamp, or the GPU queue wait's pre-gate query. That readback arrives long before the frame's Reflex report, which is about four frames old at a GPU-paced release in Gears. For the newest frame with its readiness and output known, `Ĝ` is that frame's anchor (its readiness, or for a queued GPU wait the later of its readiness and the release) plus the median gap from the anchor to the Reflex GPU end of the newest 64 frames, plus the GPU frame period for each frame since. Every frame whose pace the GPU set adds a gap, held or not: the GPU waits count a queued wait as held whether or not the GPU reached it first, and in Gears 97.5% of GPU-paced frames reached it after the release (gap 1.53 ms, standard deviation 0.07 ms). A frame whose GPU waited at the release adds none: on the GPU queue wait its Reflex GPU end does not follow the release, so its gap would measure ReLimiter's own hold. The gap is signed, within one frame interval either side of zero. On the FG input wait the GPU end follows the readiness (frame generation runs after it); on the GPU queue wait it can come first, because the pre-gate query runs at the Present after the game's measured GPU work (Deep Rock Galactic: Rogue Core −0.21 ms on every frame of every capture, Gears of War: E-Day without FG −0.34 ms). Until this was allowed, the estimate never engaged on the GPU queue wait. It replaces the older report's extrapolation, and the PRESENT_END bound applies on top of it only from a newer frame. It needs 32 gaps.
- **A frame the GPU floor releases keeps the GPU's pace.** When the GPU floor is later than the moment the game reached ReLimiter, and the earliest release (the rhythm's, or for frames not held the floor and `w + d`) is not later than it, the GPU sets the release. The game reaches ReLimiter at its SIMULATION_START marker, or earlier when it enters the Reflex Sleep for that frame (before any wait there): the pre-Sleep wait aims at the release less its margin, so the marker often lands just after it without the game being late. Such a frame is on time by construction: the cadence never judges it late, neither at its source nor at its output, so it never restarts the cadence. Its output target is at least its release plus the early side of the lead: the `(1 − c)` quantile, `c` the **Lead coverage** (the 1st percentile at the default 99%), of how long the newest 128 frames the floor released took from their release to readiness (on the GPU waits the measured readiness itself), minus the allowance, and never more than the lead itself, so the target never puts the frame's planned release after its actual one. That is about where such a frame is ready at the earliest. When it is later than the cadence's own target, the cadence continues from it. A frame the GPU finishes early keeps the cadence's target and is held to the cap as before. When such a frame passes its output late, the next frame is still spaced after it (**FG late-frame spacing**).
- Until 32 frames were released by the floor (per output type and frame generation multiplier), the early side comes from all of the lead's samples, or while a lead window restarts after the overload pause, from the old window's median minus the allowance; with no window at all the frame is judged as before.
- **A frame the driver's Sleep released is GPU-paced too (the Sleep kept).** With the Sleep bypass off the driver's Reflex Sleep paces the game and can hold a frame the cadence has not placed: it returns after the frame's source wake `S = T − L`, so the frame reaches ReLimiter late. Judged against `S` that was a source restart (SourceLate), and each restart held a frame the driver had already placed. With the switch on, a frame is driver-released when the driver's Sleep for it returned after `S` and the game had entered that Sleep on time: its entry was no later than the judged `S` (the same lead and late tolerance, source slack included, that judge a source) plus the tolerance. The driver, not the game, then set its release, and it is a GPU-paced frame as above: the cadence never judges it late at its source or its output, its output target is the later of the cadence's own target and its arrival plus the early side of the lead, it is released at once, and nothing of ReLimiter's own delays it: no rhythm, no held floor, no release floor. While the early side is not known yet the cadence judges the frame as before, but it is still marked GPU-paced, so its readiness enters the window the early side is read from. The pre-Sleep margin does not learn from such a frame, from its pre-wait or from a too-close Sleep. The rule needs the Sleep hook's entry, which the pre-Sleep placement records for every Sleep. With the switch off, or with the Sleep bypassed, nothing changes except the two driver Sleep columns of the pacing rows. The switch gates the rule so that both behaviors can be compared in one session; the gate goes away when the rule becomes the default.
- Why (Gears of War: E-Day, FG 2× at 120, GPU the limit):
  - When only frames whose marker came before the floor counted, 21% of all frames had their marker land just after the floor after a pre-Sleep wait and had their lateness judged; nearly half of those restarted the cadence a full lead after their release, and the output hold then stalled the GPU for 6–10 ms.
  - When the early side came from the lead's own samples or from readiness corrected for earlier holds, targets landed as little as 20 ms after the floor while such frames were ready no sooner than 26.8 ms after it, so the cadence did not follow the GPU.
  - With every frame at its floor, the driver's real-frame placement followed each frame's simulation-start interval (correlation 0.80–0.86, slope about 0.55) and not the GPU gap it sat in. The interval mismatch explained 58–86% of the misplaced real frames, and the start interval had a standard deviation of 1.1–2.2 ms, against 0.2–0.8 ms under the driver's own Sleep, which averages the newest five GPU frames. A replay of the rhythm on the captured GPU timeline lowered the start interval's standard deviation to 0.81–1.22 ms; replays can rule a rule out, not approve it.
  - When the output of such frames was still judged, the cadence restarted 13 to 47 times in captures of 44–56 s, 98–100% of them on a frame the floor released, and the overload pause took the holds away up to twice per capture. The restarts came where the frames' readiness ran 5.4–7.8 ms past the early side (2.0–2.5 ms otherwise): after a stretch in which the GPU was faster than the cap and frames were held, their readiness came about 5–6 ms sooner after the release, and the early side, a quantile of 128 frames, still held those samples when the GPU became the limit again. Time within 1 s of a restart or a pause had two to three times the display jumps of the rest.
- The OSD lines `GPU-paced cadence` and `GPU-paced rhythm` (Details) count the frames the GPU floor released, the rhythm's steps and how often the GPU end came from readiness. The pacing rows mark frames the floor or the driver's Sleep released with `source_flags` bit 4 (the driver's Sleep only with the Sleep kept). With `log_level=info` a `GPU-paced rhythm:` line every 5 s gives the same counts for the last 5 s, how many held floors the cap bound moved (`cap-bounded`), how many held frames got no floor (`not eligible`: no restart yet before the depth was decided, or the bound without warm readiness gaps), which depth the held floor takes (`cap bound bounded`, `at own depth` or `cold`) with how many of the newest reported held frames waited at an unmoved release, the blend between the two depths, its switches, and per 5 s the floors at their own depth, bounded and between the two with the mean gap between the depths, whether the game's render thread runs ahead of the GPU (`render thread ahead of the GPU`, `waits on the GPU` or `unknown`) with how many of the newest reported held frames it finished before the previous frame's readiness, its switches and per 5 s the frames released at the cadence's release instead of the floor's (`released at the cap's release`), how many gaps the readiness anchor holds (it needs 32), how many frames ahead of the readiness anchor the floor extrapolated (median and largest), the rhythm's period against the median, how many outputs of such frames came later than their target plus the late tolerance (followed without a restart), and the frames the driver's Sleep released (`driver-released`). - With **Adaptive cap** and its hold room on, the FG input wait gets a hold room from the GPU need (see [Adaptive cap](#adaptive-cap), **Hold room**) while this switch is on.
- The former `gpu_paced_hold_margin` and `gpu_paced_release_smoothing` keys are removed. The hold room replaces the margin's interval. - The log warns while it is on and logs `OSD: GPU-paced cadence -> on|off` for a change. Compare long frames, jitter, GPU idle gaps, the overload pauses and PC Latency, one setting per capture in the same scene, with Reflex active.

### Driver low latency off while bypassed

`bypass_low_latency_off` (default **off**, 64-bit, Reflex games with the Sleep bypass on). A developer A/B that leaves ReLimiter as the only pacer. The bypass removes the game's Reflex Sleep call from the driver, not the game's low latency mode: the game's `NvAPI_D3D_SetSleepMode` still reaches the driver with low latency on, and NVIDIA's documentation says low latency mode paces even without the Sleep call, at a less optimal point. In Gears of War: E-Day with DLSS Frame Generation 2× at a 120 FPS cap and the bypass on, that point is inside the game's Present: the driver sleeps the Present thread in `NvAPI_D3D12_SetAsyncFrameMarker` (PRESENT_END).

On, while the bypass applies, ReLimiter sends the game's newest `SetSleepMode` parameters with `bLowLatencyMode` and `bLowLatencyBoost` cleared; every other field stays the game's.

- **Only while bypassed.** The override starts on the first Reflex Sleep that is bypassed after the game's `SetSleepMode` has been seen, and ends on the first Sleep that is not: the cap is off, pacing is suspended, the Reflex driver limiter placement, Dynamic MFG passthrough, the key set back to off, or the bypass turned off. Leaving it sends the game's newest parameters exactly. It also ends at shutdown.
- **The game's calls cannot undo it.** While the override is applied, the game's own `SetSleepMode` calls (some games send them every frame) are forwarded with low latency and boost off. ReLimiter's copy of the game's parameters never changes.
- **Why.** In the Gears capture with the bypass on, the driver's in-Present sleep touched 7–12% of frames and accounted for 39–68% of the misplaced real frames. Away from it ReLimiter already paced as well as the driver's own Sleep.
- **Measured in Gears** (same session, GPU-paced cadence on): with the key on the driver's in-Present sleep was gone (no `SetAsyncFrameMarker` call above 0.1 ms, against 2.4% of frames above 1 ms with it off) and every frame still had its Reflex latency report. Display jumps above 4 ms were 11.8 per 1,000 against 15.3 with the key off and 11.5 under the driver's own Sleep; jitter above 2 ms 81 against 104 and 85; long frames 3.7 against 4.2 and 4.8; PC Latency 50.2 ms at the median and 54.6 ms at the 95th percentile, against 52.3 and 70.1 under the driver's Sleep. Real frames more than 2 ms from the middle of their generated pair stayed at 15.2 per 1,000 against 11.5: their simulation-start interval, which DLSS-G places real frames by, followed the marker's arrival before ReLimiter's release, not the release. In a second session with the key on, **Marker forward order** **After wait** (the driver sees the release) brought jumps from 30.2 to 18.5 per 1,000 and such real frames from 31.1 to 19.5, against 16.3 and 18.0 under the driver's Sleep in the same session (within the noise of 5 s blocks); PC Latency stayed at 50.4 ms (median) and 55.1 ms (95th percentile) against the driver's 52.8 and 68.7.
- **Unknown.** The effect in CONTROL Resonant, whose render thread the driver's in-Present pacing holds before the next frame today, and in games without frame generation. Verify with captures.
- The log warns while the key is on. At INFO each change logs once: `NvAPI: driver low latency mode off while the Reflex Sleep is bypassed (game requested low_latency=N boost=N)` and `NvAPI: driver low latency mode back to the game's (low_latency=N boost=N)`. `OSD: driver low latency off while bypassed -> on|off` logs a change in the overlay.
- Compare jitter above 2 and 4 ms, long frames, the frames the driver placed away from their GPU gap and PC Latency, one setting per capture in the same scene, with Reflex active, against the same capture with the key off.

### Source placement

`source_placement` (default **Pre-Sleep**, 64-bit, Reflex marker games) sets where the source wait happens. ReLimiter never changes it on its own. The Details lines show the result as **Placement**. State the placement with every latency comparison.

| Value | Behavior |
|-------|----------|
| **Marker** (`marker`) | Waits at the frame-start marker. |
| **Pre-Sleep** (`pre_sleep`, default) | Uses [pre-Sleep placement](#pre-sleep-placement) while the game calls the Reflex Sleep, otherwise the marker. |
| **Reflex driver limiter** (`driver`, NvAPI marker games) | An A/B experiment for frame generation; see below. |

`auto` from earlier versions loads as `marker`; invalid values reset to `pre_sleep`.

**Reflex driver limiter.** The driver's own Reflex frame limiter paces the game and ReLimiter plans and holds nothing (output `source_only`, reason `override`).

- ReLimiter sets the driver's `minimumIntervalUs` to the presented-frame interval it would pace (the rendered-frame interval with Adaptive cap and LFC applied, divided by the FG multiplier, in whole microseconds) on top of the game's newest Reflex settings. It re-applies the value only when it changes by 1% or more, at most every 250 ms.
- While the limit is applied, the game's own Reflex settings calls are passed on with ReLimiter's interval; leaving **Reflex driver limiter** restores the game's newest settings.
- It needs a game that calls the Reflex Sleep and is paced at SIMULATION_START, otherwise the marker placement is used. It also needs **Bypass Reflex Sleep** turned off.
- When the limit cannot be applied (the game's Reflex settings, `SetSleepMode`, have not been seen since launch, the presenting device does not match them, the driver call fails, or **Bypass Reflex Sleep** is on), frames are paced at the marker instead (placement `marker`), the log warns once, and ReLimiter tries again after 2 seconds, so the game is not left uncapped.
- The Adaptive cap's workload measurement keeps its CPU stages in this mode, because ReLimiter adds no wait of its own.
- NVIDIA does not document how the driver treats this interval with frame generation; captures show it limits presented frames, generated ones included, which is why ReLimiter divides by the FG multiplier.

### Pacing test mode

`pacing_test_mode` (`off`, the default; `reflex_only`; `driver_limiter`) says who paces, for a comparison capture. It is honoured only with `developer_settings=true`: without it the effective mode is `off` whatever the INI says (the saved value stays in the INI and in `g_config`). It is never in the user's panel, never entered automatically, and has no parameter of its own (it uses `target_fps`). It is a live key (`set pacing_test_mode reflex_only`) and counts in the developer overrides; the developer reset returns it to `off`.

| Mode | What runs |
|------|-----------|
| `off` | ReLimiter paces: the unified pacer on 64-bit, the present route elsewhere. |
| `reflex_only` | ReLimiter paces nothing, whatever the saved cap: the pipeline resolves to mode `off`, placement `none`, reason `passthrough`, the scheduler passes every frame through, and the game's own Sleep calls and Sleep mode are forwarded untouched (the Reflex Sleep bypass is off in effect, so a positive saved cap does not skip the driver's Sleep). It reproduces the former arm `unified_pacer=false`, `reflex_sleep_bypass=true`, `target_fps=0`. |
| `driver_limiter` | The Reflex driver limiter paces the source at the cap's interval (with the frame generation conversion, applied once): placement `driver_limiter`, rung `source_only` (reason `override`), no hold and no start plan of ReLimiter's. It reproduces the former arm `unified_pacer=false`, `source_placement=driver`, `reflex_sleep_bypass=false`. |

The owner is derived once: `unified` (the published `unified_pacer`) is the key `unified_pacer`, on 64-bit, with the effective mode `off`; a test mode takes the ownership from the key, with every effect of the key's own transition (plans, mailbox and feed retired, outstanding holds released, the law reset, the Sleep-mode epoch bumped). The observers the key gates (the queue probe's gate and its law feed, the probe source, the marker stamps, the margin end, readiness and gate probes) are left in the state the old arm left them in. The status file has `pacing_test_mode=` (the effective mode) next to `placement=`, and the `Pacing pipeline:` log line carries it.

Differences from the old arms, each deliberate:

- `driver_limiter` where the driver's limiter cannot apply (the game calls no Reflex Sleep, the route is not NvAPI markers, the driver refused the limiter, a 32-bit process) restores the game's behaviour: mode `off`, reason `driver_limiter_unavailable`. The arm paced at the marker or the present route instead.
- An idle cap (background, FG-off cap, OLED Care) passes through in either mode (`reflex_only`: reason `passthrough`; `driver_limiter`: `driver_limiter_unavailable`); the arms paced it at the marker.
- `reflex_only` on a fixed refresh display passes through; the arm at cap 0 paced at the refresh interval.

Notes on the measurement keys. Like the neighbouring developer pacing keys (`gpu_paced_cadence`, `bypass_low_latency_off`, `source_placement` and the rest), `pre_sleep_precise`, `driver_low_latency_off`, `driver_limiter_hold` and `gpu_start_probe` are read from the INI whether or not `developer_settings` is true; `developer_settings` shows the overlay group and, alone, enables the driver sleep status poll (`sleep_status_every_frame`). With `pre_sleep_precise` the pre-wait's target is committed as the frame's release target: when the pre-wait reached it, the wait at SIMULATION_START does not run (the recomputed lead cannot move it later). The commitment holds only within the cadence it was made in: the same grid epoch, timing mode and exact grid interval (a difference of 1 µs or less counts as the same); a cadence restart (for example `OutputLate`), a cap change, any interval change (a governor step included) or frame generation factor change, or a mode change invalidates it, and the marker-site wait then runs to the new wake. `gpu_start_qpc` is an upper bound (the sampler's time after it observed the completed Signal), not a GPU timestamp. With `gpu_start_probe` on, frames under frame generation also get an observer sample, so their rows carry the probe pair next to the FG readiness record. `driver_limiter_hold`'s limiter apply is nonblocking: while a SetSleepMode is in flight the apply is left pending and repaired at a later frame (no guarantee of the next).

Marker stamps (`unified_queue_upstream` at 1, telemetry only: nothing in the pacer reads the stamps; `src/marker_stamps.h/.cpp`). ReLimiter stamps the game's own SIMULATION_END, RENDERSUBMIT_START and RENDERSUBMIT_END in its marker hooks, on the thread that sends them, at arrival (NvAPI `SetLatencyMarker` before the driver call, Streamline's `slPCLSetMarker` at hook entry; the markers ReLimiter injects for games without Reflex and RTSS's markers are not stamped), because the driver's report of the same markers reaches ReLimiter 2.5–3 frames late. A stamp belongs to a frame named by its complete key, the marker domain (NvAPI or PCL), the producer epoch and the frame ID, all frozen at the hook's entry, before any admission step that can be descheduled, together with the ring's reset generation, and checked again at publication (in the Streamline PCL hook the capture is the first step after the clock read, before the frame token is resolved, so a call whose own token step rotated the epoch publishes nothing: the first marker of a resumed PCL lifetime, a SIMULATION_START, has no stamp); a reader (the pacing row) asks for the complete key, so an ID of the other domain or of another producer epoch finds nothing, and a hook that was suspended across a controller lifecycle reset or a producer epoch change publishes nothing into the new lifetime (it is dropped when the generation or the epoch is no longer the captured one). A marker stamped twice for one frame keeps the sample with the latest QPC, whole (its QPC, cycles and thread ID together). The ring holds 256 slots; a writer claims a slot with one compare-exchange and drops the stamp rather than wait, a reader gets a consistent copy or nothing, a later frame takes a slot over, and the ring is cleared at every controller lifecycle reset. A frame's stamps are read when its pacing row completes, not when its Source record is pushed (that record is built at the SIMULATION_START release, before any of the three exists). A stamp is one clock read and a few atomic operations, no lock and no allocation; with the key at 0 a marker call pays one relaxed load and a branch not taken.

Thread CPU time of the marker spans (`unified_queue_upstream` at 1; recorded only, nothing reads it yet). The same hooks also read the sending thread's CPU cycle counter (`QueryThreadCycleTime`) and thread ID at SIMULATION_START, SIMULATION_END, RENDERSUBMIT_START and RENDERSUBMIT_END. A span's CPU time is the cycle difference of its end and start marker divided by the cycle rate; it exists only when both markers came from the same thread and the rate is known. The rate is the TSC's, from clean clock pairs read one per cycle on the telemetry worker (no spinning for it, never on a marker call): each pair is the TSC read between two QPC reads and is rejected when that bracket is wider than 5 µs (a preemption inside a pair would shift the TSC against the QPC and publish a rate off by tens of percent; at the usual 10 MHz QPC the bracket is 0–2 ticks, and the 5 µs bound limits the pair's time error to 2.5 µs, 5e-5 of a 50 ms interval); the pair's time is the bracket's middle. Three pairs, each interval at least 50 ms, give two interval rates that must agree within 0.1%, otherwise the oldest pair is dropped and the next one waited for (4 times, then no rate); the rate is that of the whole span. It is used only when CPUID reports an invariant TSC (leaf 0x80000007, EDX bit 8) and when the thread cycle counter is verified to count TSC ticks: `QueryThreadCycleTime` is documented as a cycle counter, not a clock, so once, on the worker, a busy section of about 5 ms compares its thread-cycle delta with the TSC delta of the same section and the two must agree within 5% (a reading below that can be lost CPU time and is tried again, up to 3 times; above it the counter is not the TSC's). Without that the rate stays unknown and the CPU cells are empty for the launch. The span's duration minus its CPU time is how long the submitting thread waited inside its own span (for the render thread: for the GPU or a lock rather than building commands). The pacing row carries `render_submit_cpu_us` and `sim_cpu_us`, the START markers' thread IDs `render_submit_tid` and `sim_tid`, and the END markers' `render_submit_end_tid` and `sim_end_tid`, so a game that sends a span's markers from two threads is visible (its CPU cell is then empty); every cell is empty with the key at 0 or when a value is missing.

`gpu_queue_probe` mechanism and cost. The adopted queue is the queue the game's frames are submitted on: without frame generation the presenting queue (the queue of ReShade's present event), with frame generation the source queue of the frame generation input; never Streamline's presenter queue. One real frame is one boundary, at the point where ReLimiter's present-time work for the frame is enqueued, reached whether or not readiness or the gate is eligible (so also with the pacer passing through). Without frame generation it is the readiness site of the Present (`GpuReadinessCall`, in front of its eligibility checks; the presenting queue is noted for it by `GpuReadiness_OnPresent`, which runs for every Present of the selected D3D12 swapchain), tagged with the (swapchain generation, present sequence) of the Present's span, which the Present's pacing row carries; a Present without a span has no identity (its frames would be untagged and never emitted), so it neither adopts a queue nor delimits a frame. With frame generation it is the real frame's input, delivered by the Streamline handoff independently of the gate's demand and policy (the gate's own input, `GpuPresent_BeginFgInput`, delivers the same boundary when it runs; a repeated frame key is dropped, so one boundary per real frame): the frame's marker is recorded whenever the key is on (`ProbeRecordMarker`: frame, producer and controller present, frame generation observed by the native gate, producer epoch and controller of the current context, one input per frame), the outermost proxy Present scope takes it if it is fresh (within 250 ms) and still current (the same checks again), and the first queue `Signal` inside the scope (seen by the shared queue detour, `StreamlineHandoff_ProbeSourceSignal`) names the source queue and delivers the boundary there. The marker is the scope thread's own (claimed) or, when the engine hands its markers over across threads (Gears), the newest one another thread published into the probe's own hand-off slot (taken exactly once by the game's outermost proxy Present, which frame generation never calls): this does not use the gate's cross-thread verification, which is lost while frame generation is on, so what the probe leaves unverified is the one thing that verification checks (that Present(n) takes marker n and not n - 1); the key it uses is the one the Present's pacing row takes from the same newest marker, so a frame is attributed to the row the pipeline itself attributes that Present to. What the gate additionally requires (the qualified fences, the plugin site, the binding epoch, a readiness demand) is not required. The boundary is tagged with the frame's key (`PacingFrameKey` NvApiFrame, producer epoch, source frame id: what the pacing row of the real frame carries; the joiner matches it first) and, as the secondary identity, the input's swapchain generation. The readiness-site boundary is not used while frame generation is on (the native gate's frame generation observation or the frame generation flags), because that Present is Streamline's presenter, twice per real frame; nor within one second of the last frame generation input boundary (it neither adopts nor asks for another adoption: the flags can lag, and every flip of the adopted queue between the presenting queue and the source queue is a teardown and an adoption that yields only invalid frames; the frame generation input boundary may always switch the adopted queue), so the first non-frame-generation frames after frame generation stops can be lost for up to one second. The gate's hold `Wait` enqueue is not a second boundary while a keyed boundary is open (one logical boundary per real frame): a submission another thread enqueued between the keyed boundary and the hold's `Wait` marks the frame (an overlap submission invalidates it) instead of splitting it, and a hold `Wait` with no keyed boundary before it delimits the frame by itself (untagged). The first boundary with the key on claims the session start atomically (compare-exchange Idle to Starting, so one thread initialises even when the Present thread and a frame generation callback both see Idle), takes a COM reference on the queue and its device, logs the adoption once (queue, which site adopted it, device) and starts one thread, which makes sure the native queue detours are installed (once per process, by the same installer the Streamline queue hooks use: `StreamlineQueue_EnsureHooks`, the one owner of the detours of the native `ID3D12CommandQueue::ExecuteCommandLists`, `Signal` and `Wait`, vtable slots 10, 14 and 15; the probe only adds calls to them and never hooks anything of its own), creates the probe's own fences and a calibration helper thread, calibrates, and only then publishes the queue to the detours. For any other queue, for the adopted queue with the key off, for a nested call (ReLimiter's own submissions inside the gate's owned scope or the Streamline handoff's) and for ReLimiter's own timestamp submission, the probe's calls in the detours return after one load and a compare; a queue `Wait` on any other queue touches no state (it is only counted). A `Wait` on the adopted queue for a fence value that was already reached (`GetCompletedValue` at the call) is satisfied: it never becomes a queue packet and cannot block, so it is counted and sets no state (fence values are monotonic; the one edge is a CPU Signal of a lower value, which can lower the completed value). Every unsatisfied `Wait` on the adopted queue is a Wait event: its enqueue time is read at the detour's entry, the original runs, and right after it returns the probe signals one value of its fence (the Wait fence), whose completion stamp is the Wait's release (the queue reached it, because the Signal is queued behind the Wait); the event carries the number of submissions issued before it, the entry QPC, the release value and the QPC after that Signal returned, the waited fence and its value; a Wait whose Signal was not issued (lock timeout or a failed Signal) carries release value 0. The gate reports ReLimiter's own hold `Wait` (and the frame generation input tickets') when it releases it (`GpuQueueProbe_OnHoldRelease`, from the CPU Signal of the time fence on the gate's worker, with the QPC at which the Wait was enqueued and the release QPC), a Hold event that pairs with the Wait event of the same fence and value; with the key off the gate pays a load and a branch at each of its two sites. On the adopted queue, for the outermost `ExecuteCommandLists` call, the probe takes a per-queue flag, reads the QPC (`enq`), lets the original run, signals the done value right behind it (before the Streamline handoff's own post-call work), and pushes one event into a bounded wait-free ring; there is no fence in front of a submission any more (the Wait fences replace it: a submission's start is derived from the releases of the Waits in front of it); nothing blocks and nothing is allocated. All probe fence values (done and Wait) are claimed and signalled under one lock, so the value order is the Signal order on the queue; a Signal that cannot take the lock within 50 µs (a QPC deadline) is lost and counted, and the boundary publication has the same bound. A second submitting thread finds the flag taken and goes through untouched: that call is a lost event for the core, is tracked until its native call returns (a boundary published meanwhile is `overlap`), and when a boundary fell between its entry and its return it also invalidates the frame it lands in. Every publication carries the session generation and is dropped when the session changed meanwhile. The rundown at the end of a session waits (bounded) for the in-flight submission, for the tracked contended calls, and for the boundary callbacks, hold releases and unsatisfied Waits, which are admitted into the session by a counter incremented before their session checks, revalidated against the session generation after admission, held through publication and released last; a Wait that returns after the session changed publishes nothing into the new one. Ordering between threads is a non-blocking protocol: a boundary is published between two increments of a sequence (odd while in progress) and is `overlap` when a submission is in flight; a submission records that sequence and the queue Wait sequence when it enters and when it leaves, and the number of Waits in flight when it enters, and is `overlap` when a boundary or a Wait could have fallen inside it; a Wait event is `overlap` when a submission was in flight or issued, or a boundary published, between its entry and its fence. The completion thread (TIME_CRITICAL, named) waits on one auto-reset event, the calibration event and a stop event, at most 100 ms, never on a poll of the fence; the fence values are registered on the event at least 32 ahead of the producer. Before it blocks it drains an event that is already set and reads `GetCompletedValue`; on a wake it reads `GetCompletedValue` again, then takes one QPC, and stamps every outstanding value up to the completed one: only the lowest value, after a wait that blocked, woken by the event, for a value that was incomplete when it was registered and when the thread was about to block, is event-awaited (lateness: the calibrated latency; a completion between that last read and the block, the thread being descheduled in between, is the residual case); every other value is a late pickup, whose lateness bound is derived from the entry QPC of the submission or Wait and the completion lower bound of the value before it; `gq_stamp_late_us` reports the maximum per frame. The calibration is the wake latency of a blocked thread: the worker arms a value of a private fence on the calibration event and blocks, the helper thread (normal priority, bounded timed waits on the stop event) takes a QPC immediately before signalling that value from the CPU, and the worker's wake stamp minus that QPC is a sample (it includes the Signal call, so it is conservative; a sample whose event was already set when the worker was about to block is dropped); 16 samples are taken 1 ms apart before the probe runs, then one every ~31 ms; the nearest-rank p95 and the maximum of the last 16 go to the core. The pure core (`gpu_queue_probe_core.h`) does the accounting; the thread drains it and pushes each finished frame record to the pacing telemetry and, when the queue law's feed is on (`g_gpu_queue_law_feed`, one load and a branch otherwise), to the law's feed (`GpuQueueLawFeed_Push`). The detours stay installed once installed (with the key off the probe's part is one load and a branch, and the thread ends within 100 ms). A changed adopted queue, a destroyed queue, key off or shutdown ends the session: the probe's calls stop, an in-flight one is waited for up to 200 ms, the helper is joined, the open frames are flushed incomplete, and the references are released once the GPU has reached the last fence value (retained when it has not). A device removal, or a failed Signal, fence, `SetEventOnCompletion` or hook install, ends the probe for the session with one log line. The cost summary is logged once per session when it ends (key off, shutdown, a failure, another queue) and, when the session's thread had not got to it, by the shutdown call itself: the boundaries, submissions (and submissions per frame), contended calls, the fences by kind (done, Wait release), the queue Waits on the adopted queue (satisfied and ignored, unsatisfied and fenced), the Waits on other queues (ignored), the fences lost, the ambiguous cases by reason, the frames emitted to the telemetry (the number joined to a row is the joiner's and not known to the probe), the invalid frames by reason (overlap, incomplete, untagged, lost events), the calibration and the core's counters. Expected for a game that submits about 47 packets per frame with about 9 unsatisfied queue Waits per frame: about 47 submissions, about 45 done fences and about 9 Wait fences per frame, one boundary per real frame.

Cost of `gpu_queue_probe`, measured with a throw-away benchmark (a real NVIDIA RTX PRO 6000 Blackwell, an idle GPU, empty command lists on one direct queue, no game and no Streamline pass except where stated; the figures are means unless a percentile is named): `QueryPerformanceCounter` 0.015 µs; `ExecuteCommandLists` of one empty list 0.08 µs; `Signal` 1.04 µs (p99 4.8 µs); `Wait` on a fence already reached 2.6 µs; `GetCompletedValue` 0.03 µs; `SetEventOnCompletion` 0.86 µs for a value 32 ahead and 0.97 µs for a completed one, with at most 64 registrations pending. The probe signals one fence value behind every submission (done) and one behind every unsatisfied queue `Wait` (Wait release), nothing in front of a submission: about 54 fences per frame for a game with 47 submissions and about 9 unsatisfied Waits (the measured figure for the earlier scheme with a front fence was 5.7 µs per submission and 251 µs per frame with 87 fences). In the benchmark a frame of 47 submissions with 54 fences costs the producer about 60 µs against about 11 µs without them, so the fences add about 0.05 ms per frame (about 1 µs per Signal; the ring push and the QPC reads are inside it); modelling the extra `ObserveSignal` pass of the shared detour (callback guard, depth, last error) for each of its Signals adds about 2 µs per frame. This holds only while no thread waits for the fence: with the completion thread registered and woken for every completion, the Signal call itself rises to about 7.5 µs (p50 6.5 µs) and the same frame costs the producer 0.42 ms (0.49 ms in another run), that is about 0.4 ms per frame more, four times the 0.1 ms budget; the live figure (5.7 µs per submission) is in that range. Registering without waiting costs 0.09 ms; waking the thread only every 2 ms brings the frame to 0.28 ms but the stamps are then 0.3 to 2.8 ms late; registering only the next value does not help (0.40 ms). The Signal lock the fences are serialised by is a bounded spin of at most 50 µs (a QPC deadline) that is paid only when another thread is inside a probe Signal (a hold of about 1 to 8 µs); a contender that exceeds it loses its fence (counted, the frame invalidated) instead of waiting longer. The wake latency of a TIME_CRITICAL thread blocked in `WaitForMultipleObjects`, CPU-signalled fence to event: p50 3.9 µs, p95 7.7 µs, max 16 µs when idle; p50 19 µs, p95 41 µs, max 74 µs with a submitting thread and four spinning normal-priority threads. For a GPU-signalled done value on an idle GPU, the completion thread's stamp minus the return of the Signal call is p50 9.6 µs, p95 48 µs, max 306 µs. The completion thread's own work per wake after the stamp is about 0.1 µs. Gaps: the GPU was idle (a busy GPU delays the completion, not the call), no game or driver load on the other cores, empty command lists, no real Streamline hooks; the larger cost with the thread waiting was not explained further than the Signal call getting slower while an event is registered and woken on the same fence, so whether it also appears under a game's load is unmeasured.

`gpu_queue_probe` ordering and cost details. Every probe Signal on the adopted queue (the done fence in the `ExecuteCommandLists` detour and the Wait-release fence behind an unsatisfied `Wait`) runs inside the queue hook's recursion suppression: the Wait-release Signal runs in the forward call of `ObserveFence`, before its depth guard ends, so neither `ObserveFence` nor the Streamline handoff sees it (outside the guard it would be an outermost application Signal, which the handoff takes for a repeated source Signal of the proxy Present and so invalidates the frame generation route); the calibration signals a CPU fence, which no queue hook sees. The probe is invisible to the handoff. ReLimiter's own hold `Wait` is announced to the probe (`GpuQueueProbe_OnHoldAnnounce`: fence, wait value, enqueue QPC) before the `Wait` is enqueued, so that a frame is not resolved before the hold's release arrives (`GpuQueueProbe_OnHoldRelease`, after the CPU Signal that releases it); the stamp the gate keeps for them is written before the ticket is published as armed and cleared when the ticket is freed, never at the release. Two `Wait` sections of different threads on the adopted queue that overlap (one still open when the other begins, or opened or closed between a Wait's entry and its fence) mark the Wait events they affect `overlap`, because the first Wait's fence could then measure the second's release; the core invalidates the frames. Each pushed frame record carries the probe's session generation (not in the CSV). Nothing else on a submitting thread waits on anything the completion thread or the driver can hold: the boundary publication wait is the same 50 µs bound, the rundown and teardown waits are on the completion thread only, and `GetCompletedValue` is a read.

`gpu_queue_probe_source` (developer live key, 0 or 1, default 1, 64-bit; effective only with the probe on). Without frame generation the probe watched the queue of ReShade's present event, which is not the render queue where Streamline's swapchain proxy makes the presenting queue a separate queue: it submits a few command lists per frame and Waits once per frame on a fence the main render queue signals, so the probe's GPU side was the proxy's copy queue. At 1 the probe finds the queue by a dependency rule (`src/gpu_queue_dependency.h/.cpp`, pure). The shared queue detours record, for every queue and only with the key on, its outermost `Signal` (fence, value, queue, QPC), its `Wait`s (queue, fence, value, QPC, thread; for a Wait of the presenting queue on the Present thread the id of the Present scope it belongs to: the scope between ReShade's present event and finish_present, or the next one when the Wait was enqueued in front of it, as when the swapchain proxy waits for the render queue and then calls the native Present) into two tables of 512 entries each, and its command lists (eight queue slots); ReLimiter's own Signals and the probe's own run nested in the detour and are not recorded. The tables serve the adoption decision, not the per-frame record, so they are plain arrays behind ONE small spin lock (`Tables`), and EVERY path that takes it, on any thread, takes it with the same bounded spin (`Tables::kSpinBound` = 512 test-and-set iterations with a pause, never a kernel wait; there is no unbounded acquisition): the Signal, Wait and Execute detours (game threads) DROP and COUNT an event that does not get it (`events dropped on a lock time-out` in the summary); the evaluator's pull is SKIPPED and COUNTED (`pulls skipped`); a decision publication that does not get it is DISCARDED and counted (`decisions discarded`, `lock time-outs`); a clear is never lost (below). The evaluating thread, the detours' game threads and the probe thread all use the one bound (a pull or a publication holds the lock for a short copy or a few instructions, so a time-out is rare and the cost of one is one frame's evaluation deferred, not a stall). Cost per Signal or Wait detour call with the key on: uncontended one interlocked exchange, one epoch load, the record write and one release store (about 20-30 ns; an Execute of a queue whose row exists takes no lock, see the per-call cost paragraph below); worst case the spin bound (a few microseconds up to roughly 20 on a CPU with a long pause instruction), after which the event is dropped. With the key off (or the probe off) the lock is never taken: the call sites are one relaxed load and a not-taken branch, and queue destruction (which clears) is gated on the probe being on, the key being on and something having been recorded. ONE epoch (`Tables::Epoch`, distinct from the frame counter entries age by) is advanced by every clear (swapchain, presenting queue or queue lifetime change, any destroyed queue, the key turned off at teardown), which may run on a game thread (the thread that releases a queue) or the probe thread: `Clear` advances the epoch at once with an atomic add every reader sees and resets the tables if the lock comes free within the spin bound; otherwise the reset is a pending clear (`clears applied later`): the next successful lock holder, a detour writer or the pull, notices that the epoch it holds the tables for is behind and resets the tables before its own work, once, so a clear is neither lost nor repeated. A published decision carries the epoch it was computed for and is valid only while that epoch is current, so a clear invalidates it at once, before the tables are reset. A window whose epoch changed restarts and adopts nothing. An evaluation never runs under the lock: `Reader::Pull` copies only the entries recorded since its previous successful pull (about 512 at most; more than a table holds between two pulls are counted as lost) and the command list rows under it, then the resolver and the evaluator run on that copy, and the lock is taken again only to publish the decision; a submitting thread's detour never waits behind an evaluation. A skipped pull keeps per-frame resolution exact: the cursors do not move, the frames stay in the consumer's backlog (eight frames, each with its own scope, window and key), and the next successful pull, which copies the entries of every frame since the previous one (none lost, none twice), resolves the backlog in order with each frame's own scope and window, so a frame is never evaluated with a part of its Signals missing and never counted as having zero; eight skipped pulls in a row restart the window (`backlog overflows`). A window in which any Signal, Wait or command list record was dropped or lost (a lock time-out, a queue beyond the eight rows, entries overwritten before they were copied) does not qualify for any queue (reason `records were dropped or lost`): the loss counter is snapshotted BEFORE the window's first frame (the value the previous frame carried), so a drop inside the first frame counts, and a lost record can never hide a second boundary or change the winner. A pull that finds new loss poisons every window any affected frame belongs to (`Evaluator::BeginPull(loss, pending_frames)`): the loss belongs to a frame that was current when the pull saw it (its events were not all recorded, the NEXT pull resolves it, production's one-frame lag) or to a frame still waiting for resolution (a backlog can cross a window boundary), and one counter cannot tell them apart, so each of the next `pending_frames + 1` frames resolved, the backlog and the one current at the pull, poisons the window it belongs to, and the poison outlives the pull that saw the loss. Each frame is resolved once the following Present's boundary (the readiness site) has pushed it: the presenting queue's Waits of that Present scope, each matched to the Signal of the SAME fence and value (not the newest Signal of the fence) by another queue, add that queue; its Waits inside the frame's window add the next (3 hops at most); a fence no other queue signals (a CPU or kernel sync object) ends the branch, a (fence, value) signalled by two queues is counted as an ambiguous Signal (and as an ambiguity of the join when it is one of the presenting queue's own Waits). Fence lifetime: no hook on fence release and no fence is retained (an AddRef while a table entry names the fence would delay a game that waits for the fence's reference count or reports live objects at device teardown). Instead a Signal joins a Wait only with the same fence address and value, recorded within two windows of 64 frames of now and within 4 frames of the Wait, and the tables, counters and window are cleared on a swapchain, presenting queue or queue lifetime change (a session watching by the rule is stopped). Accepted residual risk and why it cannot adopt a wrong queue: a fence pointer reused for a CPU-signalled fence joins a stale Signal only when the reused address carries the same value within 4 frames; that adds one edge in one frame. Adoption needs one Signal and one first-hop edge on the same fence in every frame of a 64-frame window (and the dependency queue reached in every frame), so a false join can at most make a window not qualify (the law then runs on its fallback for that window), never adopt a different queue (tested); the argument also rests on the core invalidating the frame after an irregular boundary (a boundary or tag that does not match, counted as `irregular_boundary_events`), so a split frame is never reported as valid. At the end of a window of 64 frames the candidates reached in every frame are compared by command lists per frame: the most wins, a tie (among the dependency candidates, or with the presenting queue) and no dependency give the presenting queue (adopted at once, role 1, the boundary at the readiness site as before). A queue reached in only some frames of the window with AT LEAST as many command lists as the best full candidate (a tie included) leaves nothing adopted for the window (`NotQualifiedPartial`: its dependency is missing or ambiguous in the other frames, a lost Signal, a false or ambiguous join), rather than falling back to a queue with less work or letting an equally busy full candidate win; a partial candidate never wins. A winner that is not the presenting queue (role 3, `render queue by dependency`) is adopted only when its boundary can be joined to the frame identity: it is one hop away, the presenting queue reaches it through exactly one dependency (fence, value) per frame (a deeper queue may be reached through several: a multiple dependency, not an ambiguity), always the same fence, the adopted queue Signals that fence exactly once per real frame (EVERY Signal of that fence by that queue between the previous frame's matched Signal and this frame's, whatever its value, is counted, so a repeated Signal of an older value is seen; otherwise a frame would be split by its Signals while only one is waited on), the matched value rises from frame to frame (a separate check), and the presenting queue's Wait of it belonged to the Present scope of a Present that carried the frame's key every frame. Otherwise nothing is adopted: the probe reports no frames (the law runs on its report fallback, not on the presenting queue), one log line per transition names the reason. For role 3 the frame boundary is the adopted queue's own `Signal` of the dependency fence (a boundary event with the value as its id and no identity) and the presenting queue's `Wait` of the same fence and value pushes the tag (generation, present sequence, key; at the Wait when the Present's identity is known, else at the readiness site); the core defers a frame until its tag arrives. Each boundary and tag reads the session generation before its role, fence and queue checks and is checked again after admission into the session (session generation, role, fence, queue), so a call that paused in between never publishes into a replacement session. The decision is re-evaluated at window ends only: another queue wins, the dependency disappears or an unjoinable winner stops the session (the session generation changes, the law's window restarts) and the next window decision is adopted without further hysteresis. An adoption continues otherwise: the destruction of a queue that is neither the adopted nor the presenting one restarts the evaluation window (the epoch advances) but does not retire the adoption, because it says nothing about the adopted queue, whose boundary and tag mechanism does not use the tables, so its samples stay valid and stopping the law's feed for a window would disturb pacing for nothing; the adoption lasts until a completed window decides otherwise or the adopted queue, the presenting queue or the swapchain goes away. With a frame generation input adoption is unchanged (role 2); the rule is evaluated at the readiness site of those Presents for a diagnostic and logged once when its answer differs from the adopted source queue. The held output of the gate stays on the presenting queue: its announce, release and enqueue calls are no-ops for any other queue (no pool entry, no deferral), so a role 3 record's hold_block reads 0 and the queue law uses its report-based rule for the credit there (`queue_role`, CSV `gq_queue_role`). The hold's announce (`GpuQueueProbe_OnHoldAnnounce(native_queue, fence, wait_value, wait_enq_qpc, law_hold_sequence)`) carries the sequence the queue law assigned to the grant of the hold (0 = not a law hold; a zero-length hold never has one) and the core attaches the sequence of the hold a frame was queued behind (the hold that gives its hold_block) to that frame's record (`law_hold_sequence`, not in the CSV; 0 when no hold matched or the hold had none), whatever the record's valid bits, so the law can settle an invalid or irregular frame's hold. A teardown with nothing ever recorded (the key never on) clears nothing and writes nothing. Log: the adoption line names the role, the hops and the command lists per frame of each candidate; the per-window line and the session summary give the windows, the frames evaluated, the frames with an ambiguous join (the presenting queue's own dependency: a first-hop queue reached through several (fence, value) pairs, or one of its Waits signalled by two queues), the frames where a deeper queue was reached through several fence values (a multiple dependency, not an ambiguity), the frames with a missing join, the frames with the dependency fence not Signalled exactly once, the records dropped or lost in the window, the Waits no queue signals, the ambiguous Signals, the events dropped on a lock time-out per table and for command lists, the queues beyond the rows, the decisions discarded (a changed epoch or a lock time-out), the Present thread pulls skipped, the backlog overflows, the clears applied later by the next lock holder, the boundaries and tags pushed and the core's join counters (`join_ambiguous`, `join_missing`, `untagged_boundaries`, `tags_unmatched`, `irregular_boundary_events`, `frames_invalidated_by_irregular_boundary`). Open points: a winner two or three hops from the presenting queue cannot be joined (only the presenting queue's Wait has the Present's identity) and is reported as not adoptable; whether the proxy's Wait is enqueued on the Present thread (inside or in front of the Present scope) is not verified: a Wait of another thread has no scope and shows as a missing join; the frame of an evaluated Present is assigned by Present scope for the presenting queue and by the time window between two readiness sites for the others, which is approximate for deeper hops; a game with more than eight queues loses the command lists of the rest (counted as overflow, so no window qualifies); any destroyed queue restarts the evaluation window (the epoch advances); the first frame after a reset has no previous edge to count Signals against; the first 64 frames of a session carry no data (the window).

`gpu_queue_probe_source`, pending frames and counts (refinements of the paragraph above). The evaluator's mirror of the tables keeps the newest 512 entries of each; before every pull it is told the oldest time an unresolved frame still needs (`Reader::SetNeededSince`: the oldest pending frame's window begin, or the previous edge's Signal when that is older), and a full mirror overwriting an entry at or after it counts that as loss (a crowded game with hundreds of Signals per frame would otherwise lose the early extra Signal of the frame being resolved and let a window with two dependency Signals per frame qualify): the pull that evicts it poisons the frames it resolves and the current one like any other loss. A backlog overflow (eight skipped pulls) restarts the window but keeps the previous successful pull's loss baseline (`Evaluator::pull_loss`), so loss the overflowing pull discovers still poisons the retained frames and the current one. The command list counts of a window are the difference of boundary snapshots: each frame carries the command list counters of its own boundary (one bounded locked copy taken when the boundary pushed it; `Evaluator::CountAlign::Exact`), a window starts where the previous frame ended and ends at its last frame's snapshot, so a burst in the window's first frame is counted and a pull-time count that includes the next frame's work is not. The first frame after a reset (or an epoch or presenting queue change) is a BASELINE only: its end counters and first-hop edges seed the next frame, it is not one of the window's frames, and the 64 frames that follow are evaluated, so the first window divides by 64 over 64 frames like every other (a poison that touches the baseline frame carries to the first window). A frame whose boundary snapshot did not get the lock takes the counters of the pull that resolves it (`Inexact`): EVERY such frame poisons its window, an interior one too, and the window that starts after it does not qualify either (reason `records were dropped or lost`). Adoption acts on one immutable copy: the Present thread that holds the evaluator guard copies the decision (queue, role, fence, hops, candidates) together with the published queue into a `dq::AdoptionSnapshot` before it releases the guard (`MakeAdoptionSnapshot`, valid only for the published, current, adoptable winner), and `Boundary` and `Adopt` use only that copy (never a later read of the evaluator's decision, which another Present thread may reset on a lifetime change); a Present thread that did not take the guard has no snapshot and adopts nothing that frame.

`gpu_queue_probe_source`, the rule's own per-call cost and where it evaluates. Detour side. `Tables::NoteExecute` (every outermost Execute of every queue) takes no lock when the queue's row exists in the current epoch: it loads the epoch, the row count, the row's queue word and its packed counter word `[tag:20 low bits of the epoch][calls:16][lists:28]` and adds the call with ONE compare-exchange (at most `Tables::kFastAttempts` lost races, then the locked path). The tag makes the add fail against a row that a clear re-created for another queue, so an add of one queue never lands in another queue's row (a caller that loaded the epoch before a clear is ordered before it: its add lands in a row the reset discards); a pending clear (epoch advanced, tables not reset yet) sends the call to the locked path, which applies it first; a field about to overflow (65535 calls, 2^28 lists, one call above 2^28) is spilled into the exact 64-bit base counters by a lock holder, so `Row::lists` and `Row::calls` seen by `Reader::Pull` and `Tables::SnapshotRows` stay exact and unbounded. Anything new (a queue's first Execute in an epoch, a ninth queue, a spill, a pending clear) takes the old bounded-spin locked path, where the drop-and-count rules are unchanged (`DroppedLists`, `RowOverflow`); a known row never drops, so a window loses few records under a held lock. Cost per Execute: four loads, a scan up to the queue's row and one compare-exchange, no lock (the locked path costs one interlocked exchange, a row scan of up to eight rows, two stores and a release store). `RecordSignal` and `RecordWait` keep the lock on purpose: they log EVERY Signal and Wait (the resolver matches (fence, value) and counts every Signal), cost one interlocked exchange (the lock), the entry write and a release store, no row scan, and a claim-and-write ring would still need a second read-modify-write to keep a writer that was preempted across a clear and a lap from tearing a newer entry. Evaluation. The Present thread's part per real frame is `DependencyBoundary` (`FrameFeed::OnBoundary`): the scope's identity and tag push, the three-boundary ring, the frame the Present closes with the command list counters of its own boundary (`Tables::SnapshotRows`: one bounded locked copy of at most eight rows, inexact when the lock does not come free) and the loss counter of that moment (`Tables::Lost()`, lock-free), pushed into a bounded queue of `FrameFeed::kBacklog` (8) frames. The evaluation (`FrameFeed::Evaluate`: the pull of the tables, `ResolveFrame`, the evaluator, the publication, `DependencyOnDecision`) runs on ONE thread at a time (the evaluator guard): the probe's worker at the end of every step (`DependencyDrainOnWorker`, outside the step's timing) while a session runs; in every other phase (no session before the first adoption, starting, stopping, dead: there is no worker) the Present thread itself, right after its boundary (`DependencyEvaluateAfterBoundary`), so the rule works before any worker exists and the first adoption is decided by the Present thread's own evaluation; while a session runs the Present thread evaluates only when `FrameFeed::kHelpAt` (4) frames wait (the worker blocks up to `kWaitMs` between wakes). No new thread. Nothing is pulled when no boundary is new. The windows of 64 frames, the loss handling (a batch of frames is resolved as one pull at the Present that pushed its last frame: that Present's loss counter, poison of the batch plus one frame, counters of each frame's own boundary, the frame counter its entries age against taken at its Present), the epoch/clear protocol, the retain gate and the adoption snapshot taken under the evaluator guard work as described above, whichever thread evaluates; frames of an older generation or older tables epoch are discarded, never evaluated against cleared tables. A producer that finds the 8-slot queue full drops that frame and the window restarts; it needs a consumer eight frames behind. Tests (`tests/test_gpu_queue_dependency.cpp`): the Execute fast path against a model of the locked path under a randomised script and under concurrent writers with clears (never mixes queues, exact sums, exact spill), and `FrameFeed` against the per-Present evaluation modelled by `PullHarness` and against itself evaluated every 2, 3 or 7 Presents and on another thread. Only a game shows the per-call cost on the submission thread and the marker thread.

`gpu_queue_probe_source`, running adoption and queue lifetime (refinements). A window that does not qualify carries no evidence and changes nothing: while a queue is adopted it keeps the adoption (session, role, records and the law's feed continue, no stop, no role change; `dq::ApplyDecision` returns `KeepUnqualified`); only a QUALIFIED window with another result (another queue, role or fence) stops the session to adopt the new one, and the adopted queue's destruction, or the presenting queue or swapchain going away, ends it. Without an adoption an unqualified window adopts nothing. Such a window is logged at most once per session (info) and counted (`windows that did not qualify while a queue was adopted` in the dependency summary). The queue an adoption acts on is held by an owned reference taken together with the lifetime check: the Present thread that holds the evaluator guard copies the decision and takes the reference (`dq::RetainGate::RetainAtEpoch`: counted in flight, epoch re-read, then the AddRef) into an RAII ticket released on every exit path unless the session takes it over, and the queue's destroy callback (which runs before its final native Release) advances the epoch FIRST and then waits, bounded (2048 pauses; `queue destructions that stopped waiting` counts a give-up), for retainers inside that window, so a reference taken at the decision's epoch is on a live object and a queue destroyed since is never touched. If the wait gives up (a retainer descheduled inside its few-instruction window), the destroy callback takes one native reference of the queue itself and NEVER releases it (`dq::RetainGate::WaitOrLeak`): a deliberate, counted leak of one object (the references leaked are in the dependency summary), so the retainer's later AddRef always lands on a live object. With the source rule on, a boundary without a valid ticket adopts nothing (except the frame generation source, role 2), so a running-only call that finds the session idle after a stop cannot adopt the presenting queue with role 1. When the adopted queue is destroyed the law's session is retired explicitly (`GpuQueueLawFeed_RetireSession` with the session generation: the scheduler's drain empties the law's window, settles its outstanding grants and drops records of that session that are still in flight).

`gpu_queue_probe` borrowing the game's own marker (role 3 only: the render queue found by the dependency rule; roles 1 and 2 are unchanged and never take the path; no key). The probe's done marker of a submission is, by default, a Signal of its own fence issued behind the `ExecuteCommandLists` call (42 per frame in a measured game, about 0.3 ms per frame on a submission thread that is the limit). When the game itself queues a Signal directly behind every submission, that Signal is the same marker for free, and the probe only binds (fence, value) to the submission. Code: the pure rules in `src/gpu_queue_borrow.h/.cpp` (tested by `tests/test_gpu_queue_borrow.cpp`), the glue in `gpu_queue_probe_d3d12.cpp` and the Signal/Execute hooks of `streamline_queue_hooks.cpp`. The core stays keyed by the probe's own value sequence k; borrowing only changes who marks k and what the worker waits on. Mechanism: with borrowing active an Execute leave claims k without a Signal and publishes it as `pending` (a word holding k, the thread and a borrowed bit, plus a per-k slot for the worker); the Submit event is pushed when the pending marker is settled. The game's outermost Signal on the adopted queue binds it (the Signal detour calls `GpuQueueProbe_BorrowSignal` right before forwarding, after the Streamline handoff's own calls) when it comes from the same thread, of the one fence the last whole frame used, with a value strictly above the last bound value (a Signal of another fence in between does not matter). Whatever reaches the queue first instead (an Execute enter, nested ones included, a Wait, the role-3 boundary, a claim of another probe value, another Execute that entered since this one or an open Wait at the leave) SETTLES it before that call is forwarded: the probe's own Signal for k, issued under the Signal lock so a lower value is never signalled after a higher one, the frame invalid (the Submit event carries `overlap`), borrowing off until a whole frame shows the pattern again; a compare-exchange on the word gives exactly one winner between the bind and the repair, and a settle that cannot get the Signal lock gives the value up (the worker skips it, the submission is pushed without a done). A frame borrows only when the previous frame was whole: every submission followed, before the next Execute or Wait, by a same-thread Signal of ONE fence with strictly increasing values, and no Signal of that fence from another queue seen by the dependency tables (an optimisation gate, not proof: the pending protocol keeps a wrong guess harmless); the session starts with the probe's own Signals. The first bind takes ONE reference on the game's fence (the dependency tables never retain one: this is the single, documented exception), released by the worker with the session on every end path (session end, queue destruction, another adoption, failure). The worker arms an event on that fence with ONE registration outstanding per fence and waits for the newest marker only, own or borrowed (the tail stamps paragraph below); a borrowed marker issued more than the stamp guard after the Execute returned, or completed within the guard of its issue, is a late pickup (the core's existing late bound); one found complete BEFORE it was issued (someone else advanced the fence) has an inconsistent interval: the core makes it untrusted, its frame is invalid and the done chain breaks there. Waits' release Signals stay. The probe's own Signals now call the original method directly (they no longer re-enter the Signal detour, nor appear in the dependency tables). Counters in the summary line `GPU queue probe borrowing:` (marked by the game / the probe, repairs by reason, frames on the game's markers, frames invalid by a repair, late markers, completions before their issue, registrations on the game's fence, references taken and released); two info lines: when borrowing first becomes active and when it is turned off for the session (with the reason). The per-frame count of borrowed submissions is `PacingGpuQueueRecord::borrowed_submits` (CSV column `up_ql_rt_spread_us`, 0 when the probe marked all). Hardened rules. (1) Another queue signalling the pattern's or the bound fence (the dependency hook, BEFORE the Signal is forwarded; `BorrowForeignSignal`) ends borrowing for the SESSION: when a borrowed marker can be affected (borrowing active, a word pending, or a borrowed value the worker has not stamped), under the Signal lock the gate goes off and the foreign epoch rises, a pending word is settled with the probe's own Signal, and an `Invalidate` event invalidates the frame in progress and the one still open to a tag; every marker CLAIMED before the epoch rose is untrusted (the core makes a marker whose claim epoch differs from the epoch of an observation untrusted wherever one is applied, and the worker hands the rest to the core with `OnUntrusted`), so its frame is invalid and the done chain breaks there. The reason is logged once and counted in the summary line. A CPU `ID3D12Fence::Signal` of the game's fence is not observed; the bind-time check of the tail stamps paragraph below and the core's inconsistent-interval rule are the guards against it. (2) A marker between its Execute and its Submit event is visible to a boundary: writers that take the pending word (a bind, a repair, a claim's settle) raise `InFlight` BEFORE the take and drop it after pushing the Submit, and a boundary overlaps (like a busy Execute: both frames invalid) when the word is pending or a writer is in flight (`MarkerInFlight`: word first, then the count). (3) Slots: the producer claims a borrowed marker only when the worker has read the value that used the slot (`SlotAvailable`, the worker publishes its cursor); otherwise the probe's own Signal marks the value, the gate goes off and `slot reuse refused` counts it; a slot found reused by the worker (`KMode::Overwritten`, a breach) is untrusted and consumed at once (its frame invalid), never taken for an own marker, so the cursor always advances. (4) An untrusted marker whose Submit has not been processed yet is parked together with its bounds in ONE entry (64 entries; a full table drops the smallest k as a watermark, and every k at or below it without an entry is untrusted, counted, never dropped silently) and applied when the Submit arrives. (5) A value that completed before its registration has no event and calibration wakes restart the wait, so the worker runs its step on EVERY wake (event, calibration sample, timeout, stale event) and after every (re)registration, a refused one too, not only on event wakes. (6) The binding of the game's fence is closed for good by the session end (`BoundFence::Release` from any state; Closing/Released are terminal): nobody spins; a binder that is inside its retain when it closes releases its own reference when the AddRef completes (the only Release on a game thread); a second binder meeting a binder in progress gets `Busy` and its marker is settled with the probe's own Signal. (7) The claim publishes its pending word BEFORE the Signal lock is dropped (and settles a previous word under the lock), so an unsatisfied Wait on another thread can only signal an own value after the repair of this one: own values reach the queue in order. (8) Before a reference is held a whole frame only NOMINATES the fence (by address); the first observed marker of the nominated fence takes the ONE reference (a game thread AddRef, once per session) and makes the frame in progress unclean, so the whole frame that starts borrowing is of the object actually bound (a destroyed fence and a new one at the same address cannot pass as one candidate). (9) The pending word holds the full 32-bit thread id (`k` has 31 bits: past 2^31 values in a session nothing is borrowed any more). Live validation still needed: that the pattern holds in the game, the cost on the submission thread, and the equality of the records with the probe's own Signals.

`gpu_queue_probe` tail stamps. A queue runs empty only when its newest item completes, so the worker waits for the NEWEST marker only and everything else is known as an interval. Marker sequence: one sequence in probe order k across both fences (the game's borrowed Signal behind a submission, and the probe's own Signals behind unsatisfied Waits, holds, repairs and as the fallback marker); own k and game fence values are different namespaces and always go through the slot mapping. Observations are free: (completed value of the game fence, completed value of the own fence, QPC before the reads, QPC after) taken on the submission thread at every Execute enter and Wait begin on the adopted queue (`ObserveInto`: two user-mode `GetCompletedValue` reads and one extra QPC read, no lock, no allocation, no kernel call; role 3 reads both fences, roles 1 and 2 the own fence) and carried inside that item's Submit/Wait event (`obs_*` fields) so the core applies them in ring order, and by the worker at every wake and after every registration. Worker step (`gq::WorkerStep`, the pure planner in `gpu_queue_borrow.h`, driven by the worker loop in `gpu_queue_probe_d3d12.cpp`), at every wake (armed event, calibration, timeout, stale event) in this order: read T (the newest marker whose (fence, value) is fully published, never a reserved slot), take an observation, give the ARMED marker (stored explicitly: fence, value, k, session generation, registration QPC) its awaited interval only when it is covered and the wake is its own event (any other wake certifies nothing: the armed marker gets an observation interval like the rest), every other newly covered marker gets `[latest QPC it was seen incomplete, this observation's QPC]`, then register: ONE outstanding registration per fence, never re-registering a fence whose registration has not fired; with a marker pending arm T on its fence, drained arm completed+1 on each fence's event; observe again after registering and, when the armed value is already covered, treat it as a late pickup and go round again without sleeping (bounded number of immediate rounds per wake). Every wake, calibration included, and every (re)registration, a refused one too, runs the step first. The core (`OnObservation`, `OnAwaited`, `OnUntrusted`) evaluates the unchanged accounting walk on intervals: scalar fields keep their names and carry the lower ends, `empty_hi_us`, `boundary_idle_hi_us` and `min_margin_free_hi_us` the upper ends; an untrusted marker (foreign Signal, overwritten slot, lost marker) invalidates its frame and breaks the done chain until a trusted completion. A slot is consumed once its interval is closed (the worker pins no slot waiting for a stamp). Another queue's Signal of the bound game fence (or of the nominated pattern fence before the reference is taken) ends borrowing FOR THE SESSION (the hardened rules of the borrowing paragraph above); every borrowed marker claimed before the foreign epoch rose is handed to the core as untrusted when the worker closes it. Counters in the summary line `GPU queue probe borrowing:`: registrations on each fence, worker wakes by cause (armed event, late pickup, calibration, timeout, stale event), markers awaited against markers closed by observation, untrusted markers, the core's parked-table watermark hits. `PacingGpuQueueRecord::registrations` is the number of registrations the worker made since the previous record was popped (CSV 197 high part). Per submission the hooks add: role 3 with a bound fence one game fence read, and the own fence read only while an own marker is outstanding; roles 1 and 2 one own fence read; the clock reads as below; no lock beyond the existing sequencing lock, no allocation, no kernel call. Clock reads: ONE per hook entry. An Execute and its borrowed Signal read the clock twice in all: the enq at Execute enter (also the observation's `before`) and the game's Signal hook's entry read (`GpuQueueProbe_Now`, taken once in streamline_queue_hooks.cpp), which the bind uses as the marker's issue time AND as the observation's `after` (stamped when the Submit is pushed, so it is later than the fence reads by the Execute's own duration: a valid, looser upper bound) and which the dependency observer uses as its table time (it takes none of its own). A borrowed Execute leave reads no clock; an own marker reads one at leave (the issue lower bound before the probe's own Signal, also the observation's `after`). An unsatisfied Wait reads the clock three times: the detour's entry (shared with the dependency observer; the Wait's enq and the observation's `before`), the observation's `after` and the release Signal's issue time; a satisfied one reads none of its own. The probe's own fence is read at Execute enter only while an own marker is outstanding (`own_issued` above `own_seen`, what the producer last saw complete); the game fence read stays; one `GetCurrentThreadId` per Execute and Signal pair. The hooks keep no per-section cost counters or per-frame cost marks (timing the Leave section would take two clock reads and a dozen stores per submission and never covers the Enter observation); the hooks' cost is measured by the benchmark and by profiles. Statistics are not counted on the bind path (`marked_game` / `marked_probe` are counted by the worker from the slots, the frames on the game's markers from the popped records' `borrowed_submits`). Kept per submission, each for its protocol: `submissions_total` (the race check: another Execute's enter between this Execute's enter and leave), `busy` (the producer flag and the boundary's in-flight read), the Signal lock exchange (the sequencing lock: the claim and the pending word are published under the sequencing lock), the callback admission pair (the closing handshake: the rundown waits for it), the `binds_inflight` pair and the pending word's compare-exchange (the in-flight bracket: a boundary sees a marker in flight; exactly one winner of the word), the pattern tracker's counters (the gate's whole-frame test), the core ring's occupancy and head claim (the multi-producer bound). Every observation carries the foreign epoch read after its fence reads and every borrowed Submit its claim epoch (the core checks them wherever an observation is applied). When the session rundown times out (`detour_left` false) the reference on the game's fence is NOT released: it is retained with the queue, the device and the probe fence and the session goes dead; no bind can open (the active queue is cleared). At the bind, a borrowed marker whose own Execute-enter observation of the game fence already stood at or above the value being bound (a CPU `ID3D12Fence::Signal` by the game, or another writer, before the Execute) is foreign-writer evidence: the winner of the pending word (which owns the slot while it is Pending: the saved observation is read only by it, the Submit is built whole in a local before the slot's value is published, and pushed without touching the slot again) pushes the marker as usual and ends borrowing for the session through the foreign-Signal path (epoch up, so the marker is untrusted when the worker closes it; frame invalid; Invalidate event), and the core makes such a marker untrusted by itself when it sees one. Slot ownership (the comment above `BorrowSlot`): a slot's plain fields and claim metadata are read only by the claim that initialises it and by the one thread that took its pending word, and only while its value is Pending; every taker (bind, settle, lock-timeout loss) builds its whole Submit into a local before it publishes a non-Pending value and never touches the slot afterwards; the worker reads only the atomics of slots above its own consumed cursor (the tail read returns an unknown tail at or below it); `binds_inflight` and `callbacks_inflight` are visibility for the boundary and the rundown and pin no slot. Layout by writer: the probe's globals are laid out in cache lines by the thread that writes them, each group starting on a line of its own (`alignas(64)`) and checked by `static_assert`: `g` (gpu_queue_probe_d3d12.cpp: S0 read-mostly gate state written at adoption only, S1 cold session handles, S2 the producer's call-order counters, S3 its rare statistics, S4 the submission being taken, S5 the sequencing lock and value counters, S6 the Wait hooks' counters, S7 the boundary thread's, S8 the worker's, S9 the calibration helper's), `bw` (B0 the gate, B1 the bound fence and the foreign epoch, B2 the pending word, in-flight count and pattern tracker, B3 the slots, B4 rare hook statistics, B5 the worker's), `dep` (the tables' own groups in `Tables`: lock, read-mostly epoch / row count / decision, rows, logs, counters; then the read-by-every-hook scope state, the boundary's and the evaluator's) and the ring of `GpuQueueProbeCore` (producers' occupancy and head, the rarely written drop counter, the slots, then the consumer's state). The Wait hooks' statistics (`waits_seen`, `waits_satisfied`, `waits_ignored`, `fences_wait`) are counted per thread and added to the totals in blocks of 64 (the summary line is short by the unflushed remainder). The locked instructions left per submission each have a protocol: `submissions_total` and `busy` (the race check), the Signal lock (the sequencing lock), the callback admission and in-flight pairs (the closing handshake and the in-flight bracket), the pending word's compare-exchange (one winner), the tracker's value compare-exchange (monotonic gate), the ring's occupancy and head (multi-producer bound) and the dependency table's lock on a Signal or Wait record. Frame boundary markers: the last submission of a frame is no tail while the next frame's work is queued behind it, so the cycle would inherit its lateness; the worker therefore also waits for the OLDEST OPEN FRAME BOUNDARY's closing marker (`GpuQueueProbeCore::OldestOpenBoundaryMarker`, read after the drain and before the observation, passed as `WakeInput::boundary`; it may sit on either fence, armed on its own fence, one registration outstanding per fence) and `SetArmed` tells the core which markers are armed so that an armed marker is accounted only after its wake was processed. The awaited interval's bound is the MAX of a 256-sample trailing window of the wake-latency calibration (`GuardTicksOf`, floored at 20 us; the start burst still takes 16 samples), the Wait guard keeps p95. The per-session event handles are REUSED when no registration of the ended session can still fire (`ClassifyEvents`: every registered value reached; the probe's own fence is CPU-signalled to its outstanding value once the GPU has caught up, the game's fence never); only a registration still outstanding on the game's fence retires that one handle unclosed (a leak in that rare case only). Live validation still needed: the pattern and the registration count per frame in the game, the submission thread cost, record containment against the probe's own Signals.

The per-frame probe record protects itself against an irregular boundary sequence (a boundary that expired untagged, a boundary id lower than one already seen, a second boundary with one id, a tag for a frame that already finished, a tag whose boundary never appeared): each such event clears every valid bit of exactly one following emitted frame, because its cycle and occupancy span the broken frame, and is counted in the probe summary (`irregular_boundary_events`, `frames_invalidated_by_irregular_boundary`).

Sleep status instrumentation limit. The game's own `NvAPI_D3D_GetSleepStatus` calls are observed (for `driver_sleep_interval_us` and `driver_use_game_sleep`) only while `developer_settings` or `sleep_status_every_frame` is on; with both off the hook only forwards and logs the call and does not touch the feedback device, and the two columns stay empty. The observation takes its feedback-device snapshot without waiting and without draining retired device references, so with it on, a retired reference may be released late, at the next draining acquisition (a marker or Sleep hook) or retirement; at device loss or shutdown it can stay retained until then.

Unified pacer (`unified_pacer`). The first build of the unified pacer is the proving-session candidate for the pacing design; code in `src/unified_pacer.h` and `src/unified_pacer.cpp`, the Sleep hook and the Sleep-mode tuple in `src/nvapi_hooks.cpp`. Off, every pacing decision is as before. On (64-bit only, forced off in 32-bit builds), the pipeline is clamped without changing the INI values (they return when the key is turned off): smoothing On, `output_rung` Auto, `adaptive_cap`, `gpu_paced_cadence`, `driver_limiter_hold` and `pre_sleep_precise` off, `gpu_wait_interleave_s` and `stall_inject_ms` 0, `lead_coverage` 99%, `fg_late_spacing` and `lead_spike_floor` on, `gpu_queue_wait_render_queue` keep, and `source_placement` is ignored (`unified` while the game calls the Reflex Sleep, else `marker`; never the driver limiter). The overload and GPU-wait hold demotions are not applied; the physical blockers (Present route, architecture, API, fixed refresh, no native route, frame generation qualification) are unchanged. ReLimiter manages the Sleep-mode parameters the driver sees (low latency off, interval 0; with Dynamic MFG the game's own). The status file adds `unified_pacer` (the published key, 0 or 1) and `unified_driver_pacing` (1 while the self-check sees the driver's own Sleep pacing, flag `2048`), and its `placement` reads `unified`. The OSD has a **Unified pacer** checkbox in the developer group. The pacing CSV has the twenty-three `up_` columns (149–162, 178–183 and 187–189, below).

The status file also has `cross_thread_verified` (1 once ETW frame IDs have verified this game's cross-thread PRESENT_START hand-off, else 0).

## Pacing Preference

The user key `pacing_preference` (`latency`, `balanced` or `smooth`; default `balanced`; live key `set pacing_preference smooth`; an unknown text is refused or loads as `balanced`; the OSD combo **Pacing preference**) sets two developer keys' effective values for the queue-based pacer (64-bit, Direct3D 12):

| Position | `unified_queue_rank` | `unified_hold_share` |
|----------|----------------------|----------------------|
| `balanced` | the key's value | the key's value |
| `latency` | 4 | the key's value |
| `smooth` | the key's value | 1/32 (0.03125) |

**Precedence.** Each lever is resolved on its own, once, in `Config_ApplyPacingPipeline`: a developer key at its default cannot override the preference; a developer key that differs from its default decides its own value whatever the preference (to force an exact developer pair, select `balanced` first). `latency` leaves a developer share alone and `smooth` leaves a developer rank alone. The preference is not a developer setting: it is not counted in the developer overrides and the developer reset leaves it. The INI and `g_config` keep the raw developer keys; the pipeline carries the effective pair, and the 32-bit forcing of `unified_hold_share` runs after it (the share is 0 on 32-bit). The OSD notes when a developer key overrides the selected position.

The two levers act through the keys they change: `unified_hold_share` (under the queue law the share part of the law's refill is bounded by the median frame generation time of the used reports, 0 without frame generation or once the reports are expired; a decrease of the share drops a positive hold credit to 0) and `unified_queue_rank` (rank 4 instead of 2). See their rows under [Developer INI Keys](#developer-ini-keys). The effective pair is logged on the `Pacing pipeline:` line (`pacing_preference=`, `queue_rank=`, `hold_share=`).

## Pacing Details Lines

The main view shows one plain status line; the technical lines are under **Details**, a collapsed node below it. Each line below appears under the condition given. The [User Guide](USER_GUIDE.md#reading-the-status) has the one-line meanings; this section adds the technical detail.

**Route.** `Reflex markers`, `Present-based`, or `waiting for a presenting swapchain`.

**Mode | Output | Reason.** `vrr` or `fixed` from the display, `idle` while an idle cap (Background FPS, FG-Off Cap, OLED Care) is active, or `off` when ReLimiter is not pacing. Output is one of `gpu_queue_wait`, `fg_input_wait`, `marker_hold`, `native_hold`, `source_only`. Reason is listed under [Fallback Reasons](#fallback-reasons).

**Hold off.** An orange `Hold off: overload (needs 2 s without restarts)` line, shown only while the overload guard has stopped holding frames. The output is then `source_only` with the reason `infeasible`.

**A/B interleave.** An orange `A/B interleave: held block (N.N s left)` or `... not-held block ...` line, shown only while **GPU wait A/B blocks** is on.

**Placement.**
- `marker` waits at the game's frame-start marker, `present` at the Present call, `none` means ReLimiter is not pacing.
- `pre-Sleep | margin x.xx ms | residual p50 x.xx / p99 x.xx ms` is [pre-Sleep placement](#pre-sleep-placement) with its current margin and the median and 99th percentile of the measured residual; it shows `(measuring)` until the first residual arrives.
- `Reflex driver limiter (x.xx ms)` shows the presented-frame interval applied through the **Source placement** diagnostic; an orange `Reflex driver limiter (not applied)` can appear briefly while the driver limit is not in effect; frames that cannot use it are paced at the marker.

**Render handoff limit.** `Render handoff limit: +x.xx ms after the render thread takes the previous frame | n frames delayed | m stalls`, shown while frames are not held and the Reflex Sleep is bypassed. `+x.xx ms` is the learned offset, `n` counts frames it released later than the cadence asked and `m` waits that ended because the render thread took no frame for three of its frame times. Once ReLimiter has measured the GPU's frame period and the game's render timing (below), the line reads `+x.xx ms after the render thread takes the previous frame, render thread no earlier than y.yy ms before the GPU finishes it`: the GPU floor releases the next frame so that its render thread starts no earlier than `y.yy` ms before the GPU is expected to finish the previous frame. An orange `Render handoff limit: off (the render thread may wait for the next release; waiting for evidence)` means two waits in a row ended that way before ReLimiter had seen the render thread take a frame ahead of the next release; the limit comes back once it has, or after the cap, the FG mode or the game's swapchain changes.

**GPU-paced cadence.** `GPU-paced cadence: n of the newest 128 frames released by the GPU floor | t frames | m cadence moves`, shown while the developer **GPU-paced cadence** is on and the GPU floor is known. `n` counts the newest 128 planned frames the GPU floor released, `t` those since the game started, and `m` the frames whose target moved the cadence (both cumulative).

**GPU-paced rhythm.** `GPU-paced rhythm: a smooth | b late | c early bound | d restarts | GPU end from readiness r of f`, shown with the GPU-paced cadence line. `a`, `b`, `c` and `d` count the frames the rhythm paced by the step that set their release: on the rhythm, at the floor because the rhythm was not earlier, at the early bound (the floor minus half a GPU frame period), and at the floor after a restart. `f` counts held frames whose GPU floor was known and `r` those whose expected GPU end came from a frame's readiness timestamp rather than a Reflex report or PRESENT_END (all cumulative).

**Lead | Grid epoch.**
- Lead is how far ahead of each output target the game is released, whether it is still `warming` (fewer than 32 samples, using a starting estimate) or `warm`, and how many recent frames it is based on. It shows `-` until the source wait has run. The lead is limited to three frame intervals; `, at budget` after the sample count means the lead it wanted was longer and was clamped, so those frames are likely to miss their targets.
- `Lead spike floor: F ms = arrival tail T + GPU G | own quantile Q ms` follows while the spike floor applies (a GPU wait behind the wait, its memories warm), with `| sets the lead` while it is above the lead's own target.
- Grid epoch is a counter that increases each time the cadence restarts: after a cap, LFC or FG multiplier change, an Adaptive cap change of the whole-refresh count on a fixed-refresh cap that matches whole refreshes (or turning Adaptive cap off while it is lengthened on such a cap; its other interval changes do not restart the cadence), a mode change, a new swapchain or API, or a late frame.

**Release headroom / Release margin.** Shown on `gpu_queue_wait` while the collision-aware release is active.
- `Release headroom H ms | limit L ms | guarded P% | late n/N`: the release is measured against the next frame's heavy GPU work (needs NVIDIA Reflex latency reports). Shows the headroom (the fixed value, 1.00 ms by default), the newest lead limit (one frame interval, plus the game's short release-to-heavy-GPU-work time, minus the headroom), the share of leads the limit lowered (including the frames the lead is still returning up to its unguarded value), and how many waited GPU resumes came more than 1 ms after the release. The late count is a measurement only; nothing acts on it, and it needs **GPU Wait Probes**.
- `Release margin M ms | limit L ms | guarded P% | late n/N`: the same line while the release is measured against the next frame's Present call instead (no Reflex GPU active time within the newest 64 releases). The margin is fixed at 2.50 ms.
- `limit - (measuring)` until 32 frames are measured.
- `Release headroom H ms, margin M ms | guard off (output override)` when **Output override** is not **Auto**.
- `Release headroom H ms | guard off (next frame's GPU work waits behind the gate, N pairs)` when the guard has found that the next frame's GPU work runs behind the wait.
- The counts run since the last controller reset.

**Driver Sleep: `x.xx` ms.** The average time the game's Reflex Sleep call spends in the driver, shown while a GPU wait is the output. A readout only; ReLimiter does not act on it.

**Adaptive cap: interval +x.x% | phase | last: cause.** Shown with **Adaptive cap** on; see [Adaptive Cap Internals](#adaptive-cap-internals).

**Dynamic frame generation: pacing passthrough.** Shown below the status line itself, not under **Details**, while frame pacing is left to the driver.

## Mechanisms Behind the Details Lines

The output point stays the best one the game supports (the GPU waits where available) and the one **Output override** selects; three measured rules adjust the holds. A chosen **Output override** is never changed to another output point.

### Lead and late frames

For each frame ReLimiter plans a *source wait* (when the game is released) and an *output point* (the target at which the finished frame should pass on). The lead covers 99% of recent frames, plus 0.5 ms with smoothing on, and is limited to three frame intervals.

- **Late frames.** A frame that reaches its output point after its target is never held. If it is late by more than a quarter interval (at least 0.5 ms), the cadence restarts from that late frame and the grid epoch increases. The same applies when the game itself arrives late for its source wait, but only if it is late by more than a quarter interval plus the frame's *slack*: the lead minus the median time from release to the output point. A frame within the slack is released at once and keeps the cadence.
- **Skipped holds.** Holds that would be unusually long, such as a marker hold of more than 1.5 intervals, are skipped rather than performed.
- **Measurement on the GPU waits.** For `gpu_queue_wait` and `fg_input_wait`, each frame's measurement is its time to readiness. When the next frame's GPU work runs behind the wait (each GPU wait checks this from the Reflex reports: the next frame submits before the release, but its GPU work starts only after it), the measurement leaves out how long the frame's GPU work waited for the GPU to finish the previous frame, counted from where its first GPU work reached the driver (RENDERSUBMIT_START plus the measured first-submission delay). Otherwise a frame's readiness follows ReLimiter's own release of the previous frame, the measurement grows with the lead, and the lead could only rise: in CONTROL Resonant with FG 2× at 130 FPS it went from 20 to 39–43 ms after one heavier second and stayed there. A frame the cap released keeps its full measurement when its own late submissions set its readiness: its Reflex report shows its GPU waited 1 ms or more inside its work for its submissions while its first work reached the driver in the first half of its render submission. In Gears of War: E-Day with FG 2× at 120 FPS and Adaptive cap, leaving that wait out held the lead at 29 ms with half of those frames ready after their targets, and Adaptive cap lengthened the interval by 19–43% instead. A frame whose first work reached the driver only late in its render submission (in Gears, at the previous frame's Signal when the lead is long) keeps the wait left out even when its GPU waited: its submissions were held by the previous frame, and keeping its measurement held the lead at 45 ms. Frames the GPU floor released always leave the wait out. Behind the wait such a frame's measurement is taken when its Reflex report arrives, about two frames later. Where the GPU starts the next frame's work beside the wait (Deep Rock Galactic: Rogue Core), or while the order is not known, the measurement is the measured readiness. Whether a frame was late (the Adaptive cap's evidence) always uses the measured readiness, at once. The log shows the FG input wait's order with `Lead: the next frame's GPU work runs behind the FG input wait ...`, the GPU queue wait's with `Collision guard: stands aside ...`.
- **Render queue time.** On `fg_input_wait`, the measurement also leaves out the time a finished frame waited for the game's render thread while that thread was still inside the previous frame's Present (from the frame's SIMULATION_END marker to the previous frame's PRESENT_END marker, at most until its RENDERSUBMIT_START). Without this, a game that simulates a frame ahead of rendering keeps a lead one frame too long. `source_only` and the CPU holds keep the full measurement; `gpu_queue_wait` keeps it unless **GPU queue wait render queue** says otherwise.
- **Spike floor.** With **Output override** on **Auto**, while the next frame's GPU work runs behind the wait, the lead is at least the arrival tail plus the GPU's time from starting a frame to its readiness. The arrival is how long after its release a frame's first GPU work reached the driver, without the time its finished simulation waited for the render thread; the tail is the second-largest of the longest arrivals of the newest 32 blocks of 64 frames (about 31 s of frames: every arrival of that time but the longest is covered), the GPU time the median of the newest 32 frames. The lead's own 99th percentile leaves a game's rare long simulation frames out, and while the GPU runs back to back such a frame leaves the GPU waiting and every later frame inherits the lost time: in CONTROL Resonant with FG 2× at 130 FPS, simulations above 15 ms came 11–23 times per minute, the GPU waited more than 3 ms for a frame 8–18 times per minute at the own lead of 29.5 ms, and display jumps above 4 ms rose to 5.2–9.5 per 1,000 from 1.3–1.6 at an earlier lead of 40 ms. Covering all but the fourth-largest cut those waits to 2.4 per minute (6.8 with the GPU-paced cadence) and jitter above 2 ms from 25.1 to 10.4 per 1,000 for about 2.5 ms of PC latency, but left the game's 22–25 ms simulations; the second-largest covers more of them for about 1–4 ms more lead in such scenes. The floor applies only after 4 blocks and 32 GPU times, enters the lead's target (so it moves at the lead slew) and never counts as a lead at budget. It is cleared with the lead buckets (for example at an enforcement marker change) and kept at cap, FG multiplier and overload-pause changes. The log reports `Lead spike floor: on at ...` when it first sets the lead and `off (...)` after 256 frames without. Developer key `lead_spike_floor`.
- **After an overload pause.** The stepped-aside frames of every automatic hold (`gpu_queue_wait`, `fg_input_wait`, `marker_hold`) are planned with that hold's lead while the guard is active, at least the `source_only` lead measured meanwhile (this floor applies only to frames the guard demoted); on the `gpu_queue_wait` the [collision-aware release](#collision-aware-release) limits that demand as it limits held frames. When the hold resumes, its bucket starts at the lead the last stepped-aside frame was planned with, whether or not it has samples yet, and moves by one lead slew step per frame (at most `min(100 µs, I/64)`) toward the old median plus the allowance (at least the `source_only` lead) while fewer than 32 new frames are measured, and toward the warm target after that. A cap, FG multiplier, lifecycle or route reset carries no lead. The **GPU wait A/B blocks'** not-held blocks plan exactly like held blocks of the same output: no floor and the same collision-aware release.

### Collision-aware release

Applies with **Output override** on **Auto**, on `gpu_queue_wait` only. The GPU wait releases each frame at its target. If the next frame's heavy GPU work has already started on the GPU when the work after the wait becomes ready, that work waits for it, and the resume comes more than 1 ms late. The game's own long command buffers run on the same GPU engine as the work after the wait and are not interrupted for it.

- **The limit.** The lead is `L = min(Q_q(X) + allowance, I + Q10(D) − H)`: the plain lead, at most one frame interval `I`, plus the game's short release-to-heavy-GPU-work time `D` (the 10th percentile of the newest 256 frames), minus the **release headroom** `H`. The heavy work is measured as a frame's GPU ready time minus its GPU active render time from its Reflex latency report. A frame adds a `D` sample only when the frame before it was a GPU wait frame whose GPU waited at its gate (only a waited release can collide with the next frame's heavy work). While that verdict is pending (the readback probe of the predecessor's resume has not arrived) the sample is deferred and added when the verdict is known; readiness decides only when no probe time is available. A frame after one that was not waited for, was stepped aside by the overload guard, or belongs to another lifecycle or FG multiplier adds none. The limit applies once 32 frames are measured. Without Reflex latency reports (no GPU active time within the newest 64 frames planned with the GPU wait's lead), the release-to-Present time `C` (every GPU wait frame adds one) and the **release margin** `M` take their place: `I + Q10(C) − M`.
- **Frames that need more lead.** A frame that would need a longer lead reaches its GPU wait a little after the release and is shown when it is ready. Its slack is judged against the lead before the limit, so Adaptive cap does not count it as late. No mode switch, timer or GPU-load threshold is involved.
- **A relaxing limit does not jump the lead.** A tighter limit applies at once. When it relaxes, or the guard stands aside, the lead returns to the unguarded lead at the lead slew (100 µs per frame, at most `I`/64), never in one step. The frames the slew still holds back count as the guard's own reduction, not as late frames for Adaptive cap.
- **Release headroom and margin are fixed.** `H` is 1.0 ms (the developer key `gpu_wait_headroom_us`, 500–3000 µs): the distance between the release and the next frame's heavy GPU work, used with Reflex GPU active times. `M` is 2.5 ms: the distance to the next frame's Present call, used without them. Nothing widens or narrows either. Late resumes (more than 1 ms after the release) are measured and shown on the Details lines and in telemetry, but nothing acts on them. Across about 1.35 million waited GPU resumes with probes and Reflex GPU times in Deep Rock Galactic: Rogue Core, late resumes were 0.00–0.05% per 250 µs distance bin from 1 ms on, and 99.2% of all late resumes were closer than 1 ms. A headroom learned from late resumes had widened to 1.75 ms from 10 of 123 resumes at a session's start and could not narrow, because the guard keeps releases out of the region it would have to measure; that learner was removed.
- **Games that run the next frame's GPU work behind the wait.** For each frame whose GPU waited at the gate, ReLimiter asks whether the next frame had started submitting before the release and whether that frame's GPU work (the GPU start in its Reflex latency report) began more than 0.1 ms before the release. The limit stands aside, and so does the Adaptive cap's hold room, only while at least 32 such pairs exist, none of the newest 64 began earlier, and the heavy-work window is current (a Reflex GPU active time arrived within the newest 64 frames planned with the GPU wait's lead). Every frame planned with the GPU wait's lead ages that window, whether it was held, stepped aside by the overload guard or in an A/B not-held block; any Reflex report of such a frame resets the age, with or without a new `D` sample, so the age is not tied to `D` samples. Without current Reflex reports no new pair can show the order changing, so the Present-call margin guard applies until a report arrives. A single pair that began earlier brings the limit back at once, until that pair is no longer among the newest 64. Without **GPU Wait Probes** or Reflex latency reports there are no pairs and the limit stays. The pairs are kept across controller resets until the game closes; after a lifecycle reset the guard waits for a warm heavy-work window (32 frames) before standing aside again.
- **When the GPU is busy most of the interval.** The release can then come only shortly after the frame reaches the wait, and few frames wait at all. With Adaptive cap on, its hold room lengthens the interval just enough for the **Adaptive cap fit** share of frames to wait.

### Overload guard

With **Output override** on **Auto**, on every automatic hold (`marker_hold`, `gpu_queue_wait`, `fg_input_wait`): when more than 10% of frames are counted restarts of the cadence within a window of at least 1 s while Adaptive cap cannot lengthen the interval (it is off, or already at +60%), holds step aside (output `source_only`, reason `infeasible`, the orange **Hold off** line). They resume after the first whole 2 s window without any restart other than a guard-chosen `OutputLate` (below). With Adaptive cap on and below +60%, restarts lengthen the interval first and holds stay on.

- **Restarts and frames.** A restart is an `OutputLate` epoch, or a `SourceLate` epoch the pre-Sleep wait did not cause, attributed to the frame whose output or source it was; a frame with both counts once.
- **Evidence per frame.** Each judged frame keeps a record until its own output has been observed and its hold verdict is known, however many frames have been planned since, so a delayed `OutputLate` stays on its own frame. A pending verdict waits too. The 32-entry record ring is the only bound: when it is full the oldest record resolves as unknown (counts as held) with only the restarts already known. A reset drops the records, and a later `OutputLate` of a dropped frame is ignored.
- **What counts toward the pause.** A restart counts only if some frame since the previous restart (that restart frame included) was held by ReLimiter's own waits (the pre-Sleep or source wait, a GPU wait or FG input wait whose GPU waited at its gate, a marker or native CPU hold released after it began), would have been held by the [render handoff limit](#render-handoff-limit) (its preconditions hold apart from the output test, and the render thread had not taken the previous frame when this one arrived, or took it too recently for the offset), or has no verdict (the slot expired or was discarded, the key belongs to another lifecycle, or the record was dropped from a full ring: unknown counts as held). The restart frame opens the next segment. In a GPU-bound stretch of a game that runs its frames one after another none of these acts, so its restarts do not count toward the pause and holds stay on (about +1 ms of PC latency while the GPU is the limit). A cap the game truly cannot reach still pauses and uses the render handoff limit.
- **Lateness ReLimiter chose.** An `OutputLate` restart whose output is no later than the target plus the late tolerance plus the frame's own collision-aware reduction counts neither toward the pause nor against its end.
- **Ending a pause.** While paused no frame is held, so a restart that would not count toward the pause still keeps it; only guard-chosen `OutputLate` lateness is ignored.
- While the holds are paused, ReLimiter keeps pacing the game itself; with the default **Bypass Reflex Sleep** the Sleep stays bypassed, so the guard judges the same pacing it resumes into. The stepped-aside frames use their hold's lead and the resume starts from it ([Lead and late frames](#lead-and-late-frames), **After an overload pause**).
- Late frames are still never held and the cadence still restarts after a stall. An `fg_input_wait` that steps aside keeps its route, so the frame generation input route stays qualified.

### Render handoff limit

Without Reflex's Sleep, nothing else stops a game that simulates ahead of its render thread from queueing finished frames when the cap cannot be held. A frame that is not held is therefore released no earlier than the moment the game's render thread took the previous frame (its RENDERSUBMIT_START), plus a learned offset: the time the render thread still needed for that frame minus this frame's simulation, at the 5th percentile, less 0.5 ms, never below 0.

The render thread can also be held back by the GPU inside its own window, which that offset cannot see: in Gears of War: E-Day, a render thread that starts a frame more than about 11 ms before the GPU finishes the previous frame often sends almost nothing of it to the driver until the GPU nears that end, and each run of such frames starts with a stutter. With NVIDIA Reflex latency reports the limit therefore also has a **GPU floor**, measured rather than learned: the next frame's render thread starts no earlier than half the GPU's frame period plus the game's own delay to its first submitted work before the GPU is expected to finish the previous frame. That is where the driver's Reflex Sleep starts it (9.4 ms in Gears), so the frame's first work reaches the driver half a GPU frame before the GPU needs it. The GPU frame period is the median time between GPU ends of consecutive frames the GPU did not wait for; the delay to the first work is the median over frames whose work streams from the start of the render thread's window; the release comes earlier by the median time from a release to the render thread's start on frames that are not held. Each is a median of the newest 256 values and applies from 32. The expected GPU end is the later of the newest report's GPU end and the render thread's newest PRESENT_END plus the low end (5th percentile) of the reports' gap from PRESENT_END to the GPU end, each plus the GPU frame period for each frame since; the second sees a frame whose GPU frame stretched two frames before its report arrives. A game whose render thread already starts later than that against the GPU is never delayed, and one whose GPU waits for its frames has no GPU frame period and no floor. Nothing is learned from held-back frames: a term that moved the release later after each one found the edge by hitting it, a stutter each time.

- With pre-Sleep placement the wait happens inside the Reflex Sleep, before the game reads input. A wait beyond the cadence's release counts as a late source, so the guard sees the overload as before.
- A frame the limit would have held counts as evidence for the overload guard even while the frame is held, so a game that outruns its render thread still pauses; the limit itself acts only on frames that are not held.
- Held frames are not limited. Games that simulate and render one after another are never delayed. The limit applies only while the driver's Sleep does not run.
- A wait ends only if the render thread takes no frame for three of its own frame times (the median time between its newest frames, at least three intervals: a hitch); the frame is then released. Once ReLimiter has seen the render thread take a frame ahead of the next release, the limit stays on through such hitches. Before that, two such waits in a row turn it off, because a render thread that waits for the next release never takes a frame ahead of it; it comes back once that is seen, or after the cap, the FG mode or the game's swapchain changes.

## Adaptive Cap Internals

The user-facing description is in the [User Guide](USER_GUIDE.md#adaptive-cap). The interval stays between the cap interval and 60% longer (+60%, 62.5% of the cap's frame rate). With frame generation it is the rendered-frame interval, so the output frame rate drops by the same proportion.

- **Evidence.** The interval rises only while the frames themselves show it is too short: two cadence restarts within 0.5 s, 6 of the newest 24 measured frames ready after their target, or more than 10% of the frames of a window of at least 1 s restarting the cadence (a window closes after 2 s and restarts after every rise). One late frame counts once. Consecutive frames that restarted the cadence are one restart, because a hitch also restarts it on the frame queued behind it. A late frame less late than the late frame before it is the queue behind a hitch running down and is not counted among the 24: the interval is already absorbing it. Frames that stay late or grow later still count, and the 10% window counts every restarted frame. In Gears of War: E-Day with frame generation one 25 ms simulation hitch restarted the cadence on two consecutive frames after it and left five frames late, and the interval rose from +21% to +42% in 0.6 s. An isolated hitch is none of these now. A frame is ready after its target when it is ready after the target it was planned for: a frame whose game arrived late but within the cadence's tolerance has less than a full lead left, and a frame the GPU floor released under the GPU-paced cadence (developer A/B) counts like any other, so the Adaptive cap sees where the GPU kept no cap cadence. Lateness ReLimiter accepts on purpose is not evidence: the time the collision-aware release lowered the lead by, including the frames the lead slew still holds back after the limit relaxed. (An earlier cap on the GPU wait's lead lowered most leads in Deep Rock Galactic: Rogue Core and made the late share grow with the interval; it was removed.) Frames released before the evidence starts over (for example at a governor reset, a cap or frame generation change) do not count after it. The game's NVIDIA Reflex workload reports alone never lengthen it, because in some games a stage stretches to fill whatever interval it is given.
- **Rising.** With evidence, the interval rises to what recent frames need plus a margin (3% of the interval, at least 0.25 ms), by at most 8% of the cap interval per 0.25 s, up to +60%. What frames need comes from the game's workload reports (DX12 and other NvAPI Reflex games): the larger of the 90th percentile of the newest 12 reports and the **Adaptive cap fit** value of the newest second of reports, compared with the interval actually paced (after LFC). A report more than 1.5 times the median of the newest second is a hitch and is not counted. Normally the report is the longest of the game's stages (simulation, render submission, GPU work). With frame generation the GPU work includes the report's frame generation time, because the generated frames are rendered on the same GPU within each real frame's interval. Games that reach ReLimiter for each frame only after the previous frame's Present returned use the whole frame span instead, minus ReLimiter's own waits, and log `Feedback: frame span demand on`. That is judged from when the game reached ReLimiter, before any wait of ReLimiter's own: a held frame is always released after the previous Present, so judged from the release, Gears of War: E-Day and CONTROL Resonant looked serial and the interval followed their frame span instead of their GPU work. When more than 10% of a window's frames restart the cadence and the reports do not explain it, or the game sends no reports, the interval rises by 5% of the cap interval instead (cause `misses`; at least one refresh on a fixed-refresh cap that matches whole refreshes). On VRR the interval actually paced follows its target by at most 3% per frame longer.
- **Falling.** After 0.5 s of headroom (what recent frames need at the **Adaptive cap fit**, plus two margins, fits inside the interval actually paced), the interval falls to what recent frames need as a rise would size it (the larger of the 90th percentile of the newest 12 reports and the **Adaptive cap fit** value of the newest second) plus one margin, never below the cap (cause `release`); a fall therefore never lands where the next rise would put it back up. Both the headroom test and the fall also take the heaviest **Adaptive cap fit** value of each of the newest 8 seconds (once 3 seconds are known), so a lull in a load that comes back is not headroom: in Gears of War: E-Day with FG 2× at 120 FPS the GPU's work dropped from 17.5–19 ms to 14.0–14.6 ms for 1.0–1.75 s every 3.5–5 s, and falls sized from the newest second went to the cap three times in 10 s as the load returned, each with 24–39 frames late by up to 18–19 ms. The median of those seconds dipped too (17.3 ms against 17.3–18.5 ms for the load), and a fall there that failed would have raised the demand scale below. A lasting drop is followed once its heavier seconds have left the 8 seconds. Without that headroom, after 1 s without evidence the interval *probes* below what the reports say: 3% of the cap interval, 1.5 times further for each probe that held a calm second, up to 12% (cause `probe`). Without workload reports only the calm time counts. On VRR the interval actually paced falls by at most 1% per frame.
- **When it probes.** A probe waits a calm second after any fall, a `release` included, so each fall is judged before the next. No probe starts while the GPU's execution time (with frame generation, plus its AI frame time) is the largest stage in most reports of the newest second: that time does not grow with the interval, so a probe below it can only fail and make frames late. Probes remain for stages that can stretch to fill the interval, such as a render submission or a game that starts each frame after Present.
- **Failed probes.** If evidence returns after a probe, the interval goes back to the level before it (cause `probe_failed`) and the next probe needs twice as much calm time (1, 2, 4, up to 8 s). A reset restores the one-second wait.
- **Failed falls.** If evidence returns after a `release` before it has held for a calm second, the interval goes back to the level before it (cause `release_failed`), and from then on what recent frames need is scaled up so that the next fall stops one margin above the interval that failed: the *demand scale* becomes the interval actually paced at the evidence divided by what that fall used, and every rise, fall and headroom test uses the scaled value. While the scale is above 1, no probe runs. A reset sets it back to 1. The log's `Period governor: ... (release_failed) ...` line names the new scale. A fall is only blamed once the interval actually paced is below the level it fell from; while the hold room keeps it there, late frames are not a failed fall. The scale rises only when the workload reports set the level the interval fell to: not after a fall to the cap, and not while the hold room sets the interval, because then the interval at the late frames says nothing about what the reports miss. In Deep Rock Galactic: Rogue Core a fall the hold room kept at +39% was blamed for late frames while the game loaded and set a scale of 1.55, and two falls to the cap at a need of 4.6–5.5 ms set 1.40 and 1.69; each held the interval about +18% above what the game needed until the next reset, or multiplied a heavier scene's GPU time to +59%.
- **Recurring loads.** After a rise the interval does not fall for 1.5 s per overload episode within the last 20 s (rises more than 1 s apart start a new episode), up to 8 s. A failed fall (`release_failed`) counts as an episode like a rise.
- **Games that wait for the next release.** Some games finish a frame only after ReLimiter releases the next frame. ReLimiter judges each frame without the waits of later frames it released before the frame's Present: in late frames, in the lateness evidence and in the workload reports (once the Reflex clock map is stable). On the GPU waits this credit can hide lateness that came from the GPU's own throughput: in Gears of War: E-Day with FG 2× at 120 FPS the next frame's pre-Sleep wait overlapped each frame's render submission by 11–12.5 ms, and of the 12–28% of frames ready after their targets only 0.2–1.4% counted (CONTROL Resonant with FG 2× at 130 FPS and Adaptive cap fit 75: 10.8 ms on 94% of frames, 0.9% of the 15.6% counted). Crediting such frames only as far as their GPU idled inside their own work was captured on and off in both games and changed no display measure beyond the run-to-run spread; it only held the interval about 3% longer, so the full credit stays.
- **Hold room.** With the GPU wait output and **Output override** on **Auto**, the interval is also kept at least as long as the GPU wait needs to hold frames. It is the collision-aware release's limit solved for the interval: a frame is held at least a minimum hold `h` (0.25 ms) before its guarded release when `X + h ≤ I + Q10(D) − H`, `X` being the time the frame needs from release to readiness. The hold room is `Q_fit(X) + h − (Q10(D) − H)` (or `− (Q10(C) − M)` without Reflex GPU active times), with `Q_fit(X)` the **Adaptive cap fit** percentile of `X` over the newest 256 judged frames and `Q10(D) − H` the guard's current distance, so the room always uses the guard's own current values and never older ones. The interval follows it at +3% / −1% per frame (cause `room`), and while a room is reported, at least the median of the rooms each of the newest 8 seconds ended with (once 3 are known), so a lull does not take the floor away; a frame without a room (the key off, another output, stale reports) clears that at once. `h` applies only to the room, never to the release decision: at 0.5–1 ms of distance, holds under 250 µs were 3.9% late against at most 0.45% for longer holds. It needs no evidence of late frames and does not probe below the room. Frames late even against their unguarded lead are overload and add nothing. A hold room above +60% is infeasible and not applied, and there is none on fixed-refresh caps that match whole refreshes or while LFC is active. It is 0 while the collision-aware release stands aside in games that run the next frame's GPU work behind the wait, and it is gated by the developer key `adaptive_cap_hold_room`. The hold room is about the GPU's work per frame plus the release headroom, so when the GPU is the limit it lengthens the interval beyond what the game runs at: in Deep Rock Galactic: Rogue Core at a 130 FPS cap the GPU needed 7.5 ms per frame and the game ran at 8.0 ms with Adaptive cap off, while the hold room measured with an earlier, learned headroom of 1.5 ms held 9.4 ms, +22%, and the workload reports alone would have set +2%. The developer key `adaptive_cap_hold_room` turns it off for a comparison.
- **FG input wait hold room (with GPU-paced cadence).** With the developer **GPU-paced cadence** on, the FG input wait with **Output override** on **Auto** has a hold room too: the **Adaptive cap fit** percentile of the GPU need, each real frame's GPU execution time from its Reflex report (GPU active time plus the frame generation's AI frame time). Only reports with execution times count, a value above three intervals or not positive is dropped, and the window is the newest 128 values of the current frame-generation multiplier and producer epoch, at least 32; the room is 0 while those reports are not current. The need leaves out ReLimiter's own holds and the Adaptive cap's own stretch on purpose: a need that included them would feed the interval back into itself and lower the frame rate without bound. The time from one frame's readiness to the next includes the stretch, because the game submits into the longer interval (Gears of War: E-Day at 120 FPS with FG 2× and Adaptive cap fit 75: 20.1 ms at a 20.7 ms interval against 17.7 ms of GPU work). The GPU wait room's limits apply (cause `room`, +60%, none on caps that match whole refreshes or with LFC, `adaptive_cap_hold_room`), and so does the median of the newest 8 seconds: in Gears the 128 needs fell to 15.7 ms in a 1.75 s lull while the load came back at 18.2–18.7 ms, and the interval followed with 61 frames late. It replaces the former hold margin key: in Gears of War: E-Day at 120 FPS with FG 2×, the margin at Q75 (with release smoothing) had 3.5 display jumps above 4 ms per 1,000 against 12.3 with the cadence alone, at 2% lower frame rate.
- **VRR.** Interval changes move the cadence without restarting it, so the grid epoch does not increase.
- **Fixed refresh.** With a cap that matches whole refreshes, the interval is rounded up to whole refreshes. Each change of the whole-refresh count restarts the cadence (the grid epoch increases by one), and the next 32 frames are not judged; small movements of the measured refresh interval do not count as a change. Turning Adaptive cap off while it is lengthened on such a cap restarts the cadence once. Other fixed-refresh caps behave as on VRR.
- **Reset.** A cap or FG multiplier change, Dynamic MFG, OLED Care, regaining focus, a new graphics API or swapchain, and turning Adaptive cap off all return the interval to the cap immediately and clear the windows, overload episodes, probe backoff and demand scale. After a reset while it is on, the next 32 frames are not judged. Recovering from a minimized or occluded window or a failed Present keeps the current interval.

The Details line `Adaptive cap: interval +x.x% | <phase> | last: <cause>` shows the percentage the interval is longer than the cap interval; `last` is `-` until a change has started. The phase is `idle` (at the cap), `rising`, `holding` or `falling`.

| Cause | Meaning |
|-------|---------|
| `demand` | A rise sized by the workload reports, after frames showed they were late |
| `misses` | More than 10% of the frames in a window restarted the cadence and the reports do not explain it (rise by 5%) |
| `release` | A fall to what recent frames need after 0.5 s of headroom |
| `probe` | A fall below what the reports say, after a calm stretch |
| `probe_failed` | Evidence returned after a probe, and the interval went back to the level before it; the next probe waits longer |
| `release_failed` | Evidence returned after a `release`, and the interval went back to the level before it; later falls stop above the interval that failed |
| `base` | The fall reached the cap |
| `room` | The hold room started setting the interval (above the level the other rules set), set it again after another change, or fell one margin below that level |
| `reset` | A reset returned the interval to the cap |

## Pre-Sleep Placement

In the 64-bit addon, **Source placement** is **Pre-Sleep** by default. When a Reflex marker game has called the NVIDIA Reflex Sleep within the last second and ReLimiter paces it at its frame-start marker (SIMULATION_START), ReLimiter does most of the source wait inside that Sleep call, before it reaches the driver and before the game reads input for the next frame. The game is still released at the exact planned time at its frame-start marker, which trims whatever wait remains. Games paced at a later marker (RENDERSUBMIT_START or its fallback) wait only at the marker, and so does a game that does not call the Reflex Sleep. With the default **Bypass Reflex Sleep** the Sleep returns at once after the pre-Sleep wait, so the pre-Sleep wait does the pacing, and the render handoff limit also waits there.

- **Timer.** The wait runs on its own high-resolution timer without spinning. While it runs, ReLimiter requests the finest system timer resolution Windows offers (usually 0.5 ms) for the game's process and releases it when the game closes; on Windows 10 2004 and later this does not change the timer resolution of other programs. ReLimiter does not change the game's own timer requests. The wait runs without holding ReLimiter's scheduler lock, so the game's other Reflex marker calls on other threads are not blocked.
- **Prediction.** The next frame's release is predicted from the previous frame's target plus the shorter of the previous interval and the current cap interval (the cap interval times the FG multiplier and the Adaptive cap lengthening), so raising the cap cannot make the wait end late; a shorter prediction only leaves more of the wait to the marker.
- **Margin.** The wait ends a margin before the planned release, so that the timer's late wake-up, the driver's own Sleep and the game's work up to the frame-start marker (the *residual*, measured from the end the pre-Sleep wait aimed for to the moment the frame is ready for its marker wait) fit in between. The margin is the 99th percentile of the residual over the last 128 measured frames plus 0.15 ms, at least 0.15 ms; until 16 frames have been measured it is 0.5 ms. A margin longer than the time left before the release only skips that frame's pre-Sleep wait; the residual of such a frame is still measured, from its Sleep call. The measurement starts over whenever the driver's Sleep starts or stops running after the pre-Sleep wait (turning **Bypass Reflex Sleep** on or off, or leaving or entering Dynamic MFG passthrough).
- **Skipped frames.** A frame gets no pre-Sleep wait when its planned release is less than 0.2 ms or more than two intervals ahead, or when the cadence cannot predict it (for example right after a restart). The frame-start marker still paces it. A frame that its own pre-Sleep wait made late does not count as a missed frame for Adaptive cap.
- **No switching.** Pre-Sleep never stops or switches itself: it stays on while it is selected and the game calls the Reflex Sleep. Marker games that do not call the Reflex Sleep, idle caps and NVIDIA Smooth Motion (which skips the Reflex Sleep) wait only at the marker; Present-based pacing and the 32-bit addon are unaffected.

## Hook Installation

MinHook's enable freezes the process: it suspends every other thread, patches, and resumes. Two engines whose suspend loops overlap can deadlock each other (other injectors in the process use MinHook too), so ReLimiter installs its hooks in as few freezes as it can, one batch per site.

**Batch.** `HookBatch` (`hooks.h`) is lazy: constructing or destroying one takes no lock and calls nothing. The first install inside it takes the install lock and keeps it until the apply, which releases it, so an idle batch never blocks another installer (the present thread's first-present install, the focus lock and the DXGI fallback wait on that lock while the swap-chain selection lock is held). Inside the batch every install creates the hook, publishes its trampoline into the caller's original slot, then queues the enable (`MH_QueueEnableHook`); the apply is one `MH_ApplyQueued`. An install's `MH_OK` inside a batch means *queued*: whatever acts on a hook, logs it as installed or sets a state flag from it reads `Hooks_TargetEnabled` after the apply. A batch nests on one thread (the inner one is a no-op that queues into the outer), applies in its destructor if `Apply` was not called, and an empty batch calls MinHook not at all (no freeze). Outside a batch an install is create, publish, enable, as before. A group that cannot continue without the result (the Streamline hooks, the proxy and queue hooks, the FG input and queue hooks, the NGX transaction) calls `Hooks_FlushBatch()` once after its installs: the same apply (it releases the lock too), batch still open.

| Site | Hooks in the batch |
|------|--------------------|
| `Init` | The flip-metering block (`flip_metering_off`) and the NGX hooks, in `DoInit`. |
| `FirstPresent` | The first present event: the four LoadLibrary hooks and up to nine NvAPI hooks (about 13 freezes become one). The selection lock's hold gains no work. |
| `LoaderScan` | One scan of the loader-install worker: the Streamline hooks, the proxy and queue hooks, the FG input and queue hooks, NGX when its modules appear. The batch closes before the worker's 250 ms wait; discovery, factory probing and drains run without the lock, which is held only from a group's first create to its flush. NGX installed outside the worker (the OSD's retry) opens its own. |
| `FocusLock` | The four user32 hooks of the focus lock. |
| `DxgiFallback` | The DXGI `Present` / `Present1` inline pair, installed only when the native swap chain's vtable route is absent. |

**A failed apply.** `MH_ApplyQueued` is not a transaction: it stops at its first failure with the earlier hooks enabled and the later ones pending. ReLimiter then enables every hook still queued one by one with `MH_EnableHook`, logs one warning for the failed apply and one for each hook that still fails (`Hooks: ... MH_ApplyQueued failed (...)`, `Hooks: the hook at ... could not be enabled (...)`, both with MinHook's status), and leaves such a hook created and not queued, so no later apply enables it behind its owner's back. `Hooks_TargetEnabled` reports what is really enabled. The site lines say so too: `FG input: Present installation status=... enabled=...`, `FocusLock: installed on HWND ... (N of 4 hooks enabled)`, `NvAPI: ... hook installed|not installed`.

**A retained load.** The hook records survive an addon unload and load. Installing a retained target again queues it (no second `MH_CreateHook`); `EnableAllHooks` (`MH_EnableHook(MH_ALL_HOOKS)`) enables every hook, the queued ones too, so nothing stays queued, and when it stops at a failing hook it enables the rest one by one before it returns the failure.

**The installer thread.** MinHook's freeze suspends every other thread; another engine's freeze that overlaps it can suspend the thread that is freezing, and the two wait for each other for good (two ordinary freezers deadlocked within a second in a stand-alone program). ReLimiter therefore runs its freezing calls on one installer thread created at initialisation, outside the loader lock, with a security descriptor that denies `THREAD_SUSPEND_RESUME`, `THREAD_GET_CONTEXT` and `THREAD_SET_CONTEXT` to Everyone in front of the process token's default DACL (nothing else is granted). Another engine's `OpenThread` for it then fails with access denied and it skips the thread, so ReLimiter's freeze no longer waits for anything another engine can suspend. At its start the thread opens itself for a suspend; that must fail. If it succeeds (a process with the debug privilege enabled bypasses the descriptor) the thread is *unprotected* and every call runs on the requester as before. Only the raw MinHook calls that freeze run on it (the batch apply and the one-by-one enables after a failed one, a single enable or disable outside a batch, the enable-all of a reactivation, the disable at teardown); creating, publishing, queueing and every log stay on the requester, which keeps the install lock and waits, without a timeout, for the job or for the thread's death. The thread cannot be suspended by other engines, so neither can a crash-dump writer read its context; it is idle between jobs. Calls run on the requester when `hook_installer_thread` is `false`, before the thread reports ready, after teardown stopped it and inside a `HookInlineOnlyScope` (the explicit mark for code in `DllMain` or a loader callback; no call site is one today). If the thread ends before it took a job, the requester runs the job; if it ends with a job in flight MinHook's internal lock may be held for good, so MinHook is not used again in this process (every later freezing call fails with `MH_ERROR_DISABLED`, install admission closes) and nothing is replayed or terminated; creating, removing, queueing and initialising hooks make no MinHook call either (they take the same internal lock), and a hook that could not be removed stays retained. Other engines can still deadlock each other: this removes ReLimiter from that cycle, not the cycle.

`hook_installer_thread` (default **true**, both addons, `[FrameLimiter]`, restart required) is a compatibility switch, not a tuning option: `false` turns the thread off for a game or tool that does not tolerate a thread with a restricted descriptor (some anti-cheat or anti-tamper software, an unusual crash handler). The log says which applies (`Hooks: installer thread created` at start, `ready (protected)` or `unprotected` at the first present).

**Evidence.** The apply is bracketed by the `BatchApplyEntered` / `BatchApplyLeft` crumb stages with the site number (1 `Init`, 2 `FirstPresent`, 3 `LoaderScan`, 4 `FocusLock`, 5 `DxgiFallback`), so a hang inside a freeze is named by the next launch (see **Start-up evidence** below). The site byte's high bits also say whether the installer thread ran the apply, whether it was protected but not used for that call, or unprotected.

**Start-up evidence.** `Log_Init` first moves the previous log to `relimiter_<exe>.prev.log` in the same folder (`MoveFileEx` with replace; a failure, such as a log a second live launch still holds, is ignored and the new log opens as before), then opens the new log (next to the game executable, else next to the addon, else `%TEMP%`). `src/startup_breadcrumb.h/.cpp` keeps `relimiter_<exe>.crumb`, a 4 KB file in the log's folder mapped for the life of the process, holding one 40-byte record: magic, version, process ID, launch time, sequence numbers, the stage reached, the QPC at the stage and a site ID (a hook batch's `HookBatchSite` for the two batch stages). A mark is plain stores into the mapped page (no lock, allocation, flush or log), so it is safe around a MinHook freeze, and the page survives a killed or frozen process. The sequence number is odd while a record is written and equal at both ends when it is whole; a reader rejects any other record. Stages, in the order they are normally reached: `InitBegun`, `InitEnded` (DoInit), `BatchApplyEntered`, `BatchApplyLeft` (a hook batch around its `MH_ApplyQueued`, with the site), `FirstPresentEvent`, `FirstNativePresentEntered`, `FirstNativePresentReturned`, `FirstGateWaitEnqueued`, `FirstGateSignal`, `Running` (the 32nd completed present of the selected swapchain, after the first-present block ran) and `Closed` (clean shutdown, both teardown paths). Every stage except the two batch stages is first-wins, only `Closed` follows `Running` (a hook batch applied later in the session is not start-up), and a mark that finds another thread writing is dropped, never waited for. After the new log is open, `Breadcrumb_Attach` reads the previous record before it resets the file, and the logger writes ONE warning, at warning level so the default level shows it: `the previous launch ended during start-up; last stage: <stage>[ (site <name>)]` (it says ended, not hung). Nothing is logged when the previous record reached `Running` or `Closed`, or is missing, short, from another version, has a bad magic or is torn. The file is opened as the only writer (`FILE_SHARE_READ`): a second live launch of the same executable, or a read-only folder or file, makes the open fail and the process runs without marks and without a report, so a live launch's record is never reported or overwritten; a dead process holds nothing, so its record is read. A reload of the addon in the same process keeps the mapping, judges its record and resets it.

- GPU queue probe columns (developer key `gpu_queue_probe`, 163–177 and 199), what the game's presenting queue did for the frame's submissions, a frame being the `ExecuteCommandLists` calls between ReLimiter's own Present-time enqueues. Joined through the frame key when the row has one, else the Present's (swapchain generation, present sequence); every cell is empty when the row has no record, the key was off, or the value is unknown for that frame (a dropped event, a missing stamp or release, an unknown predecessor completion; each column has its own valid bit, so a frame can fill some cells and not others). The probe follows a timeline: waits are not work, every operation reaches the queue at the later of its enqueue and the completion of the operation before it, a submission completes at its fence completion, and an unsatisfied queue Wait completes at its release (a fence value signalled right after the native Wait returned); a Wait on a fence value that was already reached is not a queue wait, and nothing is signalled in front of submissions. `gq_submits` (the number of submissions), `gq_first_submit_qpc` and `gq_last_submit_qpc` (QPC when the first and the last submission was enqueued, read before the call was forwarded), `gq_first_start_qpc` (QPC when the queue reached the first submission, the releases of the Waits in front included), `gq_last_done_qpc` (QPC when the GPU finished everything queued up to the last submission, from a fence completion event), `gq_empty_us` (the exact time the queue had nothing queued inside the frame, summed over the submissions after the first: the gap `max(0, enqueue(i) − completion(i−1))` without a Wait in front, and with Waits in front the time before each Wait reached the queue and the stretch from the last release to `enqueue(i)`; a submission still blocked behind a Wait after it arrived adds nothing here and its time goes to `gq_wait_block_us`), `gq_first_gap_us` (only the gap `max(0, enqueue − completion of the previous frame's last submission)` of the first submission after the frame boundary, still an upper bound because it contains the hold and the frame-generation wait), `gq_stamp_late_us` (the largest known lateness of a completion timestamp in the frame, at least the measured idle wake latency; every timestamp can be this much later than the event), `gq_min_margin_us` (the smallest start − enqueue over the submissions: 0 when any submission arrived at a free queue), `gq_wait_block_us` (µs Waits held submissions after they arrived, summed), `gq_hold_block_us` (µs ReLimiter's own hold Wait kept the frame's first queued submission waiting; the hold is the boundary Wait of the next frame's work, so the block belongs to the frame whose submission was queued behind it; 0 when none), `gq_min_margin_free_us` (the smallest margin once the hold's delay is taken out, at least 0), `gq_boundary_idle_us` (µs the queue had neither work nor a pending Wait before the frame's first submission), `gq_cycle_us` (this frame's last completion minus the previous frame's) and `gq_wait_idle_us` (µs Waits were pending with nothing queued behind them, summed over the boundary Waits and the Waits inside the frame). `*_us` values have 3 decimals. `gq_queue_role` (column 199, appended after the feed columns): which queue the record describes, 1 the presenting queue, 2 the source queue of the frame generation input, 3 the render queue the presenting queue depends on (found through per-frame fence dependencies); empty when the row has no probe record or the role is unknown. A frame without a frame key or Present identity is counted and has no row.
- Queue law columns (developer key `unified_queue_law`, 178–183), law state repeated across rows (never take percentiles): `up_ql_base_us` (B, the interval base: with `unified_queue_need_frames` F below 16 the mean of cycle minus starve minus min(hold block, slack) over the newest F valid frames (slack = max(0, J − S), the cap's headroom the holds fill: a hold up to the slack is the cap's, only the part above it stays in B; no cap or an unreachable cap has slack 0) plus the mean over the newest 16 of the starvation of GPU-paced frames only, a frame whose start the cap, display or game term or the game's lateness set contributing none; the mean `gq_cycle_us` of the newest 16 with F = 16), `up_ql_need_us` (N, the mean of cycle minus hold block, boundary idle and wait idle; analysis only), `up_ql_service_us` (S, the hold-free, starvation-free service need), `up_ql_q_us` (the queue term), `up_ql_p_us` (the correction P added to B for the GPU interval) and `up_ql_valid_frames` (valid samples among the newest 16 arrivals). The first five are empty when the law is off or not computable; `up_ql_valid_frames` is printed whenever the law option is on and its window exists, and is empty otherwise. The render stage's marker stamps (`unified_queue_upstream` 1) are telemetry only: no decision reads them. Queue role 3 (`gq_queue_role` 3: the adopted queue is a render queue found by dependency, whose hold block reads 0): while the law is in use and the newest record's role is 3 the law's CREDIT rule is not used; the report-based rule (the report refill and the report-side hold debit) governs the credit and the holds, no hold is granted by the law (counted as a report grant), flag `0x20000000` is set on those frames and the summary line counts them (`N frames with the law in use took the report-based credit and holds`); I_gpu, B and q come from the law as usual. Switching the role keeps the one credit state and a hold is debited only by the rule that granted it. Open point: no slack-funded holds from the law's service on role 3; with the hold share 0 nothing differs from the fallback pacer. Roles 0 (unknown), 1 and 2 are as before. Law hold identity: every grant made under the law (role not 3, the law in use) gets a stable sequence at `GrantHold` (`UnifiedHoldGrant::law_sequence`, ring entry `law_hold_sequence`, never 0 and never reused); it travels with the plan (`PacingFramePlan::law_hold_sequence`, the frame-plan slot) to the GPU gate, which announces it with the hold Wait (`GpuQueueProbe_OnHoldAnnounce`); the probe attaches it to the frame record the hold delayed (`PacingGpuQueueRecord::law_hold_sequence`, 0 = none announced). A record's hold block debits EXACTLY the law grant its sequence names, once (the grant is marked paid: neither the later report-side measurement nor an eviction spends it again, whichever of the record and the measurement comes first); a record with sequence 0, one naming a sequence that is unknown (never granted, already paid, or settled and gone from the ring) and a role-3 record debit nothing, and nothing is correlated by frame key or by arrival order. A law-granted hold that no record pays (its probe session was retired by a re-adoption, the newest record's queue became role 3, the law key went off, or its frame left the ring) is settled once from the report-side measured hold (counted in the summary line, `N law-granted holds settled from the measured hold`; an unmeasured one when its measurement arrives; at ring eviction only a hold measured above zero; an unmeasured hold lost at eviction is lost). A record of a retired session is dropped and counted, never granting or debiting. The probe retires its session explicitly when its adopted queue is destroyed (`GpuQueueLawFeed_RetireSession`, an atomic maximum any thread may publish): the scheduler's drain applies it before popping (`UnifiedPacer::RetireQueueSession`), which empties the window at once, settles the outstanding law grants once as at a session change, and drops the records of that session still in the ring. Paths where the sequence cannot reach the announce, and what the record then does: the CPU presentation gate and any hold not executed by the GPU gate (no announce), a frame whose Wait was not committed (late, stale or unsupported target) and a hold on a queue the probe does not watch carry sequence 0; the record debits nothing and the grant is settled at eviction or retirement.
- Queue law log line (developer key `unified_queue_law`; nothing is logged with the key off): one line per transition, never per frame, when the law is switched off, the unified pacer is switched off, the stage's lifecycle resets, and at process shutdown, `Queue law summary (<reason>): planned N, law in use N; records N accepted (N valid, N late), N dropped from a retired session; hold grants N law / N report; holds debited N by record / N by the report rule, N never debited, N lost unmeasured` (the last counts law-granted frames that left the 64-frame ring with no record naming their hold and no hold measurement: that hold was never paid, so the credit stays that much too high). Planned frames and frames the law decided; records of the live probe session that entered the window, how many were valid samples and how many arrived more than four frames behind the frame being planned (they still enter the statistics but never make the window fresh), and the records of a retired probe session dropped; hold grants by the rule that granted them; holds spent by a probe record or by the report rule (a hold of a law-granted frame is spent only by its record); and the law-granted frames whose measured hold no record paid (counted when the frame leaves the ring or the summary is taken). The counters restart after each line.
- Marker stamp columns (developer key `unified_queue_upstream`, 0 or 1; 184–186). `sim_end_marker_qpc`, `render_submit_start_marker_qpc` and `render_submit_end_marker_qpc` (QPC): when ReLimiter's marker hook saw the frame's own SIMULATION_END, RENDERSUBMIT_START and RENDERSUBMIT_END, stamped on the thread that sent them, keyed by the frame id of the row's key; written with the key at 1; empty with the key at 0, when the marker was not seen, or when a later frame took the frame's slot. Telemetry only: no pacing decision reads them. The `*_qpc` columns are integers.
- Tail-stamp interval cells in the retired render-thread columns (187–189, 196–198; the header names `up_ql_rt_margin_us`, `up_ql_rt_offset_us`, `up_ql_q_rt_us`, `up_ql_rt_contrast_us`, `up_ql_rt_spread_us` and `up_ql_rt_wait_us` are historical; the render-thread terms of the queue law and the key `unified_queue_upstream_lead_us` were removed). They are measurements of the probe, from the joined `gq_` probe record, never decisions. The probe's per-frame scalars `gq_empty_us` and `gq_boundary_idle_us` are the LOWER ends of an interval and `up_ql_rt_margin_us` (187) and `up_ql_rt_offset_us` (188) the UPPER ends of the same two quantities (empty time, boundary idle time), so the true value lies between the pair. The free margin `gq_min_margin_free_us` is the minimum over the fed submissions of the bracket midpoints (the value the law reads): `up_ql_q_rt_us` (189) is the minimum of the upper ends, `up_ql_rt_contrast_us` (196) the minimum of the lower ends and `up_ql_rt_wait_us` (198) the error `max(S − lo_min, hi_min − S)` with S the scalar and lo_min and hi_min the two minima (the scalar is within it of the true minimum). µs, 3 decimals; empty when the row has no probe record or the value is unknown, and 0 is a real value. `up_ql_rt_spread_us` (197) packs two counters, `borrowed + 10000 × registrations` (each part capped at 9999): `borrowed` the frame's submissions whose completion marker was the game's own Signal, `registrations` the worker's fence registrations since the previous record was popped (`30017` is 17 borrowed and 3 registrations); empty without a probe record. The `up_flags` bits that belonged to the removed terms (`67108864`, `134217728`, `268435456`, `1073741824`) are never set.
- Span CPU time and marker thread columns (developer key `unified_queue_upstream`, 190–195). `render_submit_cpu_us` and `sim_cpu_us` (µs, 3 decimals): the CPU time of the thread inside the frame's own render-submit span (between its RENDERSUBMIT_START and RENDERSUBMIT_END markers) and simulation span (between SIMULATION_START and SIMULATION_END); the span's wall time minus this value is the time the submitting thread waited inside its own span. `render_submit_tid`, `sim_tid`, `render_submit_end_tid` and `sim_end_tid`: the ids of the threads that sent the RENDERSUBMIT_START, SIMULATION_START, RENDERSUBMIT_END and SIMULATION_END markers. Written with the key at 1; a CPU time is empty when the span's two markers were sent by different threads (both ids still show) or a marker or its CPU time is missing, an id is empty when that marker was not seen. They need only the frame's Source record, not the unified pacer, and nothing reads them.

**`relimiter_pacing_events_`** has one row per event:

- Capture start and end.
- Pipeline changes (output point and reason).
- Cadence restarts (grid epochs) with their reason.
- Adaptive cap changes: a rise, fall or probe starting, a rise after a failed fall, the return to the cap and resets; one row per change, not per percent.
- Hold feasibility changes (`rung_feasibility`): value 1 while holds are off, 0 when they resume; cause `overload`, `retry` (overload over), the A/B interleave's `ab_held` or `ab_not_held`, or `none` for a reset.
- `gpu_wait_cap` events appear only in files from older builds that had a GPU wait cap (the level 0..3 as value, 255 for the open top; cause `late_resumes`, `trial_failed`, `calm`, `reset`, `opened` or `closed`); current builds write none.
- Injected stalls (`stall_injected`), measurement loss (dropped records and lost ETW events), PC latency status changes and every Display Pacing snapshot.

Release and Present times describe ReLimiter's pacing, not what reached the display, especially with frame generation. Captures made by older builds can have fewer columns and event causes.

**Frame generation labels.** Under DLSS-G one app frame produces several presents on one swapchain, with the game's PC latency simulation marker on the first, the generated frame shown as soon as frame generation has computed it. The PC latency collector groups presents per swapchain from one marker present to the next: the last present of a group of several is the real frame and takes the app frame's identity (frame ID, simulation start, input ping, Present start), so its row joins ReLimiter's release and carries PC Latency; the earlier presents are generated and carry no frame identity. Presents that PresentMon types (Application, Repeated, XeFG, AFMF) are never reassigned. A present's display and PC Latency samples are published when the next marker present arrives (at most 250 ms or 8 presents later). Captures from builds before this grouping have the real and generated labels swapped under DLSS-G.
