# ReLimiter telemetry semantics

ReLimiter writes two CSV families while CSV capture is enabled: joined pacing rows (`relimiter_pacing_*`) and pacing events (`relimiter_pacing_events_*`). NVIDIA FrameView CSV is the external display-domain reference. Current source is authoritative: recheck the column tables and producers before relying on a field.

## Legacy families

Phase 1 of the pacing redesign (2026-09-27, `project-docs/002_unified_pacing_timing/phase1_purge_design.md`) removed the seven earlier families (`relimiter_frames_`, `relimiter_pcl_`, `relimiter_timeline_`, `relimiter_presents_`, `relimiter_present_associations_`, `relimiter_provenance_`, `relimiter_gpu_observations_`), their analysis scripts and their descriptions in this file. Archives made before Phase 1 still contain them: `inspect_capture.py` reports those files as legacy without parsing their rows, and `archive_capture.ps1` no longer copies them. Their schemas, semantics and analyzers remain in version control; re-analyse old archives with a revision from before Phase 1, and never map a legacy field onto a pacing column.

Files are `relimiter_pacing_<process>_<PID>_<session>_capture_<epoch>.csv` and `relimiter_pacing_events_<same suffix>.csv`. The session is the CSV writer's initialization FILETIME in decimal. The events prefix starts with the rows prefix, so match `relimiter_pacing_events_` first; a process named `events_…` makes the names ambiguous and the header decides. Both are written only while capture is enabled; producers, joins and metrics run regardless. ETW display samples exist only while native PC Latency collection runs (`native_pcl_enabled=true` and ETW access). Without them, DX11 and DX12 display samples come from DXGI frame statistics (`display_source = 2`, observer epoch 0; one display instance per present, no ready time or frame type beyond Application, and a chain break wherever presents were not observed as displayed). Builds before Phase 2 had no DXGI source, so their rows files without ETW hold only DXGI Present records (`row_kind = 2`). Vulkan and OpenGL produce no rows.

**Rows.** One row per sanitized ETW display instance (`row_kind = 1`; `display_qpc` empty for a present that was never displayed, `display_index`/`display_count` number repeated instances), or one row per native DXGI Present that never received a display sample (`row_kind = 2`, display columns empty). A display row is emitted after a 100 ms grace. A `row_kind = 2` row is emitted at least 1 s after its Present was received, once that swapchain's display stream has joined a later present start or when that swapchain never delivered a display sample (no ETW, access denied, not started), otherwise at retention expiry (3 s), so file order is not time order. A quiet stream decides nothing, because ETW delivers display samples in bursts about 1 s apart. Builds up to the Phase 0 acceptance captures (2026-09-27) also emitted a `row_kind = 2` row after 1 s of stream silence, so their bursty ETW delivery produced premature `row_kind = 2` rows (7–21% of Presents) followed by `late_display = 1` rows; the schema did not change. A display sample that later joins such a Present is still emitted with `late_display = 1`; it contributes display metrics but no holds, which stay on the earlier `row_kind = 2` row. Each hold is counted once: CPU holds and queue-wait GPU residence on the row that owns the Present, FG input-wait GPU residence (`gate_fg = 1`) on the frame's `real_frame = 1` row. `sequence` is the telemetry worker's row sequence: every row the worker processes, captured or not, numbered in processing order from 1 when the worker starts (the same number the runtime snapshot window records). Rows processed while capture is off fall between files, so a file's first row is usually not 1; within one file, rows are contiguous and gaps are CSV ring drops. Vulkan/OpenGL display rows can join only by PCL frame ID.

`join_rule`: 0 none, 1 Present attribution (the joined Present's same-thread `PRESENT_START` key), 2 PCL frame ID (low 32 bits, newest NvAPI/PCL producer epoch only), 3 PCL simulation start (builds after `6cde395`: a display whose PCL record has `pcl_sim_start_qpc` but no `pcl_frame_id` joins the newest SIMULATION_START Source of that epoch released at or before it, unless a display of another present already joined that Source). PresentMon drops the PCL frame ID of every frame whose first PCL marker is the PC latency ping (its ping branch creates the timing record without the ID); in CONTROL Resonant with FG that was 7–8% of real frames (all of them with `pcl_input_ping_qpc` set), which earlier captures leave unkeyed (`real_frame` 0, no Source, Reflex or gate columns). The events file's `join_rule_pcl_frame_id` counts rules 2 and 3. `identity_domain`/`producer_epoch`/`frame_id` are set when a key joined; Source columns only when that Source record was retained (`source_release_qpc` non-empty). Ambiguous Present candidates leave the row unjoined (`present_candidates`).

**Units and empty cells.** `_qpc` columns are integer local QPC ticks at `qpc_frequency`; empty means unknown or zero, never a measured zero. `interval_us` and `fg_divisor` use round-trip precision (shortest text that parses back to the same double), so T_out recomputes exactly; derived `_us` columns, `clock_map_offset_us`, `predicted_render_us` and the `pcl_*_us` columns are decimals with three digits. `reflex_*_us` columns are NVIDIA driver-domain microseconds (UTC wall-clock time on the Phase 0 captures), not QPC; subtract them only within one row. Enums are integers.

**Frame generation labelling (DLSS-G, from the build that groups presents per app frame).** DLSS-G emits two or more presents of one swapchain per app frame, and the app frame's PCL simulation marker (`pcl_frame_id`, `pcl_sim_start_qpc`, the input ping, `pcl_present_start_qpc`) is attached to the first of them. In captures from every earlier build that first present was labelled real (`frame_classification = 1`), but it is the interpolated frame G(N-1,N) shown as soon as generation finishes (it displays 0.12–0.18 ms after frame N's Reflex GPU render end, 1.5 ms after the frame's FG input readiness), and the markerless present after it, labelled generated through the simulation fallback (`frame_classification = 2`, `pcl_simulation_fallback = 1`, no `pcl_frame_id`), is the real frame N, about half an interval later (the class-2 row before a class-1 row displays 6.8–8.9 ms before frame N's GPU end on 95–100% of frames, so it cannot be frame N). Under DLSS-G, captures from earlier builds therefore have the two labels swapped: class 1 was the generated frame, so `real_frame`, `latency_us`, the FG input-wait residence and the joined Source/gate/ready records described the generated display, and the class-2 row was the real one. Do not compare real-frame populations across the two build generations; [INFERENCE] `latency_us` of a real-frame row should rise by about the generated-to-real display spacing against an earlier build of the same scene.

From the new build on, the collector groups presents per swapchain: a group opens at a present carrying a PCL simulation marker and holds the markerless presents that follow until the next marker present. With more than one present in the group (2x: two; MFG 3x/4x: three/four), the earlier presents are generated (`frame_classification = 2`; no `pcl_frame_id`, `pcl_sim_start_qpc` or input ping; `pcl_simulation_fallback = 1`, measured from the app frame's simulation start) and the last is real (`frame_classification = 1`), which takes the whole marker identity, so the real row joins the Source by `pcl_frame_id` (join rule 2) or `pcl_sim_start_qpc` (rule 3), counts as `real_frame`, gets the FG input-wait residence, and its PC Latency is that frame's (frame start to Present start, Present start to display and the dropped-frame accumulation use the real present). Generated rows carry no frame identity, so rules 2 and 3 never apply to them (rule 1, the Present call, still can). A group of one present (no frame generation) is unchanged. PresentMon frame types stay authoritative: a present with an Application, Repeated, XeFG or AFMF type is never reassigned and makes its group pass through exactly as before. A present that was never displayed is placed by position like any other: the last present of a dropped app frame is real and counts as a dropped frame in the PC Latency chain. A group with no closing marker after 8 presents, or none for 250 ms after its last present (the game stopped presenting), is resolved as it stands (several held presents as earlier-generated plus a real last, a lone one unchanged; after 8 presents nothing is inferred); a present of that frame arriving later is unchanged (class-2 fallback as before). Because the last present of a group is known only when the next group opens, the collector publishes each present's display sample and PC Latency sample one present later: for an untyped (DLSS-G) swapchain the OSD's PC Latency and the CSV row publication trail the display by about one display interval, and by one app-frame interval for a game without frame generation whose presents PresentMon leaves untyped; presents PresentMon types (as in the FG-off captures) are not held. Display timestamps and every QPC-domain column keep their measured values.

**Controller columns** (Phase 3, after `display_source`), from the joined Source record. The governor cells are empty when the period governor did not run for that frame (idle cap, uncapped, passthrough, suspended and DMFG frames, or an invalid governor decision); a governed frame always has them, also while Adaptive cap is off (step 0, `governor_interval_us` = the cap interval). `interval_us` stays the effective source interval (governor and LFC applied). `gate_pre_wait_qpc` (Q16) follows them and comes from the joined gate record, not the Source record. In builds from 2026-11-13 (the period governor's decisions removed) the governor cells are never written, so they are empty on every row and no row counts as governed.

Phase 4 (`phase4_design.md` P4-1 to P4-6) replaced the Phase 3 stepped ladder with a continuous period tracker: on VRR (and unsnapped fixed refresh) the governed interval I moves between I_0 and 1.6 I_0 by at most +2% per frame up and, since the design review 2026-10-03 (`design_review_20261003.md`), −0.2% per frame down (−0.05% in earlier Phase 4 builds); since the evidence-gated controller of 2026-10-04 the realized steps are +3% up and −1% down per frame. Every change is a silent grid rebase (no `grid_epoch`); on a snapped fixed refresh the tracked interval is quantized to whole refreshes and each quantized change starts a `grid_epoch` with reason 6 (governor step). The design review replaced the Phase 4 decision rules (1 s hold, probe hold, 3-in-120 and 6-in-120 miss rules, late-arrival detector, fall memory, serial-span rules) with a Swappy-style windowed policy, and the 2026-10-04 controller replaced that policy with evidence-gated rises sized by demand, `release`/`probe` falls and a hold per overload episode; only the build or date tells which rules produced a capture. The columns kept their names and positions; the file length tells the semantics (136 columns: Phase 4; 132 and 133 columns: Phase 3 ladder).

A frame never starts before its target T(n) (R ≥ T(n), the release committed once), with one documented exception: a failed marker-site start wait. When the marker waits to T(n) (the Sleep failed, was still running, or no Reflex Sleep exists) and that wait is cancelled, makes no progress or is clamped below T(n) by the maximum wait, the frame is released at once (R < T(n)), nothing is committed, the law is reset and the row carries `0x1000` in `up_flags` (with `0x10000` or `0x20000` when the Sleep was the cause). **GPU queue probe columns** (columns 163–177, appended after `up_cycle_us`; developer key `gpu_queue_probe`). What the presenting queue did for one frame, seen from the `ExecuteCommandLists` calls (enqueue) and from fence completions timestamped by a thread waiting on fence events. A frame is the submissions between ReLimiter's own Present-time enqueues on that queue, in queue order, not the game's frame markers; the record is joined to the row through the frame key when the row has one, else the Present's (swapchain generation, present sequence), so rows without either, with the key off, or for a frame the probe could not identify have empty cells. Every column has its own valid bit: a frame with a dropped event, a missing completion or release stamp, or an unknown predecessor completion is incomplete and only the columns that do not need the missing value are filled. `0.000` is a value (a valid zero), not empty. QPC columns are `qpc_frequency` ticks.

Timeline model. Queue order is the order of the frame's submissions and of the queue Waits between them. Waits are not work. Every operation reaches the queue at `max(its enqueue, completion of the operation before it)`: a submission completes when its fence value (signalled right after its call) completes, made monotone; a queue Wait completes at its release, the completion of a fence value signalled right after the native Wait returned. Only unsatisfied Waits count: a Wait on a fence value that was already reached is not a queue wait. No fence is signalled in front of submissions; a submission's start is `max(enqueue, completion of everything in front of it, the releases of the Waits in front included)`.

Law hold identity: every grant made under the law (role not 3, the law in use) gets a stable sequence at `GrantHold` (`UnifiedHoldGrant::law_sequence`, ring entry `law_hold_sequence`, never 0 and never reused); it travels with the plan (`PacingFramePlan::law_hold_sequence`, the frame-plan slot) to the GPU gate, which announces it with the hold Wait (`GpuQueueProbe_OnHoldAnnounce`); the probe attaches it to the frame record the hold delayed (`PacingGpuQueueRecord::law_hold_sequence`, 0 = none announced). A record of a retired session is dropped and counted, never granting or debiting. Paths where the sequence cannot reach the announce, and what the record then does: the CPU presentation gate and any hold not executed by the GPU gate (no announce), a frame whose Wait was not committed (late, stale or unsupported target) and a hold on a queue the probe does not watch carry sequence 0; the record debits nothing and the grant is settled at eviction or retirement.

ReLimiter uses same-frame simulation-start semantics. FrameView PC Latency can use prior-simulation-start semantics, so a difference of about one simulation interval may be semantic rather than an error. `MsPCLatency` is not automatically formula-compatible with `pcl_total_us`, and pacing rows never pair with FrameView rows by row index.

**Derived metrics** follow design section 4: display change (`display_qpc` set and not repeated); chains per native swapchain and observer epoch with breaks for observer epoch, loss window, out-of-order and gaps over max(250 ms, 8 × T_out); `T_out = interval_us / fg_divisor`, carried forward; interval, adjacent jitter, deviation, long (> 1.5 T_out) and short (< 0.5 T_out) frames; real frames (Real, or Unknown with `fg_divisor` 1, earliest qualifying display; a frame ID at or before the chain's previous real frame of the same domain and producer epoch never starts another); animation error for consecutive frame IDs without a break; latency `display − source release`; holds counted once (CPU holds and queue-wait residence on the row that owns the Present and is not `late_display`, FG input-wait residence on the real-frame row). GPU residence uses `ready_gpu_qpc` only when `ready_before_gate = 1` (the completion query preceded every ReLimiter hold); a query behind a hold measures the hold. Without FG the ready time is the readiness worker's pre-Present query. With FG it is the FG input prefix timestamp: the GPU deadline worker's readback of a query submitted on the FG input queue before that input's wait, joined by the source frame key, so every display row of the frame carries it and only the real-frame row counts the residence. Builds up to the Phase 0 acceptance captures have no FG ready times, so their FG `gpu_residence_us` is empty. Quantiles are lower-index, `sorted[floor(p × (n − 1))]`.

Runtime derived columns are not independent evidence. The runtime chain set processes every row, captured or not, keeps at most eight chains (least recently used replaced, counted by `chain_replacements`) and resets only when the worker starts. Columns at the start of a capture file and after sequence gaps therefore depend on history absent from the file. `analyze_pacing.py` recomputes every metric, restarts chains at gaps and filter holes, and compares runtime columns only where the chain state is reproducible.

The window keeps a contiguous suffix of processed rows by worker processing time, so it holds exactly the rows of the selected swapchain with window content (a display change or any metric value) whose `sequence` lies in [`window_first_row_sequence`, `window_last_row_sequence`]; display rows belong to `native_swapchain`, `row_kind = 2` rows to `present_native_swapchain`. Columns 51–81 are empty on other event types:

## ETW loss windows

EventLoss is windowed (`src/native_pcl_loss_window.h`). An increase of ETW events lost, ETW buffers lost or PresentMon completed-ring overflow (raw counters, queried about once per second) opens a loss window; it closes after 2 s without a further increase, and the next published sample returns to `native`. While it is open, display rows carry `loss_window = 1` (a chain break), PC Latency samples report `pcl_status = 7`, and the events file brackets it with `loss_window_begin`/`loss_window_end`. The loss counters on the events file are session maxima, so a nonzero counter does not mean current loss: detect loss from counter increases and segment on `loss_window`. Per-present `lost_present_count` never opens a window. Builds before windowed loss kept EventLoss (and suppressed samples) for the rest of the session; use build provenance.

## FG and DMFG

- `fg_divisor` can be fractional during its approximately 50 ms transition. Do not group it with exact floating-point equality; T_out follows the row's divisor.
- Under static FG, real-frame metrics (animation error, latency, FG input-wait residence) describe real renders; display interval and jitter cover every display change, generated ones included. Keep the two populations separate.
- Frame classification needs ETW real/generated evidence; `frame_classification = 0` with `fg_divisor` 1 counts as real, otherwise it does not qualify.
- Dynamic MFG passthrough frames carry `source_flags` bit 32 (no pacing decision), so paced-target, hold and headroom conclusions are invalid for them; the DMFG background and FG-off caps pace at their own targets.
- FrameView `MsBetweenDisplayChange` remains the independent display-domain reference for generated output.

## FrameView stream

- `TimeInSeconds` is seconds.
- Columns prefixed `Ms` are milliseconds.
- `NA` means unavailable and must not become zero.
- `MsBetweenPresents` is API/present cadence.
- `MsBetweenDisplayChange` is the primary displayed-output cadence signal.
- `MsPCLatency` is not automatically formula-compatible with ReLimiter `pcl_total_us`.
- Segment on application/process, swapchain, Present mode, drops, and FG multiplier as applicable.

## Transport caveats

Producers push Source, Present, Gate, Ready, Reflex, wait (SetAsyncFrameMarker calls) and display records into bounded nonblocking queues; a full queue drops the record and counts it (`queue_drops` events, `snapshot_dropped_records`; wait records are dropped without a count). The telemetry worker owns every join, metric and row, and hands rows and events to separate CSV rings; a full ring drops the row (a `sequence` gap, counted in `csv_row_drops`/`csv_event_drops`). The CSV writer exclusively owns file opening, writing, flushing and closing. File names carry process, PID, session and capture epoch, and re-selecting an epoch appends rather than truncates, but archive and hash captures promptly. Neither file embeds a build ID, run ID or configuration manifest: record them with the archive manifest.
